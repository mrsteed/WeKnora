## 2. 结论摘要

本次问题不是“智能路由没识别出来”。相反，路由模型已经明确把请求判定为 `full_document`，日志显示 `normalized_kind=full_document`，置信度 0.95：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L62)。

真正导致没有进入长文档流程的原因是：当前代码把“带附件/图片”的请求硬编码为**不能进入新建长文档**。这条限制同时存在于三层：

1. 路由提示词与 regex fallback。
2. Handler 对路由结果的应用门禁。
3. `session_agent_qa` 的长文档执行分支选择。

因此，即便智能路由已经判定为长文档，后端仍然会把这次请求拦下，并降级回普通 AgentQA。随后系统只是把附件内容以普通 prompt 方式拼接到 Agent 查询里：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L112)，页面也就拿不到 `long_document_enabled` 信号，自然不会进入长文档 UI。

换句话说，这不是偶发 bug，而是当前实现中的**设计性冲突**：

- 路由层说“这是长文档”。
- 执行层又说“只要有附件，就不能走长文档”。

这与“以智能路由为唯一判断标准，一旦判定进入长文档流程，前后端执行即可”的目标直接冲突。

## 3. 关键发现

### P0. 智能路由已命中 `full_document`，但 Handler 明确拒绝应用

直接证据在复现日志里已经非常清楚：

- 路由模型输出 `normalized_kind=full_document`：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L62)
- 随后 Handler 记录：`document route not applied ... blocked_by=has_attachments`：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L63)

对应代码如下：

- `detectChatRouteDecision()` 在拿到模型决策后，还会继续调用 `applyDocumentRouteDecisionWithReason()`；如果应用失败，就把失败原因写成 `blocked_by=...`：[internal/handler/session/chat_route.go](internal/handler/session/chat_route.go#L47-L58)
- `canApplyFullDocumentRouteDecisionWithReason()` 明确规定：只要 `len(reqCtx.attachments) > 0 || len(reqCtx.images) > 0`，就直接拒绝 `full_document` / `knowledge_grounded_full_document`：[internal/handler/session/chat_route.go](internal/handler/session/chat_route.go#L291-L311)
- `documentRouteBlockedReason()` 把该拒绝原因标准化为 `has_attachments` / `has_images`：[internal/handler/session/chat_route.go](internal/handler/session/chat_route.go#L338-L349)

这意味着：

- 智能路由的输出不是权威信号。
- 附件门禁的优先级高于模型路由。

这正是本次“明明已判定为长文档，仍然没有进入长文档流程”的第一根因。

### P0. 路由未应用后，Handler 会清空文档上下文，导致下游根本看不到 `full_document`

`detectChatRouteDecision()` 执行完成后，会调用 `normalizeResolvedDocumentRequestContext(reqCtx)`。[internal/handler/session/qa.go](internal/handler/session/qa.go#L1531-L1543)

而 `normalizeResolvedDocumentRequestContext()` 的保留条件里，`routeDecisionApplied` 必须为真；否则会调用 `clearResolvedDocumentRequestContext()` 把 `documentIntent`、`documentOperation`、`documentOutputMode`、`baseArtifactID` 等全部清空：[internal/handler/session/chat_route.go](internal/handler/session/chat_route.go#L145-L181)

这一步的实际效果是：

1. 模型虽然判定了 `full_document`。
2. 但因为 `has_attachments`，`routeDecisionApplied=false`。
3. 随后 Handler 把解析出的文档请求上下文清掉。
4. 下游 `buildQARequest()` 构造出来的 `QARequest.DocumentOutputMode` 仍为空：[internal/handler/session/qa.go](internal/handler/session/qa.go#L1262-L1289)

这也是为什么后续 `session_agent_qa` 没有进入专用长文档路径。

### P0. 长文档执行层再次把附件视为禁入条件，形成第二道和第三道阻断

即使只修复 Handler 一层，当前执行层也仍然会拒绝带附件的 `full_document` 请求。

长文档分支入口在 `AgentQA()` 的执行服务中：

- `shouldUseKnowledgeGroundedFullDocumentGenerationPath()` 成功时进入知识库支撑长文档：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L135-L137)
- `shouldUseDedicatedFullDocumentGenerationPath()` 成功时进入无知识库长文档：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L139-L141)

但是这两个判断函数内部都明确写了附件/图片门禁：

- `knowledge_grounded_full_document`：只要有 `Attachments` / `ImageURLs` / `ImageDescription`，直接 `return false`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L474-L483)
- `dedicated_full_document`：同样直接 `return false`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L534-L543)

这说明当前仓库并不是“漏接了一处判断”，而是**整套实现都默认：带附件的新建长文档不允许进入专用长文档流水线**。

### P0. 现有测试已经把“附件禁入长文档”固化成了预期行为

这也是为什么问题能长期存在而不被测试拦住。

现有测试明确要求：

- `chat_route_service` 的 regex fallback 在 `HasAttachments=true` 时，必须退回 `agent_qa`，并且 `UseLongDocument=false`：[internal/application/service/chat_route_service_test.go](internal/application/service/chat_route_service_test.go#L278-L295)
- `session_agent_qa` 的 grounded full document 选择逻辑里，“request with attachments stays off grounded path” 被当作正确行为：[internal/application/service/session_agent_qa_test.go](internal/application/service/session_agent_qa_test.go#L1090-L1098)

因此，本次问题不是“代码某处意外失效”，而是“当前测试本来就在保护这条错误约束”。

### P1. 即便只放开门禁，当前专用长文档提示词也不会读取附件正文

这是一条非常关键的次级根因。

当前普通 Agent 路径会把附件内容显式拼到查询里：

- `req.Attachments.BuildPrompt()` 在普通 Agent 路径中被追加到 `agentQuery`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L237-L242)
- `BuildPrompt()` 会把附件文件名、类型、大小和提取出的正文包装为 `<attachments>...</attachments>`：[internal/types/message.go](internal/types/message.go#L86-L114)

但是专用长文档路径的提示词构造函数完全没有使用附件内容：

- 无知识库长文档大纲仅使用 `User goal` + planning requirements：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L2398-L2416)
- 知识库长文档大纲仅使用 `User goal` + `<local_knowledge_context>`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L2419-L2445)
- 无知识库长文档章节写作仅使用 `User goal`、完整大纲、已完成摘要：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L3845-L3889)
- 知识库长文档章节写作仅使用 `User goal`、完整大纲、已完成摘要、`<local_knowledge_context>`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L3892-L3915)

也就是说：

- 当前专用长文档引擎根本没有“附件证据输入位”。
- 只是删掉门禁还不够；必须补附件上下文注入，否则会进入长文档流程但看不到附件内容。

### P1. 附件正文当前只保留前 500 行，直接复用也会造成信息缺失

复现日志已经显示，上传的文本文件共 1512 行，只保留了前 500 行：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L52)

对应实现也确实如此：

- `maxTextFileLines = 500`：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L23-L24)
- `processTextFile()` 明确只收集前 `maxTextFileLines` 行，并在超出时打上 `IsTruncated=true`：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L136-L158)

因此，哪怕后面把附件允许进入长文档，如果只是把现有 `BuildPrompt()` 直接塞进长文档提示词，模型看到的也仍然只是“前 500 行截断版附件”。

这不是当前“不进入长文档流程”的直接根因，但会成为修复后的第二个质量问题。

### P2. 前端不是本次阻断源，但“智能路由唯一标准”在全局上仍未彻底成立

本次场景下，前端并没有本地把普通请求提升成 `full_document`。

证据如下：

- `buildUserDocumentRequestContext()` 对普通请求返回的 `documentOutputMode` 是空字符串；只有续写/修订类请求才会显式写成 `delta_only`：[frontend/src/views/chat/utils/documentRequestContext.js](frontend/src/views/chat/utils/documentRequestContext.js#L14-L30)
- 发送请求时，前端只是把这个值原样带给后端：[frontend/src/views/chat/index.vue](frontend/src/views/chat/index.vue#L2592-L2628)

页面展示层也不是本次阻断点：

- 前端只有在后端 complete payload 带回 `long_document_enabled=true` 时，才会把消息标为长文档：[frontend/src/views/chat/index.vue](frontend/src/views/chat/index.vue#L564-L568)
- 长文档面板和规划面板都依赖 `session.long_document_enabled === true` 才可见：[frontend/src/views/chat/index.vue](frontend/src/views/chat/index.vue#L863-L865)、[frontend/src/views/chat/long-document/useLongDocumentPlanning.ts](frontend/src/views/chat/long-document/useLongDocumentPlanning.ts#L106-L108)

不过，从“唯一路由标准”的长期目标看，前端仍然保留了续写/修订意图的正则推断：

- `inferDocumentContinuationIntent()` 仍会根据自然语言把请求推成 `continue_document` / `revise_document`：[frontend/src/views/chat/index.vue](frontend/src/views/chat/index.vue#L1529-L1560)

这不是本次故障的根因，但说明“完全由智能路由统一判断”在全局上还没有彻底达成。

## 4. 本次请求为何最终表现为普通 AgentQA

结合日志与代码，本次链路实际是：

1. Agent 解析成功，且确认为“无知识库 Agent”：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L47)
2. 附件处理器提取了文本，但只保留前 500 行：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L52)
3. 智能路由模型判定本次请求属于 `full_document`：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L62)
4. Handler 因 `has_attachments` 拒绝应用该路由：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L63)
5. 请求随后进入“纯 Agent 模式”，没有知识库：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L87)
6. 系统只注册普通 Agent 工具集 `thinking / todo_write / web_search / web_fetch`：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L104)
7. 附件内容被作为普通 prompt 附加到 Agent 查询中：[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L112)

因此最后看到的是普通 Agent 生成的一次性回答，而不是长文档的：

- 规划阶段
- 分章节生成
- `long_document_enabled`
- artifact/version/generation run
- 长文档页面增强 UI

## 5. 修正原则

如果目标是“长文档判断以智能路由为唯一判断标准”，建议把原则收敛成下面这句更准确的工程定义：

> 对于“新建完整长文档”这一类请求，智能路由判定一旦命中 `full_document` / `knowledge_grounded_full_document`，后端不得再因为附件/图片而降级为普通 QA；附件/图片应作为长文档证据输入，而不是准入门禁。

但仍建议保留以下**结构化硬约束**，不要交给模型覆盖：

- `auto_continue`
- `base_artifact_id`
- 显式 `document_task_kind=translation`
- 已存在 `generation_run_id` 的续写链路

原因很简单：这些不是“自然语言意图判断”，而是已经进入某条专用操作流水线后的强结构约束。如果把它们也交给模型重新判断，容易把“续写/修订”误转成“重新新建整篇文档”。

## 6. 修正建议

### 6.1 P0：让智能路由对“新建完整长文档”真正生效

建议修改以下位置：

1. 调整路由提示词，不再把“有附件/图片”描述为新建长文档的降级信号。
   - 当前问题位置：[internal/application/service/chat_route_service.go](internal/application/service/chat_route_service.go#L120-L138)
   - 建议改成：
     - `auto_continue` / `base_artifact_id` 仍优先导向 continuation/edit。
     - “有附件/图片”只作为上下文特征，不再天然反对 `full_document`。

2. 放开 regex fallback 对附件/图片的限制。
   - 当前阻断位置：[internal/application/service/chat_route_service.go](internal/application/service/chat_route_service.go#L210-L220)

3. 放开 Handler 对 `full_document` 的附件/图片门禁。
   - 当前阻断位置：[internal/handler/session/chat_route.go](internal/handler/session/chat_route.go#L291-L311)
   - 注意：只建议放开“新建完整长文档”的附件/图片门禁；`document_edit` / `continuation` 是否支持附件，要单独评估。

### 6.2 P0：让执行层遵守已命中的长文档路由，不再二次降级

建议修改以下位置：

1. `shouldUseKnowledgeGroundedFullDocumentGenerationPath()` 不再因为附件/图片直接返回 `false`。
   - 当前位置：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L474-L483)

2. `shouldUseDedicatedFullDocumentGenerationPath()` 同样取消该门禁。
   - 当前位置：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L534-L543)

3. 如果 `RouteDecision.Kind` 已经是 `full_document` / `knowledge_grounded_full_document`，执行层应该把它视为**权威执行模式**，而不是仅作为“参考信号”。

### 6.3 P1：为专用长文档链路补齐附件证据输入

仅删除门禁不够，还必须让专用长文档引擎真的读取附件内容。

建议做法：

1. 新增统一的附件上下文构造 helper。
   - 可先复用 [internal/types/message.go](internal/types/message.go#L86-L114) 里的 `MessageAttachments.BuildPrompt()`，快速打通能力。
   - 更稳妥的做法是单独构造 `<attachment_context>`，把附件名、类型、截断说明、正文内容分层包装，避免和普通 Agent prompt 完全耦合。

2. 在以下提示词构造函数中注入附件上下文：
   - `buildDedicatedFullDocumentOutlineMessages()`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L2398-L2416)
   - `buildKnowledgeGroundedFullDocumentOutlineMessages()`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L2419-L2445)
   - `buildDedicatedFullDocumentSectionMessages()`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L3845-L3889)
   - `buildKnowledgeGroundedFullDocumentSectionMessages()`：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L3892-L3915)

3. 对 knowledge-grounded 路径明确证据优先级：
   - 本地知识库是长期事实来源。
   - 本轮附件是会话内临时资料来源。
   - 如果两者冲突，不要自动编造统一结论，应显式写“资料冲突/待确认”。

### 6.4 P1：处理“附件只保留前 500 行”的质量问题

如果修复目标只是“先让它走进长文档流程”，复用当前附件 prompt 是最快路径。

但如果目标是“根据附件内容生成完整技术方案”，当前 500 行上限会成为新瓶颈。

建议两阶段处理：

1. 止血方案：
   - 保留现有截断机制，但在长文档提示词里明确告诉模型“附件可能被截断，未覆盖部分需标注待确认”。

2. 稳妥方案：
   - 为长文档附件单独建设“分段快照/会话内临时检索”能力，按大纲章节动态抽取相关片段，而不是一次性只喂前 500 行。
   - 这样才能真正支持 1000+ 行会议纪要、长 Markdown、长文本方案材料。

### 6.5 P2：前端保持后端主导，减少残留自然语言启发式

本次故障不需要前端大改。

建议前端策略如下：

1. “普通创建类长文档”继续不在前端本地推断 `full_document`，保持后端统一路由主导。
2. 长文档 UI 继续只消费后端结构化信号 `long_document_enabled`，这点当前实现是正确的。
3. 后续若要把“唯一路由标准”贯彻到底，可逐步把 [frontend/src/views/chat/index.vue](frontend/src/views/chat/index.vue#L1529-L1560) 这类续写/修订正则下沉为显式按钮或后端结构化路由，但这不是本次 P0 阻断项。

## 7. 修正计划

建议按以下顺序落地：

### 第 1 阶段：打通路由到执行的主链路

目标：只要智能路由命中 `full_document` / `knowledge_grounded_full_document`，且请求属于“新建完整文档”，就必须进入专用长文档执行链路。

改动范围：

- [internal/application/service/chat_route_service.go](internal/application/service/chat_route_service.go)
- [internal/handler/session/chat_route.go](internal/handler/session/chat_route.go)
- [internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go)

验收标准：

- 复现请求不再出现 `blocked_by=has_attachments`。
- 日志中出现 `[FullDocument][Router] selected=dedicated_full_document` 或 `selected=knowledge_grounded_full_document`。

### 第 2 阶段：让长文档链路真正消费附件

目标：专用长文档大纲规划与章节生成能够使用上传文档内容，而不是退回普通 Agent prompt 拼接。

改动范围：

- [internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go)
- [internal/types/message.go](internal/types/message.go)
  或新增独立附件上下文 helper

验收标准：

- 大纲规划提示词中可见附件上下文。
- 章节生成提示词中可见附件上下文。
- 生成内容明显使用附件事实，而不是只依据泛化常识补全。

### 第 3 阶段：解决长附件截断带来的质量风险

目标：长文档生成不要只依赖前 500 行附件内容。

改动范围：

- [internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go)
- 长文档附件证据组织逻辑

验收标准：

- 1512 行会议纪要不会只让模型看到前 500 行。
- 长文档章节生成对后半段会议信息也有覆盖。

### 第 4 阶段：补齐回归测试

需要更新和新增的测试至少包括：

1. `chat_route_service_test`
   - 带附件且 query 明确要求完整技术方案时，fallback 不应自动降级成 `agent_qa`。

2. `chat_route_test`
   - `detectChatRouteDecision()` 在 `full_document + attachments` 场景下应 `routeDecisionApplied=true`。

3. `session_agent_qa_test`
   - 带附件的 `full_document` 请求应进入 dedicated 或 grounded full document path。
   - 专用长文档提示词应包含附件上下文。

4. 端到端回归
   - 无知识库 Agent + 附件 + “根据附件内容，生成完整技术方案”。
   - 有知识库 Agent + 附件 + “根据附件内容，生成完整技术方案”。
   - 有 `base_artifact_id` / `auto_continue` 时仍然保持 continuation/edit，不误转新建全文。

## 8. 最终判断

本次没有进入长文档流程，根因已经明确：

1. 智能路由其实已经判对了。
2. 但后端当前把附件视为新建长文档的禁入条件。
3. 该禁入条件同时存在于路由提示词、fallback、Handler 应用门禁、执行分支判断和测试预期中。
4. 即使只移除门禁，专用长文档链路现在也不会消费附件正文，还需要补附件证据注入。

因此，若要实现“以智能路由为唯一判断标准，一旦判定进入长文档流程，前后端执行即可”，必须至少完成两件事：

- 删除“附件=不能进新建长文档”的多层硬编码门禁。
- 让专用长文档引擎具备读取附件内容的能力。

只做第一件事，流程会进入，但内容质量仍然不可靠。
只做第二件事，不去掉门禁，请求依然进不去。

两者必须一起改。
