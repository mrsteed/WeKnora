# 知识库「目录文件夹」能力分析：增删改 & 文档跨目录移动审查与修改方案

> 日期：2026-09-24｜范围：WeKnora 知识库（document 型）文档目录树（`KbFolderTree`），区别于 Wiki 目录（`wiki/folders` 是独立表，增删改齐全，作为对照参考）。

---

## 0. 一句话结论

知识库的「目录」**不是独立实体，而是从每篇文档记录的 `folder_path` 字段派生出来的视图**（`ListKnowledgeFolders` 把文档按 `folder_path` 分组聚合，空了就不存在）。这决定了四种操作的成本与形态：

| 操作 | 现状 | 需要的改动 |
|---|---|---|
| 增加（新建空目录） | ❌ 不存在 | 后端 1 个新端点（派生架构下需「占位文档」或新增目录元表）+ 前端树入口 |
| 更改（重命名/移动目录） | ✅ 已完整 | 无需改动（可选体验增强） |
| 删除（删空目录） | ❌ 不存在 | 后端 1 个新端点（空目录直接 no-op / 非空给级联选项）+ 前端树入口 |
| 目录内文档移动到另一目录 | ✅ 已完整 | 无需改动（单文档/批量移动都已实现） |

也就是说：**「改」和「移动文档」已经做完；「增」和「删」两个空目录管理操作是空白**，需要按派生目录的语义来补。

## 1. 架构基础：目录是怎么来的（证据）

### 1.1 派生式目录（无独立表）
- 每篇知识记录有一个 `folder_path` 列（例如 `3.AI+业务培训与考核/关于…通知/附件`），根目录为 `''`。
- 树视图 `GET /api/v1/knowledge-bases/:id/knowledge/folders`（`routes_knowledge.go:77`，权限 `g.Viewer()`）由服务层把该 KB 下所有文档按 `folder_path` 聚合计数，经 `types.BuildKnowledgeFolderTree(counts)` 拼成树。**没有任何"空文件夹"记录存在**——目录只是文档路径的投影。
- 由此两条硬推论：
  1. **空目录无法持久化**（没有独立行去存它）；
  2. **删除/重命名目录本质都是"批量改一批文档的 `folder_path`"**——后者已由 `RenameKnowledgeFolder` 实现（`knowledge.go:613`），前者（删除）缺失。

### 1.2 目录被创建的两个既有时机
1. **上传时**：文件名可带路径（`types.SplitKnowledgeRelativePath`，`knowledge_folder.go:94`），`目录/子目录/a.doc` 上传后 `folder_path` 即 `目录/子目录`，目录随文件"自动生成"。这是目前**唯一**让目录落地的途径。
2. **移动文档到不存在目录时**：`MoveKnowledgeToFolder` 注释明确 *"a folder that does not exist yet is created by this call"*（`knowledge.go:590`）——把文档移到 `新目录/x`，目录即诞生。前端 `FolderPickerMenu` 的"新建文件夹"按钮配合确认移动即可走通这条路径（按钮本身纯本地，落库发生在确认移动，见 3.2），所以**前端实际已经能"间接触发"创建目录**（只是必须挂一篇文档，无法留空目录）。

### 1.3 既有代码位点速查
- 后端路由：`internal/router/routes_knowledge.go:77`（GET folders）、`:78`（PUT folders 重命名）、`:137`（POST /knowledge/folder 移动文档）。
- 后端服务：`internal/application/service/knowledge.go` — `MoveKnowledgeToFolder:590`、`RenameKnowledgeFolder:613`、`normalizeTargetFolderPath`（路径安全校验，`secutils.ValidateInput` 防 `../` 注入）。
- 后端仓库：`internal/application/repository/knowledge.go` — `ListKnowledgeFolderCounts:210`、`UpdateKnowledgeFolderPath:232`、`RenameKnowledgeFolderPath:255`（后两者是"批量 UPDATE folder_path"，带 tenant+kb 双条件）。
- 前端树：`frontend/src/views/knowledge/components/KbFolderTree.vue`（emits 仅 `select`/`rename`/`update:collapsed`）、`KnowledgeBase.vue` `handleFolderRename:848`、`handleFolderSelect:~810`、`folderOptions:~855`。
- 文档移动 UI：`DocumentCardView.vue`/`DocumentListView.vue` 的 `FolderPickerMenu`（emit `move-to-folder`），批量 `DocumentBatchBar.vue` emit `moveToFolder`。

## 2. 需求一：目录的"增加 / 删除 / 更改"各需哪些修改

### 2.1 更改（重命名 / 移动目录）—— ✅ 已完整，确认无需改动

**链路已全部接通**（已逐层验证）：
- 树节点右键/⋯ → `KbFolderTree` 菜单"重命名"（`folderTree.rename`）→ 行内 input
- emit `rename: {from, to}` → `KnowledgeBase.vue:2531 @rename="handleFolderRename"` → `:848` 调 `renameKnowledgeFolder(kbId, from, to)` → `PUT /api/v1/knowledge-bases/:id/knowledge/folders`
- 后端 `RenameKnowledgeFolder`：源/目标路径规范化 + 互斥校验（不能移到自己的子目录），`to` 可以是**别的父目录**（即"移动目录"）、也可以与既有目录同名（**自动合并**，与逐篇文档移动结果一致）。
- 权限：`g.OwnedKBOrAdmin() + KBAccessWrite`（owner/admin 或 org 编辑者以上）。
- 移动后 `KnowledgeBase.vue` 会按 from→to 前缀把用户当前选中的 `selectedFolderPath` 同步迁移（`L864-870`），避免浏览态悬空。

**可选体验增强（非必须）**：
- 重命名时若目标路径已存在，当前是静默合并；可加一次确认"目标目录已存在，将合并 N 篇文档"。
- 树节点 `title` 已显示完整 path，可加悬浮显示文档数 `row.total_docs`（数据已在 tree 节点上）。

> 结论：**"更改"没有任何必须项**。若要加，只建议上面两条交互增强。

### 2.2 增加（新建空目录）—— ❌ 需前后端各加 1 处

派生架构下"空目录"没有载体，两条路线：

**路线 A（推荐，架构一致）：占位文档**
- 后端新增端点 `POST /api/v1/knowledge-bases/:id/knowledge/folders`（body `{ path: string }`），权限与 PUT 一致 `g.OwnedKBOrAdmin()+KBAccessWrite`。
  - service：`EnsureKnowledgeFolder(ctx, kbID, path)` → `normalizeTargetFolderPath` 校验 → 若目录下已有文档**直接返回**（幂等）；否则插入一篇 `folder_path=path`、`title`/`file_name=「占位」`、`type` 用新的 `is_folder_placeholder` 标记的隐藏记录（建议 `parse_status='done'`、不进检索/不建向量）。
  - **关键副作用处理**（必须做，否则树污染）：
    - `ListKnowledge` / `SearchKnowledge` / `GetKnowledgeBatch` 默认过滤占位记录；
    - 树聚合照常保留（占位文档使空目录可见）；
    - 文档计数 `direct_docs` 不计占位；
    - 删除该目录 = 删除占位记录（见 2.3）。
  - 占位记录的 `folder_path` 校验、`_folder_placeholder.md` 文件名规范要写死，防止用户手动上传同名文件误伤。
- 前端：
  - `KbFolderTree.vue` 加 emit `create: [path]` 与菜单/悬浮"+"按钮（树头与每个文件夹节点右键均可建子目录）；
  - 行内 input 复用 `renameInputRef` 的交互样式；
  - `KnowledgeBase.vue` 加 `@create="handleFolderCreate"` → 调新 API → `loadFolderTree` 刷新 + 若父目录非当前浏览目录则展开它（`expanded` 需由树内部管理或上抛）。
- i18n：`knowledgeBase.folderTree.create / createSuccess / createFailed / placeholderTip`。

**路线 B（彻底）：独立 folder 元表**
- 新增 `knowledge_folders` 表（id/tenant/kb/path/name/created_at）+ 全套 CRUD。树改为"目录表 ∪ 文档路径"的并集。
- 代价大：所有读目录处都要改 join，历史数据要回填，且占位/空目录生命周期与文档解耦后要补 prune 逻辑。**不推荐**，除非要做"目录权限/目录级分享"这类元数据需求。

> 推荐路线 A：改动面小、与"目录=路径投影"自洽，占位文档是业界常见做法。

### 2.3 删除（删空目录）—— ✅ 已落地（见 §8）

- 后端新增端点 `DELETE /api/v1/knowledge-bases/:id/knowledge/folders`（body `{ path: string }`），权限同上。
  - service `DeleteKnowledgeFolder`：先 `ListKnowledgeFolderCounts` 判断 `total_docs`；
    - 空目录（含仅有占位文档）→ 删除占位记录即可，目录随之消失；
    - **非空目录默认拒绝**（返回 `409 + total_docs`），由前端弹"非空目录"提示。
  - 可选扩展：`?strategy=move&to=…` 级联把整棵子树移到目标目录（内部就是 `RenameKnowledgeFolderPath` 的批量版），或 `?strategy=delete` 级联删文档（复用 `batchDeleteKnowledge`，权限升 `g.Admin()`）。一期建议只支持空目录删除 + 提示非空。
- 前端：
  - `KbFolderTree.vue` 菜单加"删除"项（`canEdit` 才显示，与"重命名"同门控），emit `delete: [path]`；
  - `KnowledgeBase.vue` 加 `@delete="handleFolderDelete"` → 确认弹窗（"将删除空目录 X"或"目录 X 内有 N 篇文档，不可删除，请先移动文档"）→ 调 API → `loadFolderTree`；若 `selectedFolderPath` 被删则重置为 `ROOT_FOLDER_PATH`（复用 `L797-798` 的回落逻辑）。
  - 复用 wiki 侧 `WikiFolderActions.vue` 的非空确认交互文案风格（`deleteFolderNotEmpty`）保持一致。
- i18n：`knowledgeBase.folderTree.delete / deleteConfirm / deleteBlocked（实际落地键名，方案原稿 deleteEmptyOnly）/ deleteSuccess / deleteFailed`（实施见 §8.2）。

### 2.4 汇总：需求一的修改清单

| 项 | 后端 | 前端 | i18n |
|---|---|---|---|
| 增（空目录） | `POST .../folders` + `EnsureKnowledgeFolder` + 占位记录 + 列表/检索过滤 | `KbFolderTree` create 入口 + `KnowledgeBase` 处理 | 3–4 键 |
| 改（重命名/移动） | **无** | **无**（可选合并确认/文档数 tooltip） | 0 |
| 删（空目录） | `DELETE .../folders` + `DeleteKnowledgeFolder`（空→删占位，非空→409） | `KbFolderTree` delete 入口 + 确认弹窗 + selectedPath 回落 | 3–4 键 |

## 3. 需求二：目录下的文档移动到另一目录

### 3.1 结论：✅ 后端与前端主链路均已实现，无必须改动

**后端**（已完备）：
- `POST /api/v1/knowledge/folder`（`routes_knowledge.go:137`，权限 `g.Contributor()`，注意**不是** Owned，跨租户共享 KB 的 Contributor 也可移动），body `{ kb_id, knowledge_ids[], folder_path }`。
- `MoveKnowledgeToFolder`（`knowledge.go:590`）：批量 `UPDATE folder_path`（`UpdateKnowledgeFolderPath`，tenant+kb 双隔离），目标目录不存在会自动派生，目标为 `''` 表示回到根，`secutils.ValidateInput` 防路径注入，`../` 被规范化拒绝。
- 单文档/批量共用同一端点（`knowledge_ids` 长度 1 或 N）。

**前端**（三处入口齐全）：
- 单文档卡片：`DocumentCardView.vue`「移动到目录」(`move-folder` 动作) → `FolderPickerMenu`（可浏览树/搜索/**就地新建目录**/回退上级）→ emit `move-to-folder(item, path)`。
- 列表视图：`DocumentListView.vue` 同款。
- 批量：`DocumentBatchBar.vue`「移动到目录」→ 同一 `FolderPickerMenu` → `moveToFolder`（多选一次移）。
- 移动成功后 `KnowledgeBase.vue` `handleMove*` 回调：`resetPage()` + `loadKnowledgeFiles` + `loadFolderTree` 刷新，并按当前浏览目录做 from→to 前缀迁移（`L864-870`）。

### 3.2 已内置但用户不易察觉的能力（无需改，建议写进帮助）
- `FolderPickerMenu` 的"新建文件夹"（`moveToFolder.newFolderAddRoot / newFolderAddUnder`）：移动时若目标目录尚未存在，可直接命名创建。**注意机制细节**：该按钮本身不调用任何后端接口，只是把一个候选路径并入本地 `displayOptions`（并 emit 了一个目前无任何父组件监听的 `create` 事件）；目录真正落地是在用户**确认移动到该路径**时——`confirm(path)` → `moveKnowledgeToFolder` → 后端 `MoveKnowledgeToFolder` 按路径写入文档 `folder_path`，目录随之派生。因此这已是"新增目录"的一个可用入口，但**会立即挂上被移动的文档，无法留下空目录**。需求一的"增加空目录"若暂不立项，可先引导用户使用此路径。
- 可移动到**任意深度**的新路径（包括多级不存在的目录），后端按路径字符串落 `folder_path`。

### 3.3 可选增强（体验向，非必须）
| 优化 | 现状 | 改动 |
|---|---|---|
| 移动大目录的进度反馈 | 移动是同步 `UPDATE`，几百篇文档时前端无进度 | 可改走既有异步移动任务（`/move/progress/:task_id` 已存在，跨 KB 移动用）；一期可先 `MessagePlugin` 提示"正在移动 N 篇…" |
| 移动到当前所在目录的 no-op 提示 | 后端直接返回 affected，前端不感知 | 前端对比 `item.folder_path === 目标`时直接 `MessagePlugin.info('已在该目录')` 不发请求 |
| 批量栏「移动到目录」支持拖拽 | 仅按钮弹出选择器 | 可选：`doc-scroll-container` 拖到树节点触发同一 `moveToFolder`（复用 `onDocMarqueeMouseDown` 的拖拽基础设施） |

> 结论：**"移动"没有必须项**。如资源允许，建议做 3.3 前两条（低成本、高频体验）。

## 6. 风险与回归点

- **占位记录污染**（2.2）：若只加占位文档而漏改 `ListKnowledge`/`SearchKnowledge`/`GetKnowledgeBatch`/`ListKnowledgeFolderCounts` 中任一处的过滤，会出现"列表多出一篇空文档"或目录计数虚高。务必在 `knowledge_folder_move_test.go` 同目录补过滤断言。
- **占位记录与真实上传撞名**：上传 `xx/_folder_placeholder.md` 会覆盖/并列占位记录；建议占位记录 `file_name` 用不可见前缀或 `is_folder_placeholder` 布尔列 + 唯一约束 `uk(tenant,kb,folder_path,placeholder)`。**已落地对策**（§7.1）：占位 `file_name` 固定为 `.folder-placeholder`（点前缀 + `type='folder_placeholder'` 双重标识），且所有列表/检索/计数查询按 `type` 而非 `file_name` 过滤占位，故即便同名也不影响正确性。
- **删除当前浏览目录**：前端 `selectedFolderPath` 悬空会导致列表继续按已删路径请求（返回 0 条）。复用现有 `folderExistsInTree` 回落（`L797-798`）即可，但要确认删除回调里也触发。
- **重命名到自身子目录**：后端已拒绝（`strings.HasPrefix(target, source+"/")`），前端树可灰置该选项（可选）。
- **占位文档参与下载/预览**：占位记录应屏蔽 `download`/`preview`（`GetKnowledgeFile` 在 `IsFolderPlaceholder()` 时直接 404），避免导出空文件。

## 8. 实施记录：新增"删除空目录"（2026-09-24 已落地）

按 §2.3 方案实现（一期：仅空目录可删；非空 409；不做级联 strategy）。

### 8.1 后端

| 位点 | 改动 |
|---|---|
| `types/interfaces/knowledge.go` | `KnowledgeService.DeleteKnowledgeFolder(ctx, kbID, folderPath) (int64, error)`；`KnowledgeRepository.DeleteFolderPlaceholder(ctx, placeholder) (int64, error)` |
| `repository/knowledge.go` `DeleteFolderPlaceholder` | `WHERE tenant+kb+id AND type=folder_placeholder` 的**软删**（GORM `deleted_at`，与其它 knowledge 行一致；type 条件保证永不删真实文档）。`ListKnowledgeFolderCounts` 的 `deleted_at IS NULL` 语义下目录随之消失 |
| `service/knowledge.go` `DeleteKnowledgeFolder` | ① `ListKnowledgeFolderCounts` 求 `target` 直接/后代计数之和 `totalDocs`（与侧栏树同一聚合，数字永不失配）；② `totalDocs>0` → `NewConflictError("目录非空，不能删除").WithDetails({folder_path, total_docs})` → HTTP 409；③ `GetFolderPlaceholder` 取占位行（nil → 目录不存在，no-op 返回 0）；④ `DeleteFolderPlaceholder` |

| `router/routes_knowledge.go` | `kb.DELETE("/folders", g.OwnedKBOrAdmin(), g.KBAccessWrite("id"), handler.DeleteKnowledgeFolder)`（紧接 POST） |

409 响应：`werrors.NewConflictError` 自带 HTTPCode 409，`WithDetails` 把 `folder_path`/`total_docs` 放进响应 data。注意 TDesign request 拦截器在 4xx 时只透传 `message` 字符串，`total_docs` 前端拿不到——因此前端**本地树计数**先行判断（见 8.2），后端 409 作为权威兜底。
