## 4. 推荐同步策略

### 4.1 本轮主路径

本轮推荐采用：

```bash
从 upstream/main 新建整合分支
+ 按主题补回本地能力
+ 逐轮验证
+ 最后受控替换 origin/dev
```

对应分支建议：

```bash
git checkout -b sync/dev-20260819-rebuild upstream/main
```

### 4.2 为什么不建议直接在当前 dev 上做 rebase

不建议执行：

```bash
git rebase upstream/main
```

原因如下：

1. 当前差异为 `100 / 528`，逐提交 `rebase` 会把同一批热点文件反复拉入冲突。
2. 双方重叠文件达到 278 个，冲突会高度集中在 `frontend/src`、`internal/application`、`internal/handler` 等本地强定制区域。
3. 上游已经引入 `anydoc`、长期记忆、聊天时间轴持久化等较大结构变化，继续逐提交重放本地历史，成本和不确定性都偏高。
4. 当前工作区本身还有未提交改动，不适合作为直接 `rebase` 的载体。

### 4.3 为什么也不建议直接在 dev 上做大合并

直接执行：

```bash
git merge upstream/main
```

虽然可以减少历史重写，但本轮不作为首选，原因如下：

1. 当前本地 `dev` 已承载较多业务定制和历史同步修补，直接 merge 后很难区分“需要保留的本地能力”和“历史遗留但已过时的补丁”。
2. 本轮目标是从 `0.6.3` 抬升到 `0.7.2`，先从最新上游建立干净基线，再按主题引回本地能力，更容易验证每一批回放的有效性。
3. 如果首轮直接 merge，后续很难把当前在研改动与同步冲突剥离开。

### 4.4 可接受的兜底策略

如果按主题补回本地能力时发现某一类改动无法稳定 cherry-pick，则可以在 `sync/dev-20260819-rebuild` 上对 `dev` 做一次受控 `merge --no-commit`，但仍然要坚持：

1. 基线先站在 `upstream/main` 上。
2. 冲突只按模块处理，不能全量 `ours` 或 `theirs`。
3. 先完成核心业务模块，再回放当前未固化 WIP。

## 5. 推荐执行步骤

### 5.1 先冻结当前工作区

当前存在未提交改动，因此同步前先做 WIP 隔离：

```bash
git checkout dev
git switch -c wip/20260819-builtin-agent-visibility
git add internal/application/service/agent_visibility.go \
        internal/application/service/chat_pipeline/chat_completion_stream.go \
        internal/application/service/chat_pipeline/chat_completion_stream_test.go \
        internal/application/service/custom_agent.go \
        internal/application/service/agent_builtin_visibility_test.go \
        migrations/versioned/000088_builtin_agents_global_visibility.down.sql \
        migrations/versioned/000088_builtin_agents_global_visibility.up.sql
git commit -m "wip: save builtin agent visibility changes before upstream sync"
git checkout dev
git pull --ff-only origin dev
```

如果这批改动还不想提交，可以改为：

```bash
git stash push -u -m "pre-upstream-sync-20260819"
```

### 5.2 建立回退锚点

```bash
git checkout dev
git branch backup/dev-20260819-before-sync
git tag sync-dev-20260819-pre
git fetch origin --prune
git fetch upstream --prune
```

### 5.3 从最新上游新建整合分支

```bash
git checkout -b sync/dev-20260819-rebuild upstream/main
```

注意：本轮不要从当前 `dev` 切同步分支，而是直接从 `upstream/main` 切出，这样才能把上游 `v0.7.2` 作为真正基线。

处理原则：

1. 上游 `anydoc`、`DB_HOST=postgres`、构建依赖修复保留。
2. 本地开发数据目录、Docker 服务脚本、启动期友好报错保留。

#### 主题 B：权限、组织、空间、成员

#### 主题 D：长文档、导出与文档产物

目标：保住本地长文档链路，同时吸收上游聊天流和时间轴修复。

处理原则：

1. 上游聊天流稳定性、时间轴、快速问答持久化先吸收。
2. 本地长文档、导出、KaTeX 资源与文档产物链路再补回。

#### 主题 E：品牌、前端定制与用户资料

1. 本地品牌文案和修改密码入口保留。
2. 上游菜单过滤、样式修复、时间轴组件演进保留。

#### 主题 F：最后再回放当前 WIP

目标：在核心同步通过后，再处理当前的内置智能体可见性改动。

处理原则：

1. 先保证 `sync/dev-20260819-rebuild` 在不含当前 WIP 的情况下可编译、可测试。
2. 然后从 `wip/20260819-builtin-agent-visibility` 按文件或提交补回。
3. 新迁移编号、可见性枚举、推荐问题接口要基于同步后的最新代码重新复核。

### 5.5 每个主题的落地方式

建议采用下列工作方式：

```bash
git log --reverse --oneline upstream/main..dev
git cherry-pick -n <一组同主题提交>
# 解决冲突
git commit -m "sync: restore local <主题> semantics on upstream v0.7.2"
```

如果某一类改动历史过碎，可以直接手工移植代码，而不是机械 cherry-pick 全部历史。

## 7. 推送与回滚

### 7.1 推送方式

同步验证通过后，先推送临时同步分支：

```bash
git push -u origin sync/dev-20260819-rebuild
```

确认无误后，再在维护窗口内更新 `origin/dev`：

```bash
git push --force-with-lease origin sync/dev-20260819-rebuild:dev
```

之所以使用 `--force-with-lease`，是因为本轮采用的是“从上游重建分支再回放本地能力”的路径，最终会重写 `dev` 历史。

### 7.2 回滚方式

如果同步失败：

```bash
git checkout dev
git branch -D sync/dev-20260819-rebuild
```

如果已经覆盖了 `origin/dev`，则使用同步前锚点恢复：

```bash
git checkout backup/dev-20260819-before-sync
git push --force-with-lease origin HEAD:dev
```

## 8. 最终结论

本轮同步的核心判断如下：

1. 当前不是可以直接执行 `git pull upstream main` 的场景。
2. `dev` 相对 `upstream/main` 已形成 `100 / 528` 的大跨度分叉，且双方在 278 个文件上存在重叠修改。
3. 上游重点是 `v0.7.2` 的文档解析、聊天时间轴、长期记忆、数据源和 Docker 修复；本地重点是权限模型、知识库权限、IM 隔离、长文档导出、品牌与部署定制。
4. 最稳妥的主路径不是直接 `rebase`，也不是在脏工作区里直接 `merge`，而是从 `upstream/main` 新建整合分支，再按主题补回本地能力。
5. 当前未提交的内置智能体可见性改动必须先独立固化，再作为最后一批主题回放。

如果严格按本文档执行，可以在吸收最新上游 `v0.7.2` 的同时，把本地 `dev` 的核心业务语义较稳妥地迁移到新基线上。
