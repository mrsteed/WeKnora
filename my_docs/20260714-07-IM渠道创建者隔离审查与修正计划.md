# IM渠道按创建者隔离可见性审查与修正计划

## 1. 需求目标

目标已经明确：

- IM 集成渠道，每个人只能看到自己创建的渠道。
- 不能看到别人创建的渠道。
- 核心目的是避免覆盖别人渠道上的微信绑定或其他平台凭证。

这不是单纯的前端显示优化，而是一个需要后端数据模型、查询条件和写权限一起收口的可见性与所有权问题。

## 2. 当前代码审查结论

## 2.1 当前 `im_channels` 没有“创建者”字段

当前 IM 渠道模型定义在：

- internal/im/types.go

现有字段包括：

- `id`
- `tenant_id`
- `agent_id`
- `platform`
- `name`
- `enabled`
- `mode`
- `output_mode`
- `knowledge_base_id`
- `bot_identity`
- `session_mode`
- `credentials`

但没有：

- `created_by`
- `creator_id`
- `owner_user_id`

也就是说，当前 `im_channels` 在数据层根本没有能力表达“这条渠道是谁创建的”。

这与知识库、智能体等资源不同：

- `custom_agents` 已有 `CreatedBy`，见 internal/types/custom_agent.go
- 创建智能体时会从上下文写入创建者，见 internal/handler/custom_agent.go

因此当前 IM 渠道天然是“租户级共享配置”，而不是“用户级私有配置”。

## 2.2 当前数据库表结构同样没有创建者列

IM 渠道迁移定义在：

- migrations/versioned/000021_im_channel.up.sql

表结构里只有：

- `tenant_id`
- `agent_id`
- `platform`
- `name`
- `enabled`
- `mode`
- `output_mode`
- `credentials`
- `created_at`
- `updated_at`
- `deleted_at`

没有创建者字段。

这说明：

- 当前不是代码忘了过滤，而是 schema 本身不支持按创建者过滤。

## 2.3 当前后端列表查询是“租户全量”或“Agent 全量”

### A. 按 Agent 查询

后端服务层：

- internal/im/service.go 的 `ListChannelsByAgent`

当前查询条件是：

- `agent_id = ?`
- `tenant_id = ?`
- `deleted_at IS NULL`

没有任何用户维度过滤。

### B. 按租户总览查询

后端服务层：

- internal/im/service.go 的 `ListChannelsByTenant`

当前查询条件是：

- `c.tenant_id = ?`
- `c.deleted_at IS NULL`

同样没有用户维度过滤。

因此，只要同租户内有权限访问这些接口，就会看到租户里所有 IM 渠道，而不是自己创建的那一部分。

## 2.4 当前创建接口不会记录创建人

创建 IM 渠道的 handler 在：

- internal/handler/im.go 的 `CreateIMChannel`

它会写入：

- `TenantID`
- `AgentID`
- `Platform`
- `Name`
- `Mode`
- `OutputMode`
- `KnowledgeBaseID`
- `Credentials`
- `Enabled`

但不会从用户上下文取：

- 当前登录用户 ID
- 当前登录用户姓名

也不会写入任何创建者字段。

所以即使今天加一个前端筛选“只显示我创建的”，后端也没有可依赖的数据来源。

## 2.5 当前权限守卫是“角色守卫”，不是“创建者守卫”

当前 RBAC 总设计在：

- internal/router/rbac.go

现有资源类型分两类：

1. 角色守卫
   - `Viewer()` / `Contributor()` / `Admin()` / `Owner()`
2. 归属守卫
   - `OwnedKBOrAdmin()`
   - `OwnedAgentOrAdmin()`
   - 以及若干 KB 子资源变体

当前 IM 渠道路由使用的是纯角色守卫，不是归属守卫：

- 创建、列表、更新、删除、启停、微信二维码绑定，当前都不基于“谁创建了这条渠道”判断。

这也是为什么我们此前把 IM 权限放到 contributor+ 之后，实际上变成了：

- contributor 可以直接看到并修改同租户其他人创建的渠道。

从你的最新需求看，这正是现在要修正的问题。

## 2.6 前端多处直接消费“全量渠道列表”

前端至少有两类地方依赖当前后端返回的全量 IM 渠道：

### A. IM 集成管理面板

- frontend/src/components/IMChannelPanel.vue

这里会调用：

- `listAllIMChannels()`
- `listIMChannels(agentId)`

当前完全信任后端返回的数据来渲染卡片列表。

### B. 左侧菜单的会话来源元信息

- frontend/src/components/menu.vue

这里也会调用：

- `listAllIMChannels()`

目前它用这个接口推导“当前租户配置了哪些 IM 平台”。

这意味着如果后端开始只返回“我创建的渠道”，这个菜单逻辑也会连带受到影响。

这未必是坏事，但必须在方案里明确：

- 这是预期变化
- 还是需要菜单改为从别的数据源推导 IM 来源

## 2.7 当前设计下，渠道确实容易被互相覆盖

因为当前 IM 渠道是渠道级共享配置，且 `credentials` 直接保存在 `im_channels` 上，所以：

- A 用户打开渠道并重新绑定微信
- B 用户随后也打开同一个渠道并重新绑定微信

最终结果是：

- 后保存的人覆盖前保存的人
- 渠道的当前 bot 凭证被替换
- 前一个人的微信绑定对这个渠道失效

如果 contributor+ 共享可见，而没有创建者隔离，这种覆盖是必然的，不是偶发问题。

## 3. 根因总结

本问题的根因不是一处，而是三层叠加：

1. 数据模型没有创建者字段。
2. 列表查询只按租户 / agent 过滤，不按创建者过滤。
3. 更新、删除、启停等写接口只做角色控制，不做渠道归属控制。

所以：

- 前端即使临时做过滤，也是不安全的。
- 必须由后端数据和权限模型一起收口。

## 4. 修正方向判断

如果需求是：

- 每个人只能看到自己创建的渠道
- 也只能修改自己创建的渠道
- 目的就是避免互相覆盖绑定

那么最合理的解释是：

- IM 渠道在权限上要从“租户级共享基础设施”转成“用户创建的私有租户内资源”。

这并不要求立刻把渠道完全改成成员级独立运行实例模型；但至少要做到：

- 渠道有创建者
- 渠道列表按创建者隔离
- 渠道写操作按创建者隔离

## 5. 修正计划

## Phase 1：补齐数据模型

### 5.1 新增创建者字段

建议在 `im_channels` 增加：

- `created_by VARCHAR(36) NOT NULL DEFAULT ''`

建议理由：

- 当前项目的 `custom_agents` 已经使用 `CreatedBy`
- 字段语义清晰
- 与现有“资源创建者”模式保持一致

可选但不必须：

- `created_by_nickname`

这个字段不是权限判断必需，可以继续通过 join `users` 动态取展示名。

### 5.2 增加索引

建议新增索引：

- `(tenant_id, created_by)`
- `(tenant_id, agent_id, created_by)`

目的：

- 支撑“当前用户在当前租户下的渠道列表”
- 支撑“当前用户在某个 agent 下的渠道列表”

## Phase 2：补齐创建写入

### 5.3 创建 IM 渠道时写入当前用户 ID

修改：

- internal/handler/im.go 的 `CreateIMChannel`

做法：

- 从请求上下文读取当前用户 ID
- 写入 `channel.CreatedBy`

和当前智能体创建流程保持一致。

## Phase 3：后端列表按创建者隔离

### 5.4 改 `ListChannelsByAgent`

当前：

- 按 `tenant_id + agent_id` 返回所有渠道

建议改为：

- 按 `tenant_id + agent_id + created_by` 返回当前用户创建的渠道

### 5.5 改 `ListChannelsByTenant`

当前：

- 按 `tenant_id` 返回所有渠道

建议改为：

- 按 `tenant_id + created_by` 返回当前用户创建的渠道

### 5.6 handler 层把当前用户 ID 传入 service

当前 handler 只传：

- `tenantID`
- `agentID`

后续需要额外传：

- `currentUserID`

否则 service 无法完成按创建者过滤。

## Phase 4：写操作改为创建者隔离

这一步非常关键，否则用户虽然“看不到”别人的渠道，仍可能直接构造请求覆盖别人渠道。

### 5.7 更新 / 删除 / 启停接口不能只靠角色守卫

目前这些接口仍是：

- 角色守卫
- 根据 `id + tenant_id` 直接更新或删除

建议改造为：

- 查询条件至少包含 `id + tenant_id + created_by`

即：

- 只有创建者本人才能更新 / 删除 / 启停自己的渠道

### 5.8 不建议直接复用 `OwnedAgentOrAdmin`

原因：

- 你的最新需求是“每个人都不能看到别人创建的渠道”
- 这比当前 `OwnedXxxOrAdmin` 的“创建者或管理员可改”更严格
- 如果复用 `OwnedXxxOrAdmin`，admin / owner 仍然能看到并修改别人渠道
- 这与“避免覆盖他们的渠道绑定”的需求相冲突

因此建议新增一类更严格的守卫，例如：

- `RequireOwnershipOnly`
- 或 `OwnedIMChannelOnly`

语义应是：

- 只有创建者本人可以操作
- 不给 tenant admin / owner 默认绕过权

如果后续确实需要运维兜底能力，再单独增加：

- 审计查看入口
- 或只读管理员总览

而不要在第一版就给管理角色保留写入绕过。

## Phase 5：历史数据迁移与归属补齐

这是这项需求里最容易被低估的一步。

### 5.9 历史渠道没有创建者，需要一次性回填

问题：

- 现有 `im_channels` 没有创建者数据
- 一旦新逻辑上线，如果不回填，旧渠道无法归属于任何人

### 5.10 回填策略建议

建议采用分层策略：

#### A. 可自动推导的渠道

如果渠道绑定的是自定义 Agent，且该 Agent 有明确 `created_by`：

- 可以优先尝试用 `custom_agents.created_by` 回填 `im_channels.created_by`

但要注意：

- Agent 创建者不一定等于渠道创建者
- 这只是“较高可信度默认值”，不是绝对真相

#### B. 绑定内置 Agent 的渠道

这类渠道通常无法从 `agent_id` 自动推导创建者。

建议：

- 通过一次性 SQL/脚本列出所有 `created_by=''` 的渠道
- 按租户由实际业务负责人人工认领或批量指定

#### C. 没法确认归属的历史渠道

建议兜底策略：

- 暂时收归租户 owner
- 然后由 owner 在迁移窗口内手工重分配或重建

### 5.11 建议增加修复脚本

建议新增类似修复脚本：

- `scripts/im_channel_repair/assign_im_channel_creator.sh`

支持：

- 按租户列出无归属渠道
- 按渠道 ID 指定创建者
- 批量把某一类历史渠道指派给某个用户

## Phase 6：前端配合调整

### 5.12 IM 管理页无需再额外做本地过滤作为权限依据

只要后端列表已经按创建者过滤：

- `IMChannelPanel.vue` 会天然只显示当前用户自己的渠道

前端本地过滤只能作为展示层补充，不应作为权限边界。

### 5.13 Agent 编辑器内联 IM 计数会自动变成“我的渠道数”

因为它调用：

- `listIMChannels(agentId)`

后端一旦改成按 `created_by` 过滤：

- 这里显示的就是“当前用户在该 Agent 下创建的 IM 渠道数”

这是符合本需求的。

### 5.14 左侧菜单 `listAllIMChannels()` 的用途要复核

当前菜单里会调用：

- `listAllIMChannels()`

它现在用于推断已配置的 IM 平台种类。

修正后它只会看到当前用户自己的渠道，因此：

- 若菜单的意图是“显示我能使用的 IM 来源”，则符合需求。
- 若菜单的意图是“显示整个租户有哪些 IM 平台”，则需要改定义。

建议按本次需求直接收口为：

- 只代表“当前用户自己拥有的 IM 渠道来源”。

## 6. 推荐实施顺序

1. 新增 `created_by` 列与索引。
2. 创建接口写入当前用户。
3. 列表接口改成按创建者过滤。
4. 更新 / 删除 / 启停接口改成创建者隔离。
5. 增加严格 creator-only 守卫。
6. 编写历史渠道归属回填脚本。
7. 执行一次历史数据回填。
8. 再做前端联调验证。

## 7. 回归验证建议

### 7.1 可见性验证

1. 用户 A 创建渠道后，只能自己看到。
2. 用户 B 在同租户、同 Agent 下，看不到用户 A 的渠道。
3. owner / admin 默认也看不到其他人渠道（按本次严格需求）。

### 7.2 写权限验证

1. 用户 A 可以编辑自己的渠道。
2. 用户 B 不能通过构造请求更新用户 A 的渠道。
3. 删除、启停、微信重新绑定都必须受同样的创建者校验。

### 7.3 迁移验证

1. 历史渠道已成功回填 `created_by`。
2. 未回填的历史渠道不会无声丢失。
3. owner 可以通过脚本识别并处理无归属渠道。

### 7.4 绑定覆盖验证

1. 用户 A 重新绑定自己的微信，只影响自己的渠道。
2. 用户 B 无法再打开并覆盖用户 A 的渠道绑定。

## 8. 最终判断

从当前代码看，系统现在并不具备“每个人只能看到自己创建的 IM 渠道”的能力。

原因不是前端没加过滤，而是：

- schema 没有创建者字段
- 列表查询是租户全量
- 写接口是角色守卫，不是渠道归属守卫

要满足你的需求，必须至少做以下三类改造：

1. 给 `im_channels` 增加创建者字段。
2. 后端列表只返回当前用户创建的渠道。
3. 后端更新/删除/启停/绑定保存改成严格创建者校验。

否则即使页面看起来“只显示我的渠道”，别人仍然可能通过接口覆盖他人的渠道绑定。

## 9. 建议范围控制

如果你下一步要我继续落地实现，建议先只做第一版严格隔离：

- contributor+ 可以创建自己的 IM 渠道
- 每个人只能看到并操作自己创建的渠道
- 不给 admin / owner 默认绕过写权限

这样最符合你现在“避免覆盖别人渠道绑定”的目标，也最容易验证是否真的把问题收住。
