# 知识库文档权限与列表复选框审查报告

日期：2026-07-15

## 审查结论

### P0：当前实现没有建立“可见即可上传、按文档上传者归属操作”的权限模型

现状不能满足下面这组重新确认后的业务要求：

1. 账号对知识库有可见权限时，可以上传文档。
2. 上传后要保留各个上传者身份。
3. 不属于知识库创建者和管理员的账号，只能编辑、删除、操作自己上传的文件，不能操作其他人上传的文件。

关键证据：

- 上传接口已经按“可见即可上传”放行：`internal/router/router.go:277-279` 使用 `g.Viewer() + g.KBAccessRead("id")`。
- 文档模型本身已经有上传者归属字段：`internal/types/knowledge.go:157-160` 的 `CreatedBy` 明确表示“上传或创建该知识条目的内部用户 ID”。
- 前端列表也已经展示上传者：`frontend/src/views/knowledge/components/DocumentListView.vue:18-19,78-82,227,281-282` 使用 `created_by` / `created_by_nickname` 渲染“上传人”列。
- 但单文档删除、编辑、手工文档编辑、重解析、取消解析当前都额外要求“知识库创建者或租户管理员”：`internal/router/router.go:295-299` 使用 `g.OwnedKnowledgeKBOrAdmin() + g.KBAccessWriteFromKnowledgeIDParam("id")`。
- `OwnedKnowledgeKBOrAdmin` 的定义在 `internal/router/rbac.go:278`，其语义是 `creator OR TenantRoleAdmin+`，这里的 creator 指向知识库创建者，不是文档上传者。
- 对应处理器内部并没有再按文档 `CreatedBy` 做二次判定，而是统一走共享知识库级别权限校验：
  - 删除：`internal/handler/knowledge.go:992,1004`
  - 编辑：`internal/handler/knowledge.go:1536,1546`
  - 重解析：`internal/handler/knowledge.go:1644,1656`
  - 取消解析：`internal/handler/knowledge.go:1713,1725`
  - 这些处理器都调用 `resolveKnowledgeAndValidateKBAccess(..., types.OrgRoleEditor)`，其实现位于 `internal/handler/knowledge.go:154`。

结论：

1. 上传能力与“知识库可见即可上传”的目标基本一致，这部分不是主要矛盾。
2. 文档层已经具备保留上传者身份的基础数据结构和前端展示位，因此“保留各个上传者身份”不是从零开始的新能力，而是要围绕现有 `CreatedBy` 建立权限判定。
3. 当前真正缺失的是“文档上传者归属权限层”：
   - 现有路由层过严，只允许知识库创建者或管理员操作文档，导致普通上传者即使上传了自己的文件，也不能编辑或删除自己的文件。
   - 现有处理器层又过粗，只校验知识库级共享写权限，没有落实“非创建者/管理员只能操作自己上传文件”的限制。
4. 因此这个问题不能简单通过“放宽到共享 Editor”解决。若只去掉 `OwnedKnowledgeKBOrAdmin`，会把权限放大成“有知识库写权限的人都能操作所有文档”，这同样违背新需求。
5. 从新需求出发，正确的目标语义应为：
   - 知识库创建者和管理员可以操作该知识库下所有文档。
   - 其他对知识库可见的账号可以上传文档，但只能操作 `CreatedBy == 当前用户` 的文档。

对前端的影响也需要同步重写：

- 上传入口仍应按“知识库可见”显示。
- 文档菜单、批量选择、列表复选框、详情页编辑入口不能再只复用知识库级 `canEdit` / `canManage`。
- 前端必须增加按文档逐条判定的权限逻辑，至少要区分“我能上传到这个知识库”和“我能不能操作这一条文档”。

### P1：列表模式行复选框存在确定性的事件绑定错误，导致点击后不会执行业务选择逻辑

这个问题可以直接从代码确认，不是推测。

关键证据：

- 列表模式行复选框在 `frontend/src/views/knowledge/components/DocumentListView.vue:241` 使用：

  ```vue
  @change="makeRowCheckboxChangeHandler(item)"
  ```

- 但 `makeRowCheckboxChangeHandler` 在 `frontend/src/views/knowledge/components/DocumentListView.vue:172-174` 只是“返回一个函数”：

  ```ts
  const makeRowCheckboxChangeHandler = (item: KnowledgeItem) => {
    return (checked: boolean, ctx?: { e?: Event }) => onRowCheckboxChange(item, checked, ctx);
  };
  ```

- Vue 模板里的事件表达式会在事件触发时执行表达式本身，而不是把“表达式返回的函数”再二次调用。因此当前写法只会执行 `makeRowCheckboxChangeHandler(item)`，返回值会被丢弃，`onRowCheckboxChange` 不会真正收到 `checked` 和 `ctx`。
- 同页卡片模式的复选框写法是正确的对照组：`frontend/src/views/knowledge/KnowledgeBase.vue:2449`

  ```vue
  @change="(checked: boolean, ctx?: { e?: Event }) => onCardGridCheckboxChange(item.id, checked, ctx)"
  ```

结论：

1. 列表模式“单行复选框无法选中”由模板事件绑定写法错误直接导致。
2. 这个问题只影响行复选框；表头复选框 `onHeaderCheckboxChange` 的绑定方式正常。
3. 结合 `git blame`，这一行在 2026-07-08 的提交 `527986a0` 从“内联调用”改成了“工厂函数返回 handler”，属于明显的前端交互回归点。

### P2：当前缺少覆盖“文档上传者归属权限”和列表复选框的自动化测试，导致回归容易漏出

审查过程中未发现：

- 覆盖“普通上传者可以操作自己的文档、不能操作他人文档”的后端测试。
- 覆盖 `DocumentListView` 行复选框 `toggle-row` 行为的前端测试。

结果就是：

1. 后端一直没有把“知识库创建者权限”和“文档上传者权限”拆成两层，也没有被接口测试拦住。
2. 前端 2026-07-08 的事件绑定回归没有被组件测试或交互测试拦住。

## 整改计划

### 第一阶段：先消除线上现象级问题

1. 修复列表模式行复选框绑定。
   - 把 `frontend/src/views/knowledge/components/DocumentListView.vue:241` 改回直接接收事件参数的写法。
   - 推荐直接使用：

     ```vue
     @change="(checked, ctx) => onRowCheckboxChange(item, checked, ctx)"
     ```

   - 或把 `makeRowCheckboxChangeHandler` 改成真正接收事件参数的普通方法，而不是“返回函数的工厂”。

2. 先把单文档操作改成“知识库创建者/管理员可操作全部，普通账号仅可操作自己上传文件”。
   - `DeleteKnowledge`、`UpdateKnowledge`、`UpdateManualKnowledge`、`ReparseKnowledge`、`CancelKnowledgeParse` 不能再只看知识库创建者，也不能只看知识库写权限。
   - 需要新增独立的文档级判定：
     - 若当前用户是知识库创建者或管理员，放行。
     - 否则仅当 `knowledge.CreatedBy == 当前用户` 时放行。
   - 这一步的重点不是“放宽”，而是把判定维度从“知识库拥有者”改成“知识库拥有者/管理员 + 文档上传者本人”。

3. 同步前端入口显示规则，避免继续出现“前端可点、后端 403”或“前端看不到自己文件操作入口”的错配。
   - 文档上传按钮继续按知识库可见性控制。
   - 文档删除、编辑、重解析、批量选择、详情页操作入口不要再直接复用 `canEditKB` / `canManageKB`。
   - 先新增一个独立的逐条文档权限计算，至少与后端真实放行规则保持一致。
   - 对非创建者/非管理员用户，其他人上传的文档应隐藏或禁用操作入口与批量勾选入口。

### 第二阶段：按需求重构“知识库可见”与“文档可操作”的权限模型

按当前重新确认后的需求，建议按下面方式落地：

1. 单独定义“文档操作权限”，不要再混用“知识库管理权限”。
   - 知识库设置、分享管理、删除知识库：仍然保留知识库级 `manage` / `admin` 语义。
   - 文档上传：改为“知识库可见即可上传”。
   - 文档删除、编辑、重解析等文档变更能力：改为“知识库创建者/管理员可操作全部，其他用户仅可操作自己上传文档”的独立 `document ownership` 语义。

2. 后端统一到一个权限判定源。
   - 不要同时在路由层和处理器层使用两套不同语义。
   - 建议把文档级变更权限抽成独立 guard 或独立 resolver，直接围绕 `knowledge.CreatedBy`、知识库创建者和管理员角色做判定。
   - 上传、删除、编辑三类接口的语义应收敛为：
     - 上传看知识库可见性。
     - 删除/编辑/其他文档变更看“知识库创建者或管理员”与“文档上传者本人”。

3. 前端新增独立的文档级权限计算。
   - `canUpload`、`canEditKB`、`canManageKB` 继续保留各自语义。
   - 额外增加按条目计算的 `canMutateDocument(item)`，文档列表、卡片菜单、批量选择、手工文档编辑入口统一只看这个值。
   - 如果页面还需要“是否可以操作任意文档”的聚合态，再单独引入 `canMutateAnyDocument`，不要再反向复用知识库级布尔值。

4. 对相邻能力做边界复核，避免误放大权限面。
   - `move`、`batch-delete`、`reparse`、`cancel-parse`、`tag-edit` 等现有文档菜单项，原则上都应并入同一套“文档上传者归属权限”模型。
   - 若其中有个别动作需要比“编辑/删除”更高的权限，应单独明确，不要继续默认跟着知识库设置权限走。

5. 明确并固化“上传者身份”的持久化规则。
   - 文件上传、URL 导入、手工文档创建等入口都应稳定写入当前操作者的 `CreatedBy`。
   - 文档后续编辑、重解析、移动等操作不应覆盖原始上传者归属。

### 第三阶段：补测试，防止同类问题再次回归

1. 后端接口测试。
   - 增加共享知识库场景矩阵：知识库创建者、管理员、普通可见账号、文档上传者本人、非上传者普通账号。
   - 至少覆盖：
     - 可见账号可以上传文档。
     - 上传后 `CreatedBy` 正确保留。
     - 普通上传者可以编辑、删除、操作自己上传的文档。
     - 普通上传者不能编辑、删除、操作他人上传的文档。
     - 知识库创建者和管理员可以操作所有文档。

2. 前端组件测试。
   - `DocumentListView`：点击行复选框后必须发出 `toggle-row`。
   - `KnowledgeBase`：列表模式下单选、全选、Shift 连选、批量栏计数都要覆盖。
   - 补充逐条文档权限测试：自己上传的文档显示操作入口，别人上传的文档隐藏或禁用操作入口与批量勾选入口。

3. 联调验收。
   - 用“hlsa 创建全组织可见知识库、杨雪上传后删除/编辑自己文件”的真实场景做回归。
   - 补一个“杨雪尝试删除 hlsa 上传文件”的场景，确认会被正确拦截。
   - 补一个“管理员删除任意上传者文件”的场景，确认管理员保留全量操作权限。

## 补充风险

还有两个相邻风险值得在整改时一并处理：

1. 批量接口当前几乎都不是按“文档上传者归属”判定。
   - `internal/router/router.go:310` 的批量删除仍然挂在 `g.Contributor()` 上。
   - 但处理器 `internal/handler/knowledge.go:1057,1096` 只校验知识库级权限，没有校验每条文档的 `CreatedBy`。
   - 如果单条删除改成“只能操作自己上传文档”，批量删除、批量重解析、批量标签等接口也必须同步逐条校验，否则会留下绕过口子。

2. 前端批量选择语义会随权限模型变化而变化。
   - 在新需求下，非创建者/非管理员用户不应对他人上传的文档进入批量操作流。
   - 因此前端不能只修复“复选框能选中”，还要同时限制“哪些行允许被选中、被加入批量操作集合”。
