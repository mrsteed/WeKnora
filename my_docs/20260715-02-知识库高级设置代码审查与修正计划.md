# 知识库高级设置代码审查与修正计划

日期：2026-07-15

## 1. 审查范围

本次仅审查以下两个问题：

1. 高级设置中的“同时执行任务数”在批量上传场景下是否按该数量生效，以及默认值改为 3 需要改哪些代码。
2. “AI 问题生成”关闭后，文档上传仍触发 LLM 生成问题的根因，以及修正方案。

## 2. 结论摘要

### 2.1 “同时执行任务数”当前语义

当前实现控制的是“同一知识库进入后端解析流程的并发上限”，不是“浏览器同时上传多少个文件”。

也就是说：

1. 前端批量上传请求目前是串行发送的，不会按照该值并行发起多个上传请求。
2. 文件一旦上传落库后，后端会把知识记录置为 pending，并由知识库级派发器按 `max_concurrent_parse_tasks` 放行进入 `processing`。
3. 因此，这个值会限制“解析并发上限”，但不会直接限制“浏览器上传并发”。
4. 实际并发还会继续受到全局 asynq worker 并发数、docreader worker 数量等上层/下层限流的共同约束，所以它是上限，不是硬保证一定同时跑满该数量。

### 2.2 “AI 问题生成关闭后仍触发”当前根因

根因不是后端忽略了上传时的关闭配置，而是“新建知识库关闭问题生成”与“上传确认弹窗默认值”两侧语义不一致：

1. 新建知识库时，如果用户关闭了“AI 问题生成”，创建请求不会显式写入 `question_generation_config.enabled=false`，数据库里往往留下的是 `null`。
2. 上传确认弹窗读取知识库配置时，却把 `question_generation_config == null` 解释成“默认开启”。
3. 上传确认弹窗又会把当前 UI 状态无条件序列化为 `process_config.question_generation_config`，于是把原本应当视为“关闭”的知识库，在上传时重新覆盖成“开启”。
4. 后端对这个上传时覆盖配置是会认真执行的，因此最终仍然触发了问题生成任务。

## 3. 证据链

## 3.1 “同时执行任务数”证据链

### 前端批量上传是串行，不按该值并发发请求

文件：`frontend/src/views/knowledge/KnowledgeBase.vue`

`executeUploadBatch()` 中使用 `for ... of` + `await uploadKnowledgeFile(...)` 逐个上传文件。这说明浏览器侧请求并发固定为 1，而不是读取知识库的 `maxConcurrentParseTasks` 做并发池控制。

### 后端解析并发由知识库派发器控制

文件：`internal/application/service/knowledge_create.go`

`CreateKnowledgeFromFile()` 上传成功后会把知识记录写成：

- `parse_status = pending`
- `enable_status = disabled`

随后调用 `EnqueueKnowledgeFileDispatchTask(...)`。

文件：`internal/application/service/knowledge_file_dispatch.go`

`ProcessKnowledgeFileDispatch()` 会：

1. 统计同一知识库当前 `processing` 数量。
2. 读取 `kb.MaxConcurrentParseTasks`。
3. 计算 `available = limit - inFlight`。
4. 仅放行 `available` 个 pending 文件进入 `document:process`。

这说明该设置生效点在“文件已上传完成后的解析派发”，而不是上传请求层。

### 当前默认值为 5 的落点

主要落点如下：

1. `frontend/src/views/knowledge/settings/KBAdvancedSettings.vue`
   - `localMaxConcurrentParseTasks` 默认值为 5。
   - 非法输入回退到 5。
2. `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`
   - 新建表单默认值为 5。
   - 加载旧数据缺省回退到 5。
   - 更新配置时缺省回退到 5。
3. `internal/types/knowledgebase.go`
   - GORM 字段默认值是 `default:5`。
   - `EnsureDefaults()` 中兜底值是 5。
4. `internal/application/service/knowledge_file_dispatch.go`
   - 当 KB 值异常时，派发器运行时兜底值是 5。
5. `migrations/versioned/000084_kb_max_concurrent_parse_tasks.up.sql`
   - 数据库列默认值为 5。
6. 测试基线
   - `internal/application/repository/knowledgebase_sqlite_test.go`
   - `internal/application/service/vectorstore_test.go`
   这两处测试表结构也写死了 `DEFAULT 5`。

### 额外限制

文件：`internal/router/task.go`

全局 asynq worker 默认并发仍是 5。即使知识库设置改为 10，也不会突破 asynq 自身并发上限。

因此，“同时执行任务数”更准确的定义应该是：

“同一知识库的文件解析放行上限”，且最终实际并发 = 多层限流中的最小值。

## 3.2 “AI 问题生成关闭后仍触发”证据链

### 新建知识库关闭后，没有显式持久化 false

文件：`frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`

`buildSubmitData()` 里只有在以下条件成立时才会写入：

- `!isDatabase.value`
- `formData.value.questionGenerationConfig?.enabled`

即：只有开启时才发送 `question_generation_config`。关闭时直接省略该字段。

这会导致新建知识库关闭问题生成时，后端保存到库里的值很可能是 `null`，而不是显式的：

```json
{
  "enabled": false,
  "question_count": 3
}
```

### 后端把 null 视为关闭

文件：`internal/application/service/knowledge_process_config.go`

`defaultQuestionGenerationConfig(kb)` 在 `kb.QuestionGenerationConfig == nil` 时返回零值配置，也就是后端的默认语义其实是“未配置 = 不启用问题生成”。

### 上传确认弹窗把 null 视为开启

文件：`frontend/src/views/knowledge/components/UploadConfirmDialog.vue`

`initFromKbInfo(kb)` 中：

```ts
questionGenerationConfig: {
  enabled: kb.question_generation_config?.enabled ?? true,
  questionCount: kb.question_generation_config?.question_count || 3,
}
```

这里 `?? true` 直接把 `null / undefined` 解释成了开启。

### 上传确认弹窗会无条件把该状态作为 process override 发给后端

文件：`frontend/src/views/knowledge/components/UploadConfirmDialog.vue`

`buildProcessOverrides()` 会始终生成：

```ts
question_generation_config: {
  enabled: state.questionGenerationConfig.enabled,
  question_count: state.questionGenerationConfig.questionCount,
}
```

文件：`frontend/src/views/knowledge/KnowledgeBase.vue`

无论文件上传还是 URL 导入：

1. 上传确认弹窗返回 `processConfig`
2. `executeUploadBatch()` / `executeUrlImport()` 都会把 `process_config` 传给接口

### 后端会严格执行这个覆盖值

文件：`internal/application/service/knowledge_process_config.go`

`ResolveProcessConfig()` 中如果 `overrides.QuestionGenerationConfig != nil`，会直接覆盖知识库默认配置。

文件：`internal/application/service/knowledge_file_dispatch.go`

后续派发到 `document:process` 时，又会从 `knowledge.ProcessOverrides()` 恢复该配置，并把：

- `EnableQuestionGeneration`
- `QuestionCount`

带入任务载荷。

因此，当前链路是：

1. 新建 KB 关闭问题生成
2. 前端创建请求不写 false，DB 留下 null
3. 上传弹窗把 null 解读为 true
4. 上传弹窗显式提交 `process_config.question_generation_config.enabled=true`
5. 后端按覆盖值触发问题生成

这就是问题复现的完整原因。

## 4. 修正计划

## 4.1 问题一：“同时执行任务数”默认值改为 3

### 目标

把知识库级文件解析并发上限默认值从 5 统一改为 3，确保前端展示、后端兜底、数据库新建行默认值一致。

### 修改点

#### 前端

1. `frontend/src/views/knowledge/settings/KBAdvancedSettings.vue`
   - 把 `localMaxConcurrentParseTasks` 默认值从 5 改为 3。
   - 非法输入回退值从 5 改为 3。

2. `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`
   - 新建表单默认值从 5 改为 3。
   - 旧数据为空时的 UI fallback 从 5 改为 3。
   - 更新配置时 fallback 从 5 改为 3。

#### 后端

3. `internal/types/knowledgebase.go`
   - `gorm:"...default:5"` 改为 `default:3`。
   - `EnsureDefaults()` 中 5 改为 3。

4. `internal/application/service/knowledge_file_dispatch.go`
   - 运行时 fallback 由 5 改为 3。

#### 数据库迁移

5. 新增迁移，修改 `knowledge_bases.max_concurrent_parse_tasks` 默认值为 3。
   - 不建议直接改老迁移文件 `000084...up.sql`，避免污染已发布迁移历史。
   - 应新增一个新的 versioned migration，把列默认值从 5 切到 3。

#### 测试

6. 同步修改测试建表 SQL 默认值：
   - `internal/application/repository/knowledgebase_sqlite_test.go`
   - `internal/application/service/vectorstore_test.go`

### 是否需要改“批量上传行为”

如果产品预期只是“限制同一知识库同时解析多少个文件”，当前后端逻辑已经满足，不需要新增功能。

如果产品预期是“前端文件上传请求本身也按这个数量并发执行”，那么当前实现并不满足，需要单独增加一个浏览器侧上传并发池；但这将改变现有语义，建议先明确产品定义，再决定是否实施。

更稳妥的做法是先把文案改清楚，例如把“同时执行任务数”改成“同时解析任务数”或在说明里明确“该值不控制浏览器上传并发”。

## 4.2 问题二：“AI 问题生成”关闭后仍触发

### 修正目标

统一前后端语义：

- `question_generation_config == null` 应等价于“关闭”
- 上传确认弹窗不得把 null 自动解释成“开启”
- 新建知识库时关闭状态应尽量落成显式值，减少后续歧义

### 最小修正方案

#### 前端上传弹窗修正

1. 修改 `frontend/src/views/knowledge/components/UploadConfirmDialog.vue`

把：

```ts
enabled: kb.question_generation_config?.enabled ?? true
```

改为：

```ts
enabled: kb.question_generation_config?.enabled ?? false
```

这样可以立刻阻止“KB 中是 null，却在上传时被重新覆盖成 true”的问题。

2. 同时检查 `createDefaultUIState()` 中的默认值。

当前默认是：

```ts
questionGenerationConfig: { enabled: true, questionCount: 3 }
```

建议改成与后端默认语义一致的关闭值，或者至少保证只在明确需要时才回退到 true。否则将来只要某个入口忘记传 `kbInfo`，问题还会复发。

#### 新建知识库持久化修正

3. 修改 `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`

新建 document 类型知识库时，不要只在启用时发送 `question_generation_config`，而是始终显式发送：

```json
{
  "enabled": true|false,
  "question_count": 3
}
```

这样数据库里不会再留下语义不清晰的 `null`。

4. 前端 API 类型声明同步补齐 `question_generation_config` 字段

文件：`frontend/src/api/knowledge-base/index.ts`

当前 `createKnowledgeBase()` 的 TS 参数声明里没有显式列出 `question_generation_config`，建议补齐，避免后续重构时再次丢字段或被误删。

### 建议的增强修正

5. 在后端返回知识库详情时统一输出显式的 `question_generation_config`

可选方案：在知识库读路径做归一化，让 document KB 在返回 JSON 时总是带上显式配置，例如：

```json
{
  "enabled": false,
  "question_count": 3
}
```

这样前端不会再依赖“null 的隐含语义”。

是否在持久层真正回填到数据库，可单独评估；至少响应层建议做统一归一化。

### 不建议的修法

不建议仅在后端上传接口里加一个“如果 KB 是 null 就强制关掉”的补丁，而不修上传弹窗默认值。那样只能掩盖当前入口，后续 reparse / URL import / 其他上传入口仍可能继续出现语义漂移。

## 5. 回归验证清单

## 5.1 “同时执行任务数 = 3”

1. 新建知识库时，高级设置默认展示 3。
2. 不改该值直接保存，新知识库详情返回 `max_concurrent_parse_tasks = 3`。
3. 同时上传 10 个文件时，前端请求仍串行发送，但后端最多只有 3 个文件处于 `processing`。
4. 把值改成 1、3、5 分别验证，派发器只放行对应数量。
5. 修改该值后，已有 pending 文件会立即触发一次补派发。

## 5.2 “AI 问题生成关闭”

1. 新建知识库时关闭“AI 问题生成”，保存后立即上传文件，不应再触发问题生成任务。
2. 知识库详情接口应返回显式关闭值，或至少上传弹窗中显示为关闭。
3. URL 导入场景同样不应触发问题生成。
4. 重新解析场景若未手动打开问题生成，也不应触发问题生成。
5. 历史数据库中 `question_generation_config = null` 的知识库，上传弹窗也应默认显示关闭。

## 6. 建议实施顺序

1. 先修 `UploadConfirmDialog.vue` 的默认值语义，这是最直接消除现网误触发的修复点。
2. 再补新建知识库时对 `question_generation_config=false` 的显式持久化，避免继续产生 `null` 数据。
3. 同步把 `max_concurrent_parse_tasks` 默认值统一改为 3，并新增数据库迁移。
4. 最后补回归测试，覆盖“KB 配置为 null / false / true”三种问题生成状态，以及 3 并发派发行为。

## 7. 最终判断

### 关于“同时执行任务数”

当前代码已经把它实现为“解析并发上限”，不是“上传请求并发”。如果这个定义符合产品预期，只需把默认值从 5 统一改为 3，并把文案表述得更准确。

### 关于“AI 问题生成关闭后仍触发”

这是一个真实缺陷，且根因明确：

1. 新建知识库关闭时没有显式持久化 false。
2. 上传确认弹窗把 null 错误解释为 true。
3. 上传时又把该错误状态显式覆盖回后端。

按本计划修复后，可以从根上消除该问题，而不是只在某一个上传接口上打补丁。
