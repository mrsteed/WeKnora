# 水厂 SCADA 实时数据接入与 Agent 智能分析方案（20261110-01）

> 目的：回答"水厂 SCADA 实时数据如何接入 WeKnora、并用智能体（Agent）进行分析"——把
> SCADA 侧的可选对接途径逐一列清，给出"哪些能力 WeKnora 现成可复用、哪些需要新建"，
> 并给出**最合理的接入架构**与分阶段落地路径。
>
> 依据：逐条对照 `WeKnora-sync_v0.8.3_base` 仓库源码核实（v0.8.3 工作副本），关键结论
> 均标注源码路径；SCADA/工业侧协议结论为行业通用做法（OPC-UA / IEC 104 / Modbus / MQTT）。
>
> 生成日期：2026-11-10

**核心结论一句话：WeKnora 是"RAG 知识库 + Agent 智能体平台"，不是工业时序/SCADA 平台，本身没有 MQTT/OPC-UA/时序库/遥测上报接口；最合理的接法是"三层解耦"——SCADA 侧用**边缘网关把 OPC-UA/IEC 104/Modbus 转成**对外只读 API**，再把实时链路（网关封装成 **MCP Server**，WeKnora 用 **MCP Client** 近实时取数做 Agent 分析）与历史知识链路（**时序库**缓冲 + 降采样导出 **CSV** → 走 WeKnora **datasource 连接器**（cron+asynq）入库 → Agent 用 **DuckDB `data_analysis` 工具**跑 SQL 统计）分开建设，同时把 SOP/设备手册/历史故障报告作为**文档**入库供 Agent 做知识接地（grounding）。三条链路复用 WeKnora 现有机制，只有"实时传输通道 + 时序缓冲 + 数据触发分析"是能力缺口需新建。**

---

## 1. 问题本质与边界（先对齐，避免走偏）

把"水厂 SCADA 实时数据"塞进 WeKnora，最典型的走偏是**把高频遥测流当文档灌进 RAG 向量库**。
SCADA 数据有两类**本质不同**的"数据"，必须分开处理：

| 数据类型 | 形态 | 例子 | 正确去向 | 是否适合向量检索 |
|---|---|---|---|---|
| **遥测/时序流（telemetry）** | 秒级/分钟级高频，`(tag, ts, value, quality)` | 进水流量、出水浊度、泵房压力、余氯浓度、电机电流 | **时序库 + Agent 近实时查询**，**不进向量库** | ❌ 会灌爆向量库且无时间语义 |
| **知识文档（knowledge）** | 低频、非结构化/半结构化文本 | 运行 SOP、设备手册、化验规程、历史故障处置记录、行业标准 | **RAG 向量检索**（WeKnora 主场） | ✅ 这是 WeKnora 的核心能力 |

> 边界结论：**WeKnora 只负责"知识检索 + Agent 编排分析 + 出结论"；遥测的"承载/存储/降采样"
> 必须交给外部时序设施（边缘网关 + 时序库）。** 这不是功能缺陷，而是定位分工。

现状代码证据（v0.8.3）：**无** MQTT / Kafka / OPC-UA / Modbus / IEC 104 任何工业协议接入；
**无**时序数据库（无 TimescaleDB / InfluxDB / TDengine）；**无**通用"遥测上报" REST 接口。
（关键字全文检索确认，命中均为子串误匹配。）

## 2. WeKnora 现有能力盘点（可复用 vs 需新建）

### 2.1 可直接复用（几乎零改动）

| 能力 | 源码位置 | 对本方案的用途 |
|---|---|---|
| **数据源同步框架（Pull + 定时）** | `internal/datasource/connector.go`（`Connector` 接口：`Validate`/`ListResources`/`FetchAll`/`FetchIncremental`） | 新增一个 `scada` 连接器，定时把**降采样后的历史 CSV / 报表**拉进知识库 |
| **生产级定时调度** | `internal/datasource/scheduler.go`（`robfig/cron/v3` 秒级 cron + `hibiken/asynq` 入队，多副本去重、重试、死信） | "周期性拉取 SCADA 历史/快照"最合适，自带去重与重试 |
| **任务队列** | `internal/router/task.go`（`asynq.NewServeMux`、核心工作队列、退避重试） | 承接"同步任务 / 分析任务"入队 |
| **DuckDB 数据分析工具 ⭐** | `internal/agent/tools/data_analysis.go`（`DataAnalysisTableName = "dataset"`；把入库的 CSV/Excel `read_csv_auto`/`read_xlsx` 载成 DuckDB 表，Agent 只读 SELECT 统计） | **Agent 对结构化时序/报表数据做 SQL 聚合、异常筛查的现成原语** |
| **MCP Client（WeKnora 连外部）⭐⭐** | `internal/mcp/manager.go`（连接池）、`internal/mcp/client.go`，Agent 侧 `internal/agent/tools/mcp_tool.go` + `mcp_catalog.go` + `mcp_exposure.go` | **把 SCADA 边缘网关封装成 MCP Server（SSE/HTTP），Agent 直接把"取最新值/查区间/查告警"当内置工具近实时调用** —— 实时链路的关键 |
| **MCP Server（WeKnora 对外）** | `internal/mcpserver/server.go`、`tools_ingest.go`（`add_document` 支持 `content`/`url`）、挂 `/mcp/:endpoint_id`（`internal/router/routes_mcp_endpoint.go`） | 外部 BI/其它系统反向调 WeKnora 建库/检索/问答；也可用 `add_document` 推知识 |
| **Agent 编排引擎（ReAct）** | `internal/agent/engine.go` + `think/act/observe/prompts` + `tools/registry.go`（工具 JSON Schema） | 组织"取数 → 统计 → 对照 SOP → 出诊断"的多步推理 |
| **Web 抓取 / 沙箱 shell/Python** | `internal/agent/tools/web_fetch.go`、`shell_exec.go` + `internal/sandbox/`（Docker/E2B） | 灵活取数时 Agent 可 `curl` SCADA 只读接口 / 跑自定义统计脚本 |
| **技能包（Skills）** | `internal/agent/skills/`（Markdown frontmatter + 脚本，租户级加载/skillhub） | **把"SCADA 诊断 SOP / 水质异常判定流程"打包成技能注入 Agent，约束其分析套路** |
| **SSE 流式输出 + 事件总线 + 运行态流** | `internal/stream/`（Redis pubsub）、`internal/event/`（进程内总线） | 复用现有"流式返回分析结论"前端链路 |
| **IM webhook 入站** | `internal/im/`（dingtalk/feishu/wechat 等，webhook 回调） | **SCADA 告警推一条消息 → 触发 Agent 诊断**的旁路（消息语义，非遥测） |

### 2.2 需要新建（项目里不存在，方案重点）

| 缺口 | 说明 | 建议 |
|---|---|---|
| **实时/高频传输通道** | 无 MQTT/Kafka/OPC-UA/流式 ingestion | 不侵入 WeKnora 内核，**放在 SCADA 侧**：边缘网关转出 + 封装 MCP Server（近实时拉），或薄网关转 REST |
| **时序存储/缓冲** | 无时序 DB，高频数据**不能**进 RAG 向量索引 | 外部引入时序库（TimescaleDB / TDengine / InfluxDB / Kingbase 扩展），先缓冲 + 降采样 |
| **通用遥测上报 API** | 无 `POST /ingest/telemetry`（只有知识入库 + IM 入站） | 若坚持"推"式，新增一个鉴权过的轻量网关，而非改 WeKnora 内核 |
| **数据触发分析（事件驱动）** | 当前 Agent 是"一问一答 + 定时同步"节奏，无"数据变更即触发 Agent" | 借 cron 轮询 + asynq 入队；或网关检测到越限/告警时调 WeKnora chat/IM 触发 |

> 设计原则：**尽量不改 WeKnora 内核**。实时/时序的"脏活"放在 SCADA 接入侧（网关 + 时序库），
> WeKnora 只做它擅长的"知识 + Agent 分析 + 出结论"，通过 **MCP Client / datasource 连接器**
> 两个既有扩展点接入。

## 3. SCADA 对接途径全清单

SCADA 到 WeKnora 分两段：**① SCADA 侧（现场/SCADA 层）** 与 **② SCADA 与 WeKnora 之间**。

### 3.1 SCADA 侧：工业协议与网关（把"现场"变成"可读数据源"）

水厂 SCADA 常见协议（现场层 → 上位机层）：

| 层级 | 常见协议 | 说明 | 出口到 WeKnora 的转换器 |
|---|---|---|---|
| 现场 PLC/仪表 | **Modbus RTU/TCP**、**Profibus**、**BACnet**（楼宇/泵房） | 底层采集 | OPC-UA 网关 / 边缘盒子转 OPC-UA |
| 监控/通信 | **IEC 60870-5-104**（水/电遥调经典）、**DNP3**、**IEC 61850**（配电） | SCADA 主站通信 | 主站旁路读取 / Historian 数据库 |
| 现代工业接口 | **OPC-UA**（工业 4.0 事实标准，含安全/订阅/MQTT 绑定） | SCADA 服务器/网关暴露 | **首选**：直接订阅或转 REST/MQTT |

**推荐 SCADA 侧出口（关键设计）——"边缘网关 + 对外只读 API + 时序库"：**

```
现场 PLC/仪表        SCADA 主站
(Modbus/Profibus)   (IEC 104 / DNP3)
        |                 |
        v                 v
   OPC-UA 采集网关  ──>  SCADA Historian(历史库)
        |                        |
        v                        v
   [边缘网关 / 边缘盒子]          |
   - OPC-UA → 时序库写入(TimescaleDB/TDengine)
   - 降采样/聚合(1s→1min→1h)
   - 封装只读 REST: /latest /range /alarms
   - 封装只读 MCP Server(SSE/HTTP): 同批工具
```

> 原则：**SCADA 侧承担协议转换 + 时序承载 + 降采样**，对 WeKnora 只暴露"**只读、已降采样、结构化**"
> 的接口（REST / MCP）。**绝不让 Agent 直接向现场下发控制指令**（安全红线，见 §8）。

### 3.2 SCADA 与 WeKnora 之间：6 条对接途径

| # | 途径 | 数据方向 | 实时性 | WeKnora 侧机制 | 适用 |
|---|---|---|---|---|---|
| **P1** | **SCADA 边缘网关封装为 MCP Server（SSE/HTTP）→ WeKnora MCP Client** | 拉（Agent 主动查） | **近实时（秒~分钟）** | `internal/mcp/` + `tools/mcp_tool.go` | ⭐⭐ **实时/近实时 Agent 分析首选** |
| **P2** | **SCADA 历史/报表 → 时序库降采样导出 CSV → datasource 连接器（cron+asynq）入库 → DuckDB 分析** | 拉（定时） | T+1 / 历史 | `internal/datasource/` + `scheduler.go` + `tools/data_analysis.go` | ⭐⭐ **历史统计/趋势/离线诊断首选**（含报表核对） |
| **P3** | **SOP/手册/历史故障作为文档入库 → RAG 检索**（file/url/manual/MCP `add_document`） | 拉 / 推 | 静态知识 | `routes_knowledge.go`（`.../knowledge/manual`）+ `internal/mcpserver/tools_ingest.go` | ⭐ **知识 grounding**（Agent 分析时对照规程） |
| **P4** | **Agent 沙箱 shell / web_fetch 直连 SCADA 只读 REST** | 拉（灵活） | 近实时 | `tools/shell_exec.go` / `web_fetch.go` + `internal/sandbox/` | 临时/探索性取数、快速冒烟 |
| **P5** | **IM webhook：SCADA 告警推一条消息触发 Agent** | 推（事件触发） | 事件驱动 | `internal/im/` 回调 → 会话/chat | "越限即诊断"的触发旁路 |
| **P6** | **WeKnora 作为 MCP Server（`/mcp/:endpoint_id`）供外部 BI/第三方反查** | 反向拉 | 近实时 | `internal/mcpserver/` | 外部系统接入 WeKnora 知识与分析（非 SCADA 主链路） |

> **没有"直接把高频遥测推进 WeKnora"的途径**——这是定位决定的（§1）。凡是"推"，都要先在
> SCADA 侧降采样/转语义，再走 P1(查询)、P2(报表入库) 或 P5(告警事件)。

## 4. 最合理的接入架构（推荐方案）

**一句话定调：三条链路各司其职、全部落在 WeKnora 既有扩展点上，只把时序承载放在 SCADA 侧。**

- **实时分析链路（P1/MCP）**：Agent 通过 MCP Client 调 SCADA 网关的只读工具，取最新值/近区间/
  未消警告警，做"当前状态诊断"。
- **历史/离线分析链路（P2/datasource + DuckDB）**：周期性把降采样 CSV 拉进知识库，Agent 用
  `data_analysis` 工具对 `dataset` 表跑只读 SELECT，做趋势/聚合/异常筛查/报表核对。
- **知识接地链路（P3/RAG）**：把 SOP/规程/历史故障处置作为文档入库，Agent 分析结论时检索
  对照，把"数据现象"翻译成"符合哪条规程 / 类似哪次故障"。
- **触发链路（P5/IM，可选）**：越限/告警推消息，即时唤起 Agent 出诊断并回推运维。

### 4.1 为什么这样最合理（对比取舍）

| 备选 | 结论 | 理由 |
|---|---|---|
| **直接把高频遥测推进 WeKnora 知识入库** | ❌ 否决 | 无时序库、无遥测接口；秒级数据灌 RAG 会把向量库灌爆且无时间语义（§1 边界） |
| **改 WeKnora 内核加 MQTT/OPC-UA ingestion** | ❌ 不推荐 | 大改内核、与 RAG 定位冲突、维护成本高；应放在 SCADA 侧承担 |
| **只做一个"推 CSV 入库 + 定时问答"（仅 P2）** | ⭕ 够用但不够实时 | 只能做 T+1 离线分析，无法支撑"当前水质/泵组状态即时诊断" |
| **只做 MCP 近实时取数（仅 P1）** | ⭕ 实时够但历史薄 | 缺历史统计/趋势/报表核对能力，Agent 无法回答"近 30 天出水浊度均值" |
| **P1 + P2 + P3 三链路（本方案）** | ✅ **推荐** | 实时 + 历史 + 知识三者齐备，且全部复用既有扩展点，改动最小 |

## 5. WeKnora 侧需要落地的工作（最小改造面）

> 强调：**WeKnora 内核基本不动**，只做"加连接器 + 配 MCP 服务 + 建技能 + 建库"。

### 5.1 新增 `scada` 数据源连接器（P2，历史/报表链路）

按 `internal/datasource/CONNECTOR_IMPLEMENTATION_GUIDE.md` 与 `internal/datasource/README.md`
实现 `Connector` 接口（参照 `internal/datasource/connector/rss` 或 `gitlab` 等 HTTP 连接器）：

- `Validate`：校验 SCADA 网关 REST（降采样 CSV 导出接口）连通性与鉴权。
- `ListResources`：枚举要同步的"报表/主题"（如"出水水质日报""泵房电流周报""化验台账"）。
- `FetchAll/FetchIncremental`：拉取**降采样后的 CSV**（而非原始秒级流），落到知识库条目。
- 由 `internal/datasource/scheduler.go` 的 cron 触发（如每 15 分钟/每小时/每日），asynq 入队、
  多副本去重、失败重试、死信兜底（机制现成）。

> 数据形态：`(ts, point_tag, value, quality)` 或业务报表列。入库后即是文本型 CSV，
> Agent 可被 `data_analysis` 直接 `read_csv_auto` 成 `dataset` 表做 SELECT。

### 5.2 配置 SCADA 网关 MCP 服务（P1，实时链路）

- SCADA 侧把"取最新值 / 查区间 / 查未消警告警 / 查点表元数据"封装成 **MCP Server（SSE/HTTP）**。
- 在 WeKnora「MCP 服务」中登记该服务（`/api/v1/mcp-services`，`types.MCPService`），
  `internal/mcp/manager.go` 建立连接池，`internal/agent/tools/mcp_catalog.go` 把工具纳入
  tool catalog，Agent 即可像调用内置工具一样近实时取数。
- 传输走 **SSE / HTTP Streamable**（WeKnora MCP Client 出于安全**禁用 stdio**）；
  生产建议配 OAuth（`internal/mcp/oauth_manager.go`）+ 只读作用域。

> 建议的 4 个网关工具（对 Agent 最有价值，粒度别太细）：
> `scada_latest(tags[])`、`scada_range(tag, start, end, downsample)`、
> `scada_alarms(since, acked?)`、`scada_metadatas()`（点表/组态）。

### 5.3 建立知识 + 诊断技能（P3，接地链路）

- 建一个"水厂运行知识库"，把 SOP、化验规程、设备手册、**历史故障与处置**用
  `routes_knowledge.go` 的 file/manual 接口（或 MCP `add_document`）入库，走 RAG。
- 用 **Skills**（`internal/agent/skills/`）把"SCADA 诊断 SOP"（如"出水浊度偏高排查步骤""
  加药量与余氯关系判定"）打成技能包注入 Agent，约束其分析套路与输出格式，减少跑偏。

### 5.4 触发链路（P5，可选增强）

- SCADA 侧检测到越限/重要告警时，向钉钉/企业微信 IM 通道（`internal/im/`）推一条消息，
  WeKnora 接收后触发对应会话/Agent 做即时诊断并回推运维群。

## 6. Agent 分析方式设计（让"智能体分析"真正可用）

把"分析"拆成 Agent 可执行的多步（ReAct：think → act 调工具 → observe），并配 SOP 技能约束：

| 分析任务 | Agent 动作（工具组合） | 输出示例 |
|---|---|---|
| **当前状态诊断** | MCP `scada_latest` + `scada_alarms` → 对照 SOP 技能 | "2 号沉淀池出水浊度 3.8 NTU 超 1.0 NTU 限值，已消警 0 条同类告警，建议先核查加药泵 #3 电流" |
| **趋势/异常筛查** | datasource 入库 CSV → DuckDB `data_analysis` 跑 SELECT（均值/分位/环比） | "近 24h 出水浊度 P95=2.1，环比 +42%，异常集中在 02:00–04:00，与来水流量峰值相关" |
| **根因关联（知识接地）** | RAG 检索历史故障 + 当前数据 | "该现象与 2026-08 加药泵叶轮磨损故障一致，建议按 SOP §4.3 停机检查" |
| **报表核对** | DuckDB 读化验台账 CSV + 阈值 | "3 项指标超内控限值：浊度、氨氮、余氯，明细见附件" |
| **即时告警诊断（事件触发）** | IM 触发 → MCP 取数 + RAG 对照 → 回推 IM | IM 卡片：告警项 + 当前值 + 疑似原因 + 处置建议 |

> 关键：**DuckDB `data_analysis` 工具只读**（`data_analysis.go` 中非 SELECT 直接报错），且
> `dataset` 是"所选文档"的临时视图——即"一次分析挂一个已入库的 CSV/Excel"。这是把
> "结构化时序/报表交给 Agent 分析"的安全且现成的姿势。

## 7. 数据模型建议（SCADA 侧需标准化后交付 WeKnora）

| 实体 | 字段（建议） | 走哪条链路 |
|---|---|---|
| **点/测点 tag** | `tag_id, name, unit, location, type(模拟/数字), min, max, alarm_lo, alarm_hi` | P1 元数据工具 / P2 台账 |
| **时序值** | `(tag_id, ts, value, quality)` | 时序库（P1 区间查询）；降采样后 CSV（P2 入库） |
| **告警事件** | `(alarm_id, tag_id, ts, level, desc, acked_ts)` | P1 告警工具 / P5 IM 触发 |
| **化验/业务报表** | 按业务列（日期、指标、实测、限值、判定） | P2 入库 → DuckDB |
| **知识文档** | SOP/手册/历史故障（Markdown/Word/PDF） | P3 RAG |

> 交付 WeKnora 的数据**必须是降采样 + 结构化 + 只读**的形态（CSV / REST JSON / MCP 结果）。
> 原始高频流只留在时序库，由网关按需降采样后暴露。

## 8. 安全与边界（工业侧红线）

- **只读**：WeKnora 对 SCADA 的一切取数都是只读；**禁止** Agent 通过任何链路向现场下发
  控制/写命令。MCP 网关只注册读工具；REST 用只读账号。
- **网络隔离**：WeKnora 部署在管理区/办公网，SCADA 侧独立安全区（生产/监控区），两者之间
  经**单向数据边界 / 工业网闸 / DMZ 边缘网关**，WeKnora 只可达网关的只读口。
- **鉴权**：MCP 走 OAuth / API Key；datasource 连接器走 SCADA 网关鉴权；知识库按 WeKnora
  空间/租户隔离（`internal/middleware` RBAC：`full / retrieve / ingest`）。
- **数据最小化**：只把分析需要的点/降采样数据交付，不整库外泄；敏感字段脱敏。
- **审计**：网关侧记录所有对 SCADA 的只读访问；WeKnora 侧保留 Agent 调用 tool 的运行态（`internal/stream/`）便于回溯。

## 9. 分阶段落地路径

| 阶段 | 目标 | 关键动作 | 依赖/产出 |
|---|---|---|---|
| **P0 摸底** | 厘清水厂 SCADA 出口能力 | 确认：有没有 OPC-UA 网关/历史库/IEC 104 主站旁路？能否暴露只读 REST？ | 《SCADA 数据出口清单》+ 协议/点位表 |
| **P1 网关 + 时序（SCADA 侧）** | 统一只读出口 + 时序承载 | 部署边缘网关：OPC-UA 采集 → 时序库 + 降采样 + 只读 REST（`/latest /range /alarms`） | 可用只读 API + 点表元数据 |
| **P2 历史链路打通（WeKnora）** | 先跑通"离线/日报分析" | 新增 `scada` 连接器拉降采样 CSV 入库 → 建"水厂运行知识库" → Agent + `data_analysis` 跑 SQL 报表核对 | 可回答"近 30 天某指标统计/趋势" |
| **P3 实时链路打通（WeKnora）** | 近实时诊断 | SCADA 网关封装只读 MCP Server（SSE）→ WeKnora 登记 MCP 服务 → Agent 近实时取数诊断 | 可回答"当前出水水质/泵组状态" |
| **P4 知识接地 + 技能** | 分析"讲得有理" | SOP/历史故障入库 RAG；诊断 SOP 打成 Skill 注入 Agent | 结论能对照规程、可落地处置建议 |
| **P5 事件触发（可选）** | 越限即诊断 | SCADA 告警 → IM 通道 → 触发 Agent → 回推运维群 | 主动式运维提醒 |
| **P6 安全加固** | 达工业安全合规 | 网闸/只读账号/OAuth/审计/脱敏 | 通过安全评审 |

> 建议**先做 P2（历史/报表，最快见效、风险最低）→ 再 P3（实时）→ 最后 P4/P5**，
> 用"报表核对"这类低争议场景先验证 Agent 分析与数据链路，再逐步放大到实时诊断。

## 10. 风险与局限

- **WeKnora 无事件驱动的"数据到达即分析"**：实时性依赖 Agent 主动查（P1）或告警触发（P5），
  不是"流到就自动算"。若要"流式即算"，需在 SCADA 侧先做成告警/事件，再触发 WeKnora。
- **DuckDB 工具按"单文档=单 dataset"工作**：跨多个 CSV 的联合分析有限，必要时把多表
  合成一个 CSV（加 `__source` 列，类似多 sheet 的 `__sheet_name`）再入库。
- **MCP 实时性取决于 SCADA 网关**：网关查询延迟/限流直接影响 Agent 体验；给网关做只读缓存。
- **模型能力**：分析质量受底层 LLM 影响；用 Skill 固定"取数→统计→对照→结论"套路 +
  DuckDB 做精确统计（而非让 LLM 心算），可显著降低幻觉。
- **多水厂/多租户**：WeKnora 有空间/租户隔离，按水厂建独立知识库与 MCP 服务范围即可。

## 附录 B：一句话结论

> **别让 WeKnora 当 SCADA 的时序库或采集器。** 让 SCADA 侧（边缘网关 + 时序库）承担"采集/承载/
> 降采样/只读出口"，WeKnora 通过 **MCP Client（近实时取数）+ datasource 连接器（历史/报表入库）
> + RAG（知识接地）+ DuckDB 工具（SQL 统计）** 四个既有能力完成"Agent 智能分析"，实时/时序/
> 事件三处新建工作量都压在 SCADA 接入侧——这是改动最小、最贴合 WeKnora 定位、也最安全可控的接法。
