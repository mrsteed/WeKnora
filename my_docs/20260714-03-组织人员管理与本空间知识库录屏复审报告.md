## 3. 当前代码与录屏现象的对应关系

### 3.1 组织人员管理页走的是 org-tree 链路，当前写入是成功的

当前代码：

- `frontend/src/views/admin/components/EditUserDialog.vue`
  - 调用 `updateUserInOrg(props.orgId, props.user.user_id, ...)`
  - 以 `user_id` 作为目标成员标识
- `internal/handler/org_tree.go`
  - `UpdateUserInOrg` 中调用 `AssignUserToOrg`
  - 若角色更新失败，会直接返回 `Failed to update user role in organization`

日志 `my_docs/test/4` 与录屏一一致：

- `PUT /api/v1/org-tree/.../users/... request_body.role="viewer"`
- 随后又有 `request_body.role="admin"`
- 两次之后 `GET /api/v1/org-tree/.../members` 返回内容确实随之变化

结论：

- 组织树页面本身的角色编辑和回显当前是工作的。
- 这条链路不是本次“权限没有变化”的根因。

### 3.2 另一个“成员管理”页显示的是 tenant role 或旧组织链路，不是 org-tree 角色

当前代码里至少存在三套角色来源：

1. `tenant_members.role`
   - owner / admin / contributor / viewer
   - 租户成员页使用

2. `organization_members_pre_plan3.role`
   - admin / editor / viewer
   - 组织树人员管理页使用

3. `organization_tenant_members.role`
   - 旧组织空间成员表
   - `/organizations` 相关接口仍大量依赖

`internal/handler/tenant_member.go` 当前：

- `effectiveTenantRoleForUser(...)` 直接返回 `rawRole`
- `displayTenantRoleForUser(...)` 直接返回 `rawRole`

所以：

- `GET /api/v1/tenants/:id/members` 展示的是租户角色，不会显示 org-tree 的子组织管理员。

日志 `my_docs/test/4` 也能对应上：

- mxd 在 `GET /api/v1/tenants/10008/members` 里仍然是 `contributor`

结论：

- 录屏一与录屏二里“成员管理结果不一致”，本质上是跨页面读了不同的角色模型。
- 这不是“编辑没生效”，而是“页面 A 展示 org-tree role，页面 B 展示 tenant role / 旧组织 role”。

### 3.3 `/organizations` 体系仍依赖旧成员表，导致 org-tree 用户在旧页面中失真

当前 `internal/application/repository/organization.go`：

- `ListByUserID`
- `AddMember`
- `RemoveMember`
- `UpdateMemberRole`
- `ListMembers`
- `GetMember`
- `ListMembersByUserForOrgs`
- `CountMembers`

均仍依赖 `organization_tenant_members`，没有回退到 `organization_members_pre_plan3`。

这会导致：

1. org-tree 页面改成功后，旧组织页未必能读到
2. `my_role`、组织列表、共享统计、旧成员管理页都可能和组织树结果不一致

这与录屏二中“设置 > 成员管理”仍显示测试账号为 `只读` 的现象一致。

### 3.4 旧组织设置页前端又叠加了一次 tenant admin 限制

`frontend/src/views/organization/OrganizationSettingsModal.vue` 当前：

- `hasTenantAdmin = authStore.hasRole('admin') || authStore.canAccessAllTenants`
- `isAdmin = orgAdmin && hasTenantAdmin`
- `showTenantRoleHint = orgAdmin && !hasTenantAdmin`
- `handleRoleChange` / `confirmRemoveMember` 仍按 `member.tenant_id` 调接口

同时 `internal/router/router.go` 里 `RegisterOrganizationRoutes` 又把大量组织管理接口挂在 `g.Admin()` 上。

所以旧组织设置页的真实门槛是：

- 当前 tenant role 至少是 admin
- 且当前 organization role 也是 admin/owner

这与“知识库是否显示，只需要按照组织管理权限控制”的口径冲突。

## 4. 关于“本空间知识库明确应该显示哪些”的当前事实

### 4.1 当前前端实现的真实语义

当前知识库页左侧文案：

- `frontend/src/i18n/locales/zh-CN.ts`
  - `listSpaceSidebar.workspace = "本空间"`

但实际逻辑：

- `frontend/src/views/knowledge/KnowledgeBaseList.vue`
  - `spaceSelection === 'mine'` 对应左侧“本空间”
  - `mineKnowledgeBases = kbs.filter(isMyKnowledgeBase)`
  - `isMyKnowledgeBase` 判断条件仅为：
    - `creator_id === currentUserId` 或
    - `created_by === currentUserId`

当前实现结论：

- “本空间”实际上等于“我创建的知识库”
- 它不是：
  - 当前组织节点可见知识库
  - 当前 tenant 可读知识库
  - 当前组织管理员可管理知识库

这与录屏二完全一致：

- `全部` 里有 5 个卡片
- `本空间` 里是空

因为 mxd 不是这些知识库的创建者。

### 4.2 当前后端实现的真实语义

`internal/application/repository/knowledgebase.go` 当前：

- `ListAccessibleKBs` 返回：
  - 同 tenant 下 `visibility='global'`
  - 同 tenant 下 `visibility='org'`
  - 同 tenant 下 `visibility='private' AND created_by=currentUser`

`internal/application/service/kb_visibility.go` 当前：

- `CanAccessKB` 对 `visibility='org'` 直接返回 `true`

当前后端结论：

- 同 tenant 的 org 知识库，目前是 tenant-wide 可读，而不是按 org-tree 节点/子树裁剪。

这也与录屏二的 `全部` 视图一致：

- mxd 虽然是 `产品部` 的管理员，但依然能在 `全部` 里看到挂在 `技术支持部` 的 `HLSA合同库`。

### 4.3 当前数据事实

数据库核对结果：

1. mxd 当前只属于 tenant `10008`，tenant role 是 `contributor`
2. mxd 在 org-tree 中是 `产品部` 的 `admin`
3. tenant `10008` 当前唯一的 `visibility='org'` 知识库是：
   - `HLSA合同库`
   - `organization_id = 技术支持部`
4. `产品部` 与 `技术支持部` 是同级兄弟节点，不是父子关系

这意味着：

- 如果未来采用“org-tree 节点/子树可读”语义，mxd 不应因为管理 `产品部` 而自动看到 `技术支持部` 的 org 知识库。
- 如果继续采用 tenant-wide org 可读语义，那么 mxd 应看到它。

## 5. 两个问题的根因判断

### 5.1 问题一：修改账号角色后，人员管理里权限没有变化

当前复审结论：

- 如果指的是 `组织管理 > 组织人员管理` 这一页：录屏一已证明角色变化是即时生效的，不成立。
- 如果指的是 `设置 > 成员管理` 或租户成员页：现象成立，但原因不是 org-tree 更新失败，而是该页读取的是另一套角色模型。

根因拆分：

1. 页面之间角色语义不一致
   - org-tree 页显示组织角色
   - tenant 成员页显示 tenant role
   - 旧组织页又读旧表

2. 旧组织页仍依赖 `organization_tenant_members`

3. 旧组织页与路由层额外要求 tenant admin，导致 org-tree admin 可能被继续渲染成只读

### 5.2 问题二：mxd 作为组织管理员，本空间知识库不显示

当前复审结论：

- 现象成立。
- 直接原因不是“没有知识库可读”，而是“本空间”当前实现只看创建者。

根因拆分：

1. 前端“本空间”语义错误或至少命名错误
   - 文案叫“本空间”
   - 实现却是“我创建的”

2. 前后端对 org-visible KB 的口径不一致
   - 前端 `本空间` = 创建者
   - 后端 `/knowledge-bases` = tenant-wide global + org + self private
   - 产品预期又倾向“按组织管理权限控制”

3. `/organizations` 仍走旧表，导致组织空间入口和统计也会失真

## 6. 本空间“应该显示哪些”的口径分析

当前必须先冻结口径，否则不能谈“修复正确性”。

### 口径 A：本空间 = 我创建的知识库

这是当前前端真实实现。

按此口径：

- mxd 当前应看到 0 个
- 录屏二结果是“正确实现、错误文案”

### 口径 B：本空间 = 当前 tenant 下我可读的本租户知识库

按当前数据，mxd 应看到 5 个：

- global
  - 北下街数据库
  - HLSA制度库
  - HLSA技术库
  - HLSA产品库
- org
  - HLSA合同库

不应看到 private：

- HLSA财务库
- IM存储库
- `__chat_history__`

这和当前 `全部` 视图的实际结果一致。

### 口径 C：本空间 = 按组织树权限可读的知识库

如果严格按“组织管理权限控制”，更接近这个口径。

那么应再细分：

1. global 是否仍纳入本空间
2. org KB 是否要求 `organization_id` 命中“当前组织节点 + 子树”

按当前数据，mxd 管的是 `产品部`，唯一 org KB 挂在 `技术支持部`。

因此：

- 若 global 纳入，则 mxd 至少应看到 4 个 global
- 若只看 org-scope，则 mxd 当前应看到 0 个 org KB

### 建议口径

建议不要再让“本空间”承担“我创建的”语义。

更合理的方案是：

1. 单独保留“我创建的”入口
2. “本空间”明确改为以下两者之一：
   - 当前 tenant 可读集合
   - 当前组织节点/子树可读集合

如果产品坚持“知识库是否显示，只需要按照组织管理权限进行控制”，则更应采用第 2 种，而不是当前 creator-based 实现。

## 8. 修正计划

### 阶段 0：冻结术语与页面语义

先明确三件事：

1. tenant role 与 org role 是否允许在不同页面显示不同值
2. “本空间”到底表示什么
3. org-visible KB 是 tenant-wide 可读还是 org-tree 节点/子树可读

如果不冻结这三点，后续任何代码调整都会继续出现“一个页面对、另一个页面错”。

### 阶段 1：统一组织成员读取模型

目标：所有 `/organizations` 相关页面，与 org-tree 管理页读取同一套成员事实。

建议：

1. `organizationRepository` 中以下方法统一回退或直接切换到 `organization_members_pre_plan3`：
   - `ListByUserID`
   - `GetMember`
   - `ListMembers`
   - `ListMembersByUserForOrgs`
   - `UpdateMemberRole`
   - `RemoveMember`
   - `CountMembers`

2. 旧组织设置页成员操作统一改为使用 `user_id`

### 阶段 2：收口组织管理权限边界

目标：已有组织的管理操作只按组织角色判断。

建议：

1. `RegisterOrganizationRoutes` 中已有组织的管理类接口不再用 `g.Admin()` 作为前置 tenant 角色门槛
2. 路由放行后，由 handler / service 的 `IsOrgAdmin` / owner 校验作为真实授权边界
3. 前端 `OrganizationSettingsModal` 去掉 `hasTenantAdmin` 与 `orgAdmin` 的交集判断

### 阶段 3：统一“本空间”与知识库可见性语义

如果选择“按组织管理权限控制”，建议：

1. 当前 `mine` 入口改名为“我创建的”
2. 新的“本空间”不要再按创建者过滤
3. 新的“本空间”应明确绑定到以下之一：
   - 当前 tenant 可读集合
   - 当前 org-tree 节点/子树可读集合
4. 后端 `/knowledge-bases` 与前端筛选口径同步

### 阶段 4：收口附带问题

1. `favorites` / `recents` 加入保留值集合，禁止误走 `/organizations/:id/shared-knowledge-bases`
2. 若租户成员页继续展示 tenant role，则 UI 应明确标识“租户角色”
3. 如产品需要减少误解，可在租户成员页附加 org-tree 角色标签，而不是覆盖真实 tenant role

## 9. 最终判断

本次结合录屏、日志、代码、数据后的最终判断是：

1. 组织树“编辑用户角色”功能当前本身是工作的。
2. 用户感知到的“权限没有变化”，来自跨页面读取了不同角色模型，而不是 org-tree 写入失败。
3. mxd 的“本空间为空”当前是现有实现的必然结果，因为“本空间”实际被实现成了“我创建的知识库”。
4. 当前系统真正需要修的不是某一个 if 判断，而是：
   - 组织成员事实源统一
   - 组织管理授权边界统一
   - “本空间”语义统一

若不做这三项统一，继续单点打补丁，只会在不同页面之间重复出现“这里变了、那里没变”的同类问题。
