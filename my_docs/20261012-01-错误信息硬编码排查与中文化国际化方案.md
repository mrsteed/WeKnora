# 错误信息硬编码排查与中文化（国际化）方案 v2

> 日期：2026-10-12 ｜ 范围：WeKnora 后端 `internal/` + 前端 `frontend/` ｜ 状态：仅方案，未动代码
> v2 说明：本版在原方案基础上补齐遗漏口径，修正契约假设，并将迁移目标收敛为“单一语义位 + 前端统一翻译”。
> 触发问题：登录失败提示 `Invalid email or password`、空间初始化提示 `Failed to create user`，用户可见文案为英文硬编码。

## 1. 结论速览（TL;DR）

- 原文档中的 **1096 / 87 / 54** 统计在其既定口径下成立，但**不是全量用户可见错误硬编码总量**。
- 补充排查后，至少还存在：后端 **211 处** `gin.H{"error": "..."}` 直接字符串响应、**8 处** legacy `code/msg` 失败响应。这两类原文档未纳入统计。
- 当前仓库并非“没有错误码基础”，而是**存在多套并行语义位**：数值型 `error.code`、少量字符串型 `error.code`、以及已被前端消费的 `details.reason`。此时继续新增 `code_str`，会把契约分裂成第 4 套。
- v2 推荐方案：**P0/P1 不新增 `code_str`；标准错误契约统一收敛到 `details.reason` 作为稳定语义码，前端统一 `resolveError` 翻译；数值型 `error.code` 保持兼容；现有字符串型 `error.code` 由 resolver 兼容消费。**
- 迁移目标不是“把所有 message 全翻成中文”，而是**让用户可见文案彻底归前端 i18n 所有**；后端 `message` 逐步退化为兼容/日志/排障文案。

## 2. 排查范围与方法

- 后端：`internal/` 全部 `.go`（剔除 `_test.go`），按 5 类模式统计：
  1. `errors.New*Error("..."`
  2. `Message: "..."`
  3. `gin.H{"error": "..."}`
  4. legacy `c.JSON(..., gin.H{"code": 1, "msg": ...})`
  5. 服务层裸 `errors.New("..."`（仅作链路辅助判断）
- 前端：`frontend/src/api/**` 中 `|| '英文兜底'` 模式、`request.ts` 拦截器分支、页面级 `response.success === false` 失败路径、既有 `details.reason` / 字符串 `error.code` 消费点。
- 统计说明：下文是**按代码形态分组**的工程盘点，不是去重后的“最终用户可见文案条数”；不同组别不应简单相加为一个精确总数。

| NewValidationError | 170 | 中英文混写 |
| NewNotFoundError | 134 | `Agent not found`、`FAQ条目不存在` 等 |
| NewForbiddenError | 124 | `authentication required`、`无权访问该知识库` 等 |
| NewUnauthorizedError | 74 | |

| NewServiceUnavailableError | 2 | |

- 语言分布：英文 **926** 处，中文 **170** 处，呈“新模块中文、旧模块英文”的增量漂移状态。

### 3.2 直接 `gin.H{"error": "..."}` 字符串响应：211 处

这是原文档遗漏的最大一类。它们**绕过 `AppError` 中间件**，直接把英文或中文字符串塞给前端。

- 文件集中度最高的几处：
  - `internal/handler/system.go`：38
  - `internal/handler/wiki_page.go`：37
  - `internal/handler/embed_channel.go`：36
  - `internal/handler/im.go`：30
  - `internal/handler/datasource.go`：21
  - `internal/router/files.go`：18
  - `internal/middleware/auth.go`：10
  - `internal/middleware/embed_auth.go`：10
- 代表性场景：认证失败、Embed token 校验失败、Wiki/Page 参数错误、System/DocReader 检查失败。

### 3.3 legacy `code/msg` 失败响应：8 处

当前主要集中在 `internal/handler/system.go`，形式如：

```json
{ "code": 1, "msg": "连接失败: ..." }
```

特点：

- 既不走 `AppError`，也不走 `error.details.reason`。
- 其中甚至有 `HTTP 200 + code=1 + msg=失败原因` 的形态，`request.ts` 不会把它当 reject 处理。
- 不先纳入方案，后续会出现“错误翻译大部分做完，但系统设置里还会漏英文/中文直出”的情况。

### 3.4 `Message: "..."` 字面量：87 处

这组数据仍有参考价值，但要特别说明：**87 处并不全是错误文案**，里面混有成功提示、任务状态、检查结果说明等，不能直接并入“错误总量”。

与本次问题直接相关的典型项：

- `application/service/user.go` Login：`Invalid email or password` ×3、`Account is disabled` ×1
- `types/errors.go`：`Storage quota exceeded`
- `sandbox/validator.go`：安全策略拒绝原因
- `mcp_service.go`：OAuth 授权提示

结论：这 87 处应当作为**人工分层审计队列**，而不是一刀切地纳入自动迁移数量。

### 3.5 前端 API 层英文兜底：54 处

模式基本一致：

```ts
return { success: false, message: error.message || 'Failed to xxx' }
```

特点：

- 多数情况下是“后端没给 message”时的兜底；
- 一旦命中，会直接向用户展示英文；
- 它们分散在 `org-tree`、`organization`、`tenant` 等 API 封装文件里，属于典型的“早期便捷写法”。

### 3.6 现有契约事实：当前至少有 4 种错误 envelope、3 套语义位

1. **标准 `AppError` envelope**：`{ success:false, error:{ code:int, message, details } }`
2. **直接 error 字符串**：`{ error:"..." }` 或 `{ success:false, error:"..." }`
3. **手写字符串型 `error.code`**：已存在于 `sandbox_config` 一类接口，用于表达业务冲突语义
4. **legacy `code/msg` 或 `success:false,message`**：尤其是 2xx 失败返回

同时，前端/后端已经在消费 3 套“语义位”：

1. 数值型 `error.code`（中间件 AppError）
2. 字符串型 `error.code`（如 sandbox 冲突）
3. `details.reason`（空间初始化、修改密码等新链路已在消费）

这意味着：**继续新增 `code_str` 并不是最小成本路径，而是扩大契约分裂面。**

### 3.7 现有基础设施足够支撑改造，无需从零搭建

1. `AppError` 已输出 `{code, message, details}`，前端能拿到完整 error body。
2. `request.ts` 已在 reject 分支里把后端错误体摊平到顶层，便于集中解析。
3. 公共认证接口的 `401/403` 已有单独分支，登录/注册迁到真实 HTTP 错误的接线成本不高。
4. 前端 i18n 已有 `error` 命名空间以及若干子组，并非“只有 3 个键”；可以直接扩展 `error.messages.<reason>`。
5. 新代码已经在证明 `details.reason` 可用：例如空间初始化向导用 `reason + field` 判定冲突类型，改密码接口用 `details` 里的语义值做本地映射。

## 4. 根因

1. **错误契约碎片化**：不是单纯“缺错误码”，而是存在 `AppError`、direct JSON、legacy `code/msg`、`success:false,message` 多条并行链路。
2. **没有单一稳定语义位**：有的地方靠数值 `code`，有的靠字符串 `code`，有的靠 `details.reason`，更多地方直接靠 `message` 文本本身。
3. **用户文案归属错误**：后端 message 被直接视作最终 UI copy，导致语言、口吻、可本地化能力完全失控。
4. **2xx 失败返回绕开了全局错误收口**：`request.ts` 只统一 reject 的 HTTP 错误；`200 + success:false` 或 `200 + code=1` 仍需页面/调用方各自处理。
5. **大量 direct `c.JSON` 绕过治理点**：它们不经过 `AppError` 中间件，也不经过统一 helper，自然也绕过了任何潜在 lint 约束。

## 5. v2 方案：单一语义位 + 前端统一翻译

### 5.1 设计原则

1. **用户可见文案只能由前端 i18n 决定**。后端 `message` 只作为兼容、日志、调试兜底。
2. **P0/P1 不新增第 4 套语义位**。因此本版明确放弃 `code_str` 方案。
3. **标准错误契约的稳定语义位统一为 `details.reason`**。这是现有代码已在使用、且与数值型 `error.code` 不冲突的最小改动点。
4. **现有字符串型 `error.code` 先兼容消费，不作为新增默认路径**。待 legacy 清理后，再决定是否长期保留。
5. **旧的数值型 `error.code` 必须保留**。现有测试和调用方已依赖它，不能在同一轮改造里静默切换语义。

### 5.2 目标契约与迁移边界

#### 标准目标契约（推荐）

```json
{
  "success": false,
  "error": {
    "code": 1001,
    "message": "Invalid email or password",
    "details": {
      "reason": "user.invalid_credentials",
      "field": "email"
    }
  }
}
```

解释：

- `error.code`：保留既有数值码，保障兼容与测试稳定。
- `error.details.reason`：**唯一稳定语义码**，供前端 i18n 与业务分支判断使用。
- `error.message`：兼容与排障文案，不再承诺用户可见语义。

#### 现有遗留 envelope 的处理策略

| 现状 | P0/P1 处理 | 长期目标 |
|---|---|---|
| AppError 中间件错误 | 补 `details.reason` | 保持为主通道 |
| direct `gin.H{"error":"..."}` | 优先改造成 AppError | 清零新增，逐步存量清理 |
| 手写字符串型 `error.code` | resolver 兼容消费 | 视收益决定是否收敛 |
| `200 + success:false/message` | 页面侧临时适配；有条件则改成非 2xx + AppError | 逐步退出 |
| `200/4xx + code/msg` | 页面侧临时适配；System 等集中模块优先整改 | 逐步退出 |

### 5.3 前端统一错误解析

前端应新增一个真正覆盖现状的 `resolveError(raw)`，优先级建议如下：

1. `raw.error.details.reason` / `raw.details.reason`
2. `raw.error.code` 为字符串时，按字符串 code 查映射
3. legacy 顶层 `reason` / `messageCode`（仅限少量过渡接口）
4. `raw.error.message` / `raw.message`
5. 通用兜底 `t('error.generic')`

落实方式：

- 删除 API 层 54 处 `|| 'Failed to xxx'` 兜底。
- 页面上的 `MessagePlugin.error(response.message || t(...))` 逐步改成 `MessagePlugin.error(resolveError(...))`。
- `WorkspaceSetupWizard.vue`、`auth/index.ts resolveChangePasswordError` 这类页面级特殊 mapping，逐步改造成 reason -> i18n key 的统一映射，不再各自维护分支。
- 在统一 resolver 里处理“同一次失败重复 toast”的防抖/去重，避免 bootstrap 这类双弹窗问题重复扩散。

### 5.4 后端改造规则

1. **所有新改错误路径优先使用 AppError + `details.reason`**。
2. **禁止新增 raw 用户可见字符串响应**，包括：
   - `c.JSON(..., gin.H{"error": "..."})`
   - `c.JSON(..., gin.H{"code": 1, "msg": ...})`
   - `return { success:false, message:'Failed to ...' }` 这类前端兜底式复制
3. **登录/注册/邀请/空间初始化等高频链路优先迁到真实 HTTP 错误**。原因：`request.ts` 对公开认证接口的 `401/403` 已有专门分支，改造收益高、改动面小。
4. **保留服务层内部 `errors.New(...)` 作为流程语义**，但 handler/transport 层不得把它直接原样转成用户可见 message；必须补成统一 error envelope。
5. **对 87 处 `Message:` 字面量分层处理**：先区分“错误文案 / 成功提示 / 任务状态 / 检查说明”，不要机械替换。

### 5.5 三批次迁移计划

| 批次 | 范围 | 目标 | 验收锚点 |
|---|---|---|---|
| P0 高频链路 | 登录/注册/邀请、空间初始化（bootstrap）、修改密码、成员与权限冲突、认证中间件、Embed 鉴权、System 中 legacy `code/msg` | 打通 `details.reason` + `resolveError` 主链路，修复当前截图问题 | 登录失败、建用户冲突、Embed token 错误、DocReader 测试失败均能随语言切换 |
| P1 热点 direct JSON 文件 | `system.go`、`wiki_page.go`、`embed_channel.go`、`im.go`、`datasource.go`、`router/files.go` 等 direct `error` 高频文件 | 大幅减少 raw `gin.H{"error":...}` | direct string 响应显著收敛，新增 PR 不再走 raw 错误路径 |
| P2 长尾与收口 | BadRequest/Validation 长尾、存量 `Message:` 审计、页面级特殊映射归并、legacy adapter 清理 | 契约收敛到“AppError + reason”为主 | grep 门禁稳定通过，页面级 `switch(err.message)` 类逻辑基本消失 |

补充说明：

- 643 种唯一文案并不意味着要产出 643 个 reason。大量“X is required / X not found / invalid request body”可以收敛成少量通用 reason，再用 `field`、`resource`、`limit` 等 details 参数承载差异。
- 因为 direct JSON 与 legacy envelope 的存在，P0 成功标准不是“全部 grep 归零”，而是“用户最常触达的错误路径已经统一走 resolver + i18n”。

### 5.6 防回归门禁

1. **后端 grep / lint 门禁**：禁止新增以下模式：
   - `gin.H{"error": "..."}`
   - `c.JSON(..., gin.H{"code": 1, "msg": ...})`
   - 无 `details.reason` 的新用户可见 AppError 路径（P1 后逐步收紧）
2. **前端 grep 门禁**：禁止在 `frontend/src/api/**` 新增 `|| 'Failed to ...'`、`|| 'Invalid ...'` 这类英文兜底。
3. **reason 注册表测试**：每个进入注册表的 `reason` 都必须能在四语言 locale 找到对应 key。
4. **契约兼容测试**：继续保住数值型 `error.code` 的既有断言，同时新增 `details.reason` 的断言。
5. **典型链路 smoke test**：登录失败、创建用户冲突、Embed token 错误、System 检查失败、sandbox 冲突，各抽一条保证 resolver 覆盖。

### 5.7 兼容性与风险

- **保留数值型 `error.code` 是硬约束**：现有测试已断言 `1000 / 1003 / 2200` 等数值码，不能在同一轮改造成字符串码。
- **现有字符串型 `error.code` 已存在**：如 sandbox 冲突。前端 resolver 必须兼容这种现实，而不是假设全仓都只有 int code。
- **`request.ts` 不是万能入口**：它只覆盖 reject 的 HTTP 错误；`200 + success:false` / `code=1` 仍需页面或 API 封装层在迁移期兜住。
- **`Message:` 87 处是混合集**：不能拿它当纯错误总量，也不能一刀切批量替换。
- **不建议服务端按 `Accept-Language` 直接产出中文/英文文案**：会把文案主导权重新拉回后端，长期更难维护。

## 6. 验收清单（P0）

- [ ] 登录失败（错误密码 / 用户不存在 / 账号禁用）可按语言显示，不再直接暴露英文 message
- [ ] 空间初始化：手机号 / 邮箱 / 用户名冲突可精确提示，且不再出现 `Failed to create user`
- [ ] Embed token / channel 校验失败进入统一翻译，不再直出 `invalid embed channel or token`
- [ ] System 中 legacy `code/msg` 失败路径进入统一翻译，不再靠页面展示原始 `msg`
- [ ] 同一次 bootstrap 失败不再双 toast
- [ ] `curl` 抽查 P0 接口：能拿到 `details.reason`，或命中兼容的字符串型 `error.code`
- [ ] 前端单测覆盖 resolver 5 级优先级
- [ ] CI grep 门禁能阻止新增 raw error string / legacy code-msg / API 英文兜底

## 附录 C：本次问题链路存档

1. **Invalid email or password**：当前是 `LoginResponse.success=false + message` 路径，页面直接 `MessagePlugin.error(response.message || t('auth.loginError'))`，属于“2xx 失败绕过全局错误收口”的典型。
