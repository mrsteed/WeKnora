# 超级管理员创建空间后人员开通与权限接入审查方案

## 1. 问题场景与结论摘要

本次问题场景如下：

1. 使用 `admin@hlsa.com` 超级管理员创建了一个新空间。
2. 切换到该空间后，当前登录身份仍然是 `admin@hlsa.com`。
3. 在新空间中创建组织，并在组织下创建账号 `zhangzhen@hlsa.com`。
4. 使用 `zhangzhen@hlsa.com` 登录后，系统设置不可用，且大量接口返回：
   - `Forbidden: not a member of the target tenant`

结合日志与代码，核心结论如下：

### 1.1 根因不是“系统设置权限判断错了”，而是“该账号根本没有成为新空间成员”

`zhangzhen@hlsa.com` 被创建成了 **用户**，也被加入了 **组织树节点**，但并没有被加入新空间对应的 `tenant_members`。

因此：

- 它能作为一个用户存在于数据库中；
- 它也可能出现在组织树/组织人员管理里；
- 但它对新空间没有 **租户成员身份**；
- 于是登录后所有依赖 `tenant_members` 的请求全部 fail-closed 返回 403。

### 1.2 当前“在组织中创建用户”并不等于“给这个空间开通账号权限”

现有代码里，`CreateUserInOrg` 的职责实际上是：

- 创建 `users` 行；
- 创建 `organization_members_pre_plan3` 行；

它**不会**创建：

- `tenant_members` 行。

而系统设置、模型管理、知识库、智能体等空间级能力，首先依赖的是 `tenant_members.role`。

### 1.3 基于 20260707-02 文档中的统一方案，当前问题不会自动消失

文档 [WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md](WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md) 提出的统一方向是正确的，但它主要解决的是：

- 组织树权限
- 共享空间权限
- 租户 / 空间级权限

三者之间的模型统一问题。

而当前这个具体问题的根因是：

> **新空间用户开通过程缺少“租户成员 bootstrap”这一步。**

所以，哪怕后续把权限模型统一得更漂亮，如果“创建空间人员”的流程仍然绕过 `tenant_members`，这个问题依旧会发生。

### 1.4 要解决这个问题，必须引入“空间开通 / 人员开通”专门流程

最关键的设计补丁不是再去微调 `org-tree` 权限，而是建立一条完整的人员开通流程：

1. **先成为租户成员（tenant member）**
2. **再成为组织树成员（org-tree member）**
3. **最后才谈组织内角色和部门归属**

也就是说：

- **租户成员身份是前置条件**
- **组织树成员身份是附加作用域**

不能反过来。

## 2. 日志直接指向的根因

你给出的日志反复出现：

```text
SELECT * FROM tenant_members WHERE user_id = 'f6c5...' AND tenant_id = 10002
WARNING auth.go: resolveTenantRole step1 miss: user=... tenant=10002 (no_row)
WARNING auth.go: resolveTenantRole step4 fail-closed (EnableRBAC=true)
INFO ... response_body={"error":"Forbidden: not a member of the target tenant"}
```

这段日志说明了完整失败链路：

1. 认证中间件进入 `resolveTenantRole()`
2. 第一步去查 `tenant_members(user_id, tenant_id)`
3. 没查到任何 active membership 行
4. 当前用户也不是“跨租户切换到别的租户的超级管理员临时 Admin”路径
5. 当前租户又不是“完全空的孤儿租户”，因此不会触发自动补 Owner
6. `EnableRBAC=true`，所以走 fail-closed
7. 所有请求统一返回：`Forbidden: not a member of the target tenant`

这说明：

- **系统设置不可用只是症状**
- 根因是：**用户对 tenant 10002 没有租户成员记录**

## 3. 代码审查：当前创建空间与创建人员的真实链路

## 3.1 超级管理员创建空间：会自动获得新空间 Owner 身份

代码路径：

- `internal/handler/tenant.go: CreateTenant`
- `internal/application/service/tenant.go: CreateTenant`
- `internal/application/service/tenant_member.go: EnsureOwner`

关键逻辑：

- 新建 tenant 成功后，`TenantHandler.CreateTenant` 会调用：
  - `memberService.EnsureOwner(ctx, caller.ID, createdTenant.ID)`
- 这会补一条：
  - `tenant_members.role = owner`

结论：

- `admin@hlsa.com` 创建空间后，自己会自动成为该空间的 `Owner`
- 因此它切换到新空间后可以正常使用空间级能力

这部分是正确的。

---

## 3.2 在组织树中创建用户：只创建用户 + 组织成员，不创建租户成员

代码路径：

- `internal/handler/org_tree.go: CreateUserInOrg`
- `internal/application/service/user.go: CreateUserByAdmin`
- `internal/application/service/org_tree.go: AssignUserToOrg`

关键代码行为：

### 第一步：创建用户

`CreateUserInOrg` 调用：

- `userService.CreateUserByAdmin(ctx, &req, tenantID)`

`CreateUserByAdmin()` 做的事情是：

- 创建 `users` 行
- 把 `User.TenantID` 设置成当前管理员所在 tenant

但它**不会**创建 `tenant_members`。

### 第二步：加入组织树

`CreateUserInOrg` 随后调用：

- `orgTreeService.AssignUserToOrg(ctx, orgID, tenantID, assignReq)`

而 `AssignUserToOrg()` 最终写入的是：

- `organization_members_pre_plan3`

它同样**不会**创建 `tenant_members`。

### 结论

这条链路创建的是：

1. 一个用户账号
2. 一个组织树成员关系

它没有创建：

3. 一个租户成员关系

因此从空间权限角度，这个用户仍然是“未入场”的。

---

## 3.3 登录为什么还能成功，但一进空间就全部 403

代码路径：

- `internal/application/service/user.go: Login`
- `internal/application/service/user.go: buildMembershipsForUser`
- `internal/application/service/user.go: synthFallbackMembership`
- `internal/middleware/auth.go: resolveTenantRole`

### 登录阶段

`Login()` 使用的是：

- `users` 表里的账号密码验证

它不要求 `tenant_members` 一定存在。

也就是说：

- 只要 `zhangzhen@hlsa.com` 这个用户账号被建出来了
- 且密码正确
- 登录就会成功

### 登录响应阶段

如果 `tenant_members` 查不到，`buildMembershipsForUser()` 会回退到：

- `synthFallbackMembership()`

这个 fallback 会根据 `User.TenantID` 伪造一条：

- `TenantRoleViewer`

用于维持前端返回结构完整。

### 进入业务接口阶段

真正的请求鉴权不认这个 fallback，而是每次请求都走：

- `internal/middleware/auth.go: resolveTenantRole`

这里会去 `tenant_members` 查真实角色。

因为没有记录，所以直接 fail-closed 返回 403。

### 结论

当前行为是：

- 登录成功
- 但业务请求失败

这是一个典型的“账号存在，但空间成员身份未完成开通”的不一致状态。

---

## 3.4 系统设置为什么不可用

这是当前设计下的**正确结果**，不是额外 bug。

因为系统设置入口依赖的是租户 / 空间级权限：

- 前端根据 `currentTenantRole` 控制入口
- 后端 `/models`、`/tenants/kv/*`、`/system/info` 等接口都依赖 `tenant_members` 解析角色

而 `zhangzhen@hlsa.com` 当前：

- 没有 `tenant_members` 行
- 所以连 `viewer` 都不是真实成员
- 403 是符合后端设计的

进一步说：

即使未来让它成为了组织树 `admin`，如果不给它 tenant role，它仍然不能用系统设置。

这也是一个需要明确的产品规则：

> **组织管理员 ≠ 空间管理员。**

---

## 4. 基于 20260707-02 文档修正后，能否解决当前问题？

文档 [WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md](WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md) 提出的核心思想是：

- 租户 / 空间级 RBAC 继续保留
- 组织树成为同租户资源作用域权威
- 共享空间作为跨租户协作层保留
- 三者通过统一授权决策器整合

### 4.1 能解决的部分

它能解决：

- “组织权限”和“空间权限”职责混乱
- 同租户资源可见性与组织树作用域不统一
- 共享空间与部门树混用的问题

### 4.2 不能自动解决的部分

它**不能自动解决**当前这个问题，因为当前问题发生在更早一步：

- 还没进入“组织树 vs 租户 RBAC”的统一判定阶段
- 用户就已经因为没有 `tenant_members` 身份，被挡在租户门外了

换句话说：

> **这个问题属于“身份开通 / 空间 onboarding”问题，而不是“资源授权矩阵”问题。**

### 4.3 结论

基于 20260707-02 文档的目标架构，**只有在新增“空间人员开通流程”后，才能真正解决这个问题**。

否则：

- 组织树做得再统一
- 可见性做得再漂亮
- 只要新建用户没有补 `tenant_members`
- 仍然会在 `resolveTenantRole` 里被 403。

## 5. 当前代码基础上，正确的“创建空间”方案应该是什么

如果不考虑新功能开发，只讨论**当前代码能力下最合理、最不踩坑的操作方案**，建议流程如下。

## 5.1 当前代码基础上的正确操作方案

### 阶段 A：创建空间

由超级管理员 `admin@hlsa.com`：

1. 创建新空间（tenant）
2. 自动获得该空间 `Owner` 身份
3. 切换到该空间

这是正确的现有路径。

### 阶段 B：先开通空间成员身份，再做组织树分配

这是最关键的一步。

#### 场景 1：目标用户已经注册过系统

如果 `zhangzhen@hlsa.com` 已经是系统中已有用户：

- 不要走“组织中创建用户”
- 而要走：
  - `POST /tenants/:id/members`
  - 或 `POST /tenants/:id/invitations`

也就是先创建：

- `tenant_members`

然后再根据需要：

- 加入组织树节点
- 赋予组织树角色

#### 场景 2：目标用户还未注册

如果 `zhangzhen@hlsa.com` 尚未有系统账号：

优先建议走：

- `tenant invitation share link`
- `register-by-invite`

即：

1. 当前空间 Owner 生成租户邀请链接
2. `zhangzhen@hlsa.com` 通过邀请链接完成注册
3. 注册成功后 `AcceptByToken()` 自动创建 `tenant_members`
4. 注册后再分配到组织树节点

这是当前代码里已经存在的、能保证 `tenant_members` 被创建的正式链路。

### 阶段 C：组织树分配

在用户已经成为该空间成员之后，再做：

- 创建部门 / 组织树节点
- 把用户挂到对应部门
- 赋予部门角色：`admin / editor / viewer`

### 结论

当前代码基础上，**正确顺序一定是**：

```text
先 tenant_members
再 org-tree member
最后资源作用域与页面权限
```

而不是：

```text
先 org-tree create-user
希望自动获得 tenant 权限
```

## 5.2 当前代码基础上，错误但容易踩坑的方案

下面这条就是当前出问题的路径：

1. 超级管理员创建空间
2. 切换空间
3. 在组织树里创建账号 `zhangzhen@hlsa.com`
4. 希望该账号自动拥有该空间权限

为什么错：

- 组织树创建账号并不等于租户入场
- 它只创建 `users + organization_members_pre_plan3`
- 并不会写 `tenant_members`

结果就是：

- 账号能登录
- 但不是新空间成员
- 所有空间级 API 全部 403

## 6. 要彻底解决问题，需要新增什么能力

要解决这个问题，必须把“空间人员开通”从“组织树创建用户”里独立出来，变成正式的一等流程。

## 6.1 最小可行方案：修复 `CreateUserInOrg`，补 tenant membership

这是最小改动方案。

### 做法

扩展 `CreateUserInOrg`：

1. 创建 `users`
2. 创建 `tenant_members`
3. 创建 `organization_members_pre_plan3`

并且请求体新增：

- `tenant_role`
- `org_role`

不能继续只用一个 `role` 字段。

### 为什么必须拆成两个角色字段

因为当前一个用户可能同时有：

- 空间级角色：`owner/admin/contributor/viewer`
- 组织树角色：`admin/editor/viewer`

这两个角色不是一个维度。

如果继续只传一个 `role`，就会出现：

- 组织管理员是否等于 tenant admin？
- tenant contributor 是否等于 org editor？

这些无法稳定映射的问题。

### 优点

- 改动小
- 能快速解决当前问题

### 缺点

- 仍然把“创建用户”“空间成员开通”“组织树挂接”绑在一个接口里
- 后续难扩展

---

## 6.2 推荐方案：新增“空间人员开通”统一服务

推荐新增独立能力：

### `WorkspaceProvisioningService`

负责一个完整事务：

1. 创建用户（若不存在）
2. 为该用户创建 `tenant_members`
3. 可选：把该用户挂到一个组织树节点
4. 可选：设置组织树角色
5. 返回完整开通结果

### 推荐新接口

例如：

- `POST /tenants/:id/provision-users`

请求体建议如下：

```json
{
  "email": "zhangzhen@hlsa.com",
  "username": "zhangzhen",
  "password": "******",
  "tenant_role": "admin",
  "org_id": "...",
  "org_role": "admin",
  "create_user_if_missing": true
}
```

### 语义

- `tenant_role` 决定空间级权限
- `org_role` 决定部门树作用域权限

这样：

- 如果 `tenant_role=admin`，登录后能使用系统设置、模型管理等
- 如果 `org_role=admin`，还能管理组织树子节点和部门内成员

### 优点

- 语义清晰
- 不混淆空间权限与组织权限
- 后续可以自然支持批量开通、导入、审批

---

## 6.3 推荐补一个“首位空间管理员初始化”能力

超级管理员创建空间后，常见真实需求不是“自己长期持有 Owner”，而是：

- 代建空间
- 指定业务负责人为该空间 Owner/Admin

因此建议在创建空间后立刻支持：

### 方案 A：创建空间时指定初始管理员

新增 `initial_admins` / `initial_owner_email` 字段：

- 超级管理员创建空间时
- 同步指定一个或多个首批空间管理员

### 方案 B：创建空间后弹出初始化向导

创建空间成功后立即进入：

1. 设置空间名称/描述
2. 添加首位空间管理员
3. 创建组织树根节点
4. 选择是否现在创建首批部门与人员

相比 A，B 更适合 UI 产品化。

---

## 6.4 登录与鉴权层需要增加一致性保护

当前还有一个隐患：

- 用户账号存在
- `User.TenantID` 指向 tenant 10002
- 但 `tenant_members` 中没有对应 active row
- 登录成功，但后续请求 403

这会制造一种“能登录但空间坏了”的灰色状态。

### 建议的防御性改造

#### 方案 1：登录时严校验 home tenant membership

如果：

- `user.TenantID = T`
- 且 `tenant_members(user, T)` 不存在
- 且该 tenant 已经有其他 active members

则登录时就直接返回明确错误：

- `account is not provisioned into the workspace`
- 不要继续 fallback 成 viewer membership

#### 方案 2：保留登录成功，但显式返回 `membership_missing`

如果不想影响历史登录行为，可在 `/auth/me` 或登录响应里返回一个显式状态：

- `membership_missing=true`

让前端提示：

- 当前账号尚未被加入此空间，请联系空间管理员

### 建议

从产品体验看，建议做方案 1 或至少 1+2 组合。

因为当前的 `synthFallbackMembership()` 更像 rollout 兼容逻辑，不适合长期承接正式用户开通失败的场景。

## 7. `zhangzhen@hlsa.com` 想使用系统设置，应该拥有什么权限

这是一个产品规则问题，需要明确。

### 当前代码答案

若要使用系统设置中的空间级配置（如模型管理），至少需要：

- `tenant_members.role >= admin`

原因：

- `frontend/src/views/settings/ModelSettings.vue` 的按钮按 `authStore.hasRole('admin')` 显示
- `internal/router/router.go` 中 `/models` 写接口走 `g.Admin()`

### 重要区分

- **组织树 admin** 只代表部门树管理权限
- **tenant admin** 才代表空间级配置管理权限

所以：

> 如果 `zhangzhen@hlsa.com` 只是组织管理员，而不是 tenant admin，那么系统设置不可用是符合设计的。

### 推荐方案

如果希望 `zhangzhen@hlsa.com` 登录后可以管理系统设置，应赋予：

- `tenant_role = admin` 或 `owner`

而不仅仅是：

- `org_role = admin`

## 8. 推荐的完整“创建空间”方案

下面是一套完整、逻辑闭环的推荐方案。

## 8.1 目标

当超级管理员代建一个新空间后，应能够：

1. 快速把业务负责人接入该空间
2. 保证对方第一次登录就拥有正确空间权限
3. 再按组织树分配部门与部门角色
4. 不出现“账号已存在但空间无权访问”的灰色状态

## 8.2 推荐流程

### 第一步：超级管理员创建空间

- 创建 tenant
- 自动成为 `Owner`

### 第二步：初始化首位空间管理员

分两种情况：

#### 情况 A：负责人已存在系统账号

- 使用 `tenant member add / invite` 把该账号加入空间
- 赋予 `tenant_role = admin` 或 `owner`

#### 情况 B：负责人尚未注册

- 生成租户邀请链接
- 对方通过 `register-by-invite` 注册
- 自动生成 `tenant_members`
- 首次登录即可进入该空间

### 第三步：创建组织树 / 部门树

- 在空间内建立组织树节点
- 可先只建根节点与一级部门

### 第四步：分配部门成员

- 把已是 tenant member 的用户分配到 org node
- 为其设置：`org_role = admin/editor/viewer`

### 第五步：配置空间级资源

由 tenant owner/admin：

- 配置模型
- 配置内置智能体模型
- 配置 parser / storage / vector / MCP 等

### 第六步：业务资源落地

- 创建组织知识库
- 创建智能体
- 按组织树或共享空间需要分配可见性 / 共享关系

---

## 8.3 这套流程下，问题是否解决

### 对当前问题的直接效果

如果按这套方案执行：

- `zhangzhen@hlsa.com` 会先拥有 `tenant_members` 身份
- 登录后 `resolveTenantRole` 能命中 active membership
- 系统设置、模型、组织、知识库、智能体等接口不再 403

### 对未来扩展的效果

这套方案也天然兼容 [WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md](WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md) 的目标方向：

- 空间级权限先立住
- 组织树作用域再叠加
- 共享空间协作保持独立

所以它不是临时补丁，而是长期正确的 onboarding 模型。

## 10. 最终建议

### 10.1 对当前问题的直接判断

当前问题的根因非常明确：

> `CreateUserInOrg` 只创建用户与组织树成员，不创建 `tenant_members`，导致新账号不是新空间成员。

因此：

- 它无法进入空间级权限体系
- 系统设置不可用是必然结果

### 10.2 对 20260707-02 文档的补充结论

之前文档解决的是“权限模型统一”的大框架问题。

本次问题补充出来的是一个更前置的能力：

> **空间 onboarding / 人员开通必须作为独立的一等流程存在。**

没有这一步，再好的 RBAC / 组织树 / 共享空间统一方案也无法落地到真实用户接入。

### 10.3 推荐落地原则

先明确一句最重要的话：

> **在 WeKnora 中，‘成为组织成员’不等于‘成为空间成员’。要拥有新建空间的权限，必须先拥有 `tenant_members` 身份。**

基于此，建议最终采用以下规则：

1. 超级管理员创建空间后，只是代建者与初始 Owner。
2. 真正的空间运营人员，必须通过租户成员流程入场。
3. 组织树创建用户只能作为“部门归属”动作，不能再承载“空间开通”职责。
4. 若一个人需要系统设置权限，则必须赋予 `tenant admin` 或 `tenant owner`，而不是仅给 `org admin`。

如果按这个原则改造，当前问题可以被彻底解决，而且不会和后续的组织树/租户权限统一方案冲突。
