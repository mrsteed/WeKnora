# 20260922-10 子组织管理员空间角色错配修正方案

## 1. 问题现象

在「组织人员管理」页面（`frontend/src/views/admin/MemberManage.vue` + `CreateUserDialog.vue`）为某子组织（如「产品部」）创建账号时，角色选择「子组织管理员」，**期望**该账号是空间成员中的「管理员」（可在空间设置 → 空间成员中管理成员），**实际**落库后空间级角色仅为 `contributor`（协作者/访客身份），无法管理空间。

两张截图分别对应：

1. 组织人员管理 · 产品部：张军磊（`zjl@hlsa.com`），角色列显示「子组织管理员」，操作列有「取消子组织管理员」。
2. 空间成员列表：张军磊（`mxzd@hnlhlsa.comn` 截断显示）行内「编辑」下拉仅有 **所有者 / 管理员 / 访客** 三档空间级角色，当前实际为协作者身份。

数据库快照（dev 库 `weknora_mdev`，租户 `10002`，2026-09-22 实测）：

| 用户名 | 组织 | org_role | tenant_role | 说明 |
|---|---|---|---|---|
| admin | 慧联世安（根） | admin | owner | 空间所有者（创建者） |
| 马晓东 | 慧联世安（根） | admin | owner | 空间所有者 |
| 张军磊 | 产品部（子） | **admin** | **contributor** | **错配点**：组织管理员 ≠ 空间管理员 |

## 2. 根因链路（代码级）

### 2.1 角色模型：组织角色 与 空间角色是两套独立字段

| 概念 | 字段/表 | 值域 | 作用域 |
|---|---|---|---|
| 组织角色（org role） | `organization_members.role` | `admin` / `editor` / `viewer`（`internal/types/organization.go`） | 组织树节点内：管节点、管本组织成员 |
| 空间角色（tenant role） | `tenant_members.role` | `owner` / `admin` / `contributor` / `viewer`（`internal/types/tenant_member.go`） | 整个空间：管空间成员、模型、向量库、IM 等 |

「子组织管理员」是**组织角色** `admin`，它决定用户在组织树里能管本组织节点及成员；
「空间管理员」是**空间角色** `admin`，它决定用户能否进「空间成员」页管人。
两者之间靠创建/编辑链路做**投影映射**，映射逻辑写死在后端 handler，前端只是跟随。

### 2.2 后端投影映射：branch-only 管理员被限制在 contributor

`internal/handler/org_tree.go`：

```go
// create-user / put users 共用的空间角色解析
func resolveTenantRoleForCreateUser(callerTenantRole, callerIsPrivileged, req) ...
    if req.TenantRole == ""            → 兜底 defaultTenantRoleForOrgRole(orgRole)
    if caller 是 privileged/org-tree 运营者 → resolveTenantRoleForProvision（owner/admin 可授任意空间角色）
    else                                 → resolveTenantRoleForOrgScopedProvision(caller, true, req)
```

```go
func resolveTenantRoleForOrgScopedProvision(callerTenantRole, allowBranchScopedProvision, req) ...
    if allowBranchScopedProvision && !callerTenantRole.HasPermission(TenantRoleAdmin) {
        switch orgRole {
        case OrgRoleViewer:  return TenantRoleViewer
        default:             return TenantRoleContributor   // ← 子组织管理员被钉死在这里
        }
    }
    switch orgRole {
    case OrgRoleAdmin:                     return TenantRoleAdmin      // 只有空间 admin+ 调用者能走到
    case OrgRoleEditor, OrgRoleContributor: return TenantRoleContributor
    default:                               return TenantRoleViewer
    }
```

关键判定条件是 **调用者**（caller）而不是被创建人的组织角色：

- 调用者是**空间级 admin/owner**（根组织负责人、`is_super_admin`、`can_access_all_tenants`）→ 选「子组织管理员」会投影为 `tenant_role=admin`（空间管理员），符合期望。
- 调用者只是**子组织管理员**（branch-only，`tenant_role=contributor`）→ 无论给被创建人选什么组织角色（除 viewer 外），投影上限都是 `contributor`，`orgRole=OrgRoleAdmin` 的 `return TenantRoleAdmin` 分支**永远走不到**。

本次复现场景：用户是以**子组织管理员/空间协作者**身份（`callerTenantRole=contributor`）在产品部下创建了张军磊，因此命中 `default → TenantRoleContributor` 分支。

### 2.3 前端：显式传 tenant_role=contributor，把后端上限"坐实"

`frontend/src/views/admin/components/CreateUserDialog.vue` 与 `EditUserDialog.vue`：

```ts
type TenantRole = 'contributor' | 'viewer'        // 前端硬编码上限

const defaultTenantRoleForOrgRole = (role: OrgRole): TenantRole =>
  role === 'viewer' ? 'viewer' : 'contributor'    // 选「子组织管理员」时传 contributor

// 提交
createUserInOrg(props.orgId, { ..., role: 'admin', tenant_role: 'contributor' })
```

后端 `resolveTenantRoleForCreateUser` 收到非空 `TenantRole` 且 caller 无 admin 权限时，
同样落到 `resolveTenantRoleForOrgScopedProvision` 的 contributor 分支（非 owner 请求也不被拒，因为 `authorizeTenantRoleProvision` 的拒绝只对 caller 无 admin 时生效——而此处前端先钉死了值）。

> 也就是说：**前端硬编码 + 后端 branch-only 上限** 双重锁，使"子组织管理员创建子组织管理员"必然产出 contributor。

### 2.4 连带路径（同样被此映射影响）

| 入口 | 代码位置 | 行为 |
|---|---|---|
| 组织人员管理·创建用户 | `CreateUserInOrg` (`org_tree.go:1023`) → `ensureProvisionedMembership` | `tenant_role` 按 2.2/2.3 投影落地 |
| 组织人员管理·编辑用户 | `UpdateUserInOrg` (`org_tree.go:1215`) → `resolveTenantRoleForUpdateUser` | 前端同样传 `tenant_role=contributor`；`resolveTenantRoleForImplicitOrgRoleSync` 会把 caller 非 admin 时已升过 admin 的 member 维持不动（只降不升的 `shouldSync` 语义） |
| 设为/取消子组织管理员 | `SetOrgAdmin` (`org_tree.go:1413`) → `resolveTenantRoleForSetOrgAdmin` → `defaultTenantRoleForOrgRole` | admin→`contributor`（`shouldSync=true`），把已是 tenant admin 的人**降**为 contributor；viewer→viewer |
| 添加成员（已注册用户挂组织） | `AssignUser` (`org_tree.go:932`) | 只写 `organization_members`，不写 `tenant_members`；若目标用户无空间 membership 则依赖登录时自愈，**不产生空间角色** |
| 空间成员页（Owner+ 才能改角色） | `internal/router/routes_auth_tenant.go`：`POST/PUT/DELETE /tenants/:id/members` 均为 `g.Owner()` | 子组织管理员（即使修成 admin）也**只有 owner 能在空间成员页改空间角色**；`frontend TenantMembers.vue canManage = currentRole==='owner'`，UI 也不给编辑入口 |
| 新空间初始化向导 | `WorkspaceSetupWizard.vue`（`tenant_role: 'admin'`） | 由空间 admin/owner 调用，不走 branch-only 分支，行为正常 |

### 2.5 设计来由（为什么代码是这么写的）

1. `internal/types/tenant_member.go` 的 `TenantRoleAdmin` 注释明确写着：`admin` = **管理用户、集成、模型提供方、向量库、MCP、IM 等租户级基础设施**。组织树里一个"产品部管理员"显然不应获得整个空间的基础设施管理权，所以 2026-07-10 的权限收口（本地提交 `163a4765`「修正子组织管理员账号权限为只读的问题」及后续 Phase3/4）刻意把 **branch-only 调用者能开通的空间角色上限设为 `contributor/viewer`**。
2. `my_docs/20260819-03-mdev分支详细同步执行计划.md` §5.4 亦确认阶段 3 目标是"恢复组织树与空间成员管理"，两套角色的边界是有意维护的。
3. 组织人员管理页对根组织投影行已有提示文案 `adjustInTenantMembers`（"请在空间成员页面调整该成员的空间级角色"），说明**产品预期**是：组织管"组织内的事"，空间级角色走空间成员页（目前仅 Owner 可操作）。

**结论**：这不是单点 bug，而是"组织角色自动投影空间角色"这一映射策略与"子组织管理员 = 空间成员管理员"的使用预期之间的**语义冲突**，外加前端把上限硬编码进了类型（`type TenantRole = 'contributor' | 'viewer'`）。

## 3. 修正方案

### 3.1 决策前提：先把"子组织管理员"的目标语义定下来

| 方案 | 语义 | 适用场景 |
|---|---|---|
| A | 子组织管理员 = **仅组织内**的管理者（管本组织节点、本组织成员的增删和重置密码），空间级角色仍由 Owner 在空间成员页单独授予 | 空间是多部门共享的大空间，部门负责人不需要碰模型/向量库/IM 等基础设施 |
| B | 子组织管理员 = **空间成员的管理员**（即 `tenant_role=admin`），可管理空间成员（增删改角色），但不含 owner 专属能力（转移所有权、删空间） | 本部署的用法：每个空间基本对应一个公司/团队，子组织管理员就是该空间的日常管理者 ← **本次复现的实际预期** |

> 本次问题按方案 B 修。若未来出现"大空间多部门"的诉求，可把 3.3 的映射改回按部门分权（引入 org-scoped 管理范围，走 `same_tenant_scope.go` 的 `resourceManageOrgIDs` 已有骨架）。

### 3.2 数据修复（存量）

dev 库 `weknora_mdev` 存量错配仅 1 行（张军磊，产品部 org admin，tenant contributor）。修复为 admin：

```sql
-- ⚠ 只对"组织角色为 admin 且当前空间角色低于 admin"的行升格；
--    不动 owner；不动 organization_members。
UPDATE tenant_members tm
SET    role = 'admin', updated_at = NOW()
FROM   organization_members om
WHERE  om.user_id      = tm.user_id
  AND  om.tenant_id    = tm.tenant_id
  AND  om.role         = 'admin'          -- 组织角色 = 管理员
  AND  tm.role IN ('contributor','viewer') -- 空间角色被压在 admin 之下
  AND  tm.tenant_id    = 10002;           -- 按实际租户改；全库跑就删掉本条件
```

校验：

```sql
SELECT u.username, o.name AS org, om.role AS org_role, tm.role AS tenant_role
FROM   organization_members om
JOIN   organizations o ON o.id = om.organization_id
JOIN   users u         ON u.id = om.user_id
JOIN   tenant_members tm ON tm.user_id = om.user_id AND tm.tenant_id = om.tenant_id
WHERE  om.tenant_id = 10002
ORDER  BY o.path;
```

预期：张军磊 `org_role=admin / tenant_role=admin`；admin、马晓东保持 owner。

### 3.3 代码修复（增量）

#### Fix 1（后端，核心）`internal/handler/org_tree.go`

删除 `resolveTenantRoleForOrgScopedProvision` 对 branch-only caller 的上限钳制，让"组织角色 → 空间角色"的映射与**调用者身份解耦**：

```go
func resolveTenantRoleForOrgScopedProvision(
    callerTenantRole types.TenantRole,
    allowBranchScopedProvision bool,
    req *types.CreateUserInOrgRequest,
) (types.TenantRole, error) {
    orgRole, err := normalizeOrgRole(req.Role)
    if err != nil {
        return "", err
    }
    // 删除原 `if allowBranchScopedProvision && !callerTenantRole.HasPermission(TenantRoleAdmin)`
    // 的 viewer/contributor 钳制分支。组织管理权已由 isOrgAdminOf 在入口校验，
    // 这里只做纯映射。
    var mappedRole types.TenantRole
    switch orgRole {
    case types.OrgRoleAdmin:
        mappedRole = types.TenantRoleAdmin
    case types.OrgRoleEditor, types.OrgRoleContributor:
        mappedRole = types.TenantRoleContributor
    default:
        mappedRole = types.TenantRoleViewer
    }
    return mappedRole, nil
}
```

同步调整 `defaultTenantRoleForOrgRole`（`SetOrgAdmin` 联动路径在用）：

```go
func defaultTenantRoleForOrgRole(orgRole types.OrgMemberRole) types.TenantRole {
    switch orgRole {
    case types.OrgRoleAdmin:
        return types.TenantRoleAdmin     // 原为 contributor
    case types.OrgRoleViewer:
        return types.TenantRoleViewer
    default:
        return types.TenantRoleContributor
    }
}
```

> 注意：`resolveTenantRoleForImplicitOrgRoleSync` 的语义是"**不降已升格的角色**"（`currentRole` 已是 admin 时 `shouldSync=false`），Fix 1 后"设为子组织管理员"→`contributor→admin` 升格、"取消子组织管理员"→`admin→viewer` 降级 都会真实同步，符合直觉。

#### Fix 2（前端）`CreateUserDialog.vue` / `EditUserDialog.vue`

放开前端硬编码上限，透传与组织角色一致的空间角色：

```ts
type TenantRole = 'owner' | 'admin' | 'contributor' | 'viewer'

const defaultTenantRoleForOrgRole = (role: OrgRole): TenantRole => {
    switch (role) {
    case 'admin':  return 'admin'
    case 'editor': return 'contributor'
    default:       return 'viewer'
    }
}
```

#### Fix 3（可选，语义对齐）`SetOrgAdmin` handler

`resolveTenantRoleForSetOrgAdmin` 目前按 `isAdmin ? admin : viewer` 走隐含同步。Fix 1 后无需改动；若希望"取消子组织管理员"保留其空间协作者身份（而不是降到 viewer），把 viewer 分支改为对已有 membership 取 `max(现角色, viewer)` 即可——属于体验优化，非必须。

### 3.4 权限边界说明（修复后子组织管理员实际得到什么）

按方案 B，`tenant_role=admin` 后子组织管理员**同时**获得：

| 能力 | 说明 |
|---|---|
| ✅ 空间成员管理 | `internal/application/service/same_tenant_scope.go` 已实现 org-scoped 管理范围：admin 可管理"自己任 admin 的 org 及其后代"内的 org-scoped 资源；空间成员页的列表可见性随之放开 |
| ✅ 空间级 admin 全部能力（模型/向量库/IM/API Key 等） | 这是 `TenantRoleAdmin` 的既有语义（`types/tenant_member.go` 注释），**Fix 1 无法只给"成员管理"而不给其余 admin 能力**——现有 RBAC 没有更细的"仅成员管理"档位 |
| ❌ owner 专属 | 转移所有权、删除空间、改 owner 仍归 Owner（`routes_auth_tenant.go` 的 `g.Owner()` 端点不动） |

**若产品上不接受"子组织管理员顺带获得空间基础设施管理权"**，走方案 A：改前端文案与提示（把 `roleAdmin` 选项标注"组织内管理"），空间级 admin 仍由 Owner 在空间成员页单独授予；本方案的 Fix 1/Fix 2 不做。两者二选一，勿混合。

## 4. 关键风险与决策记录

1. **空间成员页改角色端点目前是 Owner+**（`g.Owner()` at `routes_auth_tenant.go`，前端 `canManage` = `currentRole==='owner'`）。若产品希望子组织管理员（admin）能在空间成员页**改成员角色**，需要另行决策：把 `PUT/POST/DELETE /tenants/:id/members` 降到 Admin+，或保留 Owner+ 只让子组织管理员"可见 + 申请"。本文档**不改**该端点，避免扩大改动面。
2. **Fix 1 的安全边界**：调用者必须已经是 `isOrgAdminOf` 校验通过的**本组织或任一祖先组织**的 admin，映射只是把 `organization_members.role` 抬到 `tenant_members.role`。`authorizeTenantRoleProvision`（显式传 `tenant_role` 时）仍然要求 caller 为空间 admin+，owner 仍只能由 owner 授予。**子组织管理员仍不能授 owner**。
3. **`tenant_members` 部分唯一索引**（`WHERE deleted_at IS NULL`）：3.2 的 UPDATE 走 UPDATE 不存在 ON CONFLICT 问题；若未来改为 INSERT 修复脚本须带 `deleted_at IS NULL` 谓词。

## 6. 补充：子组织管理员需能看到「组织人员管理」菜单（2026-09-22 追加）

### 6.1 需求

在前述角色映射维持现状（即**子组织管理员的空间级角色保持 `contributor` 也可接受**）的前提下，子组织管理员登录后必须能在侧栏看到并进入「组织人员管理」（`/platform/admin/*`）菜单。

### 6.2 根因（与角色错配相互独立）

「组织人员管理」菜单与路由的可见性判定**只依赖 `authStore.isOrgAdmin`**：

- 菜单过滤 `frontend/src/stores/menu.ts`：
  ```ts
  if (item.path === 'admin' && !authStore.isSuperAdmin && !authStore.isOrgAdmin) return false
  ```
- 路由守卫 `frontend/src/router/index.ts`（admin / memberManage / orgTreeManage 三条路由 meta 为 `requiresOrgAdmin: true`）：
  ```ts
  if (!authStore.isSuperAdmin && !authStore.isOrgAdmin) next('/platform/knowledge-bases')
  ```

而 `isOrgAdmin`（`frontend/src/stores/auth.ts`）= `hasRole('admin') || myOrgTreeOrgs.some(o => o.my_is_admin)`：

- `hasRole('admin')` 读的是**空间角色** `tenant_members.role`，子组织管理员是 `contributor` → false。
- `myOrgTreeOrgs` 由 `GET /api/v1/my-organizations` 填充（返回当前用户所在组织树节点并附 `my_is_admin`，后端 `OrgTreeHandler.GetMyOrganizations` 无额外 RBAC，仅需登录）。

**关键缺口**：`myOrgTreeOrgs` 在整个平台布局里**没有任何启动加载点**。唯一两个会拉它的组件 `components/OrganizationSwitcher.vue` 与 `components/OrgTreeSelector.vue`，经全仓检索**均未被任何页面引用（死组件）**。因此新登录/刷新后 `myOrgTreeOrgs` 恒为空，`isOrgAdmin` 退化为只看 `hasRole('admin')`，子组织管理员（contributor）恒为 false → 菜单被 `menu.ts` 隐藏、路由守卫把 `/platform/admin` 踢回知识库列表。这正是"看不到组织人员管理菜单"的直接原因。

### 6.3 代码修改（已完成）

1. `frontend/src/views/platform/index.vue`（平台布局，含 `admin` 子路由外壳）
   - `onMounted` 内、登录态成立时补一次 `useOrganizationStore().fetchMyOrgTreeOrganizations()`，使侧栏 `isOrgAdmin` 数据就绪，菜单随之显示。
   - 新增导入 `useOrganizationStore` / `useAuthStore`。

2. `frontend/src/router/index.ts`（`requiresOrgAdmin` 守卫）
   - 非 `isSuperAdmin` 时，在判定 `isOrgAdmin` 前按需拉取一次 `/my-organizations`，避免"直接访问/刷新落在 admin 路由"的场景下因数据未就绪被误踢。
   - 以 `myOrgTreeOrgsLoadedTenants`（按 `authStore.effectiveTenantId` 维度）做**每空间一次性**缓存：接口是租户隔离的（带 `X-Tenant-ID`），切换空间会重新拉取，同一空间内多次导航不重复请求。
   - 失败路径保持 fail-closed（store 维持空，菜单/路由仍隐藏），真正的授权仍以后端为准。

### 6.5 与本文档 §3 的关系

§3 解决的是"创建子组织管理员后空间级角色应为 admin"（投影语义）；§6 解决的是"子组织管理员能否看到/进入组织人员管理菜单"（菜单可见性）。两者独立：
- 只做 §6 时，子组织管理员能看到并操作菜单（其空间角色仍为 contributor），符合"contributor 也可接受"的诉求。
- 若后续采纳 §3 方案 B（投影为空间 admin），§6 的菜单可见性依旧有效且更顺（`hasRole('admin')` 亦为 true）。
