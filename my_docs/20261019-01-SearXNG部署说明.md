# SearXNG 部署说明（WeKnora）

> 生成日期：2026-10-19
> 范围：WeKnora 自托管 SearXNG 实例的容器编排、配置、端口与安全、生产运维脚本启用方式，以及后端接线的访问方式。
> 相关源码/文档：`docker-compose.yml`、`docker-compose.dev.yml`、`docker/searxng/settings.yml`、`.env.example`、`my_docs/prod_scripts/`、`website-docs/03-features/11-web-search.md`。

---

## 1. 定位与作用

SearXNG 是 WeKnora 的**可选**自托管元搜索引擎（metasearch），为智能体（Agent）提供联网搜索（`web_search`）能力，无需商业 API Key。

- 属于 Compose 中的可选 **profile**：`searxng` / `full`。
- 仅当需要在控制台选择 Provider 类型为 "SearXNG" 时才需要拉起该实例。
- 是 14 个搜索引擎中**唯一允许租户自定义 endpoint（base_url）** 的引擎，因此必须通过 SSRF 校验（见第 6 节）。

---

## 2. 容器编排（docker-compose.yml）

SearXNG 由两个服务组成：一次性的 `searxng-init`（初始化解密写盘）+ 常驻的 `searxng`。

### 2.1 为什么需要 searxng-init

SearXNG 的 entrypoint 会用 `sed` 原地替换 `/etc/searxng/settings.yml` 里的 `ultrasecretkey` 为解析后的 `SEARXNG_SECRET`。如果直接把仓库里的 `settings.yml` bind-mount 进去，entrypoint 会把解析后的 secret **写回工作区文件**，导致后续重启无法重新模板化。

因此引入一个一次性 busybox 容器，把只读模板复制进 named volume：

```yaml
searxng-init:
  image: busybox:1.36
  container_name: WeKnora-searxng-init
  command: ["sh", "-c", "cp /template/settings.yml /etc/searxng/settings.yml && chmod 0644 /etc/searxng/settings.yml"]
  volumes:
    - ./docker/searxng/settings.yml:/template/settings.yml:ro   # 只读模板
    - searxng_config:/etc/searxng                                 # 写入 named volume
  restart: "no"
  profiles: [searxng, full]
```

### 2.2 主体服务 searxng

```yaml
searxng:
  image: searxng/searxng:latest
  container_name: WeKnora-searxng
  ports:
    - "${SEARXNG_BIND:-127.0.0.1}:${SEARXNG_PORT:-8888}:8080"    # 默认只绑 loopback:8888
  volumes:
    - searxng_config:/etc/searxng                                # 复用 init 写好的配置
  environment:
    - SEARXNG_BASE_URL=http://localhost:${SEARXNG_PORT:-8888}/
    - INSTANCE_NAME=weknora-searxng
    - SEARXNG_SECRET=${SEARXNG_SECRET:-weknora-default-searxng-secret-rotate-before-exposing-publicly}
  cap_drop: [ALL]
  cap_add: [CHOWN, SETGID, SETUID]                               # 容器以非 root 降权运行所需
  restart: unless-stopped
  depends_on:
    searxng-init:
      condition: service_completed_successfully                  # 先等 init 完成
  profiles: [searxng, full]
```

关键点：

| 项 | 说明 |
|----|------|
| 镜像 | `searxng/searxng:latest` |
| 端口映射 | 宿主机 `${SEARXNG_BIND:-127.0.0.1}:${SEARXNG_PORT:-8888}` → 容器 `8080` |
| 配置 | 命名卷 `searxng_config`（dev 栈对应 `searxng_config_dev`） |
| 依赖顺序 | `depends_on searxng-init`（`service_completed_successfully`），保证配置已就位 |
| 权限 | `cap_drop: ALL` + 仅加回 CHOWN/SETGID/SETUID，满足镜像非 root 降权 |
| profile | `searxng`、`full` —— 默认**不**随核心集启动 |

## 3. 关键环境变量（.env.example）

位于 `.env.example` 的 “H1. 网络搜索（SearXNG / Tavily）” 段：

| 变量 | 默认 | 说明 |
|------|------|------|
| `SEARXNG_PORT` | `8888` | 宿主监听端口。**不要**与 `APP_PORT`（默认 8080）相同，否则 Linux 上 `localhost:8080` 会先命中 SearXNG，导致登录接口返回 SearXNG 的 HTML 404。 |
| `SEARXNG_BIND` | `127.0.0.1` | 默认仅 loopback，避免把 `limiter:false` 的实例暴露到 LAN。开放内网时显式设 `0.0.0.0` 并自行加固。 |
| `SEARXNG_SECRET` | 写死默认值 | 签 image-proxy URL 用。仅 loopback 部署可用默认值；一旦 `SEARXNG_BIND=0.0.0.0`，务必 `openssl rand -hex 32` 生成并显式设置，否则默认值可被任何人用来伪造签名。 |

> 安全红线：`SEARXNG_BIND=0.0.0.0` 之前必须轮换 `SEARXNG_SECRET`，并建议重新在 `settings.yml` 中启用 `limiter`。

## 4. 实例配置（docker/searxng/settings.yml）

`use_default_settings: true` 打底，覆盖关键字段：

| 段 · 字段 | 值 | 意图 |
|-----------|-----|------|
| `general.instance_name` | `WeKnora SearXNG` | 实例标识 |
| `general.enable_metrics` | `false` | 关闭 metrics |
| `server.secret_key` | `ultrasecretkey`（被 entrypoint 替换为 env 的 `SEARXNG_SECRET`） | 会话签名密钥 |
| `server.limiter` | `false` | 关闭 IP 限速，让 WeKnora 后端可无节流调用 `/search`；**对外暴露时必须改回 true 并配 allowlist** |
| `server.image_proxy` | `true` | 开启图片代理（URL 由 secret_key 签名） |
| `search.formats` | `html`, `json` | 允许 JSON 输出供后端解析 |
| `outgoing.request_timeout` / `max_request_timeout` | `6.0` / `10.0` | 上游引擎超时 |

后端 provider 超时（`internal/infrastructure/web_search/searxng.go`）按略高于本镜像默认值设定，避免后端比 SearXNG 自己先超时。

## 5. 启动方式

### 5.1 开发 / 常规（docker compose）

```bash
# 生产编排（docker-compose.yml）
docker compose --profile searxng up -d
# 或连同全部可选组件
docker compose --profile full up -d
```

开发机（后端跑宿主机 `go run`）时用 dev 编排：

```bash
docker compose -f docker-compose.dev.yml --profile searxng up -d
```

dev 栈差异：`container_name` 带 `-dev` 后缀、使用独立命名卷 `searxng_config_dev`，其余映射/依赖逻辑一致。

### 5.2 生产运维脚本（my_docs/prod_scripts）

```bash
cd <WeKnora 仓库根>
S=my_docs/prod_scripts

# 开启 Web 搜索（等价 --profile searxng，脚本会锁定 COMPOSE_FILE=docker-compose.yml）
$S/compose.sh profile-up searxng

# 查看合并后的编排 / 状态 / 日志
$S/compose.sh config
$S/status.sh
$S/logs.sh searxng -n
```

`compose.sh` 中 `PROFILES` 白名单包含 `searxng`，脚本会在 up 前对官方镜像做 `ensure_official_images` 预拉（`searxng/searxng:latest`）。

## 6. 后端接线（如何被 WeKnora 使用）

1. 控制台「设置 → 网络搜索」新建 Provider，类型选 **SearXNG**。
2. 填写 Instance URL（`base_url`）：
   - **容器化部署**（推荐）：`http://searxng:8080` —— 同网络内主机名直连端口 8080。
   - **本地开发**（后端在宿主机）：`http://127.0.0.1:8888`，并把 `127.0.0.1` 加入 `SSRF_WHITELIST`。
3. **无需任何 API Key**（`internal/handler/web_search_provider_credentials.go`：SearXNG 不需要凭据）。
4. SSRF 放行：`docker-compose.yml` 已默认把 `searxng` 写入 `SSRF_WHITELIST_EXTRA`（`searxng,qdrant,milvus,weaviate,doris-fe,doris-be,minio`），因此容器内主机名 `searxng` 直连无需额外配置；其它内网主机名须自行追加到 `SSRF_WHITELIST` / `SSRF_WHITELIST_EXTRA`。
5. `base_url` 经 `utils.ValidateURLForSSRF` 校验；内网地址必须在白名单内，否则拒绝。

Provider 注册与实现：
- 注册：`internal/container/container.go` → `registry.Register("searxng", infra_web_search.NewSearxngProvider)`
- 实现：`internal/infrastructure/web_search/searxng.go`（`ValidateSearxngBaseURL` 校验 + 调用 `formats=json` 的 `/search`）
- 类型常量：`internal/types/web_search_provider.go`（`WebSearchProviderTypeSearxng = "searxng"`）

## 7. 常见问题（来自 website-docs 排障）

| 现象 | 原因 / 处理 |
|------|-------------|
| 登录接口返回 HTML 404 | `SEARXNG_PORT` 与 `APP_PORT`（默认 8080）撞车，Linux 上 `localhost:8080` 先命中 SearXNG。保持 SearXNG 用 8888 或其它空闲端口。 |
| 连接测试报「引擎无响应」 | SearXNG 上游引擎被限速/不可达；`limiter:false` 不影响上游，检查网络出网与 `outgoing.request_timeout`。 |
| 暴露公网后图片代理异常 | 未轮换 `SEARXNG_SECRET`，image-proxy 签名可被伪造；先 `openssl rand -hex 32` 更新 secret 再开放。 |
