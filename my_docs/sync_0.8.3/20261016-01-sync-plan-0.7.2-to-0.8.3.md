# 20261016 WeKnora 0.7.2 -> 0.8.3 升级同步计划

## 1. 文档目标

本文档用于指导当前私有分支从上游 `v0.7.2` 升级并同步到上游 `v0.8.3`，同时保留本地已经实现且仍然有业务价值的定制能力。

本计划关注三件事：

1. 核对上游 0.8.x 的发版说明与破坏性变更。
2. 识别当前私有分支相对上游的真实分叉规模与冲突热区。
3. 给出一个可执行的分阶段同步路线，而不是直接硬 merge。

---

## 2. 已核对事实

### 2.1 当前分支与上游版本锚点

截至 2026-10-16，已核对到以下事实：

| 项目 | 结论 |
|---|---|
| 当前工作分支 | `sync_v0.8.3` |
| 当前代码基线 | 仍然是以上游 `v0.7.2` 为祖先继续演进的私有分支，不是已同步到 `v0.8.3` 的代码线 |
| 上游仓库 | `Tencent/WeKnora` |
| 上游标签 | `v0.7.2`、`v0.8.3` 均存在 |

### 2.2 差异规模

通过 git 比对得出：

| 对比项 | 数值 | 含义 |
|---|---:|---|
| 当前分支相对 `upstream/v0.7.2` | `0 / 154` | 左右提交数为 `0 154`，说明当前分支是在 `v0.7.2` 之上额外演进了 154 个提交 |
| 当前分支相对 `upstream/v0.8.3` | `754 / 69` | 左右提交数为 `754 69`，说明上游仍有 754 个提交未吸收，而当前分支仍保留 69 个上游没有的本地提交 |
| 本地自 `v0.7.2` 以来改动文件数 | `1000` | 当前私有线改动面已经很大 |
| 上游 `v0.7.2 -> v0.8.3` 改动文件数 | `3804` | 上游 0.8.x 期间改动非常大 |
| 本地与上游共同改动文件数 | `746` | 说明不能把这次升级当成轻量 cherry-pick 或无脑 merge |

结论：

1. 这不是“小版本追平”。
2. 这也不是适合直接把 `upstream/main` merge 进现有分支的场景。
3. 正确路径应当是：先落到一个干净的 `v0.8.3` 基线，再按主题回迁本地定制能力。

## 3. 上游 0.8.x 发版说明摘要

## 3.1 `v0.8.0`（2026-09-03）

上游 0.8.0 是一次平台结构升级，重点不是单个功能，而是运行时形态变化：

1. 引入会话级沙箱运行时，支持 Docker / E2B / Cube，旧的本地 host-process sandbox 被移除。
2. 技能从文件散落模式升级为租户级 Skill Catalog，支持安装、快照、环境变量与管理台编辑。
3. 新增长期记忆产品、会话工件、自动打标签、上下文压缩、LiteLLM、GitLab/IMA 数据源、XMind 解析等。
4. 引入 `third_party/anydoc-go`，文档解析链路发生了实质性变化。

与本次同步直接相关的破坏性变化：

1. 本地 host sandbox 已被上游移除，不能再按 0.7.2 的思路继续保留。
2. Docker sandbox 默认关闭，需要显式启用。
3. 0.8.0 起大量新增迁移：`000080` 到 `000090`。

## 3.2 `v0.8.2`（2026-09-24）

0.8.2 继续扩大平台能力，且开始触及我们本地已经改过的区域：

1. 新增 BrowserSkill / Local Browser、本地终端与图形桌面、Artifacts Library、Toolbox、会话 rewind/fork 等交互能力。
2. 内置 MCP Server 上线，`mcp-server/` Python 目录被上游标记为 deprecated。
3. 模型管理重构为 model catalog；管理员端用户创建、CLI setup 页面、每渠道 IM 回复语言等也被加入。
4. 检索工具面发生调整：`search_knowledge`、`read_document`、`list_documents` 等替代旧工具组合，MCP 工具兼容映射也一并引入。
5. 知识库工作流增强：批量下载原始文件 ZIP、上传面板、FAQ 筛选、知识库描述生成等。

与本次同步直接相关的破坏性变化：

1. DingTalk 渠道仅支持 Stream 模式。
2. sandbox 命令默认以 `root` 运行，行为与 0.8.0 描述已有变化。
3. `.env.example` 不再提供默认 `JWT_SECRET` / `SYSTEM_AES_KEY`，并新增 `SYSTEM_SIGNING_KEY`。
4. 组织邀请逻辑从“按名称找空间”改为“按空间 ID 精确解析”。

## 3.3 `v0.8.3`（2026-10-14）

0.8.3 是一次面向知识消费体验、模型目录与平台管理的增强发布：

1. 新增图片画廊、图片检索、跨模态 embedding / retrieval、引用原文定位与音频时间戳跳转。
2. 聊天附件改为按需读取并持久化；Agent 可通过 `attachment://` 读附件，不再完全依赖预先内联。
3. 新增平台级用户管理、邀请注册模式、管理员 model catalog 管理界面。
4. MCP 互操作增强，Agent 工具目录公开化，Docker sandbox terminal 正式补齐。
5. 新增 Seafile 连接器、更多数据源能力、`zh-TW` 界面、跨知识库 Wiki 搜索。
6. 检索、解析、Wiki、MCP、模型、数据源、索引一致性都有一轮较大修复。

对升级执行最关键的升级说明：

1. PostgreSQL 新增迁移 `000111` 到 `000118`，SQLite 新增 `000031` 到 `000036`。
2. ParadeDB 升级到 `paradedb/paradedb:v0.25.11-pg17`，老的升级命令不能照抄。
3. 图片向量不会自动为历史文档补回，若启用多模态检索需要选择性 reparse。
4. 附件保留策略改变，会增加存储占用。
5. OAuth 时间戳修复会影响旧 token，部分服务可能需要重新授权。

## 3.4 对当前私有分支最重要的破坏性影响

综合 0.8.0、0.8.2、0.8.3，当前分支升级时必须优先处理的不是 UI，而是下面这些基础面：

1. 沙箱体系替换：`internal/sandbox` 已经不是 0.7.2 时代的结构。
2. 认证密钥策略变化：`JWT_SECRET`、`SYSTEM_AES_KEY`、`SYSTEM_SIGNING_KEY` 需要重新审计。
3. MCP 能力重构：内置 MCP Server 与工具目录/允许列表语义变化，旧 Python `mcp-server/` 不应再作为主实现面。
4. 迁移跨度过大：`000080` 到 `000118` 跨度中间还夹有 `000106` 并发建索引等注意项。
5. 知识检索与引用语义变化：本地做过的“聊天参考来源定位”“知识库移动目标范围”等功能，需要重新套到上游新接口和新检索工具语义上。

## 5. 同步策略结论

## 5.1 不建议的做法

不建议直接在当前 `sync_v0.8.3` 上执行下面任何一种方案：

1. 直接 merge `upstream/main`。
2. 直接把当前私有分支整体 rebase 到 `v0.8.3`。
3. 先全量合并再靠人工删代码回退到想要的功能集合。

原因很简单：

1. 上游缺口 754 提交，不是小范围补丁。
2. 本地与上游共同改动 746 个文件，冲突会沿 `service -> handler -> frontend -> types` 链路成片爆炸。
3. 上游 0.8.x 在 sandbox、MCP、检索工具、model catalog、用户管理、数据源、文档解析等区域都做了结构升级，很多本地改动已经不能按旧上下文直接套用。

## 5.2 建议的总路线

建议采用“干净基线 + 分主题回迁”路线：

1. 以 `upstream/v0.8.3` 新建干净基线分支。
2. 当前 `sync_v0.8.3` 保留为计划和集成目标分支，不作为直接硬 merge 的起点。
3. 按主题把本地定制能力分批回迁，每一批都要求可编译、可启动、可做最小回归。
4. 凡是上游 0.8.x 已经原生具备且语义足够覆盖的能力，优先复用上游，不再维护本地平行实现。

## 5.3 推荐分支组织

建议实际执行时使用以下分支结构：

1. `sync_v0.8.3_base`：从 `upstream/v0.8.3` 新建，只验证上游原生可启动。
2. `sync_v0.8.3_stage1_platform`：平台与部署基础面。
3. `sync_v0.8.3_stage2_lowrisk`：品牌、运维、导出资源等低冲突定制。
4. `sync_v0.8.3_stage3_auth`：登录、空间初始化、创建门禁。
5. `sync_v0.8.3_stage4_scope`：组织/可见性/RBAC/IM。
6. `sync_v0.8.3_stage5_kb`：知识库目录、来源定位、批量下载、移动目标范围。
7. `sync_v0.8.3`：最终集成分支。

## 6. 分阶段同步计划

## 6.1 Phase 0：升级前冻结与审计

目标：确认输入物，避免边升级边变需求。

工作项：

1. 冻结当前私有分支，导出当前 `git log`、本地独有提交清单、共同改动文件清单。
2. 备份数据库、对象存储、`config/export`、生产 `.env`、`docker-compose` 覆盖文件。
3. 补齐上游 `v0.8.0`、`v0.8.2`、`v0.8.3` 迁移列表与配置项清单。
4. 明确哪些本地能力必须保留，哪些已经被上游覆盖可以放弃本地实现。

阶段出口：

1. 有一份升级输入清单。
2. 有一份回滚所需备份清单。
3. 有一份“必保留 / 可复用上游 / 可放弃”的能力分类表。

## 6.2 Phase 1：落地上游 `v0.8.3` 干净基线

目标：先证明纯上游 `v0.8.3` 能在我们的环境起起来，再谈本地回迁。

工作项：

1. 从 `upstream/v0.8.3` 建干净分支，不带任何本地补丁。
2. 校正部署与配置：
   - 保留现网 `SYSTEM_AES_KEY`。
   - 生成或显式配置 `SYSTEM_SIGNING_KEY`、`JWT_SECRET`。
   - 校正 ParadeDB 镜像到 `v0.25.11-pg17`。
   - 评估 Docker sandbox 是否启用。
   - 审计 DingTalk / OIDC / MCP / BrowserSkill 相关 env。
3. 跑完整迁移，记录 `000080` 到 `000118` 的执行结果和耗时。
4. 验证基础启动：app、frontend、docreader、数据库、对象存储。

阶段出口：

1. 纯上游 `v0.8.3` 能完成迁移并启动。
2. 基本聊天、知识上传、登录、管理台能 smoke pass。
3. 升级环境变量差异已经整理成表。

## 6.3 Phase 2：先回迁低冲突定制

目标：先把和上游主业务逻辑耦合较低的定制补回，快速建立可识别的私有版本。

建议优先回迁：

1. IntraMind 品牌替换。
2. 生产运维脚本、编译脚本、镜像拉取/转推逻辑。
3. `config/export` 资产挂载与离线资源。
4. dev/prod 端口、MinIO 端口、前端代理等环境适配。

注意：

1. 这一阶段只允许改部署和展示层，不要提前碰权限和知识库核心语义。
2. 如果导出链路依赖前端或 handler 新接口，先只把资源和挂载补齐，不急着恢复导出功能。

阶段出口：

1. 私有品牌与运维链路恢复。
2. 不引入核心业务回归。

## 6.4 Phase 3：登录、空间初始化与创建门禁

目标：恢复本地的账号登录习惯和空间初始化路径，但要先服从上游 0.8.3 的认证骨架。

建议回迁：

1. 用户名/邮箱双路登录。
2. 空间初始化向导与空空间 bootstrap。
3. 协作者创建知识库/智能体时隐藏或限制全局可见性。
4. 组织树跨账号缓存清理。
5. Agent 创建前的 model readiness 收口校验。

注意：

1. 上游 0.8.2/0.8.3 已重做 model catalog 与平台用户管理，创建门禁必须接到新入口，而不是只修旧按钮处理器。
2. 登录接口字段改动会影响 SDK、前端 i18n、错误文案和测试桩。

阶段出口：

1. 用户可以用“用户名或邮箱”登录。
2. 空间初始化流程可用。
3. 无模型或权限不足的创建入口被正确拦截。

## 6.5 Phase 4：组织树、RBAC、可见性与 IM 归属主线

目标：回迁这条私有分支最核心的业务差异。

建议回迁：

1. 组织树、组织人员管理、子组织管理员视角与菜单范围。
2. 同租户资源授权器、KB/知识/智能体的 global/org/private 可见性。
3. IM 渠道按创建者隔离和 `created_by` 归属。
4. Admin 页面合并和角色收口。

注意：

1. 这是全项目最高冲突区，必须以后端 service 层为主线推进，禁止先改页面再倒推后端。
2. 需要把本地“组织可见性”语义重新映射到 0.8.3 的 handler/types 结构上。
3. 本阶段要同步复核 API key allow-list、shared space、workspace 角色与 IM 管理权限，防止 0.8.3 新能力绕过本地约束。

阶段出口：

1. 组织树与成员管理权限矩阵通过回归。
2. KB/智能体/IM 的可见性语义恢复到本地预期。
3. 多账号切换不再出现缓存残留视图。

## 6.6 Phase 5：知识库目录、移动目标、批量下载与来源定位

目标：把本地最有价值的知识库体验能力迁回，但必须优先复用上游已有功能。

建议执行顺序：

1. 先对比上游 0.8.2 的“批量下载原始文件 ZIP”与本地实现，优先复用上游 API/前端骨架，只补差异。
2. 先对比上游 0.8.3 的“引用原文定位”与本地聊天参考来源定位修复，优先复用上游 source locator。
3. 在上述两个能力复用完成后，再回迁：
   - 空目录创建/删除。
   - 在线编辑 Markdown 时选择目标文件夹。
   - 知识移动目标列表按可见范围收口。
   - 文档创建者归属与 `resource-auth` 语义。

注意：

1. 目录功能当前是派生式 `folder_path` 模型，上游并未原生支持空目录；若继续保留，需明确占位策略和过滤规则。
2. `move-targets` 必须统一走可见性服务或统一授权器，不能只修前端列表。
3. 0.8.3 新增跨模态向量、图片画廊、引用定位后，知识文档模型和处理管线都有变化，目录/下载/定位都要回归验证。

阶段出口：

1. 批量下载、来源定位与目录功能可用。
2. 权限与作用域没有回退成“看得见但不能操作”或“本不该看见却可列出”的状态。

## 6.7 Phase 6：导出链路、解析链路与上游新能力取舍

目标：只保留必须的私有差异，不和上游新平台能力平行造轮子。

建议重点决策：

1. 对话导出（Markdown/PDF/Word/XLSX）是否继续作为私有增强保留。
2. 本地 MinerU 解析增强与上游 anydoc / MinerU 4.0 检测能力如何合并。
3. Python `mcp-server/` 是否彻底退居兼容层，不再继续扩展。
4. 对于已被上游 model catalog、platform user management、source citation navigation 覆盖的本地实现，是否直接下线旧代码。

阶段出口：

1. 每条私有能力都明确“保留 / 复用上游 / 废弃”结论。
2. 不再存在两套并行入口或语义相冲突的实现。

## 6.8 Phase 7：全量回归、试运行与切换

目标：在真实数据上完成升级彩排。

必须验证的场景：

1. 登录：用户名/邮箱、注册、密码重置、管理员创建用户。
2. 空间与组织：初始化向导、组织树、成员管理、菜单权限、跨账号切换。
3. 知识库：上传、目录树、空目录、移动目标、批量下载、引用原文定位、文档下载。
4. 智能体：创建门禁、默认工具、知识范围、共享/私有可见性。
5. IM：渠道创建者隔离、回复语言、附件上传、长连接稳定性。
6. 导出：Markdown/PDF/Word/XLSX 全链路。
7. 迁移：老库升级、回滚恢复、对象存储读写、附件保留策略。

阶段出口：

1. 形成试运行报告。
2. 明确回滚命令与回滚窗口。
3. 再决定是否切流到升级后的分支。

## 8. 关键风险清单

1. **权限回归风险最高**：组织树、KB/智能体可见性、IM 创建者隔离与 API key allow-list 都可能在 0.8.3 新能力下被绕开。
2. **迁移和配置风险很高**：`SYSTEM_AES_KEY` 不能变，`SYSTEM_SIGNING_KEY` 不能漏，ParadeDB 镜像不能沿用旧值。
3. **知识处理语义已变化**：多模态 embedding、图片画廊、引用定位、附件持久化都会触发知识模型和处理管线差异。
4. **MCP 与 sandbox 已不是局部功能**：它们深入到了 agent runtime、前端工具面板、部署配置和迁移表，不能按“先忽略”处理太久。
5. **当前分支里已有一部分本地提交实际上被上游覆盖**：当前分支相对 `v0.7.2` 有 154 个本地提交，但相对 `v0.8.3` 只剩 69 个独有提交，说明不少能力上游已经给出等价或更强实现；同步时必须先比语义，再决定是否保留本地代码。

---

## 9. 结论

这次升级的核心判断是：

1. 当前私有分支本质上仍停留在 `v0.7.2` 时代的结构上。
2. 上游 `v0.8.3` 不是补丁版，而是跨越 sandbox、MCP、model catalog、数据源、知识处理、平台用户管理的结构升级。
3. 由于存在 `754` 个上游未吸收提交、`69` 个本地独有提交、`746` 个共同改动文件，最佳路径不是“合并”，而是“以 `v0.8.3` 为干净基线重新集成本地能力”。
4. 同步时应当优先恢复“权限与可见性主线”“知识库目录与来源定位”“登录与空间初始化”“导出与运维”，但凡上游已有成熟等价能力，优先复用上游实现。

本计划可直接作为后续实际升级执行的分阶段操作蓝图。
