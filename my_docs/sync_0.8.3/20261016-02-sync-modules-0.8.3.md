# 20261016 WeKnora 0.7.2 -> 0.8.3 模块化同步策略

## 1. 文档目标

本文档基于上一份总计划《20261016-01-sync-plan-0.7.2-to-0.8.3.md》，进一步把同步工作拆成可执行的模块，并明确：

1. 每个模块应该从上游复用什么。
2. 每个模块必须回迁哪些本地能力。
3. 每个模块建议采用什么同步手法。
4. 每个模块的关键文件、依赖顺序、验证口径和完成标准。

本文档不是总纲复述，而是后续实际开分支、比对代码、逐批回迁时的执行蓝图。

---

## 2. 模块划分原则

本次同步不按“目录”拆，而按“业务耦合面”拆。原因是同一条业务能力通常横跨：

1. `internal/application` 服务层。
2. `internal/handler` 接口层。
3. `internal/types` 请求/响应结构。
4. `frontend/src` 页面、store 和组件。
5. `migrations`、`config`、`deploy` 等外围依赖。

因此模块必须满足两个条件：

1. 可以独立定义“先做什么、后做什么”。
2. 可以独立定义“做到什么程度算完成”。

## 4. 同步手法选择规则

为了避免“把旧世界直接搬到新世界”，每个模块统一按以下三种手法择一：

### 4.1 手法 A：纯复用上游

适用条件：

1. 上游已经具备等价或更强能力。
2. 本地只是旧实现，不再有独特业务语义。

执行方式：

1. 不移植旧代码。
2. 只补本地配置、权限门禁或展示差异。

典型模块：

1. Sandbox 主体。
2. Built-in MCP Server 主体。
3. Source citation navigation 主体。
4. 平台用户管理主体。

### 4.2 手法 B：手工移植逻辑

适用条件：

1. 本地能力必须保留。
2. 但上游上下文已经大变，旧 commit 直接 cherry-pick 风险高。

执行方式：

1. 先在 0.8.3 上读现状实现。
2. 再把本地业务语义逐条映射进去。
3. 尽量保留上游结构，只植入本地规则。

典型模块：

1. 登录 identifier 化。
2. 空间初始化向导与 bootstrap。
3. 组织/知识库/智能体可见性。
4. IM 渠道归属隔离。

### 4.3 手法 C：选择性 cherry-pick + 修边

适用条件：

1. 本地改动与上游同区域耦合较弱。
2. 变更跨文件少、结构差异小。

执行方式：

1. 先选最小 commit 粒度。
2. `cherry-pick -n` 后立即在 0.8.3 上修边，不让旧实现覆盖新骨架。
3. 每次只落一个主题。

典型模块：

1. 品牌资源与文案。
2. 运维脚本。
3. `config/export` 资源挂载。

## 5. 模块依赖关系

建议按下面顺序推进：

1. 先完成 M0，让纯上游 0.8.3 在本地环境可跑。
2. 再做 M1，让环境、品牌、脚本稳定下来。
3. 然后做 M2，恢复登录与初始化入口。
4. 再做 M3，补齐权限主线。
5. 之后做 M4，把知识库核心体验补回。
6. M5 与 M6 可以局部并行，但前提是 M3 已稳定。
7. 最后进入 M7 集成回归。

不能颠倒的依赖：

1. **M3 不能早于 M2**：因为创建门禁、账号身份与初始化入口是权限链的入口。
2. **M4 不能早于 M3**：因为目录、移动目标、文档权限都依赖可见性与 manage 语义。
3. **M6 不能早于 M4/M5**：因为导出与解析链路会依赖知识模型、引用定位、附件读取、MCP/sandbox 和 parser 新骨架。

## 6. M0：上游 0.8.3 基线、迁移、配置与启动

### 6.1 范围

M0 只做一件事：证明纯上游 `v0.8.3` 能在当前环境完成迁移并启动，不带任何本地业务补丁。

### 6.2 关键文件/目录

1. `docker-compose.yml`
2. `.env.example`
3. `docker/Dockerfile.app`
4. `docker/Dockerfile.sandbox`
5. `migrations/versioned/`
6. `migrations/sqlite/`
7. `configs/` 与本地 deploy 覆盖脚本

### 6.3 必须关注的升级点

1. `SYSTEM_AES_KEY` 必须沿用现网老值，不能重置。
2. `SYSTEM_SIGNING_KEY` 必须显式补齐。
3. `JWT_SECRET` 不能再依赖默认值。
4. ParadeDB 镜像必须切到 `paradedb/paradedb:v0.25.11-pg17`。
5. Sandbox 是否启用、是否挂 `docker.sock` 要在这一阶段定策略。
6. DingTalk、OIDC、MCP、BrowserSkill、新增数据源相关 env 都要盘点。

### 6.4 建议动作

1. 从 `upstream/v0.8.3` 创建基线分支。
2. 先不带任何私有脚本，按上游默认 Compose/部署方式起一套最小环境。
3. 跑完整迁移，记录每个阶段耗时与异常。
4. 输出一份“旧环境变量 -> 0.8.3 新环境变量/默认值”映射表。
5. 输出一份“必须保留的本地部署覆盖项”清单，供 M1 使用。

### 6.5 禁止事项

1. 这一阶段不要引入品牌替换。
2. 不要提前接入本地权限改造。
3. 不要把旧 Python `mcp-server/` 当成主启动链路。

### 6.6 完成标准

1. 纯上游 0.8.3 可以完成 DB 迁移并启动。
2. 登录、上传、聊天、基础设置页 smoke pass。
3. 生成 M1-M6 的配置输入物。

## 7. M1：品牌、部署、运维、导出资源等低冲突定制

### 7.1 本地来源

建议优先评估以下本地提交：

1. `60dbb9a90`、`5aa91ccd9`：品牌从 WeKnora 改为 IntraMind。
2. `a0c4561ba`、`d23178000`、`35f600bc5`：生产脚本、镜像拉取与 MinIO 端口整理。
3. `49b61b9e5`、`cfd6a5b87`：`config/export` 资源挂载与离线资产。
4. `7ef9f2239`、`e1646c048`：前端构建与 dev 代理适配。

### 7.2 关键文件/目录

1. `deploy/`、`scripts/`、`docker-compose*.yml`
2. `frontend/public/`、`frontend/src/layout`、登录页静态资源
3. `config/export/`
4. 本地生产与开发脚本目录

### 7.3 建议同步方法

优先用手法 C：小粒度 cherry-pick 或手工复制脚本，不把旧前端整片覆盖到上游 0.8.3 页面上。

### 7.4 具体策略

1. **品牌层**：只迁移文案、logo、标题、登录页视觉资源，不动上游 0.8.3 的页面结构和能力入口。
2. **部署层**：把本地脚本整理为“对上游部署的覆盖层”，不要复制旧 compose 主文件去替换上游。
3. **导出资源层**：先恢复 `config/export` 资源与挂载，让后续 M6 有运行前提，但导出功能逻辑本身暂不启用。
4. **开发环境层**：统一 dev 代理、MinIO 端口、启动命令，减少后续模块排查时的环境噪音。

### 7.5 验证口径

1. 品牌元素正确展示。
2. 自定义脚本仍能完成构建、启动、停止、查看日志。
3. `config/export` 在容器和本地运行模式都可见。

### 7.6 完成标准

1. 视觉品牌与运维链路恢复。
2. M2-M6 后续模块不再依赖旧分支脚本临时兜底。

7. `frontend/src/views/agent/AgentList*`
8. `frontend/src/stores/auth.ts`、`stores/orgTree.ts`

### 8.3 上游 0.8.3 冲突点

1. 平台用户管理已增强，用户创建/禁用/重置密码入口变多。
2. 邀请注册模式新增 `invite_register` 语义。
3. 密码复杂度、OIDC、管理员创建账号逻辑都增强了。
4. model catalog 和 Agent 创建入口已重做。

### 8.4 建议同步方法

优先用手法 B：手工移植逻辑，不建议直接 cherry-pick 旧登录页和旧向导代码块。

### 8.5 具体策略

#### 子模块 M2-A：登录 identifier 化

目标：恢复“用户名或邮箱登录”，同时不破坏 0.8.3 的平台用户管理和认证新语义。

动作：

1. 把 `types.LoginRequest` 从单 `email` 改为 `identifier`。
2. 在 `userService.Login` 层收口用户解析：先用户名，再邮箱兜底。
3. 保持错误模型兼容，前端统一映射为“用户名/邮箱或密码错误”。
4. 同步修改 SDK、登录页、i18n。

完成标准：

1. 邮箱可登录。
2. 用户名可登录。
3. 旧的错误文案不会泄漏“用户不存在/密码错误”的差异。

#### 子模块 M2-B：空间初始化与 bootstrap

目标：把“根组织创建 + 负责人创建/绑定 + membership + org 挂载”收口为可重试、可恢复链路。

动作：

1. 优先保留后端 bootstrap 编排接口思路，不再依赖前端串行编排多个易中断请求。
2. 落地幂等状态或至少保留“已存在根组织复用”的逻辑。
3. 对用户名/邮箱/手机号冲突返回结构化 409，而不是通用 500。
4. 前端向导本地状态只作为 UI 状态，不承担真实业务状态记忆。

完成标准：

1. 手机号重复时明确提示冲突字段。
2. 向导中途失败后刷新页面仍可继续。
3. 不会重复创建同名根组织。

#### 子模块 M2-C：创建门禁与会话缓存卫生

目标：把“禁止错误入口”做成共享门，而不是散落在单个按钮处理器里。

动作：

1. Agent 创建前的 readiness 校验要收口到 shared opener。
2. 协作者创建 KB/智能体的全局可见选项要在新入口统一受限。
3. `clearSessionResourceCaches()` 要纳入 orgTree 等跨账号残留 store。

完成标准：

1. 无模型状态不能直接打开错误的创建弹窗。
2. 跨账号登录后组织树视图不残留。
3. 协作者不会看见不该给的全局可见选项。

#### 子模块 M3-B：KB/智能体可见性

完成标准：

1. Viewer/Contributor/Admin/Owner 在同租户内的 KB/Agent 可见范围符合本地预期。
2. 共享资源不会越权列出。

#### 子模块 M3-C：组织树与成员管理

目标：恢复本地的组织人员管理语义和菜单范围。

动作：

1. 后端先恢复按用户权限过滤组织树。
2. 前端再接管理页、菜单、树选择器、成员列表。
3. 子组织管理员视角、超管视角、owner 视角分别回归。

完成标准：

1. 多角色看到的组织树一致且稳定。
2. 跨账号切换不会残留上一账号树状态。

#### 子模块 M3-D：IM 渠道归属与隔离

目标：IM 渠道按创建者隔离，防止租户内互相误见/误管。

动作：

1. `created_by` 归属链路先回到后端模型和查询条件。
2. 再接列表、详情、编辑页过滤。
3. 与 0.8.3 的 per-channel locale、附件、长连接逻辑一起回归。

完成标准：

1. 同租户不同创建者的 IM 渠道互不可误见。
2. 渠道管理员权限和可见性边界清晰。

1. 大批量下载可用。
2. 权限符合 0.8.3 现有下载语义。

#### 子模块 M4-B：引用来源定位

目标：优先复用 0.8.3 的 source locator，而不是继续依赖旧的“根目录列表里找卡片”逻辑。

动作：

1. 先验证上游对 PDF/Office/Markdown/TXT/EPUB 的定位能力。
2. 若聊天引用仍存在本地定制需求，只补 UI 流程，不重造定位后端。
3. 旧的“按 folder_path/keyword 兜底定位”逻辑只作为兼容兜底，不作为主路径。

完成标准：

1. 聊天参考来源能正确定位到原文或目标文档。
2. 子目录文档、分页文档、大库场景都不再静默失败。

#### 子模块 M4-C：目录树与空目录

目标：补回本地目录体验能力，但要承认派生式目录模型的限制。

动作：

1. 目录重命名、跨目录移动沿用现有派生模型。
2. 若必须支持空目录，则采用占位记录方案并补过滤规则。
3. 前端 `FolderPickerMenu` 的 create/delete 入口必须接真实后端，不允许再保留纯本地假按钮。

完成标准：

1. 改名、移动、回根目录、空目录创建/删除语义一致。
2. 占位目录不会污染检索、统计、列表和引用定位。

#### 子模块 M4-D：移动目标范围与文档归属

目标：把“看得到哪些目标 KB”和“允许移动到哪些目标 KB”的规则统一起来。

动作：

1. `move-targets` 列表改走 `KBVisibilityService` 或同级统一可见性服务。
2. 执行端也统一到同一 manage 语义，不允许只修列表不修执行。
3. API key allow-list 要纳入同一判断。
4. 文档创建者身份与上传人展示要接到新资源归属模型上。

完成标准：

1. 列表范围与执行权限一致。
2. 组织可见性、private/global、API key 场景都能通过测试。

## 11. M5：Agent、Model Catalog、MCP、Sandbox 的本地策略

### 11.1 模块判断

这一模块的原则很明确：**上游骨架优先，本地只补规则，不再维护旧平行实现。**

### 11.2 关键文件/目录

1. `internal/agent/`
2. `internal/mcp/`
3. `internal/sandbox/`
4. `mcp-server/`
5. `frontend/src/views/agent/`
6. `frontend/src/views/settings/` 或新 toolbox / model 设置入口

### 11.3 本地需要保留的能力

1. Agent 创建门禁必须在 shared opener 收口。
2. 协作者创建 Agent 时受可见性限制。
3. 智能体知识范围必须服从 M3 的可见性主线。

### 11.4 建议同步方法

1. **Sandbox**：完全使用上游 0.8.3 骨架，不回迁 0.7.2 时代任何旧 host sandbox 逻辑。
2. **Built-in MCP Server**：以 0.8.3 为主；旧 Python `mcp-server/` 只保留兼容或文档用途，不再继续扩展。
3. **Model Catalog**：以 0.8.3 为主，只补本地创建门禁和默认选项限制。
4. **Tool scope**：本地知识范围与可见性规则要映射到上游工具目录/默认工具语义，不允许出现“工具可选但运行时报越权”。

### 11.5 具体策略

#### 子模块 M5-A：Agent 创建门禁

1. 所有创建入口统一走 `ensureAgentCreateReady` 一类 shared opener。
2. 无聊天模型、无权限、无默认空间上下文时均应在入口处被拦截。

#### 子模块 M5-B：知识范围与默认工具

1. Agent 使用 all KB 或 selected KB 时，必须复用 M3 的可见性过滤结果。
2. Wiki-only、shared KB、org visible KB 都要单测或集成测覆盖。

#### 子模块 M5-C：MCP 与 Sandbox 的本地取舍

1. 不再把 Python `mcp-server/` 当作主产品面。
2. 不对上游 sandbox 工具链做“回退式简化”。
3. 只补本地部署需要的配置/脚本/说明。

### 11.6 完成标准

1. Agent 创建入口稳定。
2. 工具范围与知识范围不越权。
3. MCP/Sandbox 采用上游 0.8.3 主骨架。

## 15. 结论

比起上一份总计划，这份模块化同步策略给出的核心执行原则是：

1. 先把 0.8.3 当成新底座，而不是旧分支的延长线。
2. 每个模块都先判断“复用上游还是保留本地语义”，再决定同步手法。
3. 权限主线必须以后端服务层为中心推进；知识库体验模块必须先复用上游 0.8.2/0.8.3 已经具备的能力；sandbox/MCP/model catalog 必须以上游骨架为准。
4. 只有这样，后续每一批同步才能做到：范围清晰、冲突可控、验证闭环、失败可回滚。

这份文档可以直接作为下一阶段按模块开分支实施的执行清单。
