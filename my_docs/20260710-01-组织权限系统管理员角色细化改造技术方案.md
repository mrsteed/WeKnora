# 组织权限系统管理员角色细化改造技术方案

## 1. 文档目的

本文是对 [20260707-02-组织人员管理与租户权限统一设计审查报告](../my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md) 的当前代码落地版补充，目标是把以下新增业务要求收敛为一套可执行的改造方案：

1. 空间拥有者 = 组织根节点管理员 = 本空间管理员。
2. 根节点以下的子组织管理员不等于空间拥有者和空间管理员，只拥有子组织域内的人员创建与管理权限。
3. 子组织管理员对知识库和智能体的管理权限限定在本节点及后代节点资源域，不扩展到其他节点、全局资源或他人私有资源。
4. 超级管理员权限保持不变。
5. 成员管理角色显示修正为：
   - 空间拥有者显示为“拥有者”
   - 子组织管理员显示为“子组织管理员”
   - 子组织编辑显示为“协作者”
   - 只读角色显示为“只读”

本文不直接修改代码，而是给出基于当前实现的完整技术方案、改造边界、数据约束和分阶段执行计划。

---

## 2. 与 20260707-02 审查报告的关系

### 2.1 仍然成立的结论

旧报告中以下结论仍然成立：

1. 系统仍然并存三套成员/权限模型：
   - `tenant_members`：空间级 RBAC
   - `organization_members_pre_plan3`：组织树人员管理
   - `organization_tenant_members`：共享空间协作成员
2. 同租户内的知识库和智能体可见性，仍然主要依赖组织树成员关系。
3. 不应该把三套模型粗暴合并成一张成员表，而应该统一授权决策方式。

### 2.2 旧报告中已过时的部分

旧报告第 4.6 A 节提到“同租户 KB 管理权限过宽，普通组织成员也可管理 org 类型 KB”。

这个结论在当前代码中已经不准确。现在真正的实现是：

1. `internal/application/service/same_tenant_scope.go` 已经引入 `manageOrgIDs`。
2. `internal/application/service/kb_visibility.go` 和 `internal/application/service/agent_visibility.go` 的 `CanManage*` 已经基于“org admin 子树”做管理判定。
3. 也就是说，当前不是“所有组织成员都能管理”，而是“子组织 admin 仍然能管理该 admin 子树中的 org 资源”。

这说明当前代码在“子组织 admin 管理子树 org 资源”这一点上，已经接近本次新需求。但它仍然不满足本次新需求的完整口径，因为新需求要求：

> 子组织管理员可以管理本节点及后代节点资源域内的知识库/智能体，但中文显示必须明确为“子组织管理员”，且不应被误等同为空间管理员。

## 3. 当前实现盘点

## 3.1 当前空间级 RBAC

当前空间级角色来自：

- `internal/types/tenant_member.go`
- `internal/handler/tenant_member.go`
- `internal/middleware/auth.go`
- `internal/middleware/rbac.go`

角色仍然是：

- `owner`
- `admin`
- `contributor`
- `viewer`

这套角色负责的是空间控制平面能力：

1. 空间成员管理
2. 模型、向量库、MCP、API Principal 等空间配置
3. 删除空间、Owner 变更等高敏动作

这套模型本身没有问题，本次不建议改枚举值，也不建议改表结构。

## 3.2 当前组织树权限

当前组织树权限主要分布在：

- `internal/application/service/org_tree.go`
- `internal/handler/org_tree.go`
- `internal/application/repository/organization.go`
- `frontend/src/views/admin/components/MemberTable.vue`

当前组织树角色是：

- `admin`
- `editor`
- `viewer`

当前真实行为：

1. 根节点创建时，只有创建者会被自动写入根节点 `admin`。
2. 子节点创建时，不会自动给创建者补成员行。
3. `isOrgAdminOf()` 支持祖先管理员对后代组织的管理继承。
4. `GetTreeForUser()` 会把管理员对子树的 `MyIsAdmin` 全部标记成 `true`。

因此，当前“组织管理员”实际上同时承担了两件事：

1. 子树人员管理者
2. 子树资源管理者

而新需求并不是要取消第 2 项，而是要求把这两项能力明确限定在“本节点及后代节点”范围内，并与空间管理员语义拆开。

## 3.3 当前根节点与 owner 语义存在混淆

这是本次改造必须首先处理的问题。

当前代码中：

1. `CreateNode()` 为所有组织节点都写入 `OwnerID = 当前操作者`。
2. `ListOrgTreeMembers()` 使用 `(o.owner_id = omp.user_id) AS is_owner`。
3. `GetUserOrganizations()` 在判断 `MyIsAdmin` 时，把 `member.IsOwner` 也当成 admin。

这带来两个问题：

1. 组织节点的“创建者”被误当成“空间拥有者/组织拥有者”。
2. 前端成员管理页用 `is_owner` 渲染标签时，展示的是“节点创建者”，不是“空间拥有者”。

这正是当前角色显示错乱的根源之一。

## 3.4 当前 KB / Agent 管理权限已接近新要求，但口径尚未收口

当前相关代码位于：

- `internal/application/service/same_tenant_scope.go`
- `internal/application/service/kb_visibility.go`
- `internal/application/service/agent_visibility.go`
- `internal/middleware/kb_access.go`
- `internal/router/rbac.go`

当前真实行为是：

1. 读权限：仍然按组织树成员范围决定。
2. 写权限：
   - KB：`KBAccessWrite` 最终会走 `CanManageKB`
   - Agent：顶层更多依赖 `OwnedAgentOrAdmin()`
3. `CanManageKB/CanManageAgent` 目前仍把“组织 admin 子树”视为资源管理范围。

这与“子组织管理员可管理本节点及后代节点资源域”的新要求方向是一致的，但还缺两项收口：

1. 需要把这条能力明确固化为正式规则，而不是隐含在现有实现里。
2. 需要把“子组织管理员”和“空间管理员”的显示、权限边界、接口返回字段彻底区分开。

## 3.5 当前 KB 和 Agent 的写权限矩阵并不完全一致

这也是本次必须顺手收口的问题。

1. 路由注释声称 `OwnedKBOrAdmin / OwnedAgentOrAdmin` 都代表“资源拥有者或 tenant admin+”。
2. 但 KB 还额外挂了 `KBAccessWrite()`，它会调用 `CanManageKB()`。
3. 而 `CanManageKB()` 当前并没有把 tenant admin 直接当作可管理全部 KB 的角色。
4. 于是 KB 和 Agent 在“tenant admin 是否能管理非本人资源”上存在实现漂移。

本次方案必须把 KB 和 Agent 的写矩阵统一。

## 3.6 当前子组织管理员的建人能力不满足需求

当前 `CreateUserInOrg()` 流程中：

1. 接口入口只要求调用者是该组织 admin。
2. 但 `resolveTenantRoleForProvision()` 最终会调用 `authorizeTenantRoleProvision()`。
3. 该函数要求调用者 tenant role 至少是 `admin`。

因此：

1. 一个“仅有子组织 admin 身份、但 tenant role 不是 admin”的用户，当前实际上不能直接完成“创建组织内用户并开通空间成员身份”。
2. 这与“子组织管理员只拥有子组织域内的人员创建和管理权限”并不吻合。

## 4. 目标状态

## 4.1 权限模型不改三层，只改语义边界

本次不改成一张表，不改成一套全局角色，仍然保留三层：

1. 超级管理员层
2. 空间级 RBAC 层
3. 组织树层

但要明确收口边界：

### 超级管理员

保持不变：

1. 拥有最大权限
2. 可跨空间操作
3. 仍可查看和管理所有组织树、成员、知识库、智能体

### 空间级 RBAC

仍然由 `tenant_members` 负责，继续作为空间控制平面的权威来源。

语义如下：

1. `owner`：空间拥有者
2. `admin`：空间管理员
3. `contributor`：空间协作者
4. `viewer`：空间只读

### 组织树层

仍然由 `organization_members_pre_plan3` 负责，但语义要收敛成“人员域管理 + 资源可见域 + 子组织资源域管理来源”，不再被误解释为空间级全域管理员来源。

---

## 4.2 新的权限定义

| 身份 | 数据来源 | 中文显示 | 组织树作用域 | KB/Agent 管理权 | 空间配置权 |
| --- | --- | --- | --- | --- | --- |
| 超级管理员 | `users.is_super_admin / can_access_all_tenants` | 超级管理员 | 全部 | 全部 | 全部 |
| 空间拥有者 | `tenant_members.role=owner` | 拥有者 | 视为根管理员 | 全部 | 全部 |
| 空间管理员 | `tenant_members.role=admin` | 管理员 | 视为根管理员 | 全部 | 管理空间配置 |
| 空间协作者 | `tenant_members.role=contributor` | 协作者 | 无自动组织管理权 | 仅本人资源 | 无 |
| 空间只读 | `tenant_members.role=viewer` | 只读 | 无自动组织管理权 | 无 | 无 |
| 子组织管理员 | `organization_members_pre_plan3.role=admin` 且非根投影 | 子组织管理员 | 本节点及后代节点人员域 | 本节点及后代节点资源域 | 无 |
| 子组织协作者 | `organization_members_pre_plan3.role=editor` | 协作者 | 仅成员/可见域 | 仅本人资源 | 无 |
| 子组织只读 | `organization_members_pre_plan3.role=viewer` | 只读 | 仅成员/可见域 | 无 | 无 |

关键点只有两个：

1. 根管理员本质上是空间 owner/admin 在组织树里的投影，不是新的独立权威来源。
2. 子组织管理员既覆盖“人”和“树”，也覆盖“本节点及后代节点资源域”，但它不等同于空间管理员，更不拥有全空间配置权。

## 5. 推荐的技术设计

## 5.1 采用“根管理员投影”，不做双写主权

### 设计原则

根节点管理员不要再由 `organizations.owner_id` 或根节点成员表单独定义，而应该由空间级 RBAC 投影得到：

1. `tenant_members.owner` -> 根节点显示为“拥有者”
2. `tenant_members.admin` -> 根节点显示为“管理员”

也就是说：

> 根节点管理员的主权在 `tenant_members`，组织树只做投影展示，不做主权复制。

### 为什么不建议把空间 owner/admin 镜像持久化到组织树成员表

如果把 tenant owner/admin 再同步写入 `organization_members_pre_plan3`，后续会产生双写漂移：

1. 改了 tenant role 忘了同步 org row
2. 在 org-tree 页面取消 admin，但 tenant role 仍是 admin
3. root org 与 tenant member 两套真相互相打架

因此推荐做法是：

1. 组织树成员接口在根节点场景下合成“投影成员”
2. 根节点对 owner/admin 行显示只读操作
3. 真正的 owner/admin 变更仍然走空间成员管理页

这样可以满足需求 1，又不会引入第二套主权。

## 5.2 组织树 owner 字段降级为“创建元数据”，不再参与授权

当前 `organizations.owner_id` 只能继续作为历史创建元数据保留，不能再用于：

1. 判断“空间拥有者”
2. 判断“组织 owner”
3. 判断 `is_owner`
4. 推导 admin 权限

改造后：

1. org-tree 鉴权不再读取 `member.IsOwner`
2. `ListOrgTreeMembers()` 不再把 `o.owner_id = omp.user_id` 作为前端展示角色来源
3. 前端 org-tree 成员页完全改用新的 `display_role` / `role_scope` 字段

## 5.3 同租户资源授权拆成“可见”和“可管”两条链

### 可见链保持组织树逻辑

同租户内 KB / Agent 的读权限保持现状：

1. `global`：同租户可见
2. `private`：仅创建者可见
3. `org`：本人所在组织及其后代组织作用域可见

### 可管链改成“空间 admin+、资源创建者、或子组织资源域管理员”

新的管理规则统一为：

1. 超级管理员：可管全部
2. 当前 tenant role >= `admin`：可管全部同租户资源
3. 资源创建者本人：始终可管自己的资源
4. 子组织管理员：可管理 `visibility=org` 且 `organization_id` 落在本节点及后代节点中的 KB / Agent
5. 其他情况：拒绝管理

这条规则同时用于：

1. `CanManageKB`
2. `CanManageAgent`
3. `KBAccessWrite`
4. 所有 `OwnedKBOrAdmin / OwnedAgentOrAdmin` 的配套资源路径

这样可以一次性解决三个问题：

1. 满足需求 1：空间管理员真正能管理空间资源
2. 满足重要调整：子组织管理员可管理本节点及后代节点资源域
3. 消除 KB 与 Agent 写权限不一致的问题

## 5.4 组织树人员管理单独保留“子树 admin 继承”

对于组织树本身，仍然保留当前继承规则：

1. 子组织 admin 可以管理自己节点及后代节点
2. 可以创建/编辑/移动子节点
3. 可以添加成员、移除成员、调整 org role

但是这里的“管理”仍然要分两层理解：

1. 组织节点
2. 组织成员
3. 组织内用户创建/挂接
4. 本节点及后代节点的 org 资源域

它不会上升为全空间资源管理权，但会继续作为 org-scoped KB / Agent 的子树资源管理依据。

## 5.5 子组织管理员建人能力需要单独收口

这是本次唯一需要明确设计取舍的点。

### 推荐方案

允许子组织管理员创建组织用户并开通空间成员身份，但只能授予：

1. `contributor`
2. `viewer`

不能授予：

1. `admin`
2. `owner`

原因：

1. 需求 2 要求子组织管理员具备人员创建能力
2. 但又不能让其越过空间控制平面边界

因此推荐把 `CreateUserInOrg()` / `AssignUserToOrg()` 相关的 tenant role 逻辑收敛为：

1. 空间 owner/admin：按现有规则可授予 owner/admin/contributor/viewer
2. 仅子组织 admin：最多可授予 contributor/viewer

这比“完全禁止子组织 admin 建人”更符合业务要求，也不会破坏空间级 admin/owner 边界。

## 6. 具体改造点

## 6.1 后端授权核心

### 修改文件

1. `internal/application/service/same_tenant_scope.go`
2. `internal/application/service/kb_visibility.go`
3. `internal/application/service/agent_visibility.go`
4. `internal/middleware/kb_access.go`
5. `internal/router/rbac.go`

### 改造内容

1. `sameTenantOrgScope` 从单一 `manageOrgIDs` 语义，拆成：
   - `readOrgIDs`
   - `personnelManageOrgIDs`
   - `resourceManageOrgIDs`
   - `isTenantAdminOrOwner`
2. `CanManageKB / CanManageAgent` 改为依据 `resourceManageOrgIDs` 为 org 资源放权，同时保留 tenant owner/admin 全域兜底。
3. 新规则统一为：
   - super admin -> allow
   - tenant role `admin/owner` -> allow
   - creator -> allow
   - sub-org admin subtree org resource -> allow
   - else -> deny
4. `KBAccessWrite()` 与 Agent 顶层写路由统一用同一矩阵，不再出现 KB/Agent 漂移。

## 6.2 组织树权限核心

### 修改文件

1. `internal/handler/org_tree.go`
2. `internal/application/service/org_tree.go`
3. `internal/application/repository/organization.go`

### 改造内容

1. `isOrgAdminOf()` / `isOrgAdminOfAny()` 增加 tenant owner/admin 直接通过逻辑。
2. `GetOrgTree()` / `GetTreeForUser()` 中，tenant owner/admin 视为根管理员，可看全树。
3. `GetUserOrganizations()` 不再把 `member.IsOwner` 当作 admin 来源。
4. `ListOrgMembers()` 对根节点返回“空间角色投影 + 组织直属成员”的合成结果。
5. `organizations.owner_id` 不再用于 org-tree 授权，只保留元数据用途。

## 6.3 根节点成员接口响应新增展示字段

### 新增字段建议

对 org-tree 成员列表增加以下字段：

1. `display_role`
2. `role_scope`
3. `tenant_role`
4. `org_role`
5. `source`
6. `is_projected_root_admin`
7. `can_manage_personnel`
8. `can_manage_resources`

### 字段语义

1. `display_role`：前端最终显示文案对应的逻辑角色，不再自己猜
2. `role_scope`：`workspace_owner / workspace_admin / suborg_admin / org_editor / org_viewer / inherited_admin`
3. `tenant_role`：保留原始 tenant role
4. `org_role`：保留原始 org role
5. `source`：`tenant_projection / org_direct / org_inherited`

### 兼容策略

1. 现有 `role`、`is_owner`、`is_admin` 暂时保留一版
2. 前端全部切换到新字段后，再废弃旧字段

## 6.4 子组织建人与 tenant role 授权

### 修改文件

1. `internal/handler/org_tree.go`
2. `internal/handler/tenant_role_authz.go`

### 改造内容

把当前的 `authorizeTenantRoleProvision()` 拆成两类：

1. 空间级角色授予：保留现有 owner/admin 规则
2. 组织级建人授予：新增“branch admin 仅可授予 contributor/viewer”的逻辑

建议新增一个专用 helper，例如：

- `authorizeOrgScopedProvision(callerTenantRole, isBranchOnlyAdmin, requestedTenantRole)`

规则：

1. super admin -> unlimited
2. tenant owner -> unlimited
3. tenant admin -> unlimited
4. branch-only admin -> only contributor/viewer
5. 其他 -> deny

## 6.5 前端空间成员页角色显示修正

### 修改文件

1. `frontend/src/views/settings/TenantMembers.vue`
2. `frontend/src/composables/useRoleLabel.ts`
3. `frontend/src/i18n/locales/zh-CN.ts`
4. 其他多语言 locale 文件

### 目标显示

空间成员页统一显示：

1. `owner` -> 拥有者
2. `admin` -> 管理员
3. `contributor` -> 协作者
4. `viewer` -> 只读

注意：这里只改“展示文案”，不改枚举值。

## 6.6 前端组织树成员页角色显示修正

### 修改文件

1. `frontend/src/views/admin/components/MemberTable.vue`
2. `frontend/src/views/admin/components/EditUserDialog.vue`
3. `frontend/src/views/admin/components/AssignOrgDialog.vue`
4. `frontend/src/i18n/locales/zh-CN.ts`

### 目标显示

组织树成员页统一显示：

1. 根节点空间 owner 投影 -> 拥有者
2. 根节点空间 admin 投影 -> 管理员
3. 子组织 `admin` -> 子组织管理员
4. 子组织 `editor` -> 协作者
5. 子组织 `viewer` -> 只读

### 额外建议

在主角色标签之外增加一个小 scope 提示：

1. `空间角色`
2. `子组织角色`
3. `继承自上级组织`

这样可以避免所有“管理员”在 UI 上看起来完全同义。

## 6.7 根节点投影成员的交互限制

根节点成员列表中，来自 tenant role 投影的 owner/admin 行：

1. 不允许通过 org-tree 页面“取消管理员”
2. 不允许通过 org-tree 页面“移除成员”
3. 提示文案改为“请在空间成员页面调整”

这样可以确保 root 权限主权仍然只在 `tenant_members`。

## 7. 数据与上线前置条件

## 7.1 单根约束

本方案默认每个 tenant 只有一个根组织。

但当前实现允许存在多个顶层节点，因此上线前必须做数据审计：

1. 若某 tenant 顶层节点数为 0：先补建根节点
2. 若某 tenant 顶层节点数为 1：可直接上线
3. 若某 tenant 顶层节点数 > 1：必须先做“多根并单根”迁移，再开启新权限模型

建议把“多根 tenant”作为严格拦截条件，不做运行期模糊兼容。

## 7.2 历史 owner 字段兼容

由于历史 `owner_id` 是“节点创建者”，不是“空间拥有者”，因此上线时需明确：

1. 历史数据继续保留
2. 新逻辑不再把它当作 org-tree 授权依据
3. 如需展示“节点创建者”，应另开独立字段，不复用角色列

## 7.3 行为变化告知

本次上线需要明确告知一个关键边界：

1. 子组织管理员的 KB / Agent 管理权会被正式固化为“本节点及后代节点资源域”
2. 它不再被解释为空间管理员，更不覆盖其他节点资源、全局资源或他人 private 资源

因此需要提前做行为公告，避免把“子组织资源域管理员”误解成“全空间管理员”。

## 9. 最终建议

本次改造建议采用下面这条主线，不建议再回到“把所有 admin 混成一种”的旧路：

1. `tenant_members` 继续做空间主权
2. `organization_members_pre_plan3` 继续做组织树成员与人员域
3. 根节点管理员由空间 owner/admin 投影得到
4. 子组织 admin 管“树和人”，并管理本节点及后代节点资源域
5. KB/Agent 管理统一为“super admin 或 tenant admin/owner 或 creator 或子组织 admin 的子树资源域权限”

这条路线改动面可控，和现有代码结构一致，也与 20260707-02 审查报告“模型分离、统一决策”的方向一致。
