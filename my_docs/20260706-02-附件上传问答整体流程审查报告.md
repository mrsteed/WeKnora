## 2. 总结

| 问题 | 结论 |
| --- | --- |
| 附件上传到了哪里 | 由租户存储配置（`StorageEngineConfig.DefaultProvider`）决定的文件服务对象；常见是 MinIO，默认兜底是 local。对象名形如 `minio://{bucket}/{tenantID}/exports/{uuid}{ext}`。 |
| 是否进入知识库 | 不进入知识库。附件只在请求级被解码、存储到文件服务、提取纯文本/图片嵌入/音频转写，**不**写入 `Knowledge` / `KnowledgeBase` 表，不参与向量化和索引。 |
| 为什么只保留前 500 行 | 文本/解析出来的 Markdown/音频转写都被 `maxTextFileLines = 500` 截断；目的不是“节省存储”，而是为了控制注入到 LLM prompt 里的内容长度。 |
| 截断是否合理 | 在普通问答场景下大体合理；但在“根据附件生成完整技术方案”这种长文档场景下，500 行会直接丢失后半段事实，导致长文档生成质量显著下降。 |
| main 与 dev 的关键差异 | 上传通道本身几乎没变；dev 主要是新增“按租户 StorageEngineConfig 动态解析 file service”能力（`resolveAttachmentFileService`），并通过 `AttachmentUpload` 增加 `supportedTypes` 与“按 Agent 开关”限制；其他面向 Chat 的能力（长文档、artifact、续写、路由等）是 dev 单独叠加的特性，不影响上传→存储→prompt 这一段。 |

## 3. 附件上传的完整链路（dev 分支）

### 3.1 前端

1. 用户选择文件 → [frontend/src/components/AttachmentUpload.vue](frontend/src/components/AttachmentUpload.vue) 校验白名单。
   - `SUPPORTED_TYPES` 仍写死在前端，包括 docx/pdf/md/txt/csv/json/xml/yaml/log/html/jpg/png/mp3 等。
   - `dev` 新增 `supportedTypes` prop，会被 `effectiveAttachmentSupportedTypes` 覆盖（agent 自带的 `supported_file_types` 或 `runtimeContext.supportedFileTypes` 优先），否则回退到 `SUPPORTED_TYPES`。
2. 用户点发送 → [frontend/src/components/Input-field.vue](frontend/src/components/Input-field.vue) 把 `file` 转 base64 → 塞进 `attachment_uploads` 字段。
   - `dev` 新增 `isAttachmentUploadEnabledByAgent`：当 `runtimeContext.attachmentUploadEnabled === false` 时禁用按钮。

### 3.2 后端入口

`POST /api/v1/sessions/{session_id}/agent-qa` 或 `/knowledge-qa` 进入 `parseQARequest()`：

- 代码位置：[internal/handler/session/qa.go](internal/handler/session/qa.go#L1398-L1457)
- 行为：
  1. 按 `MAX_FILE_SIZE_MB`（默认 50MB）校验大小。
  2. `agent_enabled && AudioUploadEnabled` 时启用 ASR 模型 ID。
  3. 并发地把每个 base64 附件交给 `h.attachmentProcessor.ProcessAttachment()`，得到 `types.MessageAttachment`（含 `URL/FileName/FileType/FileSize/Content/LineCount/IsTruncated`）。

### 3.3 `AttachmentProcessor.ProcessAttachment`（dev）

代码：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L40-L128)

核心步骤：

1. **文件名安全校验**：`secutils.ValidateInput` + `SafeFileName` 防注入/穿越；后缀统一小写，无后缀默认 `.txt`。
2. **类型白名单**：`isValidFileType` 与前端保持一致（docx/pdf/md/txt/csv/json/xml/yaml/log/html/jpg/png/mp3 等）。
3. **文件落盘**：
   - `fileSvc := p.resolveAttachmentFileService(ctx)`：dev 新增，**优先**用 ctx 中租户 `StorageEngineConfig` 重新构造文件服务对象；兜底回退到注入期默认 `p.fileService`。
   - `fileSvc.SaveBytes(ctx, data, tenantID, "attachment_<uuid>.<ext>", false)`：
     - MinIO 路径（[internal/application/service/file/minio.go](internal/application/service/file/minio.go#L197-L215)）：`objectName = {tenantID}/exports/{uuid}{ext}`，返回 `minio://{bucket}/{tenantID}/exports/{uuid}{ext}`。
     - local 路径：写到 `LOCAL_STORAGE_BASE_DIR` + `PathPrefix`。
     - 对象存储/cos/obs 等其他 provider 行为见 [internal/application/service/file/factory.go](internal/application/service/file/factory.go)。
4. **正文提取**：
   - 文本类型（`.txt/.md/.json/.csv/.xml/.yaml/.yml/.log`）：`processTextFile()` 走 `bufio.Scanner` 累行，**截断到前 500 行**（`maxTextFileLines`），并打 `IsTruncated=true`。
   - 音频：未配置 ASR 模型时打 placeholder，否则调用 `ASR.Transcribe` 后用 `applyLineTruncation` 截断到 500 行。
   - “简单格式”（md/csv/json 等）：`processWithDocParser` → `SimpleFormatReader` → 内嵌图片用 `imageResolver.ResolveAndStore` 上传到同一个 file service → `applyLineTruncation` 500 行。
   - 复杂格式（pdf/docx/xlsx/ppt 等）：`processWithDocumentReader` → `docreader` → 图片 resolve → `applyLineTruncation` 500 行。
5. **UTF-8 清洗**：`common.CleanInvalidUTF8`，然后写日志 `attachment processed`。

### 3.4 后续消费（不是入库）

附件处理完后，整个 `MessageAttachments` 走两条路：

- **KnowledgeQA（普通 RAG/纯对话）**：[internal/application/service/session_knowledge_qa.go](internal/application/service/session_knowledge_qa.go#L201-L203)
  ```go
  if len(req.Attachments) > 0 {
      userContent += req.Attachments.BuildPrompt()
  }
  ```
  即把附件当作“用户消息里追加的一段 `<attachments>...</attachments>` 文本”直接拼进对话上下文。

- **AgentQA**：[internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L237-L242)
  ```go
  if len(req.Attachments) > 0 {
      agentQuery += req.Attachments.BuildPrompt()
  }
  logger.Infof(ctx, "Appended %d attachment(s) to agent query", len(req.Attachments))
  ```
  同样只在 query 上拼，不会被拆分成独立的 knowledge 记录。

`BuildPrompt()` 的格式（[internal/types/message.go](internal/types/message.go#L86-L114)）：

```
<attachments>
<attachment index="1" name="...">
  <metadata>
    <type>.md</type>
    <size_kb>75.49</size_kb>
  </metadata>
  <content>...</content>
  <note>This file has a total of 1512 lines, truncated to show only the first 500 lines.</note>
</attachment>
</attachments>
```

### 3.5 关键观察

- **不会进 KB**：`AttachmentProcessor` 既没调 `knowledgeService.Create`，也没调 `knowledgeService.CreateKnowledgeFromFile` 或 `IngestKnowledge`，更不会写 `knowledge_chunks`/`embeddings`。
- **存储位置**：由租户级 `StorageEngineConfig` 决定，常见是 MinIO bucket `{tenantID}/exports/{uuid}{ext}`。
- **内容形态**：落到 file service 后，存储为原始字节；前端/普通 Agent 看到的是经 `BuildPrompt()` 包装后的截断文本。
- **跨会话引用**：当前 `MessageAttachment.URL` 是 `minio://...` provider scheme，会被 [internal/application/service/file/minio.go](internal/application/service/file/minio.go#L95-L113) 的 `parseMinioFilePath` 解析，且严格校验 bucket 必须等于 `s.bucketName`。这一点意味着：如果租户把 provider 从 local 切到 minio，旧的 local 路径无法被新 provider 读取。dev 引入 `resolveAttachmentFileService` 后该问题更敏感，但属于另一条修复线，本次不展开。

## 4. 为什么只保留前 500 行

### 4.1 实现位置

- 常量定义：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L23-L24)
  ```go
  maxTextFileLines = 500
  ```
- 文本截断：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L137-L162) `processTextFile()`
- Markdown/音频统一截断：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L284-L298) `applyLineTruncation()`

### 4.2 设计动机

500 行并不是“节省存储”用的——文件原始字节已经完整存到 MinIO，截断只影响注入到 LLM prompt 的字符串。

目的是：

1. **控制单次请求的 prompt 体积**。`BuildPrompt()` 把每条附件展开为 `<attachment>...</attachment>`，多个附件叠加后 prompt token 容易爆。
2. **避免和会话上下文“拼太长”**。`BuildPrompt()` 通常会和 `chat_history`/`@mention`/system prompt 共用上下文窗口。
3. **避免误导 Agent 误把整篇附件当成全文**，在没有 KB 检索的情况下模型经常把前 500 行当成“完整证据”，然后脑补出没有的内容。

简单说，500 行是“给普通问答/Agent 的安全预算”，并不是“文档导入标准”。

### 4.3 这个限制在长文档场景下不成立

具体到 [my_docs/test/长文本.txt](my_docs/test/长文本.txt) 的复现：

- 上传会议纪要：1512 行 → 只保留 500 行（`text file truncated: total=1512, kept=500`，[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L52)）。
- 复现日志同时显示模型拿到的是 `[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L106-L107) 的 markdown 渲染片段（`<attachments>...<content>...</content><note>This file has a total of 1512 lines, truncated to show only the first 500 lines.</note>...`）。
- Agent 接到附件 prompt 拼到 query（`Appended 1 attachment(s) to agent query`，[my_docs/test/长文本.txt](my_docs/test/长文本.txt#L112)），然后开始用 `thinking` 工具总结前 500 行的事实，并按“业务模式/测评系统/AI 配方/订单支付/加盟商/机器联动/生产发货/项目周期”这种**前 500 行**能看到的结构去总结。

对“根据附件生成完整技术方案”这种任务而言，500 行截断会直接带来两个问题：

1. 模型看不到后半段事实，方案自然不会覆盖后半段。
2. 即便后来放开路由/门禁让请求进入专用长文档流程，专用长文档链路**也不会**读取附件正文，只读取用户 query 和本地知识库证据（见上一份报告 [my_docs/20260706-01-长文档智能路由命中后未进入执行流程审查报告.md](my_docs/20260706-01-长文档智能路由命中后未进入执行流程审查报告.md)）。

所以这次“未进入长文档流程”和“只保留前 500 行”是相互独立的两个问题；只有把两条都解决，才能让“根据附件生成完整方案”真正可用。

## 5. dev 与 main 在附件/文件上传链路上的关键差异

下面只列与“附件上传问答”相关的差异，不展开长文档/RBAC/数据库知识库等其他主线。

### 5.1 存储后端选择：dev 引入“按租户配置动态解析 file service”

main 实现：`attachment_processor.go` 第 90 行附近直接 `p.fileService.SaveBytes(...)`：

```go
storageURL, err := p.fileService.SaveBytes(ctx, data, tenantID, uniqueFileName, false)
```

dev 实现：在 `ProcessAttachment` 顶部增加 `resolveAttachmentFileService(ctx)`：

- 先看 `ctx` 里是否有租户 `StorageEngineConfig`，有就用 `filesvc.NewFileServiceFromStorageConfig("", tenant.StorageEngineConfig, "")` 重新构造。
- 失败时降级到注入期 `p.fileService`。
- 日志：`[attachment-storage] using provider=%s for attachments`。

代码：[internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L82-L92) 与 [internal/handler/session/attachment_processor.go](internal/handler/session/attachment_processor.go#L268-L284)。

`factory.NewFileServiceFromStorageConfig` 在 dev 与 main 中保持一致，差异只是 dev 在请求上下文里多走了一遍它。

实际效果：

- **main**：附件固定落到启动期注入的全局 `fileService`。如果租户后来在 UI 里切到“MinIO 远程”，但容器启动时还没收到这个配置，附件会继续写到 local。
- **dev**：每次处理附件都会按当前请求上下文里的租户配置解析一次，租户在 UI 切换 storage 后下一次请求就能用新 backend。

差异程度：dev 修了一个 main 的实际体验问题，但附件本身的存储格式（`{tenantID}/exports/{uuid}{ext}`）在两个分支里完全相同，minio/local 路径规则没有改。

### 5.2 解析后的下游处理：两个分支都把 file service 透传到 `processWithDocParser`/`processWithDocumentReader`

这一点在 diff 里很显眼：

```
+    if err := p.processWithDocParser(ctx, data, baseName, ext, attachment, tenantID, fileSvc); err != nil {
```

但实际上 `p.imageResolver.ResolveAndStore` 这个调用在 main 里也是用 `p.fileService`。dev 把入参替换成 `fileSvc`，让图片内嵌能跟随当前租户 provider。功能差异是“图片能落到新 provider”，并不是“附件本身行为变了”。

### 5.3 前端：dev 让 `AttachmentUpload` 接收外部 `supportedTypes`

- main：[frontend/src/components/AttachmentUpload.vue](frontend/src/components/AttachmentUpload.vue) 只读本地 `SUPPORTED_TYPES` 数组。
- dev：
  - 新增 prop `supportedTypes`。
  - 新增 `allowedTypes = computed(...)`，与本地默认合并。
  - 校验改为 `isSupportedFileType(file)`，按扩展名或 mime 匹配。
  - 上传按钮的 `accept` 也使用 `allowedTypes`。

差异本身不是“是否进入知识库”或“是否上传到 minio”，只是“哪些类型允许被前端选中”。

### 5.4 前端：dev 让 `Input-field.vue` 增加“按 Agent 开关禁用附件”

- main：附件按钮始终可点。
- dev：
  - 新增 `isAttachmentUploadEnabledByAgent`（`runtimeContext.attachmentUploadEnabled !== false` 才允许）。
  - 新增 `effectiveAttachmentSupportedTypes`（agent 配置 > runtimeContext > 默认）。
  - 拖拽上传也走同一开关。

这与上传通道无关，只影响“用户能不能点这个按钮”。

## 6. 关于“是否进入知识库”的明确结论

- “附件上传问答”**不会**写入知识库，也不会被 embedding/检索。
  - 入口 `AttachmentProcessor` 既不调 `kgService.Create` 也不调 `CreateKnowledgeFromFile`。
  - 下游 service 只把附件追加到 `userContent` / `agentQuery`。
- “上传到知识库”是另一套独立路径，对应：
  - `POST /api/v1/knowledge-bases/{kb_id}/files`（KB 级上传入口）。
  - `POST /api/v1/datasources/...`（外部数据源同步）。
  - 这些路径会触发 chunking、embedding、向量入库，与“附件问答”完全分离。

如果用户的预期是“上传附件后能让它进入知识库”，需要在产品层做两件事：

1. 在聊天页加一个明确“保存到知识库”的入口（已有 main/dev 的 `CreateKnowledgeFromFile`）。
2. 或者在 AgentQA/KnowledgeQA 流程里增加一个“附件是否升级为 KB 知识”的开关，由用户在前端显式确认（不要默认做）。

## 7. 关于 500 行截断的建议

| 选项 | 取舍 |
| --- | --- |
| 保留 500 行上限（现状） | 普通问答/Agent 仍安全可控；长文档场景会信息缺失。 |
| 把 500 行调到更大（比如 2000-5000 行） | 短期可缓解丢失事实，但 prompt 体积会快速接近模型上下文上限；多附件叠加会直接爆。 |
| 按“是否进入长文档流程”动态调整截断 | dev 的 Chat Router 已经在判断 `full_document` / `knowledge_grounded_full_document`。如果路由已判定为长文档，建议把截断窗口放到“按章节动态检索”的模型（一次性仍取前 N 行，但 N 可以放大到 4000-8000 行，并把每章只喂对应片段）。 |
| 让长文档链路真正消费附件 | 单独的修复项：把 `MessageAttachments.BuildPrompt()` 注入 `buildDedicatedFullDocumentOutlineMessages` / `buildKnowledgeGroundedFullDocumentOutlineMessages` / `build*SectionMessages`。这是上一份报告已经给出的 P1。 |

短期止血建议：维持 `maxTextFileLines=500`，但在 prompt 里把“500 行上限”显式声明为“事实预算”，并要求模型在输出里标注 `已覆盖：<章节>` / `未覆盖：<章节>`。

中期建议：把 500 行截断从“单值常量”升级为可配置项，由租户或 Agent 决定；并把“是否进入长文档流程”作为截断决策的输入。

### P1：在专用长文档链路消费附件正文

- 文件：

  - [internal/application/service/session_agent_qa.go](internal/application/service/session_agent_qa.go#L3845-L3915) 章节构建

- 在 `BuildPrompt()` 之外为长文档提供“按章节动态读取附件片段”的能力，例如把附件内容落到一个临时可检索对象，再由专用长文档引擎按章节范围读取。
