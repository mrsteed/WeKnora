# 超级管理员跨空间与空间人员开通最终开发计划

## 1. 文档目的

本方案基于以下两份审查文档汇总形成最终可落地开发计划：

- [WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md](WeKnora/my_docs/20260707-02-组织人员管理与租户权限统一设计审查报告.md)
- [WeKnora/my_docs/20260707-03-超级管理员创建空间后人员开通与权限接入审查方案.md](WeKnora/my_docs/20260707-03-超级管理员创建空间后人员开通与权限接入审查方案.md)

本次新增需求有两个非常明确的目标：

1. **超级管理员切换到任意空间后，必须能管理该空间。**
2. **超级管理员创建空间后，必须有一套完整、稳定、不会漏掉 `tenant_members` 的人员开通流程。**

本方案回答以下问题：

- 为什么超级管理员切换空间后，成员管理仍然报错。
- 为什么在组织里创建用户后，登录新空间仍然没有权限。
- 基于当前代码架构，租户权限、组织树权限、共享空间权限是否能统一。
- 如果不能完全统一，最终应如何分层并最大限度整合。
- 应该如何定义“超级管理员”的产品语义与代码权限边界。
- 最终如何形成一套可落地的开发计划。

## 2. 新增问题的核心诊断

## 2.1 现象一：超级管理员切换空间后，成员管理页报错

截图中的报错是：

```text
Access denied: URL tenant does not match the active tenant
```

### 代码根因

这不是单纯后端权限不足，而是 **前端传错了租户 ID**，与后端当前活动空间上下文不一致。

### 直接证据

#### 前端状态定义

`frontend/src/stores/auth.ts`：

- `selectedTenantId`：切换后的目标空间 ID
- `effectiveTenantId`：真正的当前活动空间 ID
- `currentTenantId`：当前实现却仍然返回 `tenant.value?.id`，也就是**home tenant / 默认租户 ID**

而 `TenantMembers.vue` 中：

- 使用的是 `authStore.currentTenantId`
- 它会把 **默认租户 ID** 填进 `/tenants/:id/members`

与此同时，请求头里：

- `frontend/src/utils/request.ts` 会自动附带 `X-Tenant-ID = weknora_selected_tenant_id`
- 也就是当前切换后的目标空间 ID

于是出现了典型不一致：

- URL path：`/tenants/<默认租户ID>/members`
- Header / auth context：`X-Tenant-ID = <切换后的空间ID>`

后端中间件 `RequirePathTenantMatch()` 会做严格校验：

- path tenant ID 必须等于当前活动 tenant context
- 否则返回：
  - `Access denied: URL tenant does not match the active tenant`

### 结论

这个问题首先是一个 **前端 active tenant 状态引用错误**，而不是“成员管理页本身权限设计错误”。

---

## 2.2 现象二：在新空间里创建用户后，登录仍然没有权限

日志核心是：

```text
SELECT * FROM tenant_members WHERE user_id = ? AND tenant_id = 10002
... record not found
resolveTenantRole step1 miss
resolveTenantRole step4 fail-closed (EnableRBAC=true)
Forbidden: not a member of the target tenant
```

### 代码根因

当前组织树“创建用户”链路：

- `internal/handler/org_tree.go: CreateUserInOrg`
- `internal/application/service/user.go: CreateUserByAdmin`
- `internal/application/service/org_tree.go: AssignUserToOrg`

只做了两件事：

1. 创建 `users`
2. 创建 `organization_members_pre_plan3`

它**没有**创建：

3. `tenant_members`

而后端所有空间级权限判定都先依赖：

- `tenant_members`
- `resolveTenantRole()`

因此：

- 用户账号存在
- 用户也在组织树里
- 但它对新空间没有租户成员身份
- 登录后所有空间级接口全部 403

### 结论

这个问题不是“组织管理员权限不够”，而是：

> **用户根本没有完成新空间入场（tenant onboarding）。**

---

## 2.3 现象三：当前“超级管理员”概念在前后端并不完全一致

当前代码里实际上有三个相近但不完全等价的字段/概念：

1. `users.is_system_admin`
2. `users.is_super_admin`
3. `users.can_access_all_tenants`

### 当前使用情况

#### 前端 UI 超管判断

`frontend/src/stores/auth.ts`：

- `isSystemAdmin = user.is_system_admin`
- `isSuperAdmin = isSystemAdmin || user.is_super_admin`

也就是说，前端把 `is_system_admin` 和 `is_super_admin` 都当成“超级管理员”。

#### 后端跨空间访问判断

`internal/middleware/access.go`：

- `IsCrossTenantSuperuser()` 只认：
  - `EnableCrossTenantAccess == true`
  - `user.CanAccessAllTenants == true`

它**不看**：

- `IsSystemAdmin`
- `IsSuperAdmin`

### 结果

就会出现一种产品语义错位：

- 用户在 UI 上看起来像“超级管理员”
- 但如果没有 `CanAccessAllTenants`
- 切空间后的某些后端路由并不会把他当跨空间超管放行

### 结论

当前系统里：

- **平台级系统管理员**
- **跨空间运营超级用户**
- **历史本地超级管理员兼容字段**

这三者还没有完成产品语义统一。

这必须纳入最终开发计划。

## 3. 最终设计原则

结合前两份审查文档和本次新增需求，推荐采用以下最终原则。

## 3.1 不把所有权限强行并成一张表，但统一成一套授权框架

继续保留三层模型：

1. **租户 / 工作空间级权限**：`tenant_members`
2. **部门树 / 组织树权限**：`organization_members_pre_plan3`（未来演进为正式部门树成员表）
3. **跨空间协作权限**：`organization_tenant_members`

不建议把三者强行压成一张成员表，因为它们解决的是不同问题。

但必须统一成同一套授权框架：

- 空间级能力上限
- 部门树资源作用域
- 跨空间协作上下文
- 资源归属判定

也就是说：

> **模型分层保留，授权决策统一。**

---

## 3.2 明确“超级管理员”的最终产品定义

结合你的要求“超级管理员能管理所有的空间”，建议把产品层的“超级管理员”定义为：

### 超级管理员（Super Admin）

必须同时具备：

1. **平台级能力**
   - 可访问系统设置
   - 可管理系统管理员
   - 可管理全局平台配置
2. **跨空间运营能力**
   - 可切换到任意空间
   - 可管理任意空间成员
   - 可管理任意空间的模型、设置、组织树、知识库、智能体
   - 在目标空间内等同 `Admin`，但不天然等同 `Owner`

### 推荐实现语义

在代码层面建议把“超级管理员”定义收敛为：

- `is_system_admin = true`
- `can_access_all_tenants = true`

并且：

- 前端 `isSuperAdmin`
- 后端 `IsCrossTenantSuperuser`
- 平台级 `RequireSystemAdmin`

统一围绕这个组合语义工作。

### 是否保留 `is_super_admin`

建议：

- `is_super_admin` 作为历史兼容字段保留一个过渡期
- 新代码不再以它作为独立权威来源
- 最终统一以：
  - `is_system_admin`
  - `can_access_all_tenants`
  为准

---

## 3.3 明确“空间管理员”和“部门管理员”不是同一角色

最终必须清晰区分：

### 空间管理员（Tenant Admin）

能力：

- 模型管理
- 租户成员管理
- 租户级配置管理
- 内置智能体配置覆盖
- 可以创建组织树节点 / 管理空间内部资源

来源：

- `tenant_members.role >= admin`

### 部门管理员（Org Tree Admin）

能力：

- 管理自己部门及子部门的人员
- 决定同租户内资源在组织树上的作用域
- 不天然拥有空间级模型/系统设置权限

来源：

- 组织树成员角色 `admin`

### 跨空间协作管理员（Collaboration Space Admin）

能力：

- 管理跨空间共享关系
- 审批/维护共享空间成员
- 不天然拥有目标空间的租户级模型/系统设置权限

来源：

- `organization_tenant_members.role = admin`

---

## 4. 最终推荐的“创建空间”方案

## 4.1 创建空间后的核心目标

超级管理员创建一个空间后，系统必须立刻支持以下流程：

1. 当前超级管理员能以运营身份进入并管理这个空间。
2. 能为这个空间创建首位业务负责人。
3. 该负责人第一次登录时就具备正确的空间权限。
4. 后续再为其分配部门树角色，而不是把部门树角色当成空间入场方式。

---

## 4.2 推荐的标准操作顺序

### 第一步：超级管理员创建空间

- 调用 `POST /tenants`
- 创建成功后，创建者自动获得：
  - `tenant_members.role = owner`

这一步保留现状即可。

### 第二步：空间初始化向导（新增）

创建空间后，不应让超级管理员直接去“组织树创建用户”。

而应该进入一个新的**空间初始化向导**：

1. 选择 / 创建首位空间负责人
2. 为负责人赋予空间级角色：
   - `owner` 或 `admin`
3. 可选：创建组织树根节点
4. 可选：把负责人挂到组织树节点，并赋 `org_role`

### 第三步：后续人员进入空间

按两种路径处理：

#### A. 已有系统账号

- 先走 `tenant member add / invite`
- 成为 `tenant_members`
- 再分配到组织树节点

#### B. 尚未注册系统账号

- 走 `tenant invitation share link`
- 由对方通过 `register-by-invite` 完成注册
- `AcceptByToken()` 自动创建 `tenant_members`
- 注册成功后，再分配到组织树节点

### 第四步：部门树分配

在成为 tenant member 之后，再设置：

- `org_id`
- `org_role`

这一步是附加作用域，不是入场凭据。

## 5. 立即可落地的修复项（P0）

这些改动不需要先做大规模架构迁移，应优先落地。

## P0-A：修复超级管理员切空间后成员管理页的 tenant ID 取值错误

### 问题

`TenantMembers.vue` 和 `TenantInfo.vue` 使用的是：

- `authStore.currentTenantId`

但当前 `currentTenantId` 实际上是 home tenant，不是 active tenant。

### 目标

所有租户级页面必须统一使用：

- `effectiveTenantId`

或直接把 `currentTenantId` 的语义改成真正的 active tenant。

### 建议改法

#### 方案 1（推荐）

- 重新定义 `authStore.currentTenantId` = active tenant id
- 新增 `homeTenantId` 表达用户注册时默认空间

#### 方案 2

- 保持 `currentTenantId` 旧语义不变
- 所有租户级页面统一改用 `effectiveTenantId`

### 受影响页面（至少）

- `frontend/src/views/settings/TenantMembers.vue`
- `frontend/src/views/settings/TenantInfo.vue`
- 所有调用 `/tenants/:id/*` 的页面与组件

### 验收标准

- 超级管理员切到空间 10002 后，成员管理请求路径应为：
  - `/api/v1/tenants/10002/members`
- 不再出现：
  - `URL tenant does not match the active tenant`

## P0-B：统一“超级管理员”定义与跨空间能力

### 问题

当前前端把：

- `is_system_admin`
- `is_super_admin`

当成超级管理员；

但后端跨空间放行只认：

- `can_access_all_tenants`

### 目标

产品上一个“超级管理员”概念，后端和前端都一致：

- 平台管理 + 跨空间管理

### 建议改法

1. 规定：
   - 超级管理员 = `is_system_admin=true` 且 `can_access_all_tenants=true`
2. 超级管理员提升/撤销接口同时维护这两个字段
3. 前端 `authStore.isSuperAdmin` 只认统一语义
4. 后端 `IsCrossTenantSuperuser` 改为读取统一 helper，而不是散落判断

### 需要新增的描述

应在文档和 UI 上明确：

#### 超级管理员权限

- 可访问系统设置
- 可切换并管理所有空间
- 可管理任意空间成员
- 可管理任意空间的模型、组织树、知识库、智能体
- 在任何目标空间内默认等同 `Admin`
- 但不自动成为业务 `Owner`

### 验收标准

- 超级管理员切到任意空间后，成员管理、模型管理、空间信息、组织树管理均可正常使用
- 不需要在目标空间内存在 `tenant_members` 行，也可执行空间级管理操作

## P0-C：创建用户时补齐 tenant membership bootstrap

### 问题

`CreateUserInOrg` 只创建用户和组织树成员，不创建 `tenant_members`。

### 目标

任何“为某空间创建人员”的正式流程，都必须完成：

1. `users`
2. `tenant_members`
3. `org-tree membership`（可选）

### 建议改法

短期有两个可选方案。

#### 方案 1：扩展 `CreateUserInOrg`

给请求体新增：

- `tenant_role`
- `org_role`

执行顺序：

1. 创建用户
2. 调 `tenantMemberService.AddMember(...)`
3. 调 `orgTreeService.AssignUserToOrg(...)`

#### 方案 2（推荐）：新增独立空间人员开通接口

例如新增：

- `POST /tenants/:id/provision-users`

请求体：

```json
{
  "email": "zhangzhen@hlsa.com",
  "username": "zhangzhen",
  "password": "******",
  "tenant_role": "admin",
  "org_id": "org-root-1",
  "org_role": "admin",
  "create_user_if_missing": true
}
```

该接口负责：

1. 创建用户（如不存在）
2. 创建 `tenant_members`
3. 可选分配组织树节点
4. 返回完整开通结果

### 推荐结论

- **不要继续把 `CreateUserInOrg` 当空间 onboarding 主路径。**
- 推荐新增独立 provisioning 接口。

### 验收标准

- 新建的 `zhangzhen@hlsa.com` 登录后，`resolveTenantRole()` 能命中 active membership
- `/models`、`/organizations`、`/agents`、`/knowledge-bases` 等不再 403

## 6. 中期架构收口（P1）

## P1-A：建立空间初始化向导

### 目标

超级管理员创建空间后，不再手工拼流程，而是进入标准 onboarding。

### 建议流程

1. 创建空间成功
2. 自动进入 `Workspace Setup Wizard`
3. 步骤：
   - 设置空间基本信息
   - 选择首位业务负责人
   - 设置其 `tenant_role`
   - 创建组织树根节点
   - 选择是否把负责人加入根节点并设置 `org_role`
   - 选择是否初始化默认模型 / 内置智能体配置

### 好处

- 避免“空间创建成功但无人能用”
- 避免超管误走组织树创建用户路径
- 把空间所有权与部门归属拆开

---

## P1-B：登录与 `/auth/me` 增加“membership missing”显式状态

### 目标

避免继续出现“能登录但所有接口都 403”的灰色状态。

### 建议改法

当满足：

- `User.TenantID = T`
- 但 `tenant_members(user, T)` 不存在
- 且 `T` 已经不是空租户

返回明确状态：

- `membership_missing=true`
- 错误提示：
  - 账号尚未被开通到该空间，请联系空间管理员

### 说明

当前的 `synthFallbackMembership()` 是 rollout 兼容逻辑，不适合长期作为正式用户态。

---

## P1-C：把“空间人员开通”和“部门树挂接”彻底分层

### 原则

- 租户成员：决定能不能进入空间、能不能用系统设置
- 部门树成员：决定在空间内部属于哪个部门、能看哪些同租户资源

### 具体规则

- 没有 tenant membership：不能进入空间
- 有 tenant membership、无部门树成员：可以进入空间，但只拥有空间级角色对应的基础能力
- 有 tenant membership + org membership：再叠加部门树资源作用域

## 7. 长期统一架构（P2）

这部分与 20260707-02 文档对齐，但在本次需求下需要明确“超级管理员”和“空间 onboarding”的位置。

## P2-A：三层模型保留，但统一进入同一授权决策器

最终统一框架：

1. **Tenant Capability**
   - 角色：`owner/admin/contributor/viewer`
   - 回答：你在这个空间里能不能做这类操作

2. **Org Scope**
   - 角色：`admin/editor/viewer`
   - 回答：你在这个空间内部能看/管哪些部门范围的资源

3. **Collaboration Context**
   - 角色：`admin/editor/viewer`
   - 回答：别的空间共享给你时，你能以什么方式使用

4. **Super Admin Override**
   - 回答：你是否拥有平台级与跨空间运营级的全局越权能力

### 建议新增统一决策器

例如：

- `CanEnterTenant(user, tenantID)`
- `CanManageTenant(user, tenantID)`
- `CanReadKB(user, kbID)`
- `CanWriteKB(user, kbID)`
- `CanManageOrgNode(user, orgID)`
- `CanUseSharedAgent(user, agentID)`

把当前散落在：

- `auth.go`
- `rbac.go`
- `kb_access.go`
- `kb_visibility.go`
- `agent_visibility.go`
- `kbshare.go`
- `agent_share.go`

里的逻辑收口。

---

## P2-B：共享空间与部门树彻底分词、分文案、分页面

### 当前问题

`Organization` 同时被当成：

- 部门树节点
- 共享空间实体

这会持续制造认知混乱。

### 建议方向

- 组织树：改叫 `部门树 / Department Tree`
- 共享空间：改叫 `协作空间 / Collaboration Space`

即便短期不拆表，代码包、页面文案、接口说明也要先拆语义。

## 8. 最终推荐的“超级管理员创建空间”产品流程

这是本次最关键的落地建议。

## 8.1 推荐标准流程

### Step 1：超级管理员创建空间

- 自动获得 `Owner`
- 可立即切入该空间

### Step 2：空间初始化向导

- 选择首位业务负责人（已有账号 or 新建账号）
- 赋予：
  - `tenant_role = owner/admin`

### Step 3：用户入场

#### 已有账号

- 直接创建 `tenant_members`

#### 新账号

- 通过 provisioning API 一次性创建
- 或发 tenant invite link，由对方注册后自动生成 `tenant_members`

### Step 4：组织树分配

- 创建部门树根节点
- 把业务负责人挂到节点上
- 赋予 `org_role`

### Step 5：空间初始化资源

- 配置模型
- 配置 built-in agent 默认模型
- 配置 parser / storage / vector / MCP 等

### Step 6：业务资源初始化

- 创建知识库
- 创建智能体
- 建立可见性 / 共享关系

## 8.2 对 `zhangzhen@hlsa.com` 的具体建议

如果只给：

- `org_role = admin`

- 使用空间级设置

## 10. 验收标准

最终方案落地后，应满足以下验收标准：

### 超级管理员跨空间能力

1. 超级管理员切换到任意空间后：
   - 成员管理可正常访问
   - 空间信息可正常访问
   - 模型管理可正常访问
   - 组织树管理可正常访问
2. 不再出现：
   - `Access denied: URL tenant does not match the active tenant`

### 新空间人员开通能力

3. 在新空间中为 `zhangzhen@hlsa.com` 开通账号后：
   - `tenant_members` 中存在 active row
   - 登录后 `resolveTenantRole` step1 能命中
   - 不再出现 `not a member of the target tenant`

### 权限边界清晰

4. `tenant admin` 可以：
   - 管理模型
   - 使用系统设置中的空间级配置
5. `org admin` 但非 `tenant admin`：
   - 可以管理部门树范围内人员和资源
   - 不能管理空间级模型与系统设置
6. 超级管理员：
   - 可管理所有空间
   - 不要求在目标空间里预先存在 `tenant_members` 行

## 11. 最终建议

本次需求的最终答案不是简单“把某个 403 放开”，而是三件事同时做：

1. **修正前端 active tenant 状态引用错误**
2. **把超级管理员定义统一为“平台管理 + 跨空间运营”**
3. **建立正式的空间人员开通流程，保证先有 `tenant_members`，再谈组织树分配**

只有这三件事一起落地，才能同时解决：

- 超级管理员切空间后成员管理报错
- 新用户在空间中登录后没有权限
- 组织树权限与空间权限职责混乱

最终推荐的架构结论是：

> **保留“租户 RBAC / 部门树 / 协作空间”三层模型，但把超级管理员能力和空间 onboarding 做成统一入口，并通过统一授权决策器把三层权限收口。**
