# 智能体知识库权限控制审查与修正方案

## 1. 审查范围

本次审查聚焦“智能体可见知识库范围是否与当前账号权限一致”，重点核对以下代码路径：

1. 知识库可见性基线
   - internal/application/service/kb_visibility.go
   - internal/application/repository/knowledgebase.go
   - internal/handler/knowledgebase.go
   - internal/middleware/kb_access.go

2. 智能体知识库范围解析
   - internal/application/service/session_knowledge_qa.go
   - internal/application/service/session_qa_helpers.go
   - internal/application/service/custom_agent.go

3. 智能体相关知识库入口
   - internal/handler/knowledgebase.go
   - internal/handler/knowledge.go
   - internal/im/cmd_search.go
   - internal/im/cmd_info.go

4. 与共享智能体相关的附加授权路径
   - internal/application/service/agent_share.go
   - internal/middleware/kb_access.go

本次结论只针对当前代码行为，不沿用任何“前端应该已经限制”“共享智能体天然等价于直接知识库授权”之类的假设。

## 2. 结论摘要

结论先行：

1. 当前系统已经有一套正确的“账号可见知识库”基线能力，核心是 KBVisibilityService + knowledgebase repository 的 ListAccessibleKBs / CanAccessKB。
2. 这套能力只在普通知识库列表、同租户知识库详情和部分资源 guard 中生效；一旦进入智能体的 KBSelectionMode=all 路径，多个入口都会直接改走“租户全量知识库”，绕过当前账号可见性控制。
3. 该问题不是单纯的前端展示问题，而是实际会影响运行时检索范围，至少覆盖：知识库列表、建议问题、知识搜索、Agent QA 运行时 KB 解析、IM `/search` 命令。
4. 当前“all 模式”的语义在不同入口之间本身也不一致：有的入口只看当前租户全量 KB，有的入口还会混入用户直接共享获得的 KB。这意味着即使只修一个 handler，整体行为仍然不一致。
5. 同租户知识库详情和部分资源访问 guard 目前仍然会走 KBVisibilityService，因此现状更接近“列表和检索越权，顶层详情不一定越权”。
6. 跨空间共享智能体当前被当成一条独立的读权限来源使用。如果要把“智能体权限 = 当前账号直连 KB 权限”贯彻到跨空间共享智能体，就不只是修 bug，而是要改变现有产品语义。

本轮建议分两步：

1. 先修同租户 / 当前账号场景下的 agent all 模式越权，把“智能体有效 KB 范围”收回到当前账号授权范围内。
2. 再单独决定是否要调整“共享智能体是否可以作为 KB 读取授权来源”这条产品语义，不建议和本轮一起混修。

## 3. 现状证据

### 3.1 当前账号的知识库权限基线已经存在

正常知识库列表在无 agent_id 时，已经明确走当前账号可见性过滤：

1. internal/handler/knowledgebase.go 的 ListKnowledgeBases 普通分支调用 `h.kbVisibility.ListAccessibleKBs(ctx, userID, currentTenantID, bypassVisibility)`。
2. internal/application/service/kb_visibility.go 再调用 repository 的 `ListAccessibleKBs`。
3. internal/application/repository/knowledgebase.go 的 `ListAccessibleKBs` 已按以下规则过滤：
   - global 或 legacy 空 visibility
   - org 且 organization_id 命中当前用户可读组织范围
   - private 且 created_by = 当前用户

这说明“账号看到哪些知识库”并不是未实现，而是已经有明确后端实现。

### 3.2 智能体知识库列表在 agent_id 分支直接绕过了 KBVisibilityService

internal/handler/knowledgebase.go 的 ListKnowledgeBases 在 `agent_id != ""` 时：

1. 先通过 `GetSharedAgentForUser` 校验能否使用该智能体。
2. 然后直接调用 `h.service.ListKnowledgeBasesByTenantID(ctx, sourceTenantID)` 取 source tenant 下全部知识库。
3. selected 模式只做 ID 白名单过滤。
4. all 模式只做 capability filter，不做当前账号可见性过滤。

这意味着：

1. 如果 sourceTenantID 恰好就是当前租户，那么 agent all 模式拿到的是“当前租户全部 KB”，不是“当前账号可读 KB”。
2. 这正对应了你描述的问题现象：账号自身有知识库权限控制，但智能体在 all 模式下没有继承这层约束。

### 3.3 Agent QA 运行时主链路也绕过了账号可见性控制

internal/application/service/session_knowledge_qa.go 的 `resolveKnowledgeBasesFromAgent` 是运行时核心解析入口。

当前 `KBSelectionMode == "all"` 时它会：

1. 直接调用 `s.knowledgeBaseService.ListKnowledgeBases(ctx)` 取得当前上下文租户的全量知识库。
2. 仅做工具能力过滤，不做当前账号可见性过滤。
3. 在“不是共享智能体”的情况下，还会额外把 `kbShareService.ListSharedKnowledgeBases(ctx, userID, tenantID)` 返回的共享 KB 混入结果。

这带来两个问题：

1. 同租户隐藏 KB 会进入智能体真实检索范围，不只是列表展示错误。
2. all 模式在运行时还会混入用户直接共享得到的 KB，但知识库列表 agent_id 分支又不会混入，前后语义已经不一致。

### 3.4 建议问题入口也复用了同样的越权逻辑

internal/application/service/custom_agent.go 的 GetSuggestedQuestions 在 `KBSelectionMode == "all"` 时：

1. 直接调用 `s.kbService.ListKnowledgeBases(ctx)`。
2. capability filter 后继续使用这些 KB 构造建议问题候选范围。
3. 同样会在某些分支下把 `ListSharedKnowledgeBases` 的结果混入。

因此建议问题不是“只读 UI 装饰”，而是另一个真实暴露越权 KB 范围的入口。

### 3.5 知识搜索入口同样存在 all 模式全量枚举

至少有两个知识搜索入口复用了相同问题：

1. internal/handler/knowledge.go 的 SearchKnowledge，在 agent_id 分支里 `mode=all` 时直接用 `ListKnowledgeBasesByTenantID(ctx, sourceTenantID)` 构建 scopes。
2. internal/im/cmd_search.go 的 `/search` 命令，在 `KBSelectionMode=all` 时直接 `c.kbService.ListKnowledgeBases(ctx)`。

这说明即使主聊天 UI 修好，如果命令入口不一起收口，系统仍然会保留另一组越权面。

### 3.6 信息展示命令也会泄漏不该暴露的 KB 名称

internal/im/cmd_info.go 在 `KBSelectionMode=all` 时，会直接 `ListKnowledgeBasesByTenantID(ctx, cmdCtx.TenantID)` 并输出名称列表。

这不一定直接泄露正文，但会泄露 KB 存在性和名称，同样属于权限范围扩大。

### 3.7 同租户知识库详情目前仍然是按 KBVisibilityService 拦截的

需要明确一个边界：当前“顶层知识库详情 / 顶层知识文件访问”并不是完全没有权限控制。

例如：

1. internal/handler/knowledgebase.go 的 validateAndGetKnowledgeBase 对同租户 KB 会先走 `CanManageKB / CanAccessKB`。
2. internal/handler/knowledge.go 的 resolveKBAccess 对同租户 KB 也优先走 `CanManageKB / CanAccessKB`。

这意味着当前问题更准确地说是：

1. 智能体范围解析和检索链路绕过了账号可见性。
2. 同租户的顶层详情页和部分资源路由没有同样放开。

所以它是“运行时越权 + 列表越权”，不完全等于“所有 KB 路由都没有权限”。

### 3.8 共享智能体当前确实被当成一条独立的 KB 读权限来源

这一点必须单独拿出来说清楚。

当前代码里，跨空间共享智能体不是简单的“复用当前账号原有 KB 权限”，而是被当成额外 viewer 权限来源：

1. internal/middleware/kb_access.go 的 `resolveSharedAgentAccess` 在 `agent_id` 命中且 `mode=all` 时，可直接对 source tenant 的 KB 授予 viewer。
2. internal/application/service/agent_share.go 的 `TenantCanAccessKBViaSomeSharedAgent` / `UserCanAccessKBViaSomeSharedAgent` 也在按“agent 可以访问这个 KB”做判定。

因此如果本轮目标只是修“当前账号在本租户内通过智能体越权看到全部 KB”，就不应顺手把共享智能体整套语义一起推翻。否则会影响“通过共享智能体可见”这条现有能力。

## 4. 根因归纳

根因不是一个 if 写错，而是三层问题叠加：

1. 语义错误
   - 当前代码把 `KBSelectionMode=all` 理解成“当前租户全部 KB”或“agent source tenant 全部 KB”。
   - 但从账号权限视角，正确语义应该是“当前账号有权使用的全部 KB”。

2. 能力过滤和权限过滤被混为一谈
   - 当前 all 模式大量代码只做 capability filter。
   - capability filter 只能解决“这个 KB 的类型 / 能力是否适配工具”，不能解决“当前账号能否看到这个 KB”。

3. 缺少统一的 Agent KB Scope Resolver
   - 同样的 all/selected/none 逻辑被复制在 handler、session service、custom agent service、IM command 等多个位置。
   - 每一处都各自拼一点规则，导致有的路径包含 shared KB，有的路径不包含，有的路径做 capability filter，有的路径不做可见性过滤。

## 5. 建议修正方案

## 5.1 修正原则

建议把“智能体有效知识库范围”统一定义为：

1. agent 配置范围
2. 与
3. 当前调用主体实际有权访问的 KB 范围
4. 的交集

其中“当前调用主体实际有权访问的 KB 范围”建议按两类来源拆开：

1. 同租户可见 KB
   - 走 `KBVisibilityService.ListAccessibleKBs`

2. 账号直接共享可见 KB
   - 走 `KBShareService.ListSharedKnowledgeBases`

这样才能同时满足：

1. 不再把同租户隐藏 KB 放进智能体 all 模式
2. 又不丢掉当前账号本来就被直接共享授权的 KB

## 5.2 推荐落地方式：新增统一的 Agent KB Scope Resolver

不建议继续在每个 handler 里临时补过滤。建议新增统一解析层，例如：

1. 新增文件
   - internal/application/service/agent_kb_scope.go

2. 提供统一方法
   - `ResolveKnowledgeBasesForPrincipal(...)`
   - `ResolveKnowledgeBaseIDsForPrincipal(...)`
   - 或直接返回 tenant-aware scopes

这个 resolver 至少要接收这些输入：

1. 当前 user_id
2. 当前 tenant_id
3. customAgent
4. 是否允许绕过同租户可见性（仅 super admin 等特殊场景）
5. 是否处于共享智能体场景

统一行为建议如下：

1. `none`
   - 返回空

2. `selected`
   - 先取当前主体真实可访问 KB 集合
   - 再和 `agent.Config.KnowledgeBases` 取交集

3. `all`
   - 直接返回当前主体真实可访问 KB 集合

4. capability filter
   - 在权限过滤之后再执行
   - 日志中区分“被权限过滤掉”和“被能力过滤掉”两个计数

## 5.3 必须替换的调用点

以下位置建议统一改用上面的 resolver，而不是继续直接 `ListKnowledgeBases/ListKnowledgeBasesByTenantID`：

1. internal/handler/knowledgebase.go
   - ListKnowledgeBases 的 agent_id 分支

2. internal/application/service/session_knowledge_qa.go
   - resolveKnowledgeBasesFromAgent

3. internal/application/service/custom_agent.go
   - GetSuggestedQuestions 的 all 模式解析

4. internal/handler/knowledge.go
   - SearchKnowledge 的 agent_id 分支

5. internal/im/cmd_search.go
   - `/search` 命令

6. internal/im/cmd_info.go
   - 智能体信息展示里的 KB 名称枚举

如果要进一步把“通过共享智能体可见”的空间视图也和最终语义对齐，还应额外审查：

7. internal/handler/organization.go
   - 组织 / 空间维度的 agent 关联 KB 统计与列表

## 5.4 推荐的分阶段实施顺序

### 第一阶段：只修当前账号在本租户内的 agent 越权

建议第一阶段只解决你当前看到的问题，不改变共享智能体既有产品语义：

1. own agent / same-tenant agent all 模式必须改成“当前账号可访问的全部 KB”。
2. 运行时检索、建议问题、知识搜索、IM 命令统一复用同一个 resolver。
3. 前端文案同步改成“全部可访问知识库”或“当前账号可访问的全部知识库”。

这一阶段的好处是：

1. 可以直接消除当前问题。
2. 不会误伤跨空间共享智能体“通过智能体可见”的既有能力。

### 第二阶段：单独决定是否收紧共享智能体的附加授权语义

如果后续产品结论是：

1. “共享智能体也不能把额外 KB 暴露给接收方”

那么才需要继续改这几处：

1. internal/middleware/kb_access.go
2. internal/application/service/agent_share.go
3. internal/handler/knowledgebase.go
4. internal/handler/knowledge.go

这一步会影响现有“通过共享智能体可见”能力，必须单独评审，不建议和第一阶段一起做。

## 6. 机会点

除了直接修 bug，本次还有几项很适合顺手收口的机会。

### 6.1 统一 all 模式语义，消除当前自相矛盾

当前 all 模式在不同位置至少有三种含义：

1. 当前租户全量 KB
2. source tenant 全量 KB
3. 当前租户全量 KB + 用户直接共享 KB

这是后续继续出权限问题的高风险点。建议统一收敛成单一语义，并在文档与前端文案中写死。

### 6.2 让前端文案与真实后端语义对齐

当前“全部知识库”的文案会让人自然理解成“空间内全部知识库”，但如果最终后端语义是“当前账号可访问的全部知识库”，那前端文案就应同步改成：

1. 全部可访问知识库
2. 当前账号可访问的全部知识库

至少这些位置需要同步：

1. frontend/src/views/agent/AgentEditorModal.vue
2. frontend/src/i18n/locales/zh-CN.ts

### 6.3 将权限过滤和能力过滤日志拆开

建议统一记录两类 drop count：

1. visibility_filtered_count
2. capability_filtered_count

这样后续排查“为什么这个 KB 不在智能体范围里”时，就能快速区分是权限原因还是工具能力原因。

### 6.4 禁止新的 agent 范围代码继续直接调用全量列表接口

建议加一个工程约束：

1. 只要代码语义是“给智能体计算可用 KB 范围”，就不允许直接调用 `ListKnowledgeBases` 或 `ListKnowledgeBasesByTenantID`。
2. 必须经过统一 resolver。

否则这个问题以后还会在新入口上重复出现。

## 7. 建议补充的回归测试

当前测试主要覆盖 capability filter，没有覆盖“all 模式 + 当前账号可见性”的权限收口。

建议至少补以下测试：

1. internal/handler/knowledgebase_pr5_list_test.go
   - 新增 `agent_id + mode=all + same-tenant visibility` 场景
   - 断言只返回当前账号可见 KB，不返回同租户隐藏 KB

2. internal/application/service/session_knowledge_qa_test.go
   - 覆盖 `resolveKnowledgeBasesFromAgent` 的 all 模式
   - 断言不会把同租户无权 KB 带入运行时 search targets

3. internal/application/service/custom_agent_suggested_questions_test.go
   - 在现有 capability filter 测试基础上增加 visibility filter 场景

4. internal/handler/knowledge.go 或对应 service test
   - 覆盖 SearchKnowledge(agent_id) 的 all 模式权限收口

5. internal/im/cmd_search.go / internal/im/cmd_info.go 对应测试
   - 防止命令入口继续枚举全量 KB 名称或全文搜索无权 KB

如果第二阶段要改共享智能体语义，还需要额外补：

6. internal/middleware/kb_access_test.go
   - 明确共享智能体是否仍然可以单独授予 viewer

## 8. 最终建议

如果按“智能体能看到的知识库应与当前账号权限保持一致”这个目标来审视当前实现，那么当前代码不能认为已经正确。

更准确的判断是：

1. 普通知识库权限控制已经存在。
2. 智能体 all 模式在多个入口绕过了这层控制。
3. 该问题已经影响到实际检索，而不是仅限于 UI 列表。
4. 当前还伴随 all 模式语义不一致的问题，必须通过统一 resolver 收口，不能只修一个 handler。

因此建议本轮实际落地目标收敛为：

1. 把智能体有效 KB 范围统一收敛为“agent 配置范围 ∩ 当前账号授权范围”。
2. 第一阶段优先修同租户 / 当前账号场景，不混改共享智能体附加授权语义。
3. 第二阶段再单独决定是否保留“通过共享智能体可见”作为独立授权来源。

这条收口路线风险最小，也最符合你当前反馈的问题现象。
