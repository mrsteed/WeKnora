# 20260819 mdev 分支权限主线同步方案

## 1. 文档目标

本文档用于指导新建 `mdev` 分支，并在最新 `upstream/main` 基线上，只同步以下本地能力：

1. 组织、空间、成员和权限链路。
2. 知识库与文档权限语义。
3. 智能体和 IM 的知识范围控制。
4. 本地品牌与用户管理定制。
5. 本地部署和运行脚本。

本方案明确排除长文档、导出和文档产物链路，目标不是把 `dev` 的全部本地能力搬到新分支，而是单独做一条“权限主线 + 知识库权限 + 智能体可见性”的最新上游整合分支。

## 4. 分支策略

### 4.1 为什么 `mdev` 必须从 `upstream/main` 起分支

建议直接执行：

```bash
git fetch origin --prune
git fetch upstream --prune
git checkout -b mdev upstream/main
```

原因如下：

1. 你要的是“最新上游代码 + 本地权限主线能力”，不是“当前 `dev` 减法裁剪版”。
2. 当前 `dev` 混有长文档、导出、品牌、运行脚本、知识库、权限等多条业务线，如果从 `dev` 起分支再删功能，反而更容易残留长文档链路。
3. `upstream/main` 当前已经是 `v0.7.2`，从它起分支可以最大化吸收上游最新结构和修复。

### 4.2 为什么不建议直接 merge `dev`

不建议执行：

```bash
git checkout -b mdev upstream/main
git merge dev
```

原因如下：

1. 这会把长文档、导出、文档产物、历史同步补丁一起带进来。
2. 你要保留的五类能力和不要保留的长文档能力，在当前 `dev` 中高度交织，merge 后再回删代价更高。
3. `mdev` 的目标是“权限主线专用最新分支”，不是 `dev` 的镜像。

### 4.3 推荐工作方式

`mdev` 建议采用“手工移植基础骨架 + 小粒度 cherry-pick 修复补丁”的混合方式：

1. 对基础权限骨架，优先按文件移植，不直接整提交 cherry-pick。
2. 对后期修复补丁，优先小粒度 cherry-pick。
3. 对混合提交，只移植其中与 `mdev` 目标一致的文件，避免整包带入聊天、长文档或导出逻辑。

3. 成员角色编辑是否联动空间权限。
4. 个人资料页修改密码。
5. 管理员重置成员密码，且不能错误重置自己。
6. 知识库列表是否只显示账号可见项。
7. 文档列表是否按“创建者/管理员/本人上传”控制编辑和处理操作。
8. Agent `all` 模式是否只使用当前账号可见知识库。
9. 建议问题、知识搜索、IM `/search`、IM `/info` 是否与同一套 KB scope 保持一致。
10. `scripts/dev.sh`、`docker-compose.dev.yml` 和启动期数据库报错是否仍符合本地运行习惯。

### 8.4 明确不测的链路

本轮 `mdev` 不以以下链路为验收项：

1. 长文档规划。
2. 文档产物生成。
3. PDF/Word 导出。
4. 文档翻译。

如果这些链路因上游最新代码而仍能运行，可视为附带结果，但不属于 `mdev` 首轮目标。

## 9. 推送策略

因为 `mdev` 是新分支，不需要像更新 `dev` 那样默认使用强推。

建议流程：

1. 新建分支后先推空分支：

```bash
git push -u origin mdev
```

2. 每个主题批次独立提交并推送：

```bash
git push origin mdev
```

3. 等 `mdev` 稳定后，再决定是否把其中一部分回流到 `dev`，或者长期把 `mdev` 作为权限主线实验分支。

## 10. 最终执行建议

本轮 `mdev` 同步建议可以浓缩为一句话：

以 `upstream/main@v0.7.2` 为干净基线，新建 `mdev`，只按主题移植“组织/空间/成员/权限 + 知识库权限 + 智能体与 IM 可见性 + 品牌与用户管理 + 本地运行脚本”，并显式排除长文档和导出链路。

落地时请遵循以下三条底线：

1. 不 merge 整个 `dev`。
2. 不把历史低编号迁移直接搬到 `mdev`。
3. 不把 `c3ce860d` 这类混合提交整体 cherry-pick 到 `mdev`。

如果按本方案执行，`mdev` 会成为一条更干净的“最新上游 + 权限主线本地能力”分支，后续也更适合继续围绕空间、组织、知识库和智能体权限可见性做迭代。
