# 组织人员管理与租户权限统一设计审查报告

## 1. 目标与结论摘要

本文聚焦回答三个问题：

1. 当前“组织人员管理权限”和“租户 / 空间级权限”在代码里分别是什么。
2. 当前知识库、智能体可见性到底依赖哪套权限。
3. 如果目标是支撑大型组织的树形部门人员管理，这两套权限是否可以统一；如果不能完全统一，应该如何最大限度整合。

先给结论：

### 1.1 当前实际存在三套权限/成员模型

当前代码里并不是两套，而是三套模型并存：

1. **租户 / 空间级 RBAC**
   - 数据源：`tenant_members`
   - 角色：`owner / admin / contributor / viewer`
   - 用途：租户级配置、模型管理、成员管理、API Principal、高敏系统操作

2. **组织树人员管理（部门树）**
   - 数据源：`organization_members_pre_plan3`
   - 角色：`admin / editor / viewer`
   - 维度：**user 级**
   - 用途：当前同租户内知识库、智能体的可见范围与组织树管理

3. **共享空间协作成员**
   - 数据源：`organization_tenant_members`
   - 角色：`admin / editor / viewer`（以及类型层还兼容 `contributor` / `owner`）
   - 维度：**tenant 级**
   - 用途：跨租户知识库/智能体共享、空间成员列表、空间加入/邀请/审批

### 1.2 当前知识库 / 智能体可见性，确实主要依赖“组织人员管理”

就**同租户内资源可见性**而言，当前实现确实主要依赖组织树人员管理：

- 知识库可见性：`internal/application/service/kb_visibility.go`
- 智能体可见性：`internal/application/service/agent_visibility.go`
- 两者都调用 `orgTreeService.GetUserOrganizations(...)`
- 该方法最终读的是 `organization_members_pre_plan3`（旧的 user 维度组织树成员表）

也就是说：

- **同租户内** KB / Agent 是否可见，主要取决于组织树成员关系。
- **跨租户** KB / Agent 共享访问，则取决于共享空间成员关系与共享表。

### 1.3 “完全统一成一套角色/一张成员表”不建议

如果你的目标是“树形组织级管理，用于大型组织的部门人员管理”，那么从代码设计角度：

- **不能把租户 / 空间级权限，和组织树部门权限，粗暴合并成同一套成员模型**。
- 原因不是技术做不到，而是它们解决的是**不同维度的问题**：
  - 租户 / 空间级权限：解决“谁能管理这整个空间的配置与基础设施”
  - 组织树权限：解决“谁在这个空间内部能看哪些部门资源、管哪些部门成员”
  - 共享空间协作权限：解决“不同空间之间如何协作共享资源”

所以，**不建议统一成一个表**，但**强烈建议统一成一个分层权限框架**。

### 1.4 推荐方向

推荐采用“三层统一、模型分离”的方案：

1. **租户 / 工作空间 RBAC**：保留，作为全局能力上限（capability ceiling）
2. **组织树 / 部门树权限**：升级为同租户内资源作用域的唯一权威来源
3. **共享空间权限**：保留为跨租户协作层，但从“组织”概念中剥离，避免与部门树混淆

一句话：

> **不要把三套模型合成一张表，但要把三套权限合并进一个统一的授权决策器。**

## 2. 当前代码中的三套权限模型

## 2.1 租户 / 空间级 RBAC

### 代码位置

- `internal/types/tenant_member.go`
- `internal/application/service/tenant_member.go`
- `internal/middleware/auth.go`
- `internal/middleware/rbac.go`
- `internal/router/rbac.go`

### 实际语义

当前 `tenant_members` 是系统里最稳定、最清晰的一套权限模型：

- `owner`
- `admin`
- `contributor`
- `viewer`

并且它已经有：

- 统一的角色等级：`viewer < contributor < admin < owner`
- 中间件守卫：`g.Viewer() / g.Contributor() / g.Admin() / g.Owner()`
- 鉴权上下文注入：`TenantRoleContextKey`

### 当前承载的能力

它负责的是“租户 / 空间作为一个完整工作区时，谁能做什么”：

- 成员管理
- 模型管理
- parser / storage / vector / MCP / websearch 等空间配置
- API Principal 配置
- 空间删除
- Owner 不可被最后移除等硬约束

### 结论

这套模型本质上是：

> **工作空间控制平面（control plane）权限**

它不适合直接替代部门树权限。

---

## 2.2 组织树人员管理（部门树）

### 代码位置

- `internal/application/service/org_tree.go`
- `internal/handler/org_tree.go`
- `internal/application/repository/organization.go`
  - `organization_members_pre_plan3`
  - `ListOrgTreeMembers`
  - `ListOrgTreeOrganizationsByUserID`
- `frontend/src/views/admin/*`

### 实际语义

当前组织树模型具有以下特征：

1. 使用 `organizations` 表中的树形字段：
   - `parent_id`
   - `path`
   - `level`
   - `sort_order`
   - `tenant_id`（`OrgTenantID`）

2. 成员关系存储在旧表：
   - `organization_members_pre_plan3`

3. 成员维度是 **user 级**，不是 tenant 级：
   - 一个组织节点下挂的是用户
   - 不适合表达“一个空间整体作为成员加入另一个空间”

4. 权限模型是局部硬编码：
   - `admin / editor / viewer`
   - 管理员对子树有继承管理能力

### 当前实际承载的职责

组织树现在并不只是一个“人员管理后台”，它已经被接进了资源可见性：

- 知识库可见性：`kb_visibility.go`
- 智能体可见性：`agent_visibility.go`

这意味着：

> **它已经是同租户内资源作用域（resource scope）的核心依赖。**

### 结论

如果你要做大型组织部门树，这一层才是正确的承载者。

但它目前还只是“半成品”：

- 角色语义不统一
- 仍使用旧表
- 管理能力与资源能力没有彻底分层

---

## 2.3 共享空间协作成员

### 代码位置

- `internal/application/service/organization.go`
- `internal/application/repository/organization.go`
  - `organization_tenant_members`
  - `ListMembers`
  - `GetMember`
- `internal/application/service/kbshare.go`
- `internal/application/service/agent_share.go`
- `frontend/src/views/organization/*`

### 实际语义

这套模型与组织树不同，它不是部门成员，而是：

> **“一个 tenant / workspace 作为协作主体加入某个共享空间”**

证据非常直接：

- Repository 层读写的是 `organization_tenant_members`
- 主身份字段是 `tenant_id`
- `representative_user_id` 只是展示用代表账号

这意味着：

- 它是 **tenant 级协作成员**
- 不是 **user 级部门人员成员**

### 当前职责

它负责的是：

- 共享空间成员列表
- 邀请 / 加入 / 审批
- 知识库共享到空间
- 智能体共享到空间
- 通过共享空间访问他人的 KB / Agent

### 结论

这套模型适合跨租户协作，不适合做大型组织内部部门树。

如果把它当部门树使用，会天然丢失：

- 部门内真实人员管理
- 用户多部门归属
- 部门管理员对子树授权
- 个人级资源权限

---

## 3. 当前 KB / Agent 可见性的真实依赖链

## 3.1 知识库可见性

### 关键代码

- `internal/application/service/kb_visibility.go`
- `internal/application/service/org_tree.go:GetUserOrganizations`
- `internal/application/repository/knowledgebase.go:ListAccessibleKBs`

### 当前链路

1. `kbVisibilityService.ListAccessibleKBs(...)`
2. 调用 `orgTreeService.GetUserOrganizations(userID, tenantID)`
3. 该方法读取 `organization_members_pre_plan3`
4. 拼出用户所在组织及其祖先/后代组织 ID 集合
5. Repository 层按以下条件过滤 KB：
   - `global`
   - `org AND organization_id IN orgIDs`
   - `private AND created_by = userID`

### 结论

当前同租户知识库可见性，**明确依赖组织树人员管理权限**。

---

## 3.2 智能体可见性

### 关键代码

- `internal/application/service/agent_visibility.go`
- `internal/application/service/org_tree.go:GetUserOrganizations`
- `internal/application/repository/custom_agent.go:ListAccessibleAgents`

### 当前链路

1. `agentVisibilityService.ListAccessibleAgents(...)`
2. 调用 `orgTreeService.GetUserOrganizations(userID, tenantID)`
3. 仍然读取 `organization_members_pre_plan3`
4. Repository 层按以下条件过滤 Agent：
   - `global`
   - `org AND organization_id IN orgIDs`
   - `private AND created_by = userID`

### 结论

当前同租户智能体可见性，也**明确依赖组织树人员管理权限**。

---

## 3.3 跨租户共享访问

### 知识库共享

关键代码：

- `internal/application/service/kbshare.go`
- `internal/application/repository/kbshare.go`

当前实现：

- 共享空间成员关系来自 `organization_tenant_members`
- `ListSharedKBsForTenant()` 明确按 `otm.tenant_id` 查询
- `CheckTenantKBPermission()` 对共享权限做裁剪

### 智能体共享

关键代码：

- `internal/application/service/agent_share.go`
- `internal/application/repository/agent_share.go`

当前实现：

- `ListSharedAgentsForTenant()` 明确按 `organization_tenant_members` 查询
- 跨空间共享使用的是 tenant 级身份
- 不是组织树的 user 级身份

### 结论

当前系统里：

- **同租户内资源可见性** → 组织树成员（旧 user 级）
- **跨租户共享访问** → 共享空间成员（tenant 级）

这正是当前模型分裂的核心事实。

## 4. 当前实现的主要设计差异与问题

## 4.1 同一个 `organizations` 表承载了两种完全不同的域模型

当前 `organizations` 同时被用作：

1. 组织树节点（有 `tenant_id`、`parent_id`、`path`）
2. 共享空间实体（跨租户协作容器）

这会导致：

- 名称上都叫 Organization
- 但语义完全不同
- 前后端页面、接口、文档、角色口径容易混淆

### 影响

- 开发者很难快速判断某个接口是“部门树”还是“共享空间”
- 新需求一来，容易把共享空间逻辑误接到部门树上
- UI 文案会不断出现“组织 / 空间 / 部门”互相串味

---

## 4.2 成员粒度不一致：一个是 user，一个是 tenant

| 模型 | 成员粒度 | 适合场景 |
|------|----------|----------|
| `organization_members_pre_plan3` | user | 同租户内部门人员管理 |
| `organization_tenant_members` | tenant | 跨租户共享协作 |

这两者都合理，但**不能混当一套权限模型**。

如果强行统一：

- 用 tenant 粒度做部门树，会丢失“人”的管理
- 用 user 粒度做跨租户共享，会失去“整个空间作为协作主体”的表达能力

---

## 4.3 角色集合不一致，且存在历史兼容混用

当前代码里同时存在：

- `TenantRole`: `owner/admin/contributor/viewer`
- `OrgMemberRole`: `owner/admin/contributor/editor/viewer`
- 其中 `editor` 与 `contributor` 在权限级别上被视作同级

结果：

- 类型层已经在试图统一
- 实际存量接口和页面仍大量使用 `editor`
- 语义没有完全收拢

这会导致：

- API 返回与前端显示不一致
- 不同页面对同一角色翻译不同
- “共享空间角色”和“租户角色”看起来像是一套，实际上不是

---

## 4.4 访问控制已经出现“同名角色，不同含义”

例如 `admin`：

- 在 `tenant_members` 里，表示当前空间管理权限
- 在组织树里，表示部门树节点管理员
- 在共享空间里，表示共享空间管理员

这三个 `admin` 不是一个意思：

- 管理空间配置
- 管理部门子树
- 管理共享协作空间

如果 UI 统一都显示“管理员”，但不标 scope，用户和开发者都会误判。

---

## 4.5 可见性与管理权限也没有统一成同一决策器

当前实现是分散的：

- KB 可见性：`kb_visibility.go`
- Agent 可见性：`agent_visibility.go`
- KB 分享权限：`kbshare.go`
- Agent 分享权限：`agent_share.go`
- 路由守卫：`rbac.go` + `kb_access.go`
- Handler 中仍有额外补判断

这会带来两个问题：

1. 同一操作在不同入口可能走不同判定链
2. 任何新的资源类型（数据源、工作流、报表）都要再复制一遍权限逻辑

---

## 4.6 当前代码中已有一些明显的语义不一致

### A. 同租户 KB 管理权限过宽

`internal/application/service/kb_visibility.go: CanManageKB`

对于 `org` 类型 KB，目前逻辑是：

- 用户只要是该组织成员，就可管理
- 并没有严格区分 `admin/editor/viewer`

这说明组织树角色虽然被拿来做可见性，但还没有真正被完整用于“资源写权限矩阵”。

### B. 跨租户 KB 共享权限与租户角色的裁剪关系不够清晰

`kbshare.go: CheckTenantKBPermission()` 当前做法是：

- 共享空间的 share permission 是一层
- 调用方当前租户的 `TenantRole` 又做了一层 cap
- 目前只对 `TenantRoleViewer` 做了明确降级

这说明“共享空间权限”和“租户 RBAC”已经发生了耦合，但规则并不透明。

### C. 通过共享智能体访问 KB 的路径与共享 KB 的裁剪规则不一致

`agent_share.go: TenantCanAccessKBViaSomeSharedAgent()` 的签名里带了 `callerTenantRole`
但当前实现根本没使用它。

这意味着：

- “通过共享 KB 访问知识库”和“通过共享 Agent 间接访问知识库”
- 现在并不是同一套授权规则

这是后续继续扩展时的高风险点。

---

## 4.7 历史设计已经出现明显漂移

从文档可以看到两次重要设计判断：

1. 早期组织树方案：
   - 结论是“不需要完整 RBAC，只要超管 + 组织角色”
2. 后续租户 RBAC 方案：
   - 已正式引入 `tenant_members` 四级角色
   - 并明确与共享空间“正交”

但当前代码层面没有做一次彻底的模型收束，于是形成了今天的局面：

- 文档口径 A：组织角色足够
- 文档口径 B：租户 RBAC + 共享空间正交
- 实现口径 C：组织树、共享空间、租户 RBAC 三层并行

这也是为什么现在做“统一”时，必须先做概念收口，而不是直接改表。

## 5. 是否能够统一？

## 5.1 结论：不能统一成“一张表 / 一套角色”，但可以统一成“一套授权架构”

### 不建议统一成一张成员表的原因

因为三者根本不是同一类问题：

| 维度 | 本质问题 |
|------|----------|
| 租户 / 空间级权限 | 这个空间的配置、模型、成员、API、基础设施谁能管 |
| 组织树权限 | 这个空间内部的部门层级、人员归属、资源作用域谁能看谁能管 |
| 共享空间权限 | 不同空间之间如何协作共享 |

如果统一成一张表，你会马上遇到：

- 一个用户在同一空间里可能属于多个部门节点，但 tenant role 只有一条
- 一个共享空间成员是 tenant，不是具体用户
- 一个部门管理员不等于空间管理员
- 一个空间管理员也不应该自动是所有部门管理员

所以，**成员表不能统一**。

### 但可以统一成一套分层授权框架

建议把权限统一成：

1. **Tenant Capability（能力上限）**
2. **Org Scope（组织树作用域）**
3. **Collaboration Context（共享空间协作上下文）**
4. **Resource Ownership（资源归属）**

这样统一的是“决策方式”，不是“数据结构”。

---

## 5.2 推荐的统一原则

### 原则 A：租户 / 空间级角色只做全局能力上限

它回答的是：

- 你在这个工作空间里，有没有资格做这类操作？

例如：

- `viewer`：只读
- `contributor`：能创建自己的 KB / Agent
- `admin`：能管理模型、向量库、MCP、成员等
- `owner`：能删空间、管高敏配置

它**不应该**负责回答：

- 你能看哪个部门的 KB
- 你能管哪个组织节点的成员

### 原则 B：组织树权限只做同租户内的资源作用域管理

它回答的是：

- 你在这个租户里，能访问哪些部门节点及其资源？

也就是：

- 用户属于哪些节点
- 节点管理员能否管理子树
- 某 KB / Agent / 数据源归属于哪个节点
- 节点成员是否可见/可编辑/可管理

### 原则 C：共享空间权限只做跨租户协作上下文

它回答的是：

- 别的空间共享给我的资源，我在协作上下文中能做什么？

它不应该承担：

- 部门树
- 空间内人员组织
- 租户级配置权限

## 6. 面向大型组织的推荐目标架构

如果你的目标是“大型组织的树形部门人员管理”，推荐的目标架构如下。

## 6.1 角色与作用域分层

### 第一层：工作空间 / 租户（Workspace / Tenant）

建议语义：

- 一个 tenant = 一个独立工作空间 / 业务域 / 公司级边界
- 它负责：
  - 数据隔离
  - 模型配置
  - 检索/解析/存储基础设施
  - 空间成员全局管理

这层权限继续使用：

- `owner/admin/contributor/viewer`

### 第二层：部门树（Department Tree / Org Tree）

建议语义：

- 一个 tenant 内有一棵组织树
- 节点表示部门 / 事业部 / 项目组 / 小组
- 成员是具体用户，不是 tenant

这层建议使用：

- `manager/editor/viewer`

如果短期不想改枚举，也可以先继续用：

- `admin/editor/viewer`

但 UI 必须明确标成：

- `部门管理员`
- 而不是泛化成“管理员”

### 第三层：共享空间（Collaboration Space）

建议语义：

- 仅用于跨租户协作
- 成员是 tenant / workspace
- 不是部门节点

这层继续使用：

- `admin/editor/viewer`

但在文案和 API 上建议统一命名为：

- `协作空间`
- 不再与部门树节点共用“组织”这一抽象名词

---

## 6.2 资源模型建议

所有同租户资源（KB / Agent / DataSource / Workflow / Prompt 等）建议都补齐统一作用域字段：

- `tenant_id`
- `org_node_id`
- `visibility_scope`
- `created_by`

推荐 `visibility_scope`：

- `private`
- `org`
- `tenant`
- `shared`

其中：

- `private`：仅创建者
- `org`：组织树节点作用域内可见
- `tenant`：租户内全体可见
- `shared`：通过共享空间对外协作

这样可以把当前 KB/Agent 两套实现统一到同一种作用域语言。

---

## 6.3 统一授权公式

### 同租户资源访问

建议统一为：

```text
Allow(op, resource, user) =
  TenantRoleAllows(op.kind)
  AND
  (
    IsResourceOwner(user, resource)
    OR
    OrgScopeAllows(user, resource.org_node_id, op.required_org_role)
    OR
    resource.visibility_scope == tenant AND op.is_read
  )
```

### 跨租户共享访问

建议统一为：

```text
AllowShared(op, sharedResource, callerWorkspace) =
  CollaborationSpaceAllows(callerWorkspace, share.permission, membership.role)
  AND
  SharedOperationPolicyAllows(op.kind, sharedResource.type)
```

这里建议明确一条产品规则：

> **共享空间的跨租户写操作应谨慎收敛，默认只读优先。**

原因：

- 大型组织内部部门管理应主要通过同租户组织树解决
- 共享空间更适合“协作引用”和“跨域协同”，不适合作为主写路径

如果要保留跨租户可写，也要明确：

- 哪些资源允许跨租户编辑
- 它是否还要受调用方本租户 role cap 影响
- 它与 source tenant 的 owner/admin 规则如何对齐

当前实现这部分规则并不统一，建议在重构时统一设计。

---

## 7. 推荐实施方案

## 7.1 推荐方案：不做表级硬统一，做“模型分拆 + 授权统一”

这是我认为最合理的方案。

### 方案核心

1. **保留 `tenant_members`**
   - 继续做工作空间全局权限

2. **把组织树升级为部门树的权威模型**
   - 用于大型组织内部人员与资源范围管理

3. **把共享空间从组织树概念中拆出去**
   - 在代码、API、文案、页面中与“部门树”彻底分离

4. **新增统一授权决策器**
   - 不再让每个 service / handler 自己拼权限

### 好处

- 符合大型组织的真实管理结构
- 与当前代码演进方向兼容
- 风险远小于强行把三套成员关系压成一套

---

## 7.2 如果短期不能拆表，如何最大限度整合

如果当前阶段不能做数据库大迁移，建议按“代码层整合优先”的方式推进。

### 第一阶段：先做概念和服务层拆分，不急着改表

即使底层表还没拆，也先把代码语义拆清楚：

- `TenantRBACService`
- `DepartmentTreeService`（封装 `organization_members_pre_plan3`）
- `CollaborationSpaceService`（封装 `organization_tenant_members`）
- `ResourceAccessResolver`

这样即使底层都还在 `organizations` 表里，业务代码也不再直接混用。

### 第二阶段：统一角色词汇和展示

- `tenant role` 明确叫：`空间角色` / `工作空间角色`
- `org tree role` 明确叫：`部门角色`
- `collaboration space role` 明确叫：`协作空间角色`

UI 上任何“管理员”都必须带 scope。

### 第三阶段：把资源可见性统一收口到 resolver

先不要大改表，而是先把以下散落逻辑统一：

- `kb_visibility.go`
- `agent_visibility.go`
- `kbshare.go`
- `agent_share.go`
- `kb_access.go`
- 各 handler 里的二次权限补判断

### 第四阶段：最后再做物理表拆分

等逻辑稳定后，再拆成：

- `org_nodes`
- `org_node_members`
- `collaboration_spaces`
- `collaboration_space_members`

这样迁移风险最低。

## 8. 具体实现计划

## Phase 0：术语和边界收口

目标：先让团队对三套模型的职责达成一致。

建议动作：

1. 在文档和代码注释中明确三类对象：
   - Tenant / Workspace
   - Department Tree / Org Tree
   - Collaboration Space
2. 前端菜单和页面标题改名：
   - `组织人员管理` → `部门与人员管理`
   - `Organization Settings` 中的成员页 → `共享空间成员`
3. 在 API 文档里补 scope 说明，避免所有“admin”都被误解成一类角色。

---

## Phase 1：新增统一授权决策器

目标：把分散在 service / handler / middleware 的权限逻辑统一到一个入口。

建议新增：

- `internal/application/service/access/tenant_capability_resolver.go`
- `internal/application/service/access/org_scope_resolver.go`
- `internal/application/service/access/collaboration_resolver.go`
- `internal/application/service/access/resource_access_resolver.go`

统一暴露接口，例如：

- `CanReadKB(...)`
- `CanWriteKB(...)`
- `CanManageKBShare(...)`
- `CanReadAgent(...)`
- `CanEditAgent(...)`

现有 `kb_visibility.go` / `agent_visibility.go` / `kb_access.go` 全改调该 resolver。

---

## Phase 2：组织树成为同租户资源作用域的唯一权威

目标：明确 KB / Agent / DataSource 等同租户可见性，都只认部门树。

建议动作：

1. `GetUserOrganizations()` 相关逻辑迁移到正式 `DepartmentScope` 抽象。
2. 修复当前同租户资源写权限过宽的问题：
   - 例如 `CanManageKB()` 不能再“只要是成员就可管理”。
3. 统一节点管理员对子树的继承规则。
4. 把 Agent 的 org 可见性与 KB 的 org 可见性收敛成同一套作用域模型。

---

## Phase 3：共享空间与部门树彻底分层

目标：共享空间只做跨租户协作，不再承载部门语义。

建议动作：

1. 代码包名、注释、文档、UI 文案逐步把 `Organization` 语义拆分成：
   - Department Tree
   - Collaboration Space
2. 共享空间成员页只展示 tenant 级成员，不再混入 user/owner 判定。
3. 明确共享空间的写权限策略：
   - 推荐默认只读
   - 可写作为特例单独设计

---

## Phase 4：数据模型拆分

目标：解决根上的“同一张 `organizations` 表承载两种域模型”的问题。

推荐拆分：

- `org_nodes`
- `org_node_members`
- `collaboration_spaces`
- `collaboration_space_members`

配套迁移：

1. 从 `organizations(tenant_id not null)` 回填 `org_nodes`
2. 从 `organization_members_pre_plan3` 回填 `org_node_members`
3. 从 `organizations(tenant_id is null or shared-space semantics)` 回填 `collaboration_spaces`
4. 从 `organization_tenant_members` 回填 `collaboration_space_members`

---

## Phase 5：UI 与产品能力收束

目标：让用户感知到的是一套清晰模型，而不是三套历史能力拼在一起。

建议动作：

1. 部门树：
   - 树结构
   - 部门成员
   - 部门管理员
   - 资源归属
2. 共享空间：
   - 跨空间协作
   - 共享 KB / Agent
   - 外部合作方或子公司访问
3. 空间设置：
   - 模型、MCP、存储、向量、解析、API
   - 与部门树彻底分开

---

## 9. 最终建议

### 9.1 如果你的目标是“大型组织的树形部门人员管理”

最合理的产品结构是：

- **一个 tenant / workspace = 一个组织或业务域的工作空间边界**
- **一个 org tree = 该工作空间内部的部门树**
- **一个 collaboration space = 与其他工作空间的协作层**

### 9.2 不推荐的方向

不推荐把：

- 租户角色
- 部门树角色
- 共享空间角色

强行统一成：

- 一张成员表
- 一套角色枚举
- 一套同名“管理员/所有者”展示

因为它们本来就不回答同一个问题。

### 9.3 推荐的统一目标

推荐统一的是：

1. **授权决策框架**
2. **资源作用域模型**
3. **页面与术语表达**

而不是表结构本身先统一。

一句话总结：

> **当前系统不适合把“组织人员管理权限”和“租户 / 空间级权限”硬并成一套；最合理的方案是保留三层模型，但把它们统一进同一套授权框架，并把部门树确立为大型组织内部资源作用域的唯一权威。**

---

## 10. 建议验收标准

完成整合后，至少满足以下标准：

1. 开发者能明确区分：
   - 空间角色
   - 部门角色
   - 协作空间角色
2. 同租户 KB / Agent 可见性只依赖部门树，不再混入共享空间成员逻辑。
3. 跨租户共享只依赖协作空间，不再混入部门树成员逻辑。
4. 所有资源访问都走统一 `ResourceAccessResolver`。
5. UI 上任何“管理员 / 所有者”都带 scope，不再出现语义混淆。
6. `organizations` 表的双重语义最终被拆分或严格隔离在代码层之后，再逐步拆分到物理表。
