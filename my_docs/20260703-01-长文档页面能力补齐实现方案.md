# 长文档页面能力补齐实现方案

## 1. 目标与约束

本文针对长文档模式页面补齐以下 5 项能力，并给出基于当前代码基线的可实施方案：

1. 导出各种格式的文档。
2. 查看版本链，并在右侧弹出基线版本列表，支持重新选择基线版本。
3. 查看完整文档，在章节扩写或局部修订后可直接合成并查看整文。
4. 设为基线，把当前版本切换为后续续写或修订的基线版本。
5. 在长文档规划过程中，结合当前工具调用展示规划中的文档大纲。

本方案遵循以下约束：

- 仅在长文档模式开启后做个性化页面定制，普通问答页不被污染。
- 复用当前仓库中已经存在的 artifact、版本链、导出和规划能力，不重建一套长文档引擎。
- 尽量把长文档专属逻辑收敛到独立文件，降低与主聊天页、主 Agent 展示组件的耦合，便于后续同步上游代码时直接拎走组件。
- 当前仓库版本为 `0.6.3`，并存在 `v0.6.1` tag。审查结果表明，更值得复用的是当前代码基线中已经沉淀但尚未装配完成的能力，而不是简单回滚到 `v0.6.1` 页面代码。

## 3. 审查结论

结论先行：

当前版本不是“完全没有这 5 个功能”，而是“后端能力已基本具备，前端状态层也已经做了一半，但页面装配层断裂，导致用户看不到或点不到”。因此，本次最合理的策略不是大改协议，而是：

- 前端补齐长文档专属组件装配。
- 后端只做两个必要补强：版本链查询完整性、规划大纲历史回放一致性。

### 3.1 后端已有能力

#### 3.1.1 文档 artifact 与版本链已经存在

当前后端已经具备完整的长文档版本化基础设施：

- `chat_document_artifact` 已经承载文档快照、父版本、版本号、状态、质量问题、能否继续/修订/设为基线等能力位。
- `internal/types/chat_document_artifact.go` 已定义：
  - `can_continue`
  - `can_manual_continue`
  - `can_manual_revise`
  - `can_use_as_base`
  - `can_view`
  - `document_generation_status`
  - `continuation_context_mode`
- `internal/application/service/chat_document_artifact.go` 已负责：
  - 根据 assistant 消息注册 artifact
  - 按 continue/revise 合并快照
  - 生成质量问题与用户提示
  - 计算派生能力位

这说明：设为基线、版本链、多轮修订，本质上已经有统一后端锚点，不需要新增表。

#### 3.1.2 Artifact API 已经完整

`internal/handler/session/chat_document_artifact.go` 已提供：

- 按会话列出 artifact
- 获取最新 artifact
- 获取单个 artifact 详情
- 获取某个 artifact 的版本链

`frontend/src/api/chat/index.ts` 已对应封装：

- `getLatestChatDocumentArtifact`
- `getChatDocumentArtifacts`
- `getChatDocumentArtifact`
- `getChatDocumentArtifactRevisions`

因此，版本链抽屉和“查看全文时按 ID 拉整文快照”的接口基础已经具备。

#### 3.1.3 完整文档交付链路已经存在

当前 complete 事件已经支持两种完整文档交付模式：

- `inline_snapshot`：快照较小时直接随 complete 事件返回整文。
- `fetch_artifact_snapshot`：快照较大时仅返回 artifact ID，前端再调用 `getChatDocumentArtifact` 拉取 `content_snapshot`。

这条能力出现在：

- `internal/handler/session/qa.go`
- `internal/handler/session/stream.go`
- `internal/handler/session/agent_stream_handler.go`

这说明“查看完整文档”不是后端缺能力，而是前端没有把这条能力稳定地挂到页面入口上。

#### 3.1.4 导出接口已经支持 4 种格式

`internal/handler/export.go` 已经提供统一导出能力：

- Markdown
- PDF
- DOCX
- XLSX

同时 `frontend/src/utils/exportUtils.ts` 已经封装：

- 导出能力探测
- 调用统一后端导出接口
- 文件名生成
- 附加知识库引用附录

因此，导出不需要后端重做，只需要把长文档 artifact 入口接到现有 `ExportDropdown`。

#### 3.1.5 规划大纲事件已经从后端发出来了

`internal/application/service/session_agent_qa.go` 中的 `PublishOutline` 已经会发送独立的 synthetic planning thought，且带结构化 `outline` 元数据。

`internal/handler/session/agent_stream_handler.go` 也已经把以下元数据透传到前端 SSE：

- `stage`
- `synthetic`
- `outline`
- `section_current`
- `section_total`
- `section_title`

这说明“规划大纲”不是后端没发，而是前端主展示组件没有把它独立收口为用户可见的大纲卡片。

### 3.2 前端已有能力

#### 3.2.1 chat/index.vue 已经有 artifact 状态机

`frontend/src/views/chat/index.vue` 已经维护了大量长文档状态：

- `chatDocumentArtifacts`
- `selectedBaseArtifact`
- `selectedBaseArtifactDisplayLocked`
- `artifactRevisionDrawerVisible`
- `artifactRevisionList`
- `artifactRevisionAnchor`
- `ensureMessageFinalDocumentContent`
- `useArtifactAsBase`
- `clearSelectedBaseArtifact`
- `handleArtifactDisplayUpdate`
- `openArtifactRevisionDrawer`

说明当前页面并非没有长文档状态，而是状态已经堆在 `chat/index.vue`，但没有完整渲染层承接。

#### 3.2.2 ChatDocumentArtifactCard.vue 已经具备目标交互

`frontend/src/views/chat/components/ChatDocumentArtifactCard.vue` 已经支持：

- 版本号与状态展示
- `ExportDropdown`
- 查看版本链
- 查看全文 / 查看修改内容切换
- 设为基线 / 取消基线
- 完整文档预览

这个组件基本就是本次需求中最需要的 UI 载体。

但问题在于：当前仓库中没有任何地方实际引用它。

#### 3.2.3 planningOutline 工具与测试已经存在

`frontend/src/views/chat/utils/planningOutline.js` 已经实现：

- 从 thinking 文本提取大纲
- 从 structured outline 元数据提取大纲
- 区分 base_document 与 generated_plan
- 在 synthetic planning thought 中做 Markdown fallback

同时存在对应测试 `frontend/src/views/chat/__tests__/planningOutline.test.js`。

这说明规划大纲的前端解析工具已经基本成型，只差接到长文档展示面板。

### 3.3 当前前端的关键断点

当前页面侧最大的问题不是缺逻辑，而是有几处明确的“断线”：

#### 3.3.1 ChatDocumentArtifactCard 组件完全未挂载

代码中存在 `ChatDocumentArtifactCard.vue`，但仓库内没有任何引用。这意味着：

- 导出入口没有落到长文档版本卡片上。
- 查看版本链按钮没有落到消息区。
- 查看全文 / 查看修改内容没有页面承接。
- 设为基线按钮没有统一的消息级入口。

#### 3.3.2 chat/index.vue 传了事件，但 botmsg.vue 没有接也没有转发

`chat/index.vue` 当前把以下内容传给 `botmsg`：

- `selectedArtifactId`
- `@view-artifact-revisions`
- `@use-artifact-as-base`
- `@clear-artifact-base`
- `@artifact-display-update`

但 `botmsg.vue`：

- 没有声明 `selectedArtifactId` 这个 prop
- 没有声明上述事件 emit
- 也没有挂载 `ChatDocumentArtifactCard`

这意味着当前这一层是“死线”，上层状态再完整也不会在页面生效。

#### 3.3.3 查看全文状态只在状态层存在，没有渲染层消费

`chat/index.vue` 已经在切换：

- `message.final_document_content`
- `message.document_display_mode = 'full' | 'delta'`

但仓库中真正消费这些状态的组件并不存在。当前这两个字段主要只被：

- `exportUtils.ts`
- 历史重建逻辑

使用，而不是实际页面展示。

因此，“查看全文”在当前版本里是半实现状态。

#### 3.3.4 AgentStreamDisplay 并没有把 planning outline 收口成独立面板

`AgentStreamDisplay.vue` 当前主要做：

- 工具调用树
- thinking 合并
- answer 展示

但没有系统使用 `planningOutline.js` 中的工具去构造“规划大纲卡片”。

结果就是：

- 后端发了 `outline` 元数据
- 前端也有 outline 解析工具
- 但页面上只剩零散步骤文本，没有稳定可见的文档规划大纲

### 3.4 当前后端仍需补强的 2 个点

#### 3.4.1 版本链查询现在有 200 条上限风险

`internal/application/service/chat_document_artifact.go` 的 `ListRevisions` 当前做法是：

- 先 `ListBySession(sessionID, 200)`
- 再在内存中过滤父子链

这对“多轮长文档修订”是不稳的：

- 当同一会话 artifact 超过 200 条时，版本链会被截断。
- 用户越频繁使用“继续生成”“局部修订”“再设为基线”，这个风险越大。

因此，版本链查询需要改成真正的链式查询，不能依赖会话前 200 条快照。

#### 3.4.2 规划大纲的历史回放还不稳定

当前历史消息重建时，`chat/index.vue` 主要通过：

- `item.final_document_content`
- `item.chat_document_artifact?.content_snapshot`
- `item.content`

反向解析一个 outline。

这有两个问题：

1. 它只能推断最终正文结构，不一定等于规划期真实大纲。
2. 如果规划期有子章节、阶段性标题或生成期删改，刷新后还原不精确。

因此，规划大纲历史回放需要优先使用后端的结构化 outline，而不是只从最终正文猜。

## 4. 需求映射与处理结论

| 需求 | 当前状态 | 处理结论 |
| --- | --- | --- |
| 导出各种格式文档 | 后端接口与前端导出工具都已具备 | 前端挂载 artifact 卡片即可，无需新协议 |
| 查看版本链与重选基线 | API 与基础抽屉已存在，但 UI 简陋，且链路受 200 条上限影响 | 前端重构版本链抽屉，后端改链式查询 |
| 查看完整文档 | complete payload 与按 artifact 拉快照已存在，但页面无稳定展示入口 | 复用现有完整文档获取逻辑，补齐展示层 |
| 设为基线 | 状态管理与 `base_artifact_id` 请求协议已存在 | 挂载页面入口并抽离成独立 composable |
| 展示规划大纲 | 后端 outline thought 与前端解析工具都在，但没渲染 | 新增长文档规划面板，并补历史回放数据源 |

## 5. 推荐总体方案

### 5.1 设计原则

1. 长文档专属 UI 只在结构化信号命中时启用，不再依赖自然语言正则控制页面显示。
2. 优先复用现有 artifact、revision、export、outline 协议，不新增平行 API。
3. 长文档页面能力收敛到独立目录，主聊天页只保留接线与状态注入职责。
4. `AgentStreamDisplay.vue` 保持通用工具流展示职责，不把所有长文档逻辑塞回去。

### 5.2 推荐前端结构拆分

建议新增独立目录：

```text
frontend/src/views/chat/long-document/
  useLongDocumentArtifacts.ts
  useLongDocumentPlanning.ts
  longDocumentTypes.ts
  components/
    LongDocumentMessageEnhancements.vue
    LongDocumentOutlinePanel.vue
    LongDocumentRevisionDrawer.vue
    LongDocumentBaselineBanner.vue
```

同时复用现有组件：

- `frontend/src/views/chat/components/ChatDocumentArtifactCard.vue`
- `frontend/src/views/chat/components/ExportDropdown.vue`

#### 5.2.1 useLongDocumentArtifacts.ts

职责：

- 从 `chat/index.vue` 中迁移以下逻辑：
  - artifact 归一化
  - latest/base 选择
  - `ensureMessageFinalDocumentContent`
  - `useArtifactAsBase`
  - `clearSelectedBaseArtifact`
  - `openArtifactRevisionDrawer`
  - `handleArtifactDisplayUpdate`
- 向页面输出一个稳定的长文档会话状态对象。

价值：

- 把当前堆在 `chat/index.vue` 的长文档状态机抽出来。
- 后续同步时只需要保留一个 composable 接口，不需要在主页面反复手改。

#### 5.2.2 useLongDocumentPlanning.ts

职责：

- 直接消费 `session.agentEventStream`。
- 复用 `planningOutline.js` 从以下来源归一化大纲：
  - thinking 事件中的 structured outline
  - complete 事件中的 outline / planning_outline
  - 历史消息返回的 planning outline
  - 最终正文 fallback
- 输出一个稳定的：
  - `planningOutline`
  - `planningStage`
  - `planningVisible`
  - `isPlanningLive`

价值：

- 避免把大纲解析再次塞进 `AgentStreamDisplay.vue`。
- 后续无论页面把大纲展示在消息上方、消息下方还是侧面板，都能直接复用。

#### 5.2.3 LongDocumentMessageEnhancements.vue

建议挂载位置：`botmsg.vue`，位于 `AgentStreamDisplay` 附近。

职责：

- 判断当前 assistant 消息是否属于长文档能力范围。
- 在消息区挂载：
  - `LongDocumentOutlinePanel`
  - `ChatDocumentArtifactCard`
- 统一向上抛出：
  - 查看版本链
  - 设为基线
  - 取消基线
  - 查看全文 / 查看修改内容

价值：

- 让长文档消息的 UI 增强与普通 botmsg 分离。
- 修复当前 `chat/index.vue -> botmsg.vue` 的死线问题。

#### 5.2.4 LongDocumentRevisionDrawer.vue

职责：

- 右侧版本链列表展示。
- 标识：
  - 当前版本
  - 当前基线
  - 最新版本
  - 状态标签
- 支持动作：
  - 设为基线
  - 查看全文
  - 导出

建议保留在 `chat/index.vue` 这一层挂载，因为它是跨消息共享抽屉。

#### 5.2.5 LongDocumentBaselineBanner.vue

把当前 `chat/index.vue` 中的基线横幅独立出去，避免主页面继续膨胀。

职责：

- 显示当前自动基线 / 手动基线
- 提示“已锁定手动基线，最新版本为 Vx”
- 支持取消锁定

### 5.3 推荐后端处理策略

后端不建议新开一套“长文档页面专用接口”，而应做最小补强。

#### 5.3.1 保留现有接口不变

以下接口建议继续复用：

- `GET /api/v1/chat-document-artifacts`
- `GET /api/v1/chat-document-artifacts/latest`
- `GET /api/v1/chat-document-artifacts/:id`
- `GET /api/v1/chat-document-artifacts/:id/revisions`
- `POST /api/v1/export/document`
- SSE complete payload 中的：
  - `chat_document_artifact`
  - `final_document_mode`
  - `final_document_artifact_id`
  - `document_generation_status`

#### 5.3.2 必做补强一：版本链改成真正链式查询

当前 `ListRevisions` 不能再基于 `ListBySession(..., 200)` 过滤。

推荐实现：

1. 在 repository 层新增“按 artifact 回溯根 + 按根查整链”的专用方法。
2. 如果当前 ORM 不方便一次查整棵链，可先：
   - 递归向上找 root
   - 再通过递归 CTE 或循环按 `parent_artifact_id` 找全部子孙
3. 对外仍返回当前的数据结构，不破坏前端 API。

这样可以确保“多轮长文档修订”不会在版本链展示时丢版本。

#### 5.3.3 必做补强二：历史消息返回稳定的 planning outline

推荐让历史加载接口中的 assistant 消息带上结构化规划大纲，来源顺序如下：

1. 当前轮 complete payload / message extra 中已有的 `outline` 或 `planning_outline`
2. 若消息归属于长文档 generation run，则优先读取 `chat_document_generation_runs.outline_json`
3. 再退回到最终正文反向解析

这样可以解决：

- 刷新页面后规划大纲丢失
- 当前仅凭最终正文反推，导致规划结果与实际展示不一致

注意：这里优先复用已有的 `outline_json` 存储，不建议为此新增数据表或迁移。

#### 5.3.4 建议补强：统一规划大纲字段命名

当前系统中可能出现：

- `outline`
- `outline_role`
- `planning_outline`

建议统一成：

- `planning_outline`：本轮生成规划大纲
- `outline_role`：`generated_plan` / `base_document`

兼容策略：

- SSE 与历史消息都允许保留现有 `outline`，但前端内部统一先读 `planning_outline`，再 fallback 到 `outline`。

## 6. 各需求的具体落地方式

### 6.1 需求一：导出各种格式的文档

#### 当前结论

- 后端导出能力已完整。
- 前端导出能力已完整。
- 缺的是长文档页面上的 artifact 入口。

#### 推荐实现

1. 在 `LongDocumentMessageEnhancements.vue` 中挂载 `ChatDocumentArtifactCard`。
2. 直接复用 `ChatDocumentArtifactCard` 里的 `ExportDropdown`。
3. `previewContent` 优先级：
   - `message.final_document_content`
   - `artifact.content_snapshot`
   - `message.content`
4. 导出内容复用 `resolveChatExportContent`，继续自动拼接知识库引用附录。

#### 是否需要后端改动

不需要。

### 6.2 需求二：查看版本链并重选基线

#### 当前结论

- 右侧 drawer 基础结构已存在。
- 但当前只是一份简单列表，没有真正形成“长文档工作区”的版本选择体验。
- 后端版本链接口在多轮场景下存在 200 条截断风险。

#### 推荐实现

1. 新增 `LongDocumentRevisionDrawer.vue`，替代当前 `chat/index.vue` 中内联的简陋 drawer 模板。
2. drawer 每项至少显示：
   - 标题
   - Vx 版本号
   - create / continue / revise 操作类型
   - 状态标签
   - 更新时间
   - 是否为当前基线
   - 是否为当前查看版本
3. 每项动作至少支持：
   - 设为基线
   - 查看全文
   - 导出
4. 当前手动锁定基线时，顶部基线横幅继续提示“最新版本已推进到 Vx”。

#### 是否需要后端改动

需要，且是必要改动：

- 版本链查询必须改成真正链式查询，避免只看前 200 条 artifact。

### 6.3 需求三：查看完整文档

#### 当前结论

- 完整文档获取协议已经存在。
- 前端也已经实现了 `ensureMessageFinalDocumentContent`。
- 但它目前没有被真正挂到消息卡片或版本链抽屉上。

#### 推荐实现

1. 保留现有 `inline_snapshot / fetch_artifact_snapshot` 协议。
2. `ChatDocumentArtifactCard` 启用：
   - `documentDisplayMode = full | delta`
   - `previewContent`
   - `toggle-document-display`
3. `handleArtifactDisplayUpdate` 继续使用当前逻辑：
   - `full` 时先懒加载完整快照
   - 成功后把 `message.document_display_mode` 切到 `full`
   - `delta` 时切回本轮修改内容
4. 版本链 drawer 里点击“查看全文”时：
   - 把该版本 artifact 作为当前展示 artifact
   - 拉取其 `content_snapshot`
   - 在消息增强区展开整文预览

#### 是否需要后端改动

原则上不需要。

只要 artifact 详情接口继续能返回完整 `content_snapshot` 即可。

### 6.4 需求四：设为基线

#### 当前结论

- `useArtifactAsBase` 已存在。
- `base_artifact_id` 也已经能通过 `startStream` 传给后端。
- 当前问题仍然是页面入口缺失和事件没接线。

#### 推荐实现

1. 在 `ChatDocumentArtifactCard` 中启用“设为基线”。
2. 在 `LongDocumentRevisionDrawer.vue` 中也提供同名动作。
3. 顶部 `LongDocumentBaselineBanner.vue` 统一展示当前基线状态。
4. 续写或修订发起时不再做额外 UI 推断，直接复用已有 `base_artifact_id` 请求协议。

#### 是否需要后端改动

不需要。

### 6.5 需求五：展示规划中的文档大纲

#### 当前结论

- 后端 planning thought 已发出。
- 前端 outline 解析工具已存在。
- 主展示组件没有把它变成稳定面板。

#### 推荐实现

1. 新增 `LongDocumentOutlinePanel.vue`。
2. 由 `useLongDocumentPlanning.ts` 统一从以下来源提取大纲：
   - 正在 streaming 的 `thinking` 事件 `outline`
   - complete 事件中的 `planning_outline` / `outline`
   - 历史消息的结构化 planning outline
   - 最终正文 fallback
3. 展示内容建议包含：
   - 文档标题
   - H2 章节列表
   - 当前阶段状态：规划中 / 已完成规划 / 正在写作
   - 当前正在生成的章节（如果后端透出了 `section_current/section_total/section_title`）
4. 展示位置建议：
   - 与当前工具调用组件同区域出现
   - 但作为独立卡片呈现，不混入工具调用树条目中

#### 是否需要后端改动

建议补一个历史规划大纲回放字段，但实时链路本身已经足够。

## 7. 长文档页面激活判定

不建议继续用自然语言正则决定页面是否进入长文档定制视图。

建议统一改成“后端单一显式信号激活”：

- 后端对当前 assistant 消息或当前流式回合统一下发 `long_document_enabled=true|false`。
- 前端 `LongDocumentMessageEnhancements` 只读取这一个字段，不再自己拼装 `artifact / document_generation_status / generation_run_id / planning stage / request output mode` 等条件。
- 页面是否启用长文档专属 UI，由后端权威判断决定；前端只负责消费结果。

### 7.1 后端信号要求

`long_document_enabled=true` 应覆盖以下几类后端已确认属于长文档专属工作区的场景：

1. 完整长文档生成。
2. 基于 artifact 的继续生成。
3. 基于 artifact 的文档修订。
4. 长文档规划阶段已经开始，且当前轮将进入长文档编排。

`long_document_enabled=false` 时，页面保持普通聊天展示，不启用长文档专属 UI。

### 7.2 信号下发位置

为保证实时与刷新后一致，后端至少需要在以下位置下发同名字段：

1. 流式 thought / progress 事件。
2. 流式 complete 事件。
3. artifact 元数据。
4. 历史消息恢复链路，或能在历史恢复后稳定附着到消息上的后端返回对象。

### 7.3 前端执行原则

前端不再做“是否长文档”的多条件推断，只执行以下逻辑：

1. `session.long_document_enabled === true`：挂载 `LongDocumentMessageEnhancements`。
2. 其他情况：按普通聊天消息展示。

## 8. 推荐实施步骤

### P0：先把现有能力接上线

目标：最快让用户看到导出、版本链、查看全文、设为基线。

1. 后端新增统一显式信号 `long_document_enabled`，并下发到流式事件与 artifact 元数据。
2. 新建 `useLongDocumentArtifacts.ts`，把 `chat/index.vue` 中的 artifact 状态逻辑抽出。
3. 在 `botmsg.vue` 中挂载 `LongDocumentMessageEnhancements.vue`。
4. 在 `LongDocumentMessageEnhancements.vue` 中实际引用 `ChatDocumentArtifactCard.vue`。
5. 打通 `view-artifact-revisions`、`use-as-base`、`clear-base`、`toggle-document-display` 事件。
6. 把当前内联版本链 drawer 抽成 `LongDocumentRevisionDrawer.vue`。

交付结果：

- 页面上能看到文档版本卡片。
- 能导出。
- 能查看版本链。
- 能设为基线。
- 能查看全文。

### P1：补齐规划大纲面板

目标：让长文档规划过程可视化。

1. 新建 `useLongDocumentPlanning.ts`。
2. 新建 `LongDocumentOutlinePanel.vue`。
3. 仅在 `session.long_document_enabled === true` 时启用规划面板。
4. 用 `planningOutline.js` 直接从 `session.agentEventStream` 提取规划大纲。
5. 后端在 planning thought 中同步下发 `long_document_enabled=true`，确保首个规划事件即可激活页面。
6. 规划完成后保留大纲卡片，不因工具步骤折叠而丢失。
7. 历史消息优先使用结构化 planning outline 回放。

交付结果：

- 规划阶段能看到完整大纲，而不只是“已识别 N 个章节”。
- 刷新页面后仍能恢复大纲展示。

### P2：做后端补强与收敛

目标：解决多轮场景的稳定性和后续同步成本。

1. 改造 `ListRevisions`，去掉 200 条限制带来的链路截断风险。
2. 历史消息返回稳定的 `planning_outline`。
3. 统一 `outline / planning_outline / outline_role` 命名策略。
4. 如有必要，把 `LongDocumentBaselineBanner` 也独立抽出。

交付结果：

- 多轮修订的版本链完整可见。
- 历史回放稳定。
- 长文档页面能力集中在独立目录，可直接迁移与同步。

## 11. 风险与规避

### 11.1 风险一：把长文档逻辑继续堆回 chat/index.vue

风险：

- 主页面继续膨胀
- 与上游同步冲突增加

规避：

- 先抽 composable，再挂独立组件。

### 11.2 风险二：继续用自然语言正则判定是否显示长文档 UI

风险：

- 普通问答误触发长文档页面
- 数据库问答或短回答也被错误挂上文档卡片

规避：

- 统一以 artifact / generation status / planning outline 等结构化信号作为激活条件。

### 11.3 风险三：大版本链截断

风险：

- 多轮修订时看不到完整历史

规避：

- 后端把版本链查询改成真正链式查询。

### 11.4 风险四：刷新后规划大纲丢失

风险：

- 用户只能在实时生成期看到大纲，刷新后体验断裂

规避：

- 历史消息返回结构化 planning outline，前端优先用结构化数据恢复。

## 12. 最终建议

本次需求不建议按“新开页面 + 新开接口 + 新开数据库结构”的方式实现。最合理的落地路径是：

1. 以前端装配层补齐为主。
2. 以后端版本链查询与规划大纲回放补强为辅。
3. 把所有长文档专属逻辑收敛到独立目录和 composable。

这样可以同时满足：

- 需求完整落地
- 与当前主线版本低耦合
- 后续同步上游时改动面可控
- 已有长文档协议与 artifact-first 设计不被推翻

从实施优先级看，建议先做 P0 和 P1，先把用户可见能力补齐，再做 P2 的后端完整性收口。
