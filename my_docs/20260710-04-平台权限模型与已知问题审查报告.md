## 2. 当前整改基线

本轮整改以**当前代码与 `main` 分支保持一致**为前提，不引入新的平台权限模型。

当前基线如下：

1. `main` 分支仍保留 `is_system_admin` 权限控制概念。
2. 因此本轮整改**不删除 `is_system_admin` 概念，也不把它从文档和设计中直接抹去**。
3. 平台管理员在当前基线下仍是组合语义：
   - `is_system_admin`
   - `is_super_admin`
   - `can_access_all_tenants`
4. 但本轮整改要做的是：
   - 收口这些字段的职责边界
   - 修正错误的数据归属
   - 消除创建空间入口与 private 资源可见性上的已知问题

一句话：

> 本轮不是“删除平台兼容概念”，而是“在保持与 main 一致的前提下，把当前权限链和数据清理到可解释、可维护、可验证”。

## 3. 已确认问题

## 3.1 平台级权限概念混用

当前系统同时使用以下平台相关字段：

1. `users.is_system_admin`
2. `users.is_super_admin`
3. `users.can_access_all_tenants`

问题：

1. 不同代码路径对这三个字段的使用方式不一致。
2. 一部分能力看 `is_system_admin || is_super_admin`。
3. 一部分能力只看 `can_access_all_tenants`。
4. 一部分能力看三者任意一个为真。

影响：

1. 平台管理员的真实权限边界不清晰。
2. 创建空间、跨空间访问、private 资源绕过等行为容易出现前后端不一致。
3. 文档、数据库字段与运行时语义容易漂移。

整改方向：

1. 保持 `main` 兼容，不删概念。
2. 统一平台管理员 helper 和展示口径。
3. 将 `can_access_all_tenants` 明确收口为“跨空间运营能力”，不再让前端单独把它误当成唯一平台管理员判据。

---

## 3.2 空间角色与组织角色边界不清

当前系统同时存在：

1. 空间级角色：`tenant_members.viewer / contributor / admin / owner`
2. 组织树角色：`organization_members_pre_plan3.admin / editor / viewer`

问题：

1. 一些历史数据把“子组织管理员”提升成了空间 `admin`。
2. 运行时某些显示逻辑又只把 `owner` 当作根层管理者。
3. 同一个“管理员”称谓在空间级与组织级上语义不同，但界面和数据层没有完全区分。

影响：

1. 子组织管理员可能获得超出预期的空间权限。
2. 空间成员列表、组织成员列表与实际职责边界不完全一致。
3. 用户很难从界面理解自己到底是在扮演空间管理员还是子组织管理员。

整改方向：

1. 空间 `admin` 只代表租户控制面管理员。
2. 组织树 `admin` 只代表组织域管理员。
3. 历史被膨胀的 `tenant_members.admin` 行需要按业务逐个回收。

---

## 3.3 private 资源可见性受平台兼容字段影响

问题：

1. 同租户 `private` 知识库与智能体当前不仅允许创建者本人访问。
2. 平台兼容字段也可能触发 private 读权限绕过。

影响：

1. 空间拥有者或空间管理员可能因为平台字段而误看见他人私有资源。
2. 这会直接破坏“仅自己可见”的产品语义。

已知案例：

1. `hlsa` 被期望为“空间拥有者/空间管理员”，但其账号同时带有平台兼容字段。
2. 这会让问题排查变复杂：到底是空间角色越权，还是平台字段越权。

整改方向：

1. private 读写边界与平台管理员 helper 对齐。
2. space owner / space admin 不自动越过 private。
3. 通过数据修正，把不应具备平台属性的账号从平台判定链中移出。

---

## 3.4 创建空间入口与后端判定链不一致

问题：

1. 创建空间按钮的前端显示条件与后端 `POST /tenants` 的权限条件不完全一致。
2. `tenant.enable_cross_tenant_access` 会影响一部分平台入口显示。
3. 结果是“能不能看到按钮”和“后端是否允许创建”不是同一套逻辑。

影响：

1. 用户会出现“按角色应该能创建空间，但界面没有入口”的现象。
2. 同一个用户在前端可见性和后端接口能力上可能不一致。

已知案例：

1. `admin` 是平台管理员，但界面曾出现“没有创建空间按钮”的现象。

整改方向：

1. 创建空间入口显示逻辑与后端 `POST /tenants` 权限判定统一。
2. `can_access_all_tenants` 只作为跨空间能力，不再单独承担“是否显示创建空间按钮”的语义。

---

## 3.5 成员展示层会放大角色混淆

问题：

1. 平台管理员在成员展示层可能被隐藏或与普通空间成员混标。
2. 组织树根节点投影、空间成员页、组织成员页之间的展示规则并不完全一致。

影响：

1. 管理员看到的成员列表与数据库真实成员集合不完全一致。
2. 容易误判是“成员丢失”还是“展示过滤”。

整改方向：

1. 明确平台管理员在成员页中的展示规则。
2. 明确哪些场景隐藏平台账号，哪些场景只做标识不隐藏。

## 4. 已知问题的直接判断

## 4.1 admin 是平台管理员，但界面没有创建空间入口

问题结论：

1. 这是平台入口判定不一致问题。
2. 根因不在单一按钮，而在平台字段组合语义与前后端判定链不一致。

直接整改目标：

1. 创建空间入口显示逻辑与后端 `POST /tenants` 能力完全统一。
2. `admin` 在当前基线下必须稳定拥有创建空间入口。

## 4.2 hlsa 是空间拥有者，却能看到私有知识库

问题结论：

1. 这是 private 可见性边界问题。
2. 根因优先怀疑平台兼容字段越权，而不是空间角色本身越权。

直接整改目标：

1. `hlsa` 保留空间 owner 能力。
2. `hlsa` 不再携带平台兼容字段。
3. `hlsa` 不再通过平台兼容字段绕过 private 资源读取边界。

## 6. 整改原则

后续整改遵循以下原则：

1. 平台级能力、空间级能力、组织级能力分层处理。
2. 先统一术语，再统一判定 helper，再统一界面入口与数据角色。
3. 在 `main` 仍保留 `is_system_admin` 的前提下，Phase 0-2 不做概念删除，只做语义收口。
4. 先修平台入口与 private 越权，再处理历史角色污染与展示层。
5. 数据修正与代码修正分阶段进行，避免一次性混改。

## 7. 分阶段整改计划

## Phase 0：术语冻结与数据审计

目标：冻结整改基线，形成统一口径。

工作项：

1. 固定“平台级 / 空间级 / 组织级 / 协作空间级”四层术语。
2. 固定“空间管理员”只指 `tenant_members.role >= admin`。
3. 固定“组织树管理员”只指 `organization_members_pre_plan3.admin`。
4. 固定“当前整改基线与 main 一致，不删除 `is_system_admin` 概念”。
5. 输出并维护平台账号白名单。
6. 输出并维护 tenant role 污染清单。
7. 把 `test1`、`Nish`、`admin` owner 交接事项从“待确认”转为“明确项”。

交付物：

1. 当前系统权限总览文档。
2. 平台权限问题与整改计划文档。
3. 平台角色审计脚本。
4. 已确认数据修正清单。

## Phase 1：平台级权限收口

目标：在不脱离 `main` 的前提下，统一平台级权限判断。

工作项：

1. 明确平台管理、创建空间、跨空间访问、private 绕过分别由哪些字段控制。
2. 统一运行时平台判定 helper，至少收口：
   - `is_system_admin`
   - `is_super_admin`
   - `can_access_all_tenants`
3. 统一登录态返回与前端状态折算。
4. 统一系统管理入口和创建空间入口。
5. 明确 `can_access_all_tenants` 是否仅承担跨空间访问能力，不再单独承担平台管理员判定。

结果要求：

1. 前端显示与后端接口不再冲突。
2. `admin` 稳定拥有创建空间入口。
3. 平台管理员边界可解释、可测试、可追踪。

## Phase 2：private 资源边界收口

目标：消除平台兼容字段导致的 private 资源越权。

工作项：

1. 明确 private 只由谁可见、谁可管。
2. 统一 KB / Agent 的 private 判定。
3. 清理平台兼容字段对 private 的隐式绕过。
4. 先完成 `hlsa` 的平台字段回收。
5. 对 `hlsa` 做回归验证：
   - 仍保留 owner 管理能力
   - 不能再看到他人 private KB / Agent

结果要求：

1. private 越权都能明确定位到 creator 规则或平台管理员规则。
2. 空间 Owner/Admin 不再因为历史平台字段读到不该看的 private 资源。

## Phase 3：空间角色与组织角色分层

目标：把空间 `admin` 与组织树 `admin` 的边界彻底分清。

工作项：

1. 清理“子组织管理员 -> tenant admin”的历史映射残留。
2. 先处理 `test1` 和 `慧联世安` 中 6 个二级组织 admin。
3. 修正根节点投影与组织树显示逻辑。
4. 修正空间成员页与组织成员页的角色展示口径。

结果要求：

1. 子组织管理员只承担子树职责。
2. 空间管理员只承担租户控制面职责。

## Phase 4：业务空间 owner 交接

目标：回收平台账号 `admin` 在业务空间中的 owner 身份。

工作项：

1. `IntraMind` owner 交接给 `intramind`
2. `zhangzhen` owner 交接给 `zhangzhen`
3. `慧联世安` owner 交接给 `hlsa`
4. `NisH` 若确认升级 `Nish` 为 owner，则同步回收 `admin` 在该空间的 owner 身份

结果要求：

1. `admin` 只承担平台管理职责，不再承担业务空间 owner 身份。
2. 业务空间 owner 与真实业务负责人一致。

## Phase 5：成员展示与前端语义修正

目标：让界面展示与真实权限边界一致。

工作项：

1. 统一平台管理员在成员页中的显示/隐藏规则。
2. 统一知识库与智能体列表中“我创建的 / 他人创建的 / private / shared”语义。
3. 避免界面层继续放大权限误解。

## 8. 验收标准

完成 Phase 0-2 后，至少满足以下标准：

1. `admin` 稳定显示创建空间入口，且后端允许创建空间。
2. `hlsa` 保留空间 owner 能力，但不能再看到他人 private 资源。
3. `test1` 不再是空间 `admin`。
4. `Nish` 升级为 owner 后，NisH 的 owner 关系清晰可解释。
5. 平台管理员、空间管理员、组织树管理员三者在文档、数据库和运行时路径上都可被清晰区分。

---

## 9. 建议实施顺序

建议按以下顺序执行：

1. Phase 0
2. Phase 1
3. Phase 2
4. Phase 3
5. Phase 4
6. Phase 5

原因：

1. 先固定术语和数据清单，避免边改边漂移。
2. 先统一平台判定，再修 private 越权，风险最低。
3. 角色污染和 owner 交接放在后面，便于业务确认和数据回滚。
