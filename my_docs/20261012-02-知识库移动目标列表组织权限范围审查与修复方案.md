# 知识库移动目标列表组织权限范围审查与修复方案

## 1. 结论

当前“移动到知识库”弹窗的候选目标列表**没有按当前用户的组织权限可见范围收口**。

根因不在前端，而在后端 `GET /api/v1/knowledge-bases/:id/move-targets`：

1. 路由只校验了**源知识库**的读权限。
2. Handler 直接调用租户级全量列表 `h.service.ListKnowledgeBases(ctx)`。
3. 返回前只做了“同类型 / 同 EmbeddingModel / 非自身 / 非临时”的业务过滤，**没有走 `KBVisibilityService`**，也**没有做 API key allow-list 收口**。

因此，在同一租户内，当前用户会看到其组织权限范围外的知识库名称与知识数量。

## 2. 现状审查

### 2.1 前端调用链

- `frontend/src/views/knowledge/KnowledgeBase.vue`
  - `handleMoveKnowledge()` 调用 `listMoveTargets(kbId.value)`。
  - `moveTargetKbs` 直接喂给 `DocumentCardView.vue` / `DocumentListView.vue` 的“移动到知识库”菜单。
- `frontend/src/api/knowledge-base/index.ts`
  - `listMoveTargets(sourceKbId)` 对应 `GET /api/v1/knowledge-bases/:id/move-targets`。

结论：前端没有本地权限过滤，候选范围完全由后端接口决定。

### 2.2 后端候选列表接口

关键位置：

- `internal/router/routes_knowledge.go:251-252`
  - `kb.GET("/:id/move-targets", g.Viewer(), g.KBAccessRead("id"), handler.ListMoveTargets)`
  - 这里只对 `:id`（源 KB）做了 `KBAccessRead`。

- `internal/handler/knowledgebase.go:1503-1555`
  - `ListMoveTargets()` 先取源 KB。
  - 然后直接执行 `allKBs, err := h.service.ListKnowledgeBases(ctx)`。
  - 再按以下条件过滤：
    - 不是自身
    - 不是临时 KB
    - `Type` 相同
    - `EmbeddingModelID` 相同

问题点：`ListMoveTargets()` **没有**调用 `h.kbVisibility.ListAccessibleKBs(...)`，也没有调用 `filterKnowledgeBasesForAPIKeyScope(...)`。

### 2.3 全量列表 service 的语义

关键位置：

- `internal/application/service/knowledgebase.go:348-406`
  - `ListKnowledgeBases(ctx)` 本质上是 `repo.ListKnowledgeBasesByTenantID(ctx, tenantID)`。

- `internal/application/repository/knowledgebase.go:83-92`
  - `ListKnowledgeBasesByTenantID()` 查询的是当前租户下所有 `is_temporary=false` 的 KB。

结论：`ListMoveTargets()` 当前拿到的是**当前租户内全部知识库**，不是“当前用户可见的知识库”。

### 2.4 系统里已经存在的正确可见性实现

关键位置：

- `internal/application/service/kb_visibility.go:35-61`
  - `KBVisibilityService.ListAccessibleKBs()`：先解析当前用户的组织范围，再从仓库层按可见性过滤。

- `internal/application/repository/knowledgebase.go:94-124`
  - `ListAccessibleKBs(ctx, userID, tenantID, orgIDs)`：
    - `global`：同租户可见
    - `org`：仅 `organization_id` 落在 `orgIDs` 范围内可见
    - `private`：仅创建者本人可见

- `internal/application/service/same_tenant_scope.go:36-146`
  - `resolveScope()` 通过 `GetUserOrganizations + GetDescendantIDsByPaths` 计算：
    - 本人组织
    - 本人组织后代
    - 本人担任管理员的组织及其后代（管理范围）

结论：系统已经具备“按当前用户组织可见范围列出 KB”的正确基础设施，只是 `move-targets` 没有复用。

## 3. 发现的问题

### P1. `move-targets` 泄露同租户超范围知识库

严重性：高

原因：`ListMoveTargets()` 用的是租户全量 KB 列表，不是 `KBVisibilityService.ListAccessibleKBs()`。

结果：

- 用户可看到不属于自己组织可见范围的目标 KB 名称。
- 用户可看到这些 KB 的 `knowledge_count`。
- 对 private / 其他组织 org-scoped KB 会造成同租户信息泄露。

### P1. 候选列表权限模型与真正执行权限模型不一致

严重性：高

关键位置：

- `internal/handler/knowledge.go:2923-2944`
  - `POST /api/v1/knowledge/move` 对源/目标 KB 都执行 `requireKBOwnershipOrAdmin()`。

- `internal/middleware/rbac.go:370-416`
  - `EvaluateOwnershipOrRole()` 的语义是：
    - 资源创建者可过
    - 否则需要租户 `Admin+`
    - 这**不是** `KBVisibility.CanManageKB()` 那套 org-scope 管理权限语义

这意味着当前有两套规则：

1. 列表接口（现在实际上是“租户全量”）
2. 执行接口（creator 或 tenant Admin+）

如果产品目标是“按当前用户组织权限范围决定哪些 KB 可作为移动目标”，那仅修 `move-targets` 还不够，`POST /knowledge/move` 也要和它统一到同一套规则。

### P2. `move-targets` 没有做 API key allow-list 收口

严重性：中

`ListKnowledgeBases()` 主列表路径会在 handler 里做 `filterKnowledgeBasesForAPIKeyScope(ctx, kbs)`，但 `ListMoveTargets()` 没有这一层。

结果：限定 KB allow-list 的 API key，理论上也可能在候选列表里看到 allow-list 外的目标 KB。

### P2. `move-targets` 缺专项测试

严重性：中

现有测试主要覆盖：

- `knowledge_move_gate_test.go`
- `knowledge_move_gate_test.go`（service）

但没有针对以下场景的 handler / service 测试：

- 组织可见范围过滤
- private / org / global 三类可见性差异
- API key allow-list 过滤
- 列表与执行权限一致性

## 4. 推荐修复方案

## 4.1 推荐目标语义

推荐把“可移动目标知识库”定义为：

> 当前调用者**既能看到、又能实际执行移动到该目标 KB** 的知识库集合。

理由：

1. 仅按“可见”展示会导致用户点进去后在真正提交时 403，体验不一致。
2. “移动知识到目标 KB”本质是双边写操作，目标端至少应该满足“可管理”语义，而不只是“可读”。
3. 用户提出的是“结合当前用户的组织权限可见范围显示目录”，本质诉求是**不要看到超范围目标**；进一步收敛到“可管理目标”更符合最终可操作性。

因此建议最终语义是：

- 基础集合：当前用户在其组织权限范围内可触达的 KB
- 最终集合：其中当前用户**有权把知识移动进去**的 KB

## 4.2 修复原则

### 原则 A：`move-targets` 不再直接枚举租户全量 KB

`ListMoveTargets()` 必须复用现有 `KBVisibilityService` / same-tenant scope 体系，而不是继续走 `ListKnowledgeBases(ctx)`。

### 原则 B：列表权限与执行权限必须统一

不应出现：

- 列表里能看到，但提交时 403
- 列表里看不到，但按组织管理语义其实应该能移动

应把候选目标生成逻辑与 `POST /knowledge/move` 的授权校验收拢到同一套 helper / service。

### 原则 C：后端过滤为准，前端不做权限推断

前端只消费后端返回的候选列表，不应在浏览器里根据当前组织树自行拼可见范围。

## 4.3 具体落地建议

### 方案一：推荐方案（统一到“可管理目标”）

#### Step 1. 抽出统一 helper

建议新增一层统一 helper，例如：

- `KnowledgeBaseHandler.listMovableTargets(...)`
或
- `KBVisibilityService.ListMovableTargetKBs(...)`
或
- `KnowledgeBaseService.ListMoveTargetsForCaller(...)`

输入建议：

- `ctx`
- `sourceKB`
- `userID`
- `tenantID`
- `bypassVisibility`

输出：

- 已按权限和业务条件过滤完的 `[]*types.KnowledgeBase`

#### Step 2. 候选集合先走可见范围

先基于现有 `kbVisibility.ListAccessibleKBs(ctx, userID, tenantID, bypassVisibility)` 获取**用户可见 KB 集合**。

这样可直接复用现有：

- global / org / private 可见性规则
- 当前用户组织及后代组织可见范围
- super admin / bypass 逻辑

#### Step 3. 再按“可管理”收口

在可见集合上进一步筛掉当前用户不能作为移动目标操作的 KB。

这里有两个可选实现：

##### 实现 A：最小改动

对候选 KB 逐个调用 `kbVisibility.CanManageKB(...)`。

优点：

- 改动直观
- 不需要先改 repository 接口

缺点：

- N+1 查询

##### 实现 B：推荐

在 service 层基于已加载的 KB 结构体，直接复用 `sameTenantResourceAuthorizer.canManageResource(...)` 做内存过滤，避免逐个 `GetKnowledgeBaseByIDAndTenant`。

原因：

- `canManageResource()` 的判断只依赖：
  - `visibility`
  - `organization_id`
  - `creator_id`
  - 当前用户 scope
- 这些字段在候选 KB 列表里已经都具备

这样可以避免再补一个 repository 层批量接口。

#### Step 4. `POST /knowledge/move` 与候选列表使用同一套规则

如果产品确认“组织管理员应能在其管理范围内移动知识到目标 KB”，则 `MoveKnowledge()` 不应继续只用：

- `requireKBOwnershipOrAdmin(c, req.SourceKBID)`
- `requireKBOwnershipOrAdmin(c, req.TargetKBID)`

而应改为基于 `kbVisibility.CanManageKB(...)` 或同一统一 helper 来校验源/目标 KB。

否则会出现：

- 列表按 org-scope 给出了目标 KB
- 但提交仍因 creator/Admin 旧规则被拒绝

这是本次修复里最重要的“一致性收口”。

#### Step 5. 保留现有业务过滤条件

权限过滤之后，再保留当前已有的业务条件：

- 排除自身
- 排除临时 KB
- `Type` 必须一致
- `EmbeddingModelID` 必须一致

可选补强：

- 如产品希望 `reuse_vectors` 模式下就不展示跨 store 目标，可在候选接口里增加模式参数并前置过滤
- 但这不是本问题主轴，可后续再做

#### Step 6. API key 也做同样收口

`move-targets` 返回前补 `filterKnowledgeBasesForAPIKeyScope(ctx, kbs)`，确保限定 key 不会看到 allow-list 外的目标 KB。

### 方案二：仅修列表，不动执行权限（不推荐，但可快速止血）

如果短期只想先解决“能看到所有 KB”的问题，可先：

1. `ListMoveTargets()` 改用 `kbVisibility.ListAccessibleKBs(...)`
2. 返回前再做 `filterKnowledgeBasesForAPIKeyScope(...)`

这样能先止住超范围展示。

但它有明显缺点：

- 仍然保留“列表权限”和“执行权限”两套规则
- 组织管理员场景下可能继续出现“看得到但 move 403”

因此它只适合做热修，不适合作为最终方案。

## 5. 推荐改动点

### 后端必改

1. `internal/handler/knowledgebase.go`
   - 重写 `ListMoveTargets()` 的候选集合来源
   - 不再直接调用 `h.service.ListKnowledgeBases(ctx)`

2. `internal/handler/knowledge.go`
   - 评估并收口 `MoveKnowledge()` 的源/目标 KB 鉴权
   - 推荐改为与候选列表相同的“可管理”规则

3. `internal/application/service/kb_visibility.go`
   - 可新增“可管理 KB 列表” helper，或暴露 move-target 专用 helper

4. `internal/application/service/same_tenant_scope.go`
   - 无需改规则本身，但应作为 move-target 权限收口的统一基础设施

### 前端建议

前端无需自行推导组织可见范围，只保留现有：

- 打开菜单时调用 `listMoveTargets()`
- 空列表时展示 `moveNoTargets`

如果产品希望用户感知更明确，可补一条空态文案，例如：

- “当前组织权限范围内没有可移动的目标知识库”

### 可选增强

如果产品还希望“移动弹窗继承当前知识库页选中的组织筛选上下文”，可给 `move-targets` 追加可选参数：

- `organization_id`

但这属于**页面筛选上下文**，不是**权限范围**本身，建议和本次权限修复分开做，避免混淆。

## 6. 测试建议

至少补以下测试：

### 6.1 `ListMoveTargets` handler 测试

1. 用户只属于组织 A，目标列表只返回：
   - global（若最终策略允许）
   - 组织 A 及其后代范围内的 org-scoped KB
   - 用户自己创建的 private KB

2. 组织 B 的 org-scoped KB 不应返回。

3. 他人创建的 private KB 不应返回。

4. `source_kb_id` 自身不应返回。

5. `Type` 不同 / `EmbeddingModelID` 不同 / `is_temporary=true` 不应返回。

6. API key allow-list 生效：只返回 allow-list 与候选集合的交集。

### 6.2 `MoveKnowledge` handler 测试

如果最终采用“可管理目标”语义：

1. 组织管理员对自己管理范围内的 org-scoped KB 可以 move。
2. 对管理范围外的 KB 返回 403。
3. creator 仍可 move 自己创建的 private/global/org KB。
4. tenant owner/admin 的既有管理能力不回退。

### 6.3 一致性测试

建议新增一组断言：

> 某个目标 KB 只要出现在 `move-targets` 响应中，则同一调用者对该目标发起 `POST /knowledge/move` 不应再因为权限原因 403。

这组测试能长期防止“列表规则”和“执行规则”再次漂移。

## 7. 推荐实施顺序

### 第一阶段：止血

1. `ListMoveTargets()` 改用 `KBVisibilityService`
2. 加上 API key allow-list 过滤
3. 补 handler 测试，先止住“看到所有 KB”

### 第二阶段：语义统一

1. 明确产品结论：移动目标到底按“可见”还是“可管理”
2. 推荐统一为“可管理”
3. 同步改 `MoveKnowledge()` 鉴权，使其与候选列表一致
4. 补一致性测试

## 8. 最终建议

本问题不建议只做前端修饰或局部过滤。

**推荐最终方案**：

1. `move-targets` 改为基于 `KBVisibilityService` 的权限收口
2. 候选集合按“当前用户组织权限范围内可管理的 KB”返回
3. `POST /knowledge/move` 与 `move-targets` 统一为同一套授权规则
4. 同步补 API key allow-list 过滤与专项测试

这样才能同时解决：

- 超范围目标 KB 展示
- 列表与执行不一致
- API key 候选越权
- 后续回归缺乏保护
