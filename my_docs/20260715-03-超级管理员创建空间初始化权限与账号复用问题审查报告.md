# 超级管理员创建空间后初始化权限与账号复用问题审查报告

- 日期：2026-07-15
- 范围：空间初始化向导、组织树管理、空间删除后的账号生命周期
- 说明：本文仅审查当前代码路径，不修改业务代码

## 1. 结论摘要

1. 问题 1 属实。当前“新建用户并挂入组织”的初始化路径会忽略第一步选择的 tenant_role，实际按第二步组织角色映射 tenant_members.role，所以“拥有者 + 管理员”最终会落成“管理员”。
2. 问题 2 属实。删除空间时当前只软删 tenants 和 tenant_members，不会清理 users；同时 users 的 username、email、phone 唯一约束没有按 deleted_at 放开，因此删除空间后同标识不能重新创建。
3. 问题 3 属实。tenant owner / tenant admin 在后端本来就有组织树管理权限，但前端按钮显示只认 super admin 和 node.my_is_admin，而 owner / admin 读取整棵树时后端没有把 my_is_admin 标成 true，导致“创建子组织”按钮被整体隐藏。

## 2. 问答

### 问 1：为什么第一步选“拥有者”，第二步选“管理员”，初始化后登录空间显示“管理员”而不是“拥有者”？

**结论**

这是当前代码的既有行为，不是单纯的数据偶发异常。第一步的空间级角色在“新建用户”分支里没有真正进入落库决策。

**原因**

1. 前端向导在“新建用户”分支里，确实同时提交了组织角色和空间角色：WorkspaceSetupWizard 会发送 role=form.orgRole 与 tenant_role=form.tenantRole（frontend/src/components/WorkspaceSetupWizard.vue:611-617）。
2. 后端 CreateUserInOrg 没有使用支持 tenant_role 的 resolveTenantRoleForProvision，而是调用了 resolveTenantRoleForOrgScopedProvision（internal/handler/org_tree.go:322-330、333-352、960）。
3. resolveTenantRoleForOrgScopedProvision 的逻辑是“按组织角色推导空间角色”：org admin -> tenant admin，org editor -> tenant contributor，org viewer -> tenant viewer。这个 helper 根本不读取 req.TenantRole（internal/handler/org_tree.go:333-352；对应测试见 internal/handler/org_tree_provision_test.go:130-156）。
4. CreateUserInOrg 随后用这个推导结果写 tenant_members，登录后 /auth/me 返回的 memberships 也是从 tenant_members 读取出来的（internal/handler/auth.go:485-510）。
5. 前端当前空间角色展示完全依赖 memberships：authStore.currentTenantRole 直接读取当前 tenant 的 membership.role（frontend/src/stores/auth.ts:145-159）。因此只要 tenant_members.role 是 admin，界面就一定显示“管理员”。
6. 仓库里其实已经存在支持 tenant_role 的 helper 及测试，但 CreateUserInOrg 没有走这条分支（internal/handler/org_tree.go:322-330；internal/handler/org_tree_provision_test.go:74-125）。所以这不是“缺少能力”，而是“走错了实现路径”。

**修正方案**

1. 调整 CreateUserInOrg 的 tenant role 决策：
   - 平台 super admin、tenant owner、tenant admin 创建用户时，空间级角色应以 tenant_role 为准，调用 resolveTenantRoleForProvision 做授权校验。
   - 只有 branch-only org admin 继续保留现有“org role -> tenant role”映射，并维持 contributor / viewer 上限，防止子组织管理员越权授予 owner / admin。
2. 保持“先建 tenant_members，再挂组织成员”的顺序不变，这一顺序当前是正确的。
3. 补充 handler 级测试，不要只测 helper：
   - tenant_role=owner + org role=admin 时，tenant_members.role 必须是 owner。
   - tenant admin 不能授予 owner。
   - branch org admin 传 tenant_role=owner / admin 必须被拒绝或降级。
4. 对现网已错开的账号做一次性数据修复：把业务上应为 owner 的 tenant_members.role 修正为 owner。

**补充判断**

当前“新建用户”这条初始化路径里，第一步 owner 选择对结果是无效参数。也就是说，现状不是“显示错了”，而是“数据库里的 tenant_members.role 本来就写成了 admin”。

### 问 2：hlsa 所属空间已经删除，用户名和邮箱现在是否会级联逻辑删除？为什么不能重复创建？应该怎么修？

**结论**

当前不会级联逻辑删除 users。即便后续补做 soft delete，如果不把 username、email、phone 的唯一约束改成 deleted_at IS NULL 的部分唯一索引，依然不能重复创建相同标识。

**原因**

1. 删除空间的 repository 只做两件事：软删 tenant_members，再软删 tenant（internal/application/repository/tenant.go:146-153；对应测试见 internal/application/repository/tenant_test.go:193-221）。这里完全没有处理 users。
2. 组织树“删人”路径里，只有当用户已经没有同租户组织归属、再没有任何 tenant membership 时，才会进一步 DeleteUser（internal/application/service/org_tree.go:631-659）。也就是说，当前 tenant delete 路径绕过了这套账号清理逻辑。
3. CreateUserByAdmin 在创建前会先查 username、email、phone；只要查到现有用户就直接报错（internal/application/service/user.go:154-187）。你日志里的 user with this username already exists 就是这一层抛出来的。
4. 数据库层的唯一约束也会继续阻止重建：
   - username 是全局唯一约束（migrations/versioned/000001_agent.up.sql:28；internal/types/user.go:52）
   - email 是全局唯一约束（migrations/versioned/000001_agent.up.sql:32；internal/types/user.go:54）
   - phone 也是唯一索引，但当前条件只有 phone 非空，没有 deleted_at 过滤（migrations/versioned/000039_add_user_phone.up.sql:5）
5. CreateUserInOrg 的 orphan reuse 只能复用“tenant_id 仍等于当前 tenant 且已不挂任何组织”的账号（internal/handler/org_tree.go 中 findReusableProvisionedUser / isReusableProvisionedUser / provisionUserForOrg 这组逻辑）。空间删除后遗留的 user 记录仍保留旧 tenant_id，新空间 tenant_id 已变化，因此这条复用逻辑也救不了该账号。
6. user.TenantID 仍然承担 home tenant 语义。认证中对“home tenant + orphan tenant”还有专门分支（internal/middleware/auth.go:569-582）。如果 tenant 已删但 user.TenantID 还指向旧 tenant，后续登录、切换、默认空间选择都会留下逻辑孤儿风险。

**推荐修正方案**

1. 先明确账号生命周期规则，建议采用“可复用账号标识”的方向：
   - 用户在其他 tenant 仍有 active membership：保留 user，不删除。
   - 用户在所有 tenant 都没有 active membership，且不是平台 super admin：软删 user。
   - 如果 user.TenantID 指向被删 tenant，但该用户还有其他 active memberships：把 home tenant 迁移到一个仍然有效的 tenant，避免 home tenant 悬空。
2. 做 schema 改造，否则 soft delete 后仍无法复用相同标识：
   - 删除 users_username_key、users_email_key 这两个全局唯一约束。
   - 改为创建带 deleted_at IS NULL 条件的部分唯一索引。
   - phone 也要同步改成 active-only unique：phone IS NOT NULL AND phone != '' AND deleted_at IS NULL。
   - internal/types/user.go 的模型标签也要同步调整，避免后续迁移或自动建表再次回到全局唯一。
3. 把 tenant delete 的账号清理从 repository 直删提升到 service 级编排：
   - 先收集被删 tenant 的 active members。
   - 事务内删除 tenant_members 与 tenant。
   - 同步或事务后按用户逐个做 rehome / soft delete 判定。
4. 做一次性数据修复：
   - 找出 user.tenant_id 指向已删除 tenant，且没有任何 active tenant_members 的孤儿账号。
   - 如果这些账号业务上已经无效，则在索引改造落地后软删；如果还需要保留到其他空间，则先 rehome，再保留。
5. 如果业务明确不允许“删除空间后重复使用原用户名/邮箱/手机号”，那就不能走上面的方案，而要做“复活已有账号并重新挂入新空间”的产品能力。但这与当前“希望重复创建”的诉求是冲突的。

**短结论**

你现在遇到的问题不是前端重复校验，而是后端与数据库一起阻止了重建：users 没删，唯一约束也没放开。

### 问 3：为什么现在无论管理员还是拥有者，都无法在组织树上创建子组织，按钮直接不存在？

**结论**

这不是“owner / admin 后端无权创建子组织”，而是“后端允许、前端隐藏”。根因是前后端对“可管理节点”的约定不一致。

**原因**

1. 后端 CreateOrgNode 已经允许 tenant owner / tenant admin 在空树时 bootstrap 第一个根组织（internal/handler/org_tree.go:625-662；bootstrap 条件函数见 internal/handler/org_tree.go:312-320，测试见 internal/handler/org_tree_provision_test.go:161-180）。
2. 后端 isOrgAdminOf 还对 tenant admin / owner 做了直接放行，所以从权限判断上讲，他们本来就能管理组织树节点。
3. 但前端页面顶部“创建根组织”和空树态“创建第一个组织”按钮只在 authStore.isSuperAdmin 时显示（frontend/src/views/admin/OrgTreeManage.vue:5、18）。这会直接挡住 owner / admin 的空树初始化入口。
4. 节点上的新增、编辑、删除按钮只在 authStore.isSuperAdmin 或 node.my_is_admin === true 时显示（frontend/src/views/admin/components/OrgTreeNodeItem.vue:34-41、88-90）。
5. 真正的错位点在后端返回树数据：GetTreeForUser 对 super admin 或 tenant admin / owner 会直接 return s.GetTree(ctx, tenantID)（internal/application/service/org_tree.go:333-338）。
6. 但 GetTree 构造节点时并没有给 MyIsAdmin 赋 true，它只填充基础信息和成员计数（internal/application/service/org_tree.go:228-290）。因此 owner / admin 虽然能看到整棵树，但每个节点的 my_is_admin 默认都是 false。
7. 结果就是：后端会放行创建子组织，前端却因为 my_is_admin=false 把按钮全部隐藏掉。你截图里的“能看到根组织，但没有新增按钮”与这条代码路径完全一致。

**推荐修正方案**

1. 先修后端 contract：
   - tenant owner / tenant admin 读取组织树时，不要直接返回原始 GetTree 结果。
   - 应返回“整棵树 + 每个节点 MyIsAdmin=true”的结果，保证返回数据与后端权限一致。
   - 最直接的做法是复用 copyNodeTree，把整棵树按可管理子树输出。
2. 再修前端显示条件：
   - 节点操作按钮不应只看 super admin / node.my_is_admin，至少还要接受 tenant owner / tenant admin。
   - 顶部根组织创建按钮也要与后端 bootstrap 规则一致：super admin 始终可见；tenant owner / admin 仅在空树时可见。
3. 补充测试：
   - service 测试：GetTreeForUser(owner/admin) 返回的节点必须带 MyIsAdmin=true。
   - 组件测试：owner / admin 进入组织树页面时，根节点应显示“创建子组织”按钮。
   - 手工回归：owner / admin 创建子组织、编辑节点、拖拽移动都要走一遍。

**额外观察**

现有测试已经覆盖了 GetUserOrganizations 的 root projection（internal/application/service/org_tree_projection_test.go），但没有覆盖 GetTreeForUser(owner/admin) 的 manage flag 传播，这就是这类 UI 回归能漏出来的原因。

## 3. 建议开发计划

### 阶段 0：现网止血

1. 对当前已经初始化错位的目标账号，先人工确认哪些 tenant_members.role 应提升为 owner。
2. 对当前已经删除空间但仍占用 username / email / phone 的孤儿账号，先做名单梳理，区分“应删除”与“应保留并迁移 home tenant”。

### 阶段 1：修复空间初始化角色路径

1. 修改 internal/handler/org_tree.go，让 CreateUserInOrg 在 tenant owner / admin 场景使用 resolveTenantRoleForProvision。
2. 保留 branch org admin 的 tenant role 上限收口，不要放开 owner / admin 授予。
3. 增加 handler 级测试，覆盖 owner / admin / branch admin 三类角色决策。
4. 验收标准：第一步选 owner、第二步选 admin，新账号登录后当前空间角色显示 owner。

### 阶段 2：修复组织树管理按钮与可管理标记

1. 修改 internal/application/service/org_tree.go，保证 tenant owner / admin 拿到的整棵树节点都带 MyIsAdmin=true。
2. 修改 frontend/src/views/admin/OrgTreeManage.vue 与 frontend/src/views/admin/components/OrgTreeNodeItem.vue，使按钮显示条件与后端权限一致。
3. 增加前端组件测试与后端 service 测试。
4. 验收标准：owner / admin 打开组织树后，能看到“创建子组织”按钮，并成功创建子组织。

### 阶段 3：修复删除空间后的账号生命周期与标识复用

1. 修改 tenant delete 业务编排，删除 tenant 时同步处理受影响 users。
2. 新增数据库迁移，把 username / email / phone 改为 active-only unique。
3. 增加数据修复脚本，清理已存在的 orphan users，并处理 home tenant 迁移。
4. 验收标准：删除空间后，若账号已无其他有效空间归属，则可以再次使用相同 username / email / phone 创建新账号；若账号仍属于其他空间，则账号保留且 home tenant 不悬空。

### 阶段 4：回归与发布

1. 后端测试：go test ./internal/handler ./internal/application/service ./internal/application/repository
2. 前端校验：frontend 目录下运行 npm run type-check
3. 手工回归场景：
   - 超管新建空间 -> 新建负责人 owner + root org admin
   - owner 登录 -> 组织树创建子组织
   - 删除空间 -> 重建同 username / email / phone 账号
4. 发布前先执行一次生产数据审计，确认没有会与新唯一索引冲突的历史脏数据。

## 4. 优先级建议

1. 最高优先级：问题 1 和问题 3。它们直接影响“新空间是否能正确交付负责人”和“负责人能否继续搭组织树”。
2. 次高优先级：问题 2。它涉及 schema、数据修复和账号生命周期，改动面更大，但如果不做，测试和正式使用都会持续被“旧账号残留”卡住。

## 5. 最终判断

当前三类问题都不是单点小 bug，而是三条相互关联的链路不一致：

1. 初始化向导提交了 tenant_role，但 create-user handler 没按这个字段落库。
2. tenant delete 删除了空间关系，却没有完成 user 生命周期收口。
3. 后端权限已允许 owner / admin 管组织树，但返回给前端的节点标记和前端显示条件没有同步。

建议按“初始化角色修正 -> 组织树按钮修正 -> 账号生命周期与唯一索引修正”的顺序推进，这样可以先恢复新空间交付能力，再处理删除空间后的账号复用问题。
