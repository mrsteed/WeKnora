## 2. 结论摘要

### 2.1 结论 1：当前系统存在三套“成员”数据源并行，且没有单一权威同步机制

当前代码并行使用了三套不同语义的成员数据：

1. tenant_members
   - 表示“空间/租户成员身份”
   - 决定认证后能否进入空间，以及 Owner / Admin / Contributor / Viewer 租户级权限
2. organization_members_pre_plan3
   - 表示“组织树里的按用户成员关系”
   - 当前“组织人员管理”仍然主要读取这张旧表
3. organization_tenant_members
   - 表示“按 tenant 键的组织共享成员关系”
   - 当前共享空间/组织协作能力使用这张表

这三者当前没有被强制保持一致，直接导致：

- 一个用户可以出现在组织树里，但不是空间成员
- 一个用户可以是空间成员，但不出现在当前组织人员里
- 运维修复脚本若选错“当前有效人员”的数据源，会把仍应保留的空间成员误删

### 2.2 结论 2：马晓东登录报错的直接根因是缺少 tenant_members，而不是密码、组织角色或前端问题

从 WeKnora/my_docs/test/1 中的现场日志可以直接确认：

- 马晓东登录本身成功
- 登录后访问 auth/me、knowledge-bases、models、organizations 等接口时，后端统一报：
  - Forbidden: not a member of the target tenant
- 同一日志里明确出现：
  - SELECT * FROM tenant_members WHERE user_id = '11741004-5077-43ce-8f6b-8622c31e40d7' AND tenant_id = 10008
  - record not found

也就是说：

- 马晓东在 users 中存在
- 马晓东在组织树成员关系中存在
- 但他在 tenant_members 中没有 active row
- 认证中间件因此 fail-closed

### 2.3 结论 3：hlsa 根节点不显示，不是“查不到人”，而是代码显式把系统管理员/超级管理员过滤掉了

当前存在两层过滤：

1. internal/handler/org_tree.go 的 listProjectedRootAdminMembers()
   - 在根节点投影空间 Owner/Admin 时，显式跳过：
   - user.IsSuperAdmin 或 user.IsSystemAdmin 为 true 的用户
2. internal/application/repository/organization.go 的 ListOrgTreeMembers()
   - 查询 organization_members_pre_plan3 时，SQL 里显式过滤：
   - users.is_super_admin = false 且 users.is_system_admin = false

因此即便 hlsa 是当前空间 Owner，只要它同时具备系统管理员/超级管理员标志，就会被组织人员管理列表排除。

### 2.4 结论 4：“空间成员为空”不是前端渲染 bug，而是当前空间成员接口与组织人员接口根本不是一套来源

当前“空间成员”页走的是：

- frontend/src/views/settings/TenantMembers.vue
- GET /api/v1/tenants/:id/members
- internal/handler/tenant_member.go: ListMembers
- internal/application/repository/tenant_member.go: ListPagedByTenant / CountFilteredByTenant

这条链只认 tenant_members。

同时，这条链在仓库层还显式过滤掉：

- users.is_super_admin = true
- users.is_system_admin = true

而“组织人员管理”走的是：

- internal/handler/org_tree.go: ListOrgMembers
- internal/application/service/org_tree.go: ListOrgMembers
- internal/application/repository/organization.go: ListOrgTreeMembers

这条链读的是 organization_members_pre_plan3。

因此当前现场出现的“组织人员 13 个，但空间成员 0 个”，不是偶发现象，而是两条查询链路天然可能返回完全不同的结果。

### 2.5 结论 5：CreateUserInOrg 当前代码已补 tenant_members，但“已有用户分配到组织”与历史数据仍然会漏

当前 internal/handler/org_tree.go 的 CreateUserInOrg() 已经做了：

1. 创建 users
2. 调 ensureProvisionedMembership() 补 tenant_members
3. 再调用 AssignUserToOrg() 写组织树成员

这说明“新建用户并分配到组织”这条主链已经部分修复。

但仍有两个缺口：

1. AssignUser() 这条“把已有用户加入组织”的路径，只写组织树成员，不保证 tenant_members 同步补齐。
2. 历史用户数据在修复前已经建成，只要没有 tenant_members，就会持续 403。

因此，马晓东这类问题更符合“历史数据遗留”或“走了仅组织分配路径”的特征，而不是当前 CreateUserInOrg 主链再次完全失效。

### 2.6 结论 6：当前一次性修复脚本的口径与组织人员管理实际数据源不一致，存在二次清理风险

当前仓库中的脚本：

- scripts/tenant_membership_repair/repair_tenant_memberships.sh

在判定“当前组织人员里面可用的账号”时，使用的是 organization_tenant_members。

但当前组织人员管理页面实际读取的是 organization_members_pre_plan3。

这意味着：

- 如果 organization_tenant_members 与 organization_members_pre_plan3 不一致
- 脚本会把“页面里仍然存在的组织人员”判成 stale tenant member
- 继而把这些 tenant_members 逻辑删除

本轮已执行脚本前的 dry-run 结果中，tenant 10008 曾出现：

- stale_membership_count = 13

执行后复核为：

- stale_membership_count = 0

这说明 tenant_members 已被按脚本口径收缩，但并不能证明 organization_members_pre_plan3 与之同步；反而与“组织人员仍有 13 个、空间成员变空”的现象是相互印证的。

## 3. 代码审查发现

## 3.1 P0：认证准入只认 tenant_members，组织树成员不会被兜底成最小空间角色

代码位置：

- internal/middleware/auth.go

当前 resolveTenantRole() 的逻辑是：

1. 先查 tenant_members
2. 若命中 active membership，则返回对应 tenant role
3. 若未命中，只允许“跨租户超管直通”或“孤儿租户自愈”两种特殊路径
4. 否则在 RBAC enforced 下直接 fail-closed

关键点：

- 这里不会因为“用户在组织树里存在”而自动授予一个最小空间身份
- 所以“组织树成员 ≠ 可登录空间成员”

这正是马晓东登录后所有租户接口统一 403 的根因。

## 3.2 P0：组织树人员管理与空间成员管理读的是两张完全不同的成员表

代码位置：

- internal/application/repository/organization.go
- internal/handler/tenant_member.go
- internal/application/repository/tenant_member.go

当前组织树成员管理：

- AddOrgTreeMember / RemoveOrgTreeMember / UpdateOrgTreeMemberRole / ListOrgTreeMembers
- 全部基于 organization_members_pre_plan3

当前空间成员管理：

- ListMembersPage / AddMember / UpdateRole / RemoveMember
- 全部基于 tenant_members

这两套模型目前没有事务级联同步保证。

影响：

- 组织树显示人数与空间成员人数天然可能不一致
- 子组织管理员的组织角色和空间角色可能漂移
- 任一修复脚本只要拿错表做“当前有效成员”口径，就会误清理

## 3.3 P1：根节点人员投影和组织成员查询都在显式隐藏系统管理员/超级管理员

代码位置：

- internal/handler/org_tree.go
- internal/application/repository/organization.go

具体表现：

1. listProjectedRootAdminMembers()
   - 对根节点投影用户做如下过滤：
   - user.IsSuperAdmin 或 user.IsSystemAdmin 时 continue
2. ListOrgTreeMembers()
   - SQL WHERE 中直接过滤 users.is_super_admin / users.is_system_admin

结果：

- hlsa 即使是当前空间 Owner，也不会在组织人员管理根节点看到
- “只隐藏超级管理员账号”的业务要求与当前实现不一致

## 3.4 P1：空间成员查询仓库层也在隐藏系统管理员/超级管理员

代码位置：

- internal/application/repository/tenant_member.go

当前 CountFilteredByTenant() / ListPagedByTenant() 都包含：

- COALESCE(users.is_super_admin, FALSE) = FALSE
- COALESCE(users.is_system_admin, FALSE) = FALSE

这意味着：

- 只要空间内剩下的有效 tenant_members 主要是系统管理员/超级管理员
- “空间成员”页面就会直接显示空列表

这与当前现场截图高度一致。

## 3.5 P1：AssignUser 仍是“只加组织、不加空间成员”的旧语义

代码位置：

- internal/handler/org_tree.go: AssignUser
- internal/application/service/org_tree.go: AssignUserToOrg

当前行为：

1. 只往 organization_members_pre_plan3 写入组织成员
2. 不检查目标用户是否已有 tenant_members
3. 不补 tenant_members
4. 不做 tenant role 映射

因此：

- 只要某个已有用户被“分配到组织”但没有补 tenant_members
- 该用户在组织里可见，但登录后仍无空间准入权限

这会持续制造“子组织管理员能在组织里看到，但一登录就 403”的历史脏数据。

## 3.6 P1：当前 CreateUserInOrg 已做 tenant_members 补齐，但历史数据不会被自动修复

代码位置：

- internal/handler/org_tree.go: CreateUserInOrg

当前主链路已经包含：

- ensureProvisionedMembership()

因此：

- 新建用户主链已优于旧版本
- 但旧数据仍不会自动回补
- 已存在用户再次绑定组织时，也不会因为 AssignUser 而自动补 tenant_members

换句话说：

- 当前代码处于“新老路径行为不一致”的过渡态

## 3.7 P1：当前修复脚本把 organization_tenant_members 当成了“当前组织人员真值表”，与页面实际口径不一致

代码位置：

- scripts/tenant_membership_repair/repair_tenant_memberships.sh

脚本当前行为：

1. 用 organization_tenant_members 推导当前人员
2. 以此清理 tenant_members

但页面当前行为：

1. 组织人员管理读 organization_members_pre_plan3

因此这份脚本在当前系统里只能作为“半成品运维脚本”，不能继续直接用于生产修复，除非先统一成员真值表口径。

## 5. 对 4 个问题的逐项判断

## 5.1 hlsa 账号应该在根节点上显示，只隐藏超级管理员账号

判断：当前代码不满足。

根因：

1. 根节点投影过滤了 is_system_admin / is_super_admin
2. 组织成员旧表查询也过滤了 is_system_admin / is_super_admin

额外注意：

- 当前 hlsa 数据本身同时带有 is_super_admin = true
- 如果业务要求是“hlsa 可见，但只隐藏超级管理员”，则必须先明确：
  - hlsa 到底应不应该保留 legacy `is_super_admin=true`
  - 还是仅保留 `is_system_admin=true + 当前空间 owner`

否则“只隐藏超级管理员”这条业务规则与当前 hlsa 数据本身就是冲突的。

## 5.2 hlsa 账号，空间成员显示为空；应该按组织人员管理的人员进行显示

判断：当前代码不满足，且不是单点 bug，而是接口语义不一致。

根因：

1. 空间成员页只读 tenant_members
2. 组织人员页读 organization_members_pre_plan3
3. tenant_members 查询还过滤系统管理员/超级管理员

所以当前“空间成员 0，组织人员 13”是系统设计分裂后的自然结果。

## 5.3 马晓东账号登录后报错，账号是产品部子组织管理员

判断：当前问题根因已确认。

根因：

- 马晓东在组织树里有组织角色，但在 tenant_members 中没有 active membership

因此：

- 登录本身成功
- 空间级认证准入失败
- 所有受租户保护的接口统一 403

## 5.4 子组织管理员登录后，权限完全不正常

判断：这是系统性问题，不是单个账号偶发。

只要某个子组织管理员存在以下任一情况，就会出现“权限完全不正常”：

1. 只有 organization_members_pre_plan3，没有 tenant_members
2. tenant_members.role 与组织角色映射不一致
3. 被清理脚本按错误真值表删掉了 tenant_members

本质上说：

- 当前系统把“子组织管理员”当作组织域内角色
- 但真正的登录准入、菜单显示、知识库/模型/共享/集成能力又先看 tenant_members
- 一旦两边漂移，子组织管理员就会呈现为“在组织里存在、在空间里不存在”的断裂状态

## 6. 详细修正计划

## Phase 0：冻结现场与回滚进一步误清理风险

目标：先止血，防止继续按错误真值表清理 tenant_members。

动作：

1. 暂停继续使用当前 scripts/tenant_membership_repair/repair_tenant_memberships.sh 对生产数据做 execute。
2. 先导出 tenant 10008 的四张关键表快照：
   - users
   - tenant_members
   - organization_members_pre_plan3
   - organization_tenant_members
3. 对照导出 3 类用户集合：
   - 仅在 organization_members_pre_plan3
   - 仅在 tenant_members
   - 两边都在但角色不一致

交付物：

- 一份 tenant 10008 的差异清单

## Phase 1：修正展示层，先让 hlsa 和根节点显示正确

目标：先修“看不见 hlsa / 空间成员为空”的展示问题。

代码改造：

1. internal/handler/org_tree.go
   - 修改 listProjectedRootAdminMembers()
   - 不再用 `user.IsSuperAdmin || user.IsSystemAdmin` 一刀切隐藏
   - 新规则改为：
     - 默认显示当前空间 Owner
     - 是否隐藏跨租户平台账号，改为更窄的业务规则，不再复用系统管理员标记
2. internal/application/repository/organization.go
   - 修改 ListOrgTreeMembers()
   - 去掉对 `users.is_system_admin` 的硬过滤
   - 是否保留 `is_super_admin` 过滤，需按业务最终定义决定
3. internal/application/repository/tenant_member.go
   - 修改 CountFilteredByTenant() / ListPagedByTenant()
   - 不再因为 `is_system_admin=true` 把 hlsa 从空间成员页过滤掉

验收标准：

1. hlsa 在根节点人员列表可见
2. hlsa 在空间成员页可见
3. 当前“空间成员”列表不再在 only-owner 场景下显示空状态

## Phase 2：修正成员真值表口径，先把“空间成员页”改成按组织人员口径显示

目标：满足“空间成员应按组织人员管理的人员进行显示”。

推荐做法：

1. 不要直接把 TenantMembers.vue 继续绑死在 raw tenant_members 上
2. 新增一个后端聚合接口，例如：
   - GET /tenants/:id/effective-members
3. 该接口返回：
   - 当前 tenant 下 organization_members_pre_plan3 中出现过的用户
   - 这些用户对应的 tenant_members 状态
   - 组织角色、tenant 角色、是否缺空间成员、是否系统管理员

原因：

- UI 需要展示“当前组织人员里有哪些账号”
- 但系统又必须知道“这些账号是否真的具备 tenant_members 准入身份”
- 单独看任何一张表都不够

前端改造：

1. frontend/src/views/settings/TenantMembers.vue
   - 列表接口改为新的 effective-members
   - 增加状态列：
     - 正常
     - 缺空间成员
     - 组织内账号但已禁用
2. 保留现有 tenant role 标签，但新增 org role / provisioning state 提示

验收标准：

1. 空间成员页人数与组织人员管理人数能对齐到同一批账号
2. 即使某人暂时没有 tenant_members，也能在空间成员页被明确识别为“待修复账号”，而不是直接消失

## Phase 3：修正准入链路，彻底解决子组织管理员登录 403

目标：任何组织内有效账号，只要被定义为该空间可用账号，就必须具备 tenant_members。

代码改造：

1. 保持 internal/middleware/auth.go 的 fail-closed 不变
   - 不建议在认证中间件里因为“用户在组织树里”就自动放开登录
   - 否则会继续放大数据漂移
2. 修正所有“把人放进组织”的入口，让它们都同步保证 tenant_members 存在：
   - internal/handler/org_tree.go: AssignUser
   - 任何批量导入/邀请转组织成员的入口
3. 为 AssignUser 增加与 CreateUserInOrg 同等级的 membership bootstrap：
   - 根据 org role 自动映射 tenant role
   - admin -> tenant admin
   - editor/contributor -> tenant contributor
   - viewer -> tenant viewer

验收标准：

1. 任意“组织树中新增/分配”的账号，登录后不再出现 `not a member of the target tenant`
2. 马晓东账号补齐 tenant_members 后，auth/me、knowledge-bases、models、organizations 等接口恢复正常

## Phase 4：做 tenant 10008 的历史数据回补

目标：一次性修复现存坏数据。

建议顺序：

1. 从 organization_members_pre_plan3 生成“当前有效组织账号名单”
2. 对 tenant 10008 中缺 tenant_members 的这些账号批量补齐 tenant_members
3. tenant role 映射规则：
   - 根节点 Owner / 空间 Owner -> owner
   - 组织 admin -> admin
   - editor/contributor -> contributor
   - viewer -> viewer
4. 对已经存在但角色偏高/偏低的 tenant_members 做角色对齐
5. 再做一次只读核验：
   - 能登录的组织账号数
   - 组织人员页人数
   - 空间成员页人数
   - 各角色人数

特别说明：

- 本轮不建议继续用当前 repair_tenant_memberships.sh 直接 execute 做“按当前组织人员清理”
- 除非先把脚本真值表从 organization_tenant_members 改成 organization_members_pre_plan3，或者改成显式可选数据源

## Phase 5：统一长期模型，消除三套成员表的漂移

目标：从“每次修数据”转成“代码层面不再产生漂移”。

建议长期方向：

1. 明确权威边界：
   - tenant_members：认证准入与空间级 RBAC 权威
   - organization_members_pre_plan3：组织树人员域权威（短期保留）
   - organization_tenant_members：共享组织/协作域权威
2. 所有组织人员变更都必须同步更新 tenant_members
3. 所有 tenant_members 清理动作都必须先校验 organization_members_pre_plan3 是否仍在用
4. 后续若要彻底统一，再评估把组织树成员从 pre_plan3 迁移为正式新表，但不能在未收口前混用

## 7. 建议的实施优先级

建议按如下优先级执行：

1. 先停用当前错误口径的继续清理
2. 先修 hlsa 显示过滤
3. 再修空间成员页的数据源
4. 再补齐 AssignUser 的 tenant_members bootstrap
5. 最后做 tenant 10008 的历史数据回补

原因：

- 先修展示，可以立刻恢复可观测性
- 再修入口，可以阻止继续产生坏数据
- 最后做历史回补，避免边修边继续写坏数据

## 8. 最终判断

本次问题不是单点 bug，而是“组织树成员、空间成员、共享组织成员”三套模型长期并存、同步约束不足后形成的系统性漂移。

当前最关键的事实是：

1. hlsa 并不是没空间身份，而是被系统管理员/超级管理员过滤逻辑隐藏了。
2. 马晓东并不是账号坏了，而是 tenant_members 缺失。
3. 子组织管理员权限异常并不是前端按钮问题，而是租户准入与组织角色脱钩。
4. 当前空间成员页之所以为空，不是“没有人”，而是它读的根本不是组织人员管理那套数据。

因此，修复重点不应再停留在前端文案或单个接口权限，而应立即回到：

- 成员真值表统一
- tenant_members 补齐
- 组织入口自动开通空间身份
- 展示层停止错误隐藏系统管理员/Owner
