# 当前系统权限总览说明

> 状态：基于当前开发分支代码与 `main` 分支现状整理。
>
> 本文档描述**当前系统实际存在并生效的权限模型**，用于长期维护、排查与后续设计收口。
>
> 参考资料：
> - `docs/RBAC说明.md`
> - `docs/权限角色与API边界统一说明.md`
> - 当前仓库 `internal/`、`frontend/` 实现

---

## 1. 文档目的

本文档回答以下问题：

1. 当前系统有哪些权限层。
2. 各层权限分别由哪张表、哪个字段、哪些代码路径负责。
3. 平台级、空间级、组织级、协作空间级权限之间如何协同。
4. 知识库、智能体、共享空间、跨空间切换、创建空间等关键能力当前由什么规则控制。

本文档是**当前系统权限总览**，不是目标方案说明，也不是整改计划。

---

## 2. 权限体系总览

当前系统实际并存 4 个权限层：

1. **平台级权限**
   - 数据来源：`users`
   - 关键字段：`is_system_admin`、`is_super_admin`、`can_access_all_tenants`
   - 负责平台级管理、跨空间访问、部分资源越权

2. **空间级 RBAC**
   - 数据来源：`tenant_members`
   - 角色：`viewer / contributor / admin / owner`
   - 负责租户控制面与租户内角色上限

3. **组织树权限**
   - 数据来源：`organization_members_pre_plan3`
   - 角色：`admin / editor / viewer`
   - 负责同租户内组织树读写与 org-scoped 资源作用域

4. **协作空间权限**
   - 数据来源：`organization_tenant_members`
   - 角色：`admin / editor / viewer`
   - 负责跨租户共享空间成员关系与共享通道

这四层不是同一维度：

1. 平台级权限解决“谁能越过租户边界”。
2. 空间级 RBAC 解决“谁能管理当前租户”。
3. 组织树权限解决“谁在当前租户里能看哪些组织域资源”。
4. 协作空间权限解决“不同租户之间如何共享资源”。

---

## 3. 数据源与角色来源

| 权限层 | 存储位置 | 角色/字段 | 主要用途 |
| --- | --- | --- | --- |
| 平台级权限 | `users` | `is_system_admin` / `is_super_admin` / `can_access_all_tenants` | 平台管理、跨空间访问、部分资源越权 |
| 空间级 RBAC | `tenant_members` | `viewer` / `contributor` / `admin` / `owner` | 成员管理、模型、存储、MCP、向量库、租户配置 |
| 组织树权限 | `organization_members_pre_plan3` | `admin` / `editor` / `viewer` | 组织树成员管理、同租户 org-scoped 资源读写 |
| 协作空间权限 | `organization_tenant_members` | `admin` / `editor` / `viewer` | 共享空间成员、邀请、共享关系 |

补充说明：

1. `tenant_members` 是**空间控制面**的主来源。
2. `organization_members_pre_plan3` 是**组织树用户归属与组织域作用域**的主来源。
3. `organization_tenant_members` 是**跨租户共享空间**的主来源，不等于组织树成员。
4. `users` 中的平台字段会被多个中间件、Handler 和前端状态折算使用。

## 4. 平台级权限

## 4.1 当前字段

当前系统保留以下 3 个平台相关字段：

1. `users.is_system_admin`
2. `users.is_super_admin`
3. `users.can_access_all_tenants`

它们在当前实现中不是严格分层，而是被不同控制链按不同方式组合。

## 4.2 当前平台级控制面

| 能力 | 当前控制方式 | 说明 |
| --- | --- | --- |
| 系统设置 `/system/admin/*` | `RequireSystemAdmin`，上下文布尔值来自 `user.IsSystemAdmin || user.IsSuperAdmin` | 当前把 system admin 与 super admin 视作同类平台管理员 |
| 创建空间 `POST /tenants` | `caller.IsSuperAdmin || caller.IsSystemAdmin` | `CanAccessAllTenants` 不是该接口的唯一条件 |
| 跨租户搜索/浏览 | `RequireCrossTenantAccess` 要求 `CanAccessAllTenants=true` 且 `enable_cross_tenant_access=true` | 这是平台能力里最特殊的一条，单独受配置开关控制 |
| `X-Tenant-ID` 跨空间切换 / URL tenant bypass | `IsCrossTenantSuperuser`，要求 `enable_cross_tenant_access=true` 且 `CanAccessAllTenants || IsSystemAdmin || IsSuperAdmin` | 路径校验与切换校验都走这条语义 |
| 同租户 private 资源绕过 | `isPrivilegedResourceOperator()`，条件是 `IsSystemAdmin || IsSuperAdmin || CanAccessAllTenants` | 影响 KB / Agent 等资源读写 |
| 删除租户兜底 | `OwnerOrSystemAdminDelete` | 当前 system admin / super admin 都可绕过普通 Owner 限制 |

## 4.3 当前语义特征

当前系统的“平台超级权限”并不是一个单字段概念，而是：

1. 一部分能力看 `IsSystemAdmin || IsSuperAdmin`
2. 一部分能力看 `CanAccessAllTenants`
3. 一部分能力看 `IsSystemAdmin || IsSuperAdmin || CanAccessAllTenants`
4. 其中跨租户访问还额外受 `tenant.enable_cross_tenant_access` 开关控制

因此，当前系统里“平台管理员”是一个**组合语义**，不是单一字段语义。

## 4.4 与 `main` 分支的一致性

`main` 分支当前仍然保留 `is_system_admin` 概念，且该概念不仅存在于数据模型，也存在于实际权限控制链：

1. `internal/types/user.go`
2. `internal/middleware/auth.go`
3. `internal/middleware/rbac.go`
4. `internal/handler/tenant.go`
5. `internal/handler/system.go`
6. `frontend/src/stores/auth.ts`
7. `frontend/src/components/UserMenu.vue`
8. `migrations/versioned/000053_system_admin_and_settings.up.sql`

因此，**当前系统总览**必须把 `is_system_admin` 作为现行权限概念保留下来。

## 5. 空间级 RBAC

本节以 `docs/RBAC说明.md` 为主，描述当前租户内权限控制。

## 5.1 角色矩阵

每个租户成员（`tenant_members` 一行）拥有且仅拥有一个角色：

| 角色 | 标识 | 典型场景 | 关键能力 |
| --- | --- | --- | --- |
| 只读 | `viewer` | 只查阅、提问的成员 | 仅读，不可发起任何变更 |
| 贡献者 | `contributor` | 上传文档、维护自己的 KB / Agent | 可变更 `creator_id == 自己` 的资源；他人资源等同 Viewer |
| 管理员 | `admin` | 租户内运维 | 可变更租户内任意资源；管理成员；配置共享基础设施（模型、解析器、存储、向量库等） |
| Owner | `owner` | 租户创建者 | Admin 的全部权限 + 可删除租户；不会被其他 Admin 降级；每个租户有且只有一位 |

角色等级为：

`viewer < contributor < admin < owner`

## 5.2 当前空间级能力边界

按当前实现，空间级 RBAC 主要负责：

1. 空间成员管理
2. 模型、向量库、MCP、网络搜索、存储、解析器等租户基础设施管理
3. 租户配置与 API Key 相关能力
4. Owner 删除租户、维持唯一 Owner 等硬约束

补充说明：

1. API Key 合成的虚拟用户在所属租户内固定为 Admin。
2. 若租户没有任何活跃成员，首位通过认证的真人会被自动提升为 Owner。
3. 空间级 RBAC 决定的是**租户控制面**，不是组织树作用域。

---

## 6. 组织树权限

## 6.1 数据来源与角色

组织树权限来自：

1. `organizations`
2. `organization_members_pre_plan3`

当前组织树成员角色：

1. `admin`
2. `editor`
3. `viewer`

这是**用户级**组织归属模型，不是租户级共享模型。

## 6.2 当前作用域规则

按当前代码实现：

1. 组织树读范围取决于用户所在组织与其后代组织。
2. org-scoped 资源的管理范围取决于用户担任 `admin` 的组织及其后代组织。
3. `tenantRoleGrantsRootOrgProjection()` 当前只对 `tenant_members.role=owner` 提供根节点投影。
4. 普通 `tenant_members.admin` 不会自动获得根组织投影。

补充说明：

1. 组织树 `admin` 与空间 `admin` 不是同一个概念。
2. 当前实现中，这两者仍有部分显示层与管理边界上的混用，需要维护时特别注意。

---

## 7. 协作空间权限

协作空间权限来自：

1. `organization_tenant_members`
2. `kb_shares`
3. `agent_shares`

这是**租户级共享成员**模型，不是组织树成员模型。

当前协作空间角色：

1. `admin`
2. `editor`
3. `viewer`

其职责是：

1. 共享空间成员管理
2. 邀请 / 审批 / 加入
3. KB / Agent 共享关系维护
4. 共享资源访问通道建立

补充说明：

1. 协作空间管理员不天然等于空间管理员。
2. 协作空间权限不会改写源租户的资源归属。

---

## 8. 资源归属与资源权限

## 8.1 `creator_id` / `created_by`

当前系统通过资源归属字段实现“自己资源”和“他人资源”的区别：

1. `knowledge_bases.creator_id`
2. `custom_agents.created_by`
3. 子资源沿归属链回溯到所属 KB 或 Agent

由此形成两类守卫：

1. **角色守卫**
   - `Viewer()` / `Contributor()` / `Admin()` / `Owner()`
2. **归属守卫**
   - `OwnedKBOrAdmin()` / `OwnedAgentOrAdmin()` / `OwnedChunkKBOrAdmin()` 等

## 8.2 同租户资源可见性

当前 KB / Agent 同租户可见性统一走：

1. `sameTenantResourceAuthorizer`
2. `KBVisibilityService`
3. `AgentVisibilityService`

当前 read 规则：

| Visibility | 当前读取规则 |
| --- | --- |
| `global` | 同租户可读 |
| `org` | 命中组织树读范围可读 |
| `private` | 创建者本人可读；平台级 privileged operator 可绕过 |

当前 manage 规则：

| Visibility | 当前管理规则 |
| --- | --- |
| `global` | 创建者、平台高权、以及特定根层作用域可管理 |
| `org` | 创建者、平台高权、根层作用域、org admin 子树范围可管理 |
| `private` | 创建者、平台高权、以及特定根层作用域可管理 |

## 8.3 当前 private 资源的特殊点

当前实现中：

1. `private` 的**读**并不直接由 `tenant_members.admin/owner` 决定。
2. `private` 的平台绕过取决于 `isPrivilegedResourceOperator()`。
3. 该函数当前把 `IsSystemAdmin`、`IsSuperAdmin`、`CanAccessAllTenants` 都视为绕过条件。

因此，当前系统里的 private 读取边界仍然带有平台兼容字段影响。

## 9. 跨空间与创建空间

## 9.1 当前跨空间访问

当前跨空间访问有两类入口：

1. `RequireCrossTenantAccess`
   - 用于 `/tenants/all`、`/tenants/search` 等真正跨租户路由
   - 当前只认 `CanAccessAllTenants=true`
   - 且要求 `tenant.enable_cross_tenant_access=true`

2. `IsCrossTenantSuperuser`
   - 用于 `X-Tenant-ID` 路径、URL tenant bypass 等
   - 当前认 `CanAccessAllTenants || IsSystemAdmin || IsSuperAdmin`
   - 同样要求 `tenant.enable_cross_tenant_access=true`

## 9.2 当前创建空间

`POST /tenants` 的当前控制链与跨空间列表并不完全一致：

1. 后端 `TenantHandler.CreateTenant` 允许 `IsSuperAdmin || IsSystemAdmin`
2. 若 `CanAccessAllTenants=true`，允许使用完整 payload 路径
3. 否则走受限的自助创建路径

因此，当前“平台管理者能否创建空间”和“能否浏览全部空间”不是完全同一套条件。

## 10. 成员展示与前端状态

## 10.1 当前前端状态折算

当前前端 `authStore` 中：

1. `isSystemAdmin = user.is_system_admin`
2. `isSuperAdmin = isSystemAdmin || user.is_super_admin`
3. `canAccessAllTenants = user.can_access_all_tenants`

因此，前端显示层会把 system admin 纳入 super admin 展示语义。

## 10.2 当前成员列表行为

当前组织树成员列表和空间成员列表都会对平台管理员做额外过滤：

1. `ListOrgTreeMembers()` 过滤 `is_super_admin=true` 和 `is_system_admin=true`
2. `CountFilteredByTenant()` / `ListPagedByTenant()` 也过滤二者
3. 根节点投影成员时同样会跳过 `IsSuperAdmin || IsSystemAdmin`

因此，当前成员展示结果并不完全等价于数据库中的真实成员集合。

## 11. 当前系统的维护要点

维护当前权限系统时，至少要同时检查以下 4 组位置：

1. **用户模型与登录态**
   - `internal/types/user.go`
   - `internal/handler/auth.go`
   - `frontend/src/api/auth/index.ts`
   - `frontend/src/stores/auth.ts`

2. **平台级守卫与跨空间访问**
   - `internal/middleware/access.go`
   - `internal/middleware/rbac.go`
   - `internal/handler/tenant.go`

3. **同租户资源可见性**
   - `internal/application/service/same_tenant_scope.go`
   - `internal/application/service/kb_visibility.go`
   - `internal/application/service/agent_visibility.go`
   - `internal/handler/rbac_lookups.go`

4. **成员展示与组织树**
   - `internal/application/repository/organization.go`
   - `internal/application/repository/tenant_member.go`
   - `internal/handler/org_tree.go`
   - `internal/handler/tenant_member.go`

任何一处单独修改，都可能造成“后端权限正确但前端显示错误”或“UI 隐藏了入口但 API 仍可访问”的不一致。

---

## 12. 与 `main` 分支的关系

当前 `main` 分支仍然保留 `is_system_admin` 概念，并在模型、路由、中间件、系统管理接口、前端状态和迁移里持续使用。

因此：

1. 当前系统的正式总览说明必须保留 `is_system_admin` 概念。
2. 若后续要推进到仅保留 `is_super_admin`，那属于新一轮权限收口改造，而不是当前系统现状本身。
