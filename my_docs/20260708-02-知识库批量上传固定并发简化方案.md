# 20260708-02-知识库批量上传固定并发简化方案

## 1. 本次需求收敛

本次不做批次计划、不做暂停继续、不做独立上传批次表，只实现三个目标：

1. 批量上传后，文件先进队列，但同一知识库同时最多只启动固定数量的解析任务，默认 5。
2. 还没真正开始执行的文件显示为“未开始”；已经开始执行的文件继续沿用当前状态展示逻辑。
3. 在知识库设置的“高级设置”里增加“同时执行任务数”，默认 5，修改后立即对后续派发生效。

## 2. 当前代码事实

### 2.1 前端上传并不是并发风暴

当前文件夹上传在 frontend/src/views/knowledge/KnowledgeBase.vue 的 executeUploadBatch 中是逐文件 await 上传，不是 Promise.all 并发上传。

因此这次不需要做前端“分批上传”重构。

### 2.2 当前真正的问题在后端立即入队

internal/application/service/knowledge_create.go 中，CreateKnowledgeFromFile 在保存 knowledge 后会立即 enqueue document:process。

所以问题不是上传太快，而是“所有文件一保存完就都能进入解析队列”。

### 2.3 当前已经有 pending 状态，但前端显示没有拆开

frontend/src/views/knowledge/components/DocumentListView.vue 当前把：

1. pending
2. processing

都显示成了同一个“处理中”状态。

因此“未开始”不需要新建状态，只需要把 pending 单独显示出来。

### 2.4 现有 asynq.concurrency 不能直接满足“立即生效”

internal/application/service/system_setting.go 已明确说明：

1. asynq.concurrency 是 asynq worker pool 大小。
2. 它在 server 启动时读取。
3. 修改后需要重启。

所以，如果直接依赖当前的系统设置 asynq.concurrency，是做不到“知识库高级设置里改完立即生效”的。

结论：

1. 全局默认值可以改成 5。
2. 但“立即生效”的实际控制点，必须放在知识库上传派发逻辑里，而不是指望热更新 asynq server 并发。

## 3. 推荐的最小可执行方案

本次采用“固定并发上限 + 补位派发”的最小方案，不引入批次表，也不复用 task_pending_ops。

核心思路：

1. 文件上传后仍然创建 knowledge 记录，parse_status 先保持 pending。
2. 新增一个“是否已经提交到解析队列”的内部字段。
3. 只有当同一知识库当前已提交的解析任务数小于上限时，才把新的 knowledge 真正 enqueue 到 document:process。
4. 当某个文档处理结束后，再从同库中补位派发下一个 pending 文档。

这就能得到用户要的行为：

1. 20 个文件上传后，如果上限是 5，则只有前 5 个真正开始解析。
2. 剩余 15 个保持 pending，前端显示“未开始”。
3. 任意一个进行中的文件完成后，系统自动补位启动下一个 pending 文件。

## 4. 实现设计

### 4.1 并发控制口径

并发控制单位采用“同一知识库当前已提交到解析链路的文档数”。

统计口径建议为：

1. parse_task_enqueued = true
2. parse_status in pending, processing, finalizing

原因：

1. pending 但已提交到 asynq 的文档，虽然还没被 worker 真正拿到，也应该占一个槽位。
2. processing 和 finalizing 都属于“已经开始执行”的文档，也必须继续占用槽位。
3. completed、failed、cancelled 不再占用槽位。

### 4.2 默认值策略

默认值统一改为 5，但分成两层：

#### 1. 全局兜底默认值

把以下默认值从 32 改为 5：

1. internal/router/task.go 中的 defaultAsynqConcurrency
2. internal/application/service/system_setting.go 中 asynq.concurrency 的默认值
3. 对应部署环境里的 WEKNORA_ASYNQ_CONCURRENCY 默认值

作用：

1. 降低系统整体异步压力上限。
2. 即使某些入口没走知识库级补位逻辑，也不会像现在这样默认开到 32。

#### 2. 知识库级运行时上限

新增知识库字段 max_concurrent_parse_tasks，默认 5。

作用：

1. 这是文件批量上传实际采用的运行时上限。
2. 该值在每次派发时实时读取，所以修改后可立即生效。

实际有效值建议定义为：

1. 如果 knowledge_base.max_concurrent_parse_tasks > 0，则用它。
2. 否则回退到系统设置 asynq.concurrency。
3. 如果系统设置也没有值，则回退到环境变量 WEKNORA_ASYNQ_CONCURRENCY。
4. 最终默认 5。

这样既保留用户提到的 WEKNORA_ASYNQ_CONCURRENCY 语义，也满足 KB 高级设置即时生效。

### 4.3 数据结构最小改动

本方案只建议新增两个字段。

#### knowledge_bases

新增字段：

1. max_concurrent_parse_tasks int not null default 5

用途：

1. 知识库高级设置中的“同时执行任务数”。
2. 上传与补位派发时实时读取。

#### knowledges

新增字段：

1. parse_task_enqueued bool not null default false

用途：

1. 标记该 knowledge 是否已经真正提交到 document:process 队列。
2. 避免同一条 knowledge 被重复入队。
3. 支撑“补位派发”统计槽位数。

### 4.4 上传时的简化派发逻辑

在 internal/application/service/knowledge_create.go 中调整 CreateKnowledgeFromFile：

1. 仍然保存文件。
2. 仍然创建 knowledge，parse_status = pending。
3. 初始 parse_task_enqueued = false。
4. 创建完成后，不再无条件 enqueue document:process。
5. 改为调用 tryDispatchPendingKnowledge(kbID)。

tryDispatchPendingKnowledge(kbID) 的逻辑：

1. 读取知识库 max_concurrent_parse_tasks。
2. 统计当前已占用槽位数。
3. 计算 available = limit - occupied。
4. 如果 available <= 0，直接返回。
5. 按创建时间升序查询 parse_status = pending 且 parse_task_enqueued = false 的 knowledge。
6. 取前 available 条，逐个 enqueue document:process。
7. enqueue 成功后，把这些 knowledge 的 parse_task_enqueued 置为 true。

这样批量上传时自然形成：

1. 先上传的前 5 个被派发。
2. 后面的都只是 pending，不会进入执行。

### 4.5 处理完成后的补位逻辑

关键点不是上传时限流，而是“完成一个，补一个”。

因此需要在文档处理进入终态后统一补位。

建议新增一个公共 helper，例如：

1. releaseParseSlotAndDispatchNext(kbID, knowledgeID)

行为：

1. 把当前 knowledge 的 parse_task_enqueued 置为 false。
2. 再调用 tryDispatchPendingKnowledge(kbID)。

应接入的终态收口点：

1. document:process 正常完成，knowledge 最终进入 completed。
2. document:process 或后处理链路失败，knowledge 最终进入 failed。
3. 用户取消，knowledge 进入 cancelled。
4. dead-letter 回调把知识置 failed 时，也要补位。

这里的关键不是“ProcessDocument 函数返回”，而是“knowledge 离开 in-flight 状态”。

否则如果在 parse 结束但 finalizing 还没结束时就提前补位，会重新把模型服务压力放大。

### 4.6 修改知识库设置时立即生效

知识库高级设置保存成功后，不需要重启。

建议在 internal/application/service/knowledgebase.go 的 UpdateKnowledgeBase 成功后追加一步：

1. 如果 max_concurrent_parse_tasks 发生变化，立即调用 tryDispatchPendingKnowledge(kbID)。

效果：

#### 从 5 调大到 8

1. 保存成功后立刻补派发 3 个 pending 文档。
2. 不需要等已有任务完成。

#### 从 5 调小到 2

1. 已经开始的 5 个继续跑完。
2. 在途数降到 2 以下之前，不再启动新的 pending 文档。

这就是“修改后这个值即可生效”在当前架构下最小且合理的实现方式。

## 5. 前端展示改动

### 5.1 列表状态展示

当前 frontend/src/views/knowledge/components/DocumentListView.vue 中：

1. pending
2. processing

都映射成了 statusProcessing。

本次应改为：

1. pending -> 未开始
2. processing -> 当前逻辑
3. finalizing -> 当前逻辑
4. failed -> 当前逻辑
5. cancelled -> 当前逻辑
6. completed -> 当前逻辑

这样就满足：

1. 没执行的文件显示未开始。
2. 已经执行的文件按当前逻辑显示。

### 5.2 知识库高级设置

当前 frontend/src/views/knowledge/settings/KBAdvancedSettings.vue 只有 AI 问题生成。

本次在同一组件里新增一项：

1. 同时执行任务数

建议控件：

1. t-input-number
2. 最小值 1
3. 默认值 5
4. 可选最大值 20

展示文案建议：

1. 标签：同时执行任务数
2. 说明：批量上传时，同一知识库同时进入解析流程的最大文档数。未开始的文件会保持“未开始”，已完成一个后自动补位下一个。

### 5.3 提交数据链路

## 7. 验收标准

### 场景 1：默认值验证

前置条件：

1. 新建知识库，不改高级设置。

期望：

1. 默认同时执行任务数为 5。
2. 批量上传 20 个文件后，最多只有 5 个文档进入 processing/finalizing。
3. 其余文档显示未开始。

### 场景 2：补位执行

前置条件：

1. 同时执行任务数为 5。
2. 批量上传 20 个文件。

期望：

1. 任意一个文档进入 completed/failed/cancelled 后，系统自动补位启动下一个 pending 文档。
2. 任意时刻同库在途文档数都不超过 5。

### 场景 3：调大并发值立即生效

前置条件：

1. 知识库已有大量 pending 文档。
2. 当前同时执行任务数为 5。

操作：

1. 在知识库设置高级设置中改成 8 并保存。

期望：

1. 保存成功后立即新增派发 3 个 pending 文档。
2. 不需要重启服务。

### 场景 4：调小并发值立即生效

前置条件：

1. 当前已有 5 个在途文档。

操作：

1. 把同时执行任务数改成 2。

期望：

1. 已经开始的 5 个继续完成。
2. 在途数降到 2 以下之前，不再派发新的 pending 文档。

## 8. 与上一版复杂方案相比，这一版删掉了什么

本次明确不做：

1. upload batch 主表
2. task_pending_ops 作为上传待派发表
3. 批次暂停 / 继续 / 取消
4. 批次进度卡片
5. 按批次维度的计划管理

保留的只有一个最小控制目标：

1. 上传可继续堆积。
2. 执行并发固定为 5 或知识库设置值。
3. 未执行的文档显示未开始。

## 9. 最终建议

按照当前需求，这就是最合适的落地路径：

1. 把全局默认 WEKNORA_ASYNQ_CONCURRENCY 从 32 改成 5，先兜底。
2. 给知识库新增 max_concurrent_parse_tasks，默认 5。
3. 给 knowledge 新增 parse_task_enqueued，用它做“是否已提交到解析队列”的内部标记。
4. 上传时只补位派发，不再全部立即 enqueue。
5. 终态时自动补位。
6. 前端把 pending 单独显示为未开始。

这套方案不复杂，但能直接满足本次需求，而且与当前代码结构兼容度最高。
