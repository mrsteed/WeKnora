## 2. 代码复核后的关键结论

### 2.1 `mdev` 如果新建数据库，当前 `schema_migrations.version=88` 只作为参考，不再作为首轮兼容约束

当前引用点如下：

| 项目 | 当前值 |
|---|---|
| 本地 `dev` 头提交 | `c3ce860d` |
| `upstream/main` 头提交 | `9b4f792a` |
| `upstream/main` 迁移上界 | `000084_memory.*` |
| 当前数据库 `schema_migrations.version` | `88` |
| 当前数据库 dirty | `false` |

这意味着：

1. `mdev` 必须从 `upstream/main` 起分支。
2. 如果 `mdev` 首轮使用的是全新隔离数据库，那么当前共享开发库的 `version=88` 只是一份现状参考，不再是 `mdev` 的迁移兼容目标。
3. 在 fresh DB 前提下，`mdev` 可以直接以上游 `000084` 为基线，自行设计一组新的 `000085+` 迁移尾巴，只承接本轮真正需要的权限主线语义。
4. 只有当后续明确要求 `mdev` 接当前旧库、导入旧库数据或复用旧库账本时，才需要单独补一套“历史数据回填/兼容迁移”方案；这不应污染首轮 `mdev` 迁移设计。

### 2.2 upstream 已经有 tenant 级 RBAC 和组织共享成员主干，但编号与本地不同

再次审查后确认：

1. upstream 已经有 `tenant_members`，对应的是 `migrations/versioned/000043_tenant_rbac.*`。
2. upstream 已经有 `organization_tenant_members`，对应的是 `migrations/versioned/000045_org_tenant_members.*`。
3. upstream 已经有 `organizations.owner_tenant_id`，对应的是 `migrations/versioned/000046_org_owner_tenant_id.*`。

因此：

1. 本地的 `000078_tenant_rbac`、`000080_org_tenant_members`、`000081_org_owner_tenant_id` 本质上是对同一批语义的历史重编号，不应再原样复制到 `mdev`。
2. `mdev` 应以上游 `000043/000045/000046` 为数据库主干，而不是再把本地 `000078/000080/000081` 重放一遍。

### 2.3 upstream 缺少的不是 tenant-RBAC 主干，而是本地 same-tenant 可见性与组织树骨架

### 2.5 当前权限模型实际上是“双层共享 + 一层组织树”并存，`mdev` 不能把它误合并成一套

代码复核后确认：

1. 共享空间、组织共享、KB share、Agent share 主要依赖 `organization_tenant_members` 和 `tenant_members`。
2. 同租户内资源可见性、组织树节点、子组织管理员、same-tenant 范围管理，依赖 `organization_members`。
3. `same_tenant_scope.go` 通过 `orgTreeService.GetUserOrganizations` 读取用户级组织树范围。
4. `organization.go` 的共享与列表查询则大量依赖 tenant 级成员关系。

因此 `mdev` 的正确目标不是把两套模型互相替换，而是：

1. 保留 upstream 的 tenant 级共享与成员模型。
2. 在其上恢复本地用户级组织树和 same-tenant 资源可见性。

### 2.6 Agent 和 IM 的权限问题不是列表问题，而是运行时 scope 问题

再次审查后确认，真正决定行为的入口在：

1. `internal/application/service/agent_kb_scope.go`
2. `internal/application/service/session_knowledge_qa.go` 中的 `resolveKnowledgeBasesFromAgent`
3. `internal/application/service/custom_agent.go` 中的 `GetSuggestedQuestions`
4. `internal/handler/knowledgebase.go` 的 `agent_id` 分支
5. `internal/im/cmd_search.go`
6. `internal/im/cmd_info.go`

只恢复列表页可见性，不能解决 Agent `all` 模式、建议问题、IM `/search`、IM `/info` 的实际越权范围问题。

### 2.7 当前 `dev` 是 `CreatedBy` 与 `CreatorID` 双轨并存，但 `mdev` 应统一为 `CreatorID`

再次审查后确认：

1. `types.KnowledgeBase` 同时有 `CreatedBy` 与 `CreatorID`。
2. repository 里存在 `syncKnowledgeBaseCreatorFields`，会在读写时互相回填。
3. `internal/handler/rbac_lookups.go` 与 `KnowledgeService.GetOwningKBCreatorID` 已经把 `CreatorID` 当作知识库所有权主字段。
4. upstream 的 tenant-RBAC 主干已经用 `creator_id`。
5. 本地 same-tenant 可见性、知识库创建入口、创建者昵称填充和部分前端列表逻辑仍然在使用 `created_by`。

在 `mdev` 新建数据库的前提下，建议直接统一为 `CreatorID`，而不是继续保留双轨：

1. `knowledge_bases` 不再新增或延续 `created_by` 字段，所有权统一落在 `creator_id`。
2. same-tenant 可见性 SQL、KB 创建入口、创建者昵称逻辑、前端“我创建的”判断统一改读 `creator_id`。
3. `syncKnowledgeBaseCreatorFields` 这类双向兼容辅助逻辑在 `mdev` 中应逐步删除，而不是继续扩散。
4. 如果短期内仍需保留 `created_by_nickname` 这类展示字段，可以继续保留，但它应从 `creator_id` 派生，而不是依赖独立的 `knowledge_bases.created_by` 存储列。
5. 这里的统一仅针对 `knowledge_bases`。`knowledges.created_by` 仍应保留，因为它表达的是“文档上传者/创建者”，语义不同于知识库 owner。

## 3. `mdev` 的正确同步策略

### 3.1 分支策略

严格按以下方式起分支：

```bash
git fetch origin --prune
git fetch upstream --prune
git checkout -b mdev upstream/main
```

不建议从 `dev` 切分支，也不建议把 `dev` 整体 merge 到 `mdev`。

### 3.2 工作区前置条件

当前工作区不是完全 clean，至少存在未提交文档：

1. `my_docs/20260819-02-mdev分支权限主线同步方案.md`

执行同步时建议二选一：

1. 先提交或 stash 当前文档变更，再在当前仓库起 `mdev`。
2. 直接使用新的 worktree 或新的本地 clone 做 `mdev` 同步。

推荐第二种，这样可以避免文档草稿与真正的同步代码混在同一工作区中。

### 3.3 数据库策略

`mdev` 首轮建议明确采用 fresh DB 策略，而不是兼容当前共享开发数据库。

推荐顺序：

1. 直接新建一套隔离数据库给 `mdev` 使用。
2. 以上游 `000084` 为迁移基线，在 `mdev` 中新增一组新的 `000085+` 迁移，只保留本轮需要的权限主线语义。
3. 在 fresh DB 上从零执行完整迁移，作为 `mdev` 首轮唯一验收基线。
4. 当前共享开发数据库的 `version=88` 只用于对照“本地曾经演化出哪些能力”，不作为 `mdev` 首轮迁移目标。
5. 如果后续需要接旧库，再单独设计导入脚本、数据回填脚本或兼容迁移，不在首轮文档中预先绑定。

## 4. 迁移计划

### 4.1 不应复制的迁移

以下本地迁移不要原样复制到 `mdev`：

1. `000078_tenant_rbac.*`
2. `000080_org_tenant_members.*`
3. `000081_org_owner_tenant_id.*`

原因：upstream 已经分别以 `000043`、`000045`、`000046` 引入了同类结构。

### 4.2 `mdev` 的新迁移尾巴建议

在 fresh DB 策略下，不再为了兼容旧账本而“原义承接本地 `000085` 到 `000088`”。更合理的做法是：

1. 保留 upstream 到 `000084` 的迁移树。
2. 在 `mdev` 上重新设计一组新的 `000085+` 迁移，只引入本轮需要的 schema。

建议的迁移尾巴如下：

1. `000085_mdev_org_tree_foundation.*`
	目标：为 `organizations` 增加 org-tree 结构字段，为 `users` 增加 `is_super_admin`。
2. `000086_mdev_kb_agent_visibility.*`
	目标：为 `knowledge_bases` 增加 `visibility`、`organization_id`，为 `custom_agents` 增加 `visibility`、`organization_id`，并补齐查询索引。
3. `000087_mdev_im_channels_created_by.*`
	目标：为 `im_channels` 增加 `created_by` 和相关索引。由于是 fresh DB，历史 backfill 逻辑可以大幅简化，甚至保留为 no-op。
4. `000088_mdev_knowledges_created_by.*`
	目标：为 `knowledges` 增加 `created_by` 和索引，用于文档上传者权限控制。
5. `000089_mdev_user_active_login_uniques.*`
	目标：把用户名、邮箱、手机号的唯一约束改成 active-only 语义。
6. `000090_mdev_builtin_agents_global_visibility.*`
	目标：仅作为可选修复迁移。对 fresh DB 首轮不是必需项，只有在未来导入旧数据或复用非 fresh DB 时才建议启用。

### 4.3 `knowledge_bases` 字段统一策略

`mdev` 应直接把 `knowledge_bases` 的 owner 统一为 `creator_id`，不再延续 `created_by` 双轨。

这意味着新的迁移策略应遵循：

1. `knowledge_bases` 不新增 `created_by` 列。
2. `knowledge_bases` 的 same-tenant 可见性、owner 判断、创建者昵称填充统一改为读取 `creator_id`。
3. `frontend` 端“我创建的”“可管理”“显示创建者”逻辑统一改读 `creator_id`。
4. 如需短期兼容显示层，可保留 `created_by_nickname` 这类展示字段，但必须由 `creator_id` 派生。
5. `knowledges.created_by` 保持独立，不参与这次统一。

### 4.4 迁移注意事项

1. 由于 `mdev` 首轮使用 fresh DB，`000089_mdev_user_active_login_uniques` 一般不会因为历史重复数据失败；只有未来导入旧数据时，才需要额外做重复值预检。
2. `000090_mdev_builtin_agents_global_visibility` 在 fresh DB 首轮默认可以不启用，因为当前代码里的 `updateBuiltinAgent` 已经会把新的 built-in override row 持久化为 `global`。
3. `organization_members` 是本地用户级 org-tree 的权威成员表，不能删除。`org-tree` 与 same-tenant 可见性依赖它。
4. 如果未来把 `mdev` 接到旧库或导入旧数据，应额外新增一份“legacy import / backfill”文档，而不是回头污染这套 fresh-DB-first 迁移尾巴。

## 7. 最终建议

本轮 `mdev` 详细执行建议可以归纳为：

1. `mdev` 从 `upstream/main` 起分支，不 merge 整个 `dev`。
2. 以上游已有的 `tenant_members`、`organization_tenant_members`、`owner_tenant_id` 为基础，不再重放本地重编号迁移。
3. 本地真正要补的是：org-tree、same-tenant KB/Agent 可见性、Agent 运行时 KB scope、文档上传者权限、IM 创建者隔离、修改密码、本地启动脚本。
4. 在 fresh DB 策略下，`mdev` 不必兼容当前共享开发库的 `version=88`；它应以上游 `000084` 为基线，自行设计新的 `000085+` 迁移尾巴。
5. `knowledge_bases` 建议直接统一到 `CreatorID`，不再延续 `CreatedBy` 双轨；`knowledges.created_by` 继续保留为文档上传者语义。
6. `organization_members` 与 `organization_tenant_members` 必须并存，前者服务于 org-tree 与 same-tenant 可见性，后者服务于共享空间与租户级共享。
7. 第一轮优先完成权限主线，不要把品牌、长文档、导出一起带入。

如果严格按本计划执行，`mdev` 会成为一条基于最新 upstream 的“空间/组织/权限/知识库/智能体可见性主线”分支，而不是当前 `dev` 的削减版。
