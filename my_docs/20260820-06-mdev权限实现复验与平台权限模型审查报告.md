#### 1.2.2 §3.1 A3 的"看似差异实测等价"

`kbAccessPrivilegedOperatorFromContext`（`middleware/kb_access.go:506-519`）实现为：取到 `*types.User` 时**只**判 `types.IsPlatformPrivilegedUser(user)`，取不到 user 时才兜底 `types.IsSystemAdminFromContext(ctx)`；与 05 报告目标式 `A || B`（无条件叠加）写法不同。

1. ctx 中 `SystemAdmin` 标志由 `auth.go:111/264` 写 session 时置位，来源即 `user.IsSystemAdmin`（同一 user 对象）；

3. 故"取到 user"路径下 `IsPlatformPrivilegedUser(user)` ⇒ `IsSystemAdminFromContext(ctx)`，两个分支的判定源同源，行为等价。

## 2. 三类权限语义界定（基于代码实证）

### 2.1 定位速览

| 维度 | SystemAdmin | SuperAdmin | space_admin（OrgRoleAdmin） |
|---|---|---|---|
| 标志位 | `User.IsSystemAdmin`（`user.go:102`，DB 索引） | `User.IsSuperAdmin`（`user.go:100`，default false） | **非用户级标志**，组织树节点角色 `OrgRoleAdmin`（节点 `MyIsAdmin=true`） |
| 作用域 | 平台级（跨全部租户） | 平台级（跨全部租户） | 单租户内、限定组织子树 |
| 授予方式 | 仅 `system.go` 的 promote API（幂等、写审计），**无 API 可降级**，撤销只能改 DB | `PUT /org-tree/super-admin`（`org_tree.go:1695` `SetSuperAdmin`）可设可撤，有自我撤销保护 | `orgTreeService.SetOrgAdmin`（`org_tree.go:675`）按 org 节点授予/取消 |
| 上游谱系 | **upstream/main 原有** | **mdev 本地分叉新增** | **mdev 本地分叉新增**（org-tree 体系） |

### 2.2 各自的行为通道

**公共通道**（两者平台身份被刻意合并，§3 详述）：`IsPlatformPrivilegedUser` → 跨租户直通（`access.go`）、KB 门控直接 `OrgRoleAdmin`（`kb_access.go:350-356`）、列表 `bypass=true`（全租户可见）、`OwnerOrSystemAdminDelete`（`rbac.go:234`）。

**SystemAdmin 独有**：`RequireSystemAdmin` 守卫（`middleware/rbac.go:147`，经 `IsSystemAdminFromContext`）保护 `/system/admin/*`（promote 自身、审计日志）与 `RegisterOrgTreeSuperAdminRoutes`（授予 SuperAdmin 的 API 本身）。注意：因 `ToUserInfo` 合并下发（§2.3），**JWT 会话侧两个身份都能通过该守卫**；API-key 侧则只认 platform scope。

**SuperAdmin 独有**：
- `RequireSuperAdmin()` 中间件（`middleware/super_admin.go`）只认 `IsSuperAdmin`——**当前零路由挂载，属死守卫**（全仓 grep 仅定义处一处）；
- `ToUserInfo` 单独下发 `is_super_admin`（`user.go:273`），驱动前端 `authStore.isSuperAdmin`，是 KB/Agent 编辑器可见性行显示（`isSuperAdmin || myOrgTreeOrgs.length > 0`）与 platform 管理页入口的直接依据。

**space_admin**：
- 读范围：所属 org + **Path 前缀全部后代**（`same_tenant_scope.go` `resolveScope`）→ 仅见 `visibility=org` 且落在子树内的 KB/Agent；
- 管范围：自己是 `MyIsAdmin` 的 org + 后代 → `CanManageKB/CanManageAgent=true`；子树外或仅普通成员身份的 org 只读；
- 特例：admin 身份落在 level ≤ 1 根节点（`userHasExplicitRootAdminMembership`）时 `isTenantAdminOrOwner=true`，对本租户**所有**资源获得管理权；
- 不享受：平台特权直通、跨租户、`RequireSuperAdmin`/`RequireSystemAdmin` 路由；列表 `bypass=false` 走子树过滤。

### 2.3 一个必须留意的实现细节

`ToUserInfo()` 把 `IsSuperAdmin` **合并**进下发前端的 `IsSystemAdmin` 字段（`user.go:274`：`IsSystemAdmin: u.IsSystemAdmin || u.IsSuperAdmin`）。后果：

1. 前端 `is_system_admin` 对纯 SuperAdmin 也是 true，前端 **无法**凭该字段区分两种平台身份，必须依赖单独的 `is_super_admin`（这正是 05 报告追踪的 `userInfoFromApi` 漏拷 bug 的温床）；
2. 该合并**只作用于前端序列化**，后端 ctx 侧的 `SystemAdmin` 标志（`auth.go:111` `SystemAdmin: user.IsSystemAdmin`）不含 SuperAdmin 兜底（风险详见 §4.1）。

### 2.4 判定优先级（资源访问视角）

1. **跨租户**：`IsPlatformPrivilegedUser`（两个平台身份任一）直通；纯 `CanAccessAllTenants` 需全局 `EnableCrossTenantAccess`。
2. **自租户**：平台特权 → 直接 `OrgRoleAdmin`；space_admin → org 子树读/管；普通成员 → 按 `visibility`（global 全员读 / org 子树读 / private 仅创建者）；tenant Owner/根级 admin → 全租户管理。
3. 三者是**正交维度**而非互斥等级：同一用户可同时是某 org 的 admin 与 SuperAdmin，后者优先生效。

### 2.5 `canBypassSameTenantResourceVisibility` 语义（纠偏备忘）

该 handler 层 helper（`internal/handler/rbac_lookups.go:321`，与 dev 逐字一致）= `IsPlatformPrivilegedUser`，**只认两个平台身份，不认 tenant owner/admin**。租户 Owner/Admin 的管理权走 service 层 `canManageResource` 的 `isTenantAdminOrOwner` 分支，是独立于 bypass 的第二通道。05 报告 §3.2 B6 中"超管/tenant owner/tenant admin 返回 true"的描述与 dev 实际不符，以本条与 §1.2.3 为准。

## 3. SystemAdmin vs SuperAdmin：重叠度分析

### 3.1 主线行为完全等价（刻意设计）

| 共享判定 | 位置 | 效果 |
|---|---|---|
| `IsPlatformPrivilegedUser = IsSystemAdmin \|\| IsSuperAdmin` | `context_helpers.go:144` | 跨租户直通、KB `OrgRoleAdmin` 直通、列表 bypass、platform 路由 bypass |
| `HasCrossTenantAccessCapability` | `context_helpers.go:152` | 跨租户能力判定 |
| `OwnerOrSystemAdminDelete` 并列判断 | `rbac.go:234` | 平台身份可删任意 tenant（含跨租户开关关闭时） |
| `ToUserInfo` 合并 | `user.go:274` | 前端两身份不可区分（见 §2.3） |

**结论：一旦两者之一为 true，运行时权限主线（可见性/门控/跨租户）行为完全一致。全 router 中不存在"仅当一个身份为 true 才放行"的生效路由。**

### 3.2 三处实质差异

1. **授予路径**：SystemAdmin 只能 promote（`system.go:1360`，幂等 + 审计），无 API 降级（撤销必须改 DB），是 bootstrap 后的"第 0 个管理员"身份；SuperAdmin 可经 UI/API 反复授予/撤销（`SetSuperAdmin`，带自我撤销保护 `req.UserID == currentUserID && !req.IsSuperAdmin` 拦截）。**SuperAdmin 的授予 API 本身挂在 `SystemAdmin()` 守卫下**（`router.go:287` `superAdmin := v1.Group("", rbacGuards.SystemAdmin())` → `RegisterOrgTreeSuperAdminRoutes`），即 SystemAdmin 是 SuperAdmin 的上游制造者。
2. **一处不对称守卫（当前不生效）**：`RequireSuperAdmin`（`middleware/super_admin.go:13`）只认 `IsSuperAdmin`，是唯一把两者区分开的守卫——但零路由挂载，属死代码。
3. **前端身份语义**：`is_super_admin` 驱动业务 UI 门控（可见性行、platform 入口）；`is_system_admin` 已退化为"平台特权"合并标记。

### 3.3 结论

能力上几乎重复，语义上有意双轨：SystemAdmin = 不可撤销的运维/平台身份；SuperAdmin = 可由平台管理员回收的业务超管。双轨的收敛层是 `IsPlatformPrivilegedUser`（上游无此函数，mdev 为兼容两标志而造）。

## 4. 与 upstream/main（Tencent/WeKnora）的谱系关系

### 4.1 证据

对 `upstream/main` 全仓核查：

| 项 | upstream/main | mdev |
|---|---|---|
| `IsSystemAdmin` | ✅ 12 文件使用（types/middleware/rbac/system handler/routes） | ✅ |
| `IsSuperAdmin` | ❌ **零命中** | ✅ |
| `IsPlatformPrivilegedUser` 包装函数 | ❌ 不存在 | ✅ `context_helpers.go:144` |
| `middleware/super_admin.go` | ❌ 文件不存在 | ✅（死守卫） |
| `/org-tree/super-admin` 路由 | ❌ | ✅ |

SuperAdmin 的引入可归属本地分叉提交：`e0b24635`/`dac28ba9`（"提交组织用户管理相关的功能代码"，最早引入）与 `eef49445`（`feat(org-tree): 组织树管理与组织人员管理（含超管权限与用户密码管理）`，mdev 提交链上的正式功能提交）。

**结论：上游主推（且目前唯一存在）的平台级权限是 SystemAdmin；SuperAdmin（连同整个 org-tree/space_admin 体系）是 mdev 本地分叉新增。**

### 4.2 由此产生的架构风险（建议跟进）

**风险 R1（中）：ctx 侧 system-admin 标志未合并，纯 SuperAdmin 用户在上游路径上会被静默降级。**

`auth.go:111/264` 写 session 时 `SystemAdmin: user.IsSystemAdmin`——不叠加 `IsSuperAdmin`；`ToUserInfo` 的合并只作用于前端序列化，**不作用于后端 ctx**。后果：任何直接消费 `IsSystemAdminFromContext` 的下游（`RequireSystemAdmin` 守卫的 JWT 分支、`service/model.go` 等上游代码）对"只有 `IsSuperAdmin`、没有 `IsSystemAdmin`"的账号判定为 false。具体影响面：
- **`/system/admin/*`（含 promote、审计日志）**：纯 SuperAdmin 账号走 JWT 且非 platform API-key 时被 403——即 SuperAdmin 无法经 UI 提升新的 SystemAdmin，也无法经 UI 授予 SuperAdmin（`/org-tree/super-admin` 挂在同一守卫组下）。这类操作必须用真正的 SystemAdmin 账号或 DB 操作完成；
- **`service/model.go` 等上游新增的 `IsSystemAdmin` 判定**：纯 SuperAdmin 账号静默失去相应能力；
- **`middleware/kb_access.go` 无 user 兜底分支**：若某装配路径未把 user 写入 `c.Keys`（当前 `applyAuthSession` 恒写入，实际不触发），纯 SuperAdmin 不会被判为特权操作者。

当前生产主路径（user 对象恒在 ctx 中，走 `IsPlatformPrivilegedUser`）不受影响；回归面在于**上游每次同步引入新的 `IsSystemAdminFromContext` 消费点时，纯 SuperAdmin 账号会被静默降级**。

**建议**：在 `auth.go` 两处写 session 时改为 `SystemAdmin: user.IsSystemAdmin || user.IsSuperAdmin`，使 ctx 侧与 `ToUserInfo`/前端语义对齐；或维持现状但在 05/本报告中标注"纯 SuperAdmin 账号不享有 /system/admin 路由"为预期行为（二选一，需团队决策）。

**风险 R2（低）：`RequireSuperAdmin` 死守卫。** 当前零挂载。若长期不需要"只认 SuperAdmin"的路由，删除；若保留作为未来 platform 路由的守卫，应改为基于 `IsPlatformPrivilegedUser` 判定以免与 `RequireSystemAdmin` 语义分叉。

**风险 R3（低，源自 §1.1）：fail-open 防御分支。** KB handler 的 `kbVisibility == nil` 回退（List 走全量、同租户直接给 `OrgRoleAdmin`）与 agent handler 的 `visibilityService == nil` 回退，在 `container.go` 强制 `Provide` 下是死代码，但语义是 fail-open。若未来出现手工装配/测试装配不注入这两个 service 的路径，权限会静默放宽。建议后续改为 fail-closed（nil 时 403），非本轮必须。

**风险 R4（备忘）：D2 内置 agent 本地化元数据合并未移植。** `ApplyBuiltinAgentLocalizedMetadata`（dev）在 mdev 全仓不存在，内置 agent 合并仍为 `map[string]bool` 旧写法。若多语言环境下内置 agent 名称/描述需本地化，需单独一轮移植。
