# 知识库创建成功后加载失败根因分析与修复方案

日期：2026-10-09

## 1. 问题摘要

现象不是“知识库创建失败”，而是“知识库创建成功后，前端立即回读该知识库详情失败”，因此页面会同时出现两条提示：

- `知识库创建成功`
- `加载知识库数据失败`

本次问题的根因是“跨租户脏组织 ID 被带入知识库创建请求”，导致知识库记录虽然成功落库，但其 `organization_id` 指向了另一个租户的组织节点。随后前端创建弹窗会立即调用详情接口回读刚创建的知识库；后端在基于组织范围做可见性校验时发现当前用户并不属于该组织，于是返回 403，前端最终展示“加载知识库数据失败”。

## 2. 现象复盘

### 2.1 用户可见现象

页面创建知识库后同时出现：

- 成功 toast：`知识库创建成功`
- 失败 toast：`加载知识库数据失败`

这说明：

1. `POST /api/v1/knowledge-bases` 已经成功。
2. 创建后的二次读取 `GET /api/v1/knowledge-bases/:id` 失败。

### 2.2 前端代码行为

知识库创建弹窗在创建成功后不会立即关闭，而是继续调用一次详情加载：

- 创建成功后执行 `await loadKBData(createdKbId)`
- `loadKBData` 内部会并行请求：
  - `getKnowledgeBaseById(kbId)`
  - `listKnowledgeFiles(kbId, { page: 1, page_size: 1 })`
- 任何一步失败，都会触发：`MessagePlugin.error(t('knowledgeEditor.messages.loadDataFailed'))`

也就是说，只要知识库创建后“详情不可读”，就会出现当前这个表象。

## 4. 根因链条

本次故障由三层问题叠加造成。

### 4.1 前端把组织选择缓存成了全局 localStorage

组织 store 使用如下本地缓存键：

- `weknora_current_org_id`

该键没有 tenant 维度隔离，且用户切换租户时不会自动清空。因此如果用户曾在租户 `10002` 选中过“产品部”，随后切换到租户 `10004`，这个旧组织 ID 仍然会残留在本地。

### 4.2 创建知识库时默认组织选择优先读了脏缓存

知识库创建弹窗在“组织可见”模式下，会自动推导一个 `organization_id`。旧逻辑优先级是：

1. 调用方显式传入的 `initialOrganizationId`
2. `uiStore.kbEditorInitialOrganizationId`
3. `orgStore.currentOrganizationId`
4. `orgStore.myOrgTreeOrgs[0]?.id`

问题在于这里直接使用了 `orgStore.currentOrganizationId`，但它可能是前一个租户遗留下来的组织 ID，而且没有校验它是否存在于“当前租户可见组织列表”中。

### 4.3 后端只校验 organization_id 非空，没有校验归属租户

后端创建/更新知识库时，旧逻辑仅检查：

- 当可见性为 `org` 时，`organization_id` 不能为空

但没有进一步验证：

1. 该组织是否存在
2. 该组织是否属于当前 tenant

因此，跨租户的脏组织 ID 可以被成功写入 `knowledge_bases.organization_id`。

### 4.4 创建后回读详情时 RBAC 正常拦截，于是前端误以为“加载失败”

知识库详情读取时，后端会按当前用户在当前租户下的组织可见范围校验 `organization_id`。

因为脏知识库的 `organization_id` 指向租户 `10002` 的组织，而当前请求上下文属于租户 `10004`，所以：

- 创建接口成功写入
- 详情接口读取被 403 拦住

前端弹窗里统一捕获为：

- `加载知识库数据失败`

这就是“明明创建成功，却提示加载失败”的直接原因。

## 5. 为什么会出现重复知识库

用户每次看到“加载知识库数据失败”，直觉上会认为创建没成功，于是继续重试。

由于实际上 `POST /knowledge-bases` 每次都成功，所以每重试一次都会额外产生一条新的知识库记录。最终造成：

- 指挥中心重复 2 次
- 灭火和特种灾害救援科重复 4 次

这些都是前端“成功后回读失败”引发的二次污染，而不是用户真的创建了多个有效知识库。

## 7. 已执行的代码修复

### 7.1 前端修复一：租户切换时清理组织上下文缓存

修复文件：

- `frontend/src/stores/auth.ts`

处理方式：

- 在 `clearTenantScopedClientState()` 中追加 `useOrganizationStore().clearState()`
- 使 tenant 切换时同步清空：
  - 当前组织 ID
  - 我的组织树列表
  - 共享资源缓存

效果：

- 不再把上一个租户的 `weknora_current_org_id` 带到下一个租户。

### 7.2 前端修复二：重新拉组织树后自动纠偏无效组织 ID

修复文件：

- `frontend/src/stores/organization.ts`

处理方式：

- 拉取 `fetchMyOrgTreeOrganizations()` 后，检查当前 `currentOrganizationId` 是否存在于新返回的组织列表中
- 若不存在，则自动切到当前租户的第一个有效组织；若为空则清空

效果：

- 即使本地还残留旧值，只要拉一次当前租户组织树，就会自动纠偏。

### 7.3 前端修复三：创建弹窗只接受当前租户有效组织

修复文件：

- `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`

处理方式：

- `resolveAutoOrganizationID()` 不再盲信 `currentOrganizationId`
- 改为只从“当前租户可见组织列表”里挑选候选 ID
- 候选优先级仍保留，但增加了“必须在当前租户组织树中存在”的约束

效果：

- 旧缓存即便存在，也不会再被带入创建请求。

### 7.4 前端修复四：每次打开知识库弹窗都刷新当前租户组织树

修复文件：

- `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`

处理方式：

- 打开知识库创建/编辑弹窗时，不再仅在 `myOrgTreeOrgs` 为空时才拉取组织树
- 改为每次打开弹窗都主动刷新一次当前租户组织树

效果：

- 即使内存里还暂存着上一个租户的组织树，只要打开知识库弹窗，就会强制切回当前租户真实组织列表，不再误用旧租户节点。

### 7.5 后端修复一：创建/更新知识库时校验 organization_id 属于当前租户

修复文件：

- `internal/handler/knowledgebase.go`

处理方式：

- 为 `KnowledgeBaseHandler` 注入 `OrgTreeService`
- 新增 `validateKnowledgeBaseOrganization()`
- 在创建和更新知识库时，当 `visibility == 'org'`：
  - 校验 `organization_id` 非空
  - 校验该组织存在于当前 tenant 内
  - 若不属于当前 tenant，直接返回 400：`organization_id does not belong to current tenant`

效果：

- 前端即便再次带入脏值，后端也会立即拒绝，避免再次写出脏数据。

### 7.6 后端修复二：创建者对自己创建的知识库保持读权限

修复文件：

- `internal/application/service/same_tenant_scope.go`

处理方式：

- 在 `canReadResource()` 中增加创建者豁免：
  - 若 `CreatedBy == userID`，则允许读取

效果：

- 即便未来再次出现组织可见性边界数据不一致，创建者也不会被自己创建出来的 KB 立即锁死在外。

注意：

- 这一条是兜底和权限语义对齐修复，不替代前端缓存修复和后端归属校验。

### 7.7 前端修复五：创建成功后详情回读失败时不再出现误导性的双 toast

修复文件：

- `frontend/src/views/knowledge/KnowledgeBaseEditorModal.vue`
- `frontend/src/i18n/locales/zh-CN.ts`
- `frontend/src/i18n/locales/en-US.ts`
- `frontend/src/i18n/locales/ko-KR.ts`
- `frontend/src/i18n/locales/ru-RU.ts`

处理方式：

- `loadKBData()` 改为向调用方返回成功/失败结果，并允许创建后回读场景抑制默认错误 toast
- 创建分支在 KB 已经创建成功但详情回读失败时，改为提示：
  - “知识库创建成功，但详情加载失败，请刷新后重试”
- 避免继续同时弹出“创建成功”和“加载知识库数据失败”这组相互冲突的提示

效果：

- 即便未来再出现创建后回读异常，用户也能明确知道“创建已成功，只是详情页初始化失败”，不会再误判为创建本身失败。

### 9.1 立即建议

1. 清理浏览器本地缓存中的旧组织选择值，或直接刷新当前租户会话。
2. 继续以当前保留的两条有效知识库为准开展后续业务。

2. 对 `knowledge_bases.organization_id` 增加租户一致性巡检脚本，定期扫描跨租户引用。

## 10. 最终结论

本次“加载知识库数据失败”不是知识库创建失败，而是：

1. 前端把其他租户的组织 ID 带进了当前租户的创建请求。
2. 后端没有校验 `organization_id` 的租户归属，导致脏知识库成功落库。
3. 创建后回读详情时，RBAC 正常拒绝越租户组织引用，返回 403。
4. 前端将该 403 统一表现为“加载知识库数据失败”。

本次已完成：

- 脏数据清理
- 前端缓存与默认组织选择修复
- 创建弹窗强制刷新当前租户组织树
- 后端组织归属校验修复
- 创建者读兜底修复
- 创建后回读失败的提示收口修复
- 文档沉淀
