# 网络搜索与网页抓取代理链路审查报告

## 1. 审查范围

本次修订只依据 [test/2](test/2) 与当前代码实现，不再使用其他日志、当前 shell 的 DNS 结果，或对运行环境模式的额外外推。

本次实际核对的代码路径如下：

- Agent 工具网页抓取： [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go)
- Agent 工具网络搜索： [../internal/agent/tools/web_search.go](../internal/agent/tools/web_search.go)
- Agent 工具结果回灌： [../internal/agent/tools/registry.go](../internal/agent/tools/registry.go)、[../internal/agent/observe.go](../internal/agent/observe.go)、[../internal/agent/act.go](../internal/agent/act.go)
- 自动 pipeline 网页抓取： [../internal/application/service/chat_pipeline/web_fetch.go](../internal/application/service/chat_pipeline/web_fetch.go)
- 现有仓库里已显式配置 chromedp profile 目录的参考实现： [../internal/utils/export/export.go](../internal/utils/export/export.go)

## 2. 结论摘要

1. 仅从 [test/2](test/2) 看，`web_search` 在该轮是成功的，日志不能支持“网络搜索本身报错”的结论。
2. [test/2](test/2) 证明当前问题集中在 `web_fetch`，而且是连续两段失败：
   - `chromedp` 启动时无法在浏览器 profile 目录下创建 `SingletonLock`。
   - `chromedp` 失败后，HTTP fallback 把 HTTPS 请求改写成按 IP 直连，但没有显式保留 TLS `ServerName`，于是触发 `x509: cannot validate certificate ... because it doesn't contain any IP SANs`。
3. `chromedp` 当前实际使用的 profile 目录已在日志中直接暴露，为 `/home/hlsa/.local/go-tmp/chromedp-runner*`。
4. 当前 `web_fetch` 代码没有显式配置 `chromedp.UserDataDir(...)`，因此 profile 目录由 chromedp 默认策略自动创建，不受 WeKnora 自身配置控制。
5. 页面抓取失败后仍然能返回结果，是因为 Agent 会把失败的工具结果继续回灌给模型，而该轮里先前成功的 `web_search` 结果仍在上下文中，模型据此继续生成答案。

## 3. 日志证据与根因对应

### 3.1 `web_search` 在 [test/2](test/2) 中是成功的

[test/2](test/2) 显示：

- Round-3 中执行了 `web_search`。
- `DuckDuckGo HTML search returned 5 results`。
- `web_search` 最终 `success=true`。

因此，本次修订后不再把“网络搜索报错”作为 [test/2](test/2) 的结论。

### 3.2 `web_fetch` 先失败在 chromedp 启动，再失败在 HTTPS fallback

[test/2](test/2) 中三条 URL 的失败链路一致。

第一段错误：

```text
chromedp run failed: chrome failed to start:
Failed to create /home/hlsa/.local/go-tmp/chromedp-runner.../SingletonLock:
Permission denied (13)
```

第二段错误：

```text
http error: Get "https://111.7.96.35:443/...":
tls: failed to verify certificate:
x509: cannot validate certificate for 111.7.96.35 because it doesn't contain any IP SANs
```

对应代码行为：

- [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go) 的 `fetchHTMLContent` 先调用 `fetchWithChromedp`。
- `fetchWithChromedp` 失败后，同函数会继续调用 `fetchWithHTTP`。
- `fetchWithHTTP` 最终走到 `fetchWithTimeout`，该函数会把 URL 主机改写成 `PinnedIP:port`。

这就形成了 [test/2](test/2) 中能直接看到的两段错误链：

1. 浏览器 profile 目录创建锁文件失败。
2. HTTP fallback 按 IP 发起 HTTPS 请求，证书校验按 IP 进行，命中 IP SAN 缺失。

### 3.3 `chromedp` 当前到底在哪个目录下

[test/2](test/2) 已经给出了实际目录，例如：

- `/home/hlsa/.local/go-tmp/chromedp-runner3572682719`
- `/home/hlsa/.local/go-tmp/chromedp-runner56936592`
- `/home/hlsa/.local/go-tmp/chromedp-runner3531112384`

这些目录不是 WeKnora 在 [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go) 里显式指定的，而是当前代码只使用了：

- `chromedp.DefaultExecAllocatorOptions[:]`

但没有追加：

- `chromedp.UserDataDir(...)`

所以当前 `web_fetch` 的 chromedp profile 目录属于“默认自动生成目录”。对这份日志对应的运行环境来说，默认目录恰好落在 `/home/hlsa/.local/go-tmp/chromedp-runner*`。

## 4. 按问题分级的审查发现

### P1. `chromedp` profile 目录当前不可控，且没有显式预检

影响代码： [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go)

现状：

- 当前实现没有显式设置 `chromedp.UserDataDir(...)`。
- [test/2](test/2) 已证明浏览器 profile 实际落到了 `/home/hlsa/.local/go-tmp/chromedp-runner*`。
- 当前实现也没有在启动前对 profile 基目录做 `mkdir`、权限检查或可写性预检。

后果：

- 一旦默认目录不可写，`chromedp` 会在真正抓取前直接失败。
- 运维侧也无法通过 WeKnora 配置把 profile 目录稳定迁移到已知可写目录。

### P1. Agent 工具版 HTTPS fallback 有确定性证书校验缺陷

影响代码： [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go)

现状：

- `validateAndResolve` 先解析出 `PinnedIP`。
- `fetchWithTimeout` 再把原始 URL 改成 `https://PinnedIP:port/...`。
- 当前底层客户端没有为这条 HTTPS 连接显式设置 `TLSClientConfig.ServerName = vp.Host`。

后果：

- 只要 fallback 命中 HTTPS 站点，证书匹配就会按 IP 进行。
- [test/2](test/2) 已经证明这会直接触发 `x509 ... doesn't contain any IP SANs`。

### P2. 页面抓取失败后仍然返回结果，是当前 Agent 的受控降级行为

影响代码： [../internal/agent/tools/registry.go](../internal/agent/tools/registry.go)、[../internal/agent/observe.go](../internal/agent/observe.go)、[../internal/agent/tools/web_search.go](../internal/agent/tools/web_search.go)

现状：

- `web_fetch` 失败后，`ToolRegistry.ExecuteTool` 会把错误结果继续保留在工具消息中。
- `appendToolResults` 会把失败结果写回 LLM 上下文。
- [test/2](test/2) 里，在 `web_fetch` 失败之前，`web_search` 已经成功返回了 5 条结果。

后果：

- 模型不会因为 `web_fetch` 失败而立即中断。
- 模型仍可基于 `web_search` 的 `title`、`url`、`snippet` 继续生成答案。

## 5. 为什么“抓取不到也能返回结果”

这个问题在 [test/2](test/2) 对应的 Agent 路径里可以直接解释清楚。

### 5.1 同一轮里，`web_search` 先成功，`web_fetch` 后失败

[test/2](test/2) 展示了以下顺序：

1. Round-2 调用 `web_fetch` 之前，已有成功的 `web_search` 工具结果。
2. Round-2 的 `web_fetch` 对 3 个页面全部失败。
3. 下一轮模型继续读取工具输出，最终基于前面的 `web_search` 内容给出答案。

### 5.2 工具失败不会自动终止 Agent 推理

当前 Agent 机制不是“任一工具失败就整轮报错退出”，而是：

- 把失败信息写回工具消息。
- 允许模型根据错误提示改用别的路径。
- 如果已有足够上下文，模型就直接完成回答。

因此，当前现象应表述为：

- `web_fetch` 失败了；
- 但 Agent 仍然利用之前成功的 `web_search` 摘要结果继续完成了回答。

## 6. `chromedp` 目录的推荐配置方法

### 6.1 当前目录

仅根据 [test/2](test/2)，当前 `web_fetch` 的 chromedp profile 目录实际位于：

- `/home/hlsa/.local/go-tmp/chromedp-runner*`

这里的 `*` 是每次抓取生成的随机后缀。

### 6.2 当前代码为什么不能控制这个目录

[../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go) 当前只做了：

- `chromedp.DefaultExecAllocatorOptions[:]`
- 各种 `chromedp.Flag(...)`

但没有做：

- `chromedp.UserDataDir(profileDir)`

所以 `web_fetch` 目前没有自己的 profile 目录配置入口。

### 6.3 推荐做法：配置“基目录”，每次抓取创建独立子目录

注意：当前 `web_fetch` 是并发抓取多个 URL 的。如果把所有抓取都固定到同一个 profile 目录，后续很容易因为 Chrome 的 `ProcessSingleton` 机制再次互相冲突。

因此推荐的配置方式不是“所有请求共用一个固定目录”，而是：

1. 配一个可写的基目录。
2. 每次抓取在该基目录下创建一个独立 profile 子目录。
3. 把这个独立子目录传给 `chromedp.UserDataDir(...)`。

可参考如下实现方式：

```go
baseDir := strings.TrimSpace(os.Getenv("WEKNORA_WEB_FETCH_CHROMEDP_BASE_DIR"))
if baseDir == "" {
	baseDir = "/tmp/weknora-web-fetch"
}

if err := os.MkdirAll(baseDir, 0o700); err != nil {
	return "", fmt.Errorf("failed to create chromedp base dir: %w", err)
}

profileDir, err := os.MkdirTemp(baseDir, "chromedp-runner-*")
if err != nil {
	return "", fmt.Errorf("failed to create chromedp profile dir: %w", err)
}
defer os.RemoveAll(profileDir)

opts := append(
	chromedp.DefaultExecAllocatorOptions[:],
	chromedp.UserDataDir(profileDir),
	chromedp.Flag("host-resolver-rules", hostRule),
	chromedp.Flag("headless", true),
	chromedp.Flag("disable-setuid-sandbox", true),
	chromedp.Flag("disable-dev-shm-usage", true),
	chromedp.Flag("disable-gpu", true),
)
```

这套方式有三个好处：

1. profile 基目录变成显式可配置。
2. 每次抓取都用独立子目录，不会把多个并发请求挤进同一个 Chrome profile。
3. 可以把默认目录从 `/home/hlsa/.local/go-tmp` 迁移到运维明确授权的可写目录，例如 `/tmp/weknora-web-fetch` 或 `/data/weknora/chromedp`。

### 6.4 仓库内已有可复用的参考写法

仓库里已经有一套显式指定 chromedp profile 目录的实现，在 [../internal/utils/export/export.go](../internal/utils/export/export.go)：

- 先创建任务级临时目录。
- 再在其下创建 `chromium-profile` 子目录。
- 最后通过 `chromedp.UserDataDir(browserProfileDir)` 传给浏览器。

`web_fetch` 最稳妥的改法就是复用这一路径管理思路，而不是继续依赖 chromedp 默认目录。

## 7. 整改计划

### 7.1 第一阶段：先修 `chromedp` 目录问题

目标：先让 `chromedp` 运行目录可控、可写、可排障。

计划：

1. 在 [../internal/agent/tools/web_fetch.go](../internal/agent/tools/web_fetch.go) 为 `chromedp` 增加显式 `UserDataDir`。
2. 新增 `WEKNORA_WEB_FETCH_CHROMEDP_BASE_DIR` 之类的运行时配置项。
3. 按“基目录 + 每次抓取独立子目录”的方式创建 profile。
4. 启动前补充 `mkdir` 与可写性检查；失败时把目录路径写进日志。

优先级：最高

### 7.2 第二阶段：修复 HTTPS fallback 的 `ServerName`

目标：避免 `chromedp` 失败后又在 HTTPS fallback 上确定性失败。

计划：

1. 为按 IP 直连的 HTTPS 请求显式设置 `TLSClientConfig.ServerName = vp.Host`。
2. 补充单测，覆盖“证书只包含域名 SAN、不包含 IP SAN”的站点。

优先级：最高

### 7.3 第三阶段：明确结果层的降级状态

目标：让用户能看出答案是否来自全文抓取。

计划：

1. 当 `web_fetch` 全部失败时，在工具结果里明确标记 `fetched_count=0`。
2. 前端或 prompt 层补充“当前答案仅基于搜索摘要”的提示。

优先级：高
