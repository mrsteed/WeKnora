# 空间初始化与组织创建稳定性优化方案

> 实施状态（2026-10-09 晚）：**P0、P1 已完成落地**。当前代码已补齐后端 bootstrap 编排接口、幂等状态持久化、结构化步骤结果、用户冲突结构化错误，以及前端向导对 bootstrap 接口与本地持久化状态的适配。

## 1. 背景与问题复现

本次审查聚焦 **超级管理员创建新空间后，继续通过“空间初始化向导”创建首位负责人并初始化组织树** 的链路。

用户反馈的两个问题可以稳定串联成同一条故障链：

1. 新建负责人时，如果手机号已被占用，前端提示 `Failed to create user`，没有明确告诉操作者“手机号重复”。
2. 修改手机号后再次重试，有概率提示 `Failed to create org tree node`，导致操作者误以为组织树创建也失败。

结合代码审查，这两个问题本质上分别来自：

- **错误语义丢失**：后端在“创建用户”失败时统一包成 500 / `Failed to create user`。
- **初始化状态未恢复**：首次失败前，根组织其实已经创建成功；但向导刷新/重开后没有恢复该状态，重试时又去尝试创建根组织。

---

## 2. 关键链路审查结果

### 2.1 当前创建链路

入口链路分为两段：

1. **创建空间**
   - 后端：`internal/handler/tenant.go`
   - 服务：`internal/application/service/tenant.go`
   - 结果：创建 tenant，并为创建者补齐 owner membership。

2. **空间初始化向导**
   - 前端：`frontend/src/components/WorkspaceSetupWizard.vue`
   - 第 1 步：选择“已有账号 / 新建用户 / 邀请链接”
   - 第 2 步：创建根组织，并把负责人加入空间与组织树
   - 后端组织树与人员接口：`internal/handler/org_tree.go`

### 2.2 “手机号重复却显示 Failed to create user”的根因

`CreateUserInOrg` 的执行顺序是：

1. `provisionUserForOrg(...)`
2. `ensureProvisionedMembership(...)`
3. `AssignUserToOrg(...)`

其中第 1 步最终调用：

- `internal/application/service/user.go`
  - `CreateUserByAdmin(...)`

`CreateUserByAdmin(...)` 里虽然已经做了用户名 / 邮箱 / 手机号重复检查，但返回的是普通 error；到了：

- `internal/handler/org_tree.go`
  - `CreateUserInOrg(...)`

又被统一包成：

```go
Failed to create user
```

所以前端拿不到“手机号已存在”的明确语义，只能弹出通用失败提示。

### 2.3 “改手机号后再次创建，提示 Failed to create org tree node”的根因

新建用户模式下，前端先执行：

1. `ensureRootOrg()`
2. `createUserInOrg(...)`

也就是说：

- **第一次提交时，根组织通常已经创建成功**
- 之后才因为手机号冲突，导致“创建用户”失败

但前端对“已创建的根组织”只保存在 `WorkspaceSetupWizard.vue` 的本地 `createdRootOrg` 状态里，没有落到持久层；而 `workspaceSetupStore` 只持久化了 tenant 基础信息，没有持久化根组织创建结果。

因此一旦发生：

- 页面刷新
- 组件重挂载
- 再次打开向导

就会丢失“根组织已创建”这一事实。此时再次点“执行初始化”，前端会重新走创建根组织逻辑，最终把错误暴露成 `Failed to create org tree node`。

> 这类问题的本质不是“第二次创建真的应该失败”，而是 **重试没有复用第一次已经成功的前置步骤**。

## 3. 本次已落地修复

### 3.1 明确返回用户名 / 邮箱 / 手机号冲突

已修改：

- `internal/application/service/user.go`
- `internal/handler/org_tree.go`

处理方式：

1. `CreateUserByAdmin(...)` 返回明确的 typed errors：
   - `ErrUsernameAlreadyExists`
   - `ErrEmailAlreadyExists`
   - `ErrPhoneAlreadyExists`
   - `ErrUserAlreadyExists`
2. `CreateUserInOrg(...)` 针对这些错误返回明确的 409 Conflict：
   - `Username already exists`
   - `Email already exists`
   - `Phone already exists`

这样前端不再只拿到 `Failed to create user`。

### 3.2 重试时优先复用已存在根组织

已修改：

- `frontend/src/components/WorkspaceSetupWizard.vue`
- `frontend/src/utils/workspaceSetupRootOrg.ts`

处理方式：

1. 向导在需要创建根组织前，先调用 `getOrgTree()`
2. 从当前租户已有组织树中挑选**可信可复用的 root org**
3. 如果已经存在匹配的根组织，则直接复用，而不是再次创建

复用规则当前采取保守策略：

- 若仅有一个 root org：直接复用
- 若存在多个 root org：优先按根组织名精确匹配
- 若无法可信匹配：不自动复用，避免误挂错组织

### 3.3 增加最小回归测试

新增测试：

- 后端：`internal/application/service/user_create_admin_test.go`
  - 校验手机号重复
  - 校验 DB 唯一约束错误能映射到具体字段
- 前端：`frontend/src/utils/workspaceSetupRootOrg.test.ts`
  - 校验根组织复用逻辑

## 4. 本次修改后的预期行为

### 场景 A：手机号已存在

预期：

1. 根组织可先创建成功
2. 创建负责人时返回 `Phone already exists`
3. 前端明确提示手机号冲突
4. 操作者修改手机号后可直接继续重试

### 场景 B：失败后刷新页面再重试

预期：

1. 向导重新打开时，会先探测当前租户已有组织树
2. 若根组织已存在，则复用已有 root org
3. 不再重复创建 root org
4. 不再因为状态丢失而出现 `Failed to create org tree node`

## 5. 建议继续推进的稳定性优化（按优先级）

以下是“全面提升组织创建稳定性”的建议，不全部属于本次必须修改，但建议纳入后续迭代。

### P0：把“空间初始化”收敛为后端编排接口

当前向导把初始化拆成多次前端串行调用：

1. 创建根组织
2. 创建 / 复用用户
3. 创建 tenant member
4. 组织树挂载

问题是：

- 前端需要自己维护部分成功状态
- 中间任何一步失败都要靠补偿或手工重试
- 页面刷新后天然容易丢上下文

建议增加一个后端编排接口，例如：

- `POST /api/v1/tenants/:id/bootstrap`

由后端一次接收：

- 负责人模式
- 新用户信息 / 已有用户信息
- tenant role
- root org 配置
- org role

后端统一完成：

- 幂等检查
- 顺序编排
- 失败补偿
- 明确错误分类

这会是创建稳定性的**根本性优化**。

### P0：给初始化链路引入幂等键

建议在“空间初始化向导”提交时带上 `idempotency_key`，服务端记录：

- tenant_id
- root_org_id
- provisioned_user_id
- membership_done
- org_assignment_done

这样同一轮初始化重复点击 / 刷新重试时，后端可以继续未完成步骤，而不是从头重放。

### P1：统一用户冲突错误模型

目前用户名 / 邮箱 / 手机号冲突的检测分散在：

- 预检查
- DB 唯一索引兜底
- 不同 handler 自行包错

建议统一为结构化错误，例如：

```json
{
  "code": "user_conflict",
  "field": "phone",
  "message": "Phone already exists"
}
```

这样前端可以：

- 高亮具体字段
- 做本地化提示
- 记录更稳定的埋点

### P1：把“根组织已创建”持久化到 workspace setup store

本次已经通过**服务端探测复用**解决核心问题，但仍建议补上本地持久化：

- `tenantId`
- `createdRootOrg.id`
- `createdRootOrg.name`
- 初始化模式
- 已选择的 tenant role / org role

这样即使后端探测临时失败，前端也能优先恢复最近一次成功的本地初始化状态。

### P1：为部分成功增加显式补偿与状态提示

当前 `CreateUserInOrg(...)` 在某些情况下已经做了部分成功返回，例如：

- 用户已创建
- tenant member 已创建
- 但组织挂载失败

建议进一步标准化结果：

- `created_root_org`
- `created_user`
- `created_membership`
- `assigned_org`

让前端能把“已完成/未完成”的状态明确展示给管理员，而不是一个 message 字符串混合描述。

### P1：避免 handler 层统一吞并错误

本次问题说明：**一旦 handler 统一包成 500 generic error，前端几乎无法做正确交互**。

建议对以下错误统一保留语义：

- 参数校验错误 -> 400
- 资源不存在 -> 404
- 角色 / 权限不足 -> 403
- 唯一约束冲突 -> 409
- 部分成功 -> 200 + structured partial result
- 真正系统异常 -> 500

### P2：增加初始化链路的审计与埋点

建议新增以下日志 / audit event：

- tenant bootstrap started
- root org created / reused
- user provisioned / reused
- tenant membership created / updated
- org assignment success / failed
- bootstrap completed / partially completed / failed

这样以后再出现“10003 删除、10004 重建”这类现场时，可以直接从日志定位卡在哪一步。

### P2：补齐集成级测试矩阵

建议补充以下自动化场景：

1. 超管创建空间 -> 新建负责人成功
2. 新建负责人手机号重复 -> 返回 409 + phone conflict
3. 第一次失败后刷新页面 -> 第二次重试成功复用根组织
4. tenant member 创建失败 -> 新用户是否正确回滚
5. org assignment 失败 -> 是否返回 partial success
6. 多 root org 场景 -> 是否避免误复用

## 7. 结论

这次问题不是单点 bug，而是“**初始化流程跨多接口、多步骤，但失败恢复与错误语义不完整**”导致的。

本次修复已经解决两个直接痛点：

1. **手机号重复时，错误不再被吞成 `Failed to create user`**
2. **首次失败后再重试，会优先复用已存在根组织，避免再次报 `Failed to create org tree node`**

如果后续要把“组织创建稳定性”继续做到更高，建议优先推进：

1. **后端统一 bootstrap 编排接口**
2. **初始化幂等键**
3. **结构化部分成功结果**
4. **更完整的集成测试与审计埋点**

这四项做完后，空间初始化链路的可恢复性、可观测性和维护成本都会明显改善。
