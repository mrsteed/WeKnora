# 组织管理创建子组织管理员只读权限问题审查与修正计划

## 1. 问题结论

结论明确：当前“空间拥有者在组织管理里创建子组织管理员”这条链路，确实会把新账号的空间级角色写成 `viewer`，因此该账号首次登录后显示“只读”，而不是预期的“协作者”。

这不是单纯的前端展示错误，而是 `tenant_members.role` 在创建时就被写错了。前端只是把这个错误结果如实展示出来。

同时，当前编辑组织成员的链路不会回写 `tenant_members`，所以一旦首次创建时写成 `viewer`，后续仅调整组织角色并不能自动把该账号修回“协作者”。

## 2. 现状代码审查

### 2.1 组织管理创建用户的前端请求没有传 `tenant_role`

组织管理页的创建对话框位于：

- `frontend/src/views/admin/components/CreateUserDialog.vue`

当前对话框只采集并提交这些字段：

- `username`
- `email`
- `phone`
- `password`
- `role`

提交 `createUserInOrg(...)` 时没有携带 `tenant_role`。

这意味着组织管理页面当前只表达了“组织角色”，没有表达“空间级角色”。

### 2.2 后端在 owner/admin 调用时，会把空 `tenant_role` 默认解释为 `viewer`

关键代码位于：

- `internal/handler/org_tree.go`

当前逻辑链路如下：

1. `CreateUserInOrg()` 先调用 `resolveTenantRoleForCreateUser(...)`
2. 对于 tenant owner / tenant admin / privileged operator，这个 helper 会走 `resolveTenantRoleForProvision(...)`
3. `resolveTenantRoleForProvision(...)` 中，如果 `req.TenantRole` 为空，就默认设置为 `viewer`

也就是说：

- 如果调用方是空间拥有者或空间管理员
- 且前端没有传 `tenant_role`

那么后端不会根据组织角色去推导“协作者”，而是直接把空间级角色收成 `viewer`。

这正是本问题的根因。

### 2.3 错误角色会被直接写入 `tenant_members`

同样在：

- `internal/handler/org_tree.go`

`CreateUserInOrg()` 的顺序是：

1. 创建或复用用户
2. 调用 `ensureProvisionedMembership(...)` 写入 `tenant_members`
3. 再调用 `AssignUserToOrg(...)` 挂到组织节点

因此，账号第一次被创建时，空间级角色已经在第 2 步写死。

在当前实现下：

- 组织角色选 `admin`
- 前端未传 `tenant_role`
- 调用者是 owner/admin

最终写入的仍然是：

- `tenant_members.role = viewer`

### 2.4 登录后的“当前空间角色”直接依赖 `tenant_members`

相关代码位于：

- `internal/handler/auth.go`
- `frontend/src/stores/auth.ts`

当前 `/auth/me` 会从 `tenant_members` 组装 `memberships` 返回前端；前端 `authStore.currentTenantRole` 再直接从当前租户的 membership.role 读取角色。

因此只要 `tenant_members.role` 是 `viewer`，登录后前端就一定会显示只读，并且大量以 `hasRole('contributor')` 为门槛的写操作入口都会被隐藏。

### 2.5 当前编辑组织成员不会修正 `tenant_members`

相关代码位于：

- `internal/handler/org_tree.go` 的 `UpdateUserInOrg()`

当前更新逻辑只会：

1. 更新用户基础信息
2. 如果有 `req.Role`，调用 `AssignUserToOrg(...)` 更新组织角色

但不会同步更新：

- `tenant_members.role`

这意味着：

- 首次创建时被错误写成 `viewer`
- 之后即便在组织管理里把此人改成子组织管理员

也不会自动变成“协作者”。

### 2.6 现有测试把这个错误默认行为固化下来了

相关测试位于：

- `internal/handler/org_tree_provision_test.go`

当前已经存在：

- `TestResolveTenantRoleForProvision_DefaultsViewerForTenantAdmin`

这说明底层 helper 当前确实把“空 `tenant_role`”解释为 `viewer`。真正缺失的是另一层覆盖：

- `resolveTenantRoleForCreateUser(...)`
- 在 owner/admin 调用、且未传 `tenant_role` 时
- 应如何基于 org role 做缺省映射

也就是说，当前测试缺口不是“完全没有角色测试”，而是“没有覆盖 create-user 包装层的缺省分支”，所以这个问题才会漏出来。

### 2.7 WorkspaceSetupWizard 已经证明系统支持显式传 `tenant_role`

相关代码位于：

- `frontend/src/components/WorkspaceSetupWizard.vue`

该页面在调用 `createUserInOrg(...)` 时会显式传：

- `tenant_role: form.tenantRole`

这说明后端能力并不缺，只是“组织管理创建用户”这条前端链路没有把该能力接上。

## 3. 根因链路

当前问题的完整链路可以概括为：

1. 空间拥有者在组织管理页面选择“子组织管理员”
2. 前端只提交 `role=admin`，没有提交 `tenant_role`
3. 后端因为调用方是 owner/admin，走 `resolveTenantRoleForProvision(...)`
4. 空 `tenant_role` 被默认解释为 `viewer`
5. `ensureProvisionedMembership(...)` 把 `tenant_members.role` 写成 `viewer`
6. 登录后 `/auth/me` 把这个 `viewer` 返回前端
7. 前端 `authStore.currentTenantRole` 读到 `viewer`
8. 页面显示只读，且 contributor 以上入口被隐藏

所以这次问题的本质不是：

- “子组织管理员的展示标签错了”

而是：

- “组织管理创建用户时，空间级角色缺省策略错了”

## 4. 正确的目标语义

针对“组织管理创建用户”这条链路，建议明确以下语义：

1. 子组织管理员不是空间管理员。
2. 子组织管理员登录后，空间级默认应为 `contributor`，不是 `admin`。
3. 组织角色为 `editor` 时，空间级默认也应为 `contributor`。
4. 组织角色为 `viewer` 时，空间级默认才应为 `viewer`。
5. 只有显式指定 `tenant_role` 时，才允许空间 owner/admin 创建更高的空间级角色。

也就是默认映射应该是：

| 组织管理创建时的 org role | 缺省 tenant role |
| --- | --- |
| `admin` | `contributor` |
| `editor` | `contributor` |
| `viewer` | `viewer` |

## 5. 修正建议

### 5.1 P0：先修后端默认策略，堵住根因

优先修改：

- `internal/handler/org_tree.go`

建议将 `resolveTenantRoleForCreateUser(...)` 改成以下语义：

1. 如果请求里显式传了 `tenant_role`：
   - 继续沿用当前显式授权逻辑
   - owner/admin/privileged operator 仍可按权限边界授予明确的 tenant role
2. 如果请求里没有传 `tenant_role`：
   - 不再默认 `viewer`
   - 改为按组织角色做缺省映射
   - `admin/editor -> contributor`
   - `viewer -> viewer`

这样做的原因是：

- 能从根上修复“组织管理创建用户未传 tenant_role”的所有调用方
- 不依赖前端是否忘记传字段
- 不会影响 WorkspaceSetupWizard 这类已经显式传 `tenant_role` 的调用方

不建议只做前端补丁，因为那样 API 本身仍然保留一个危险默认值，只要将来再出现新的调用方漏传 `tenant_role`，问题会重复出现。

### 5.2 P0：同步修改单元测试

需要修改或新增：

- `internal/handler/org_tree_provision_test.go`

至少覆盖以下场景：

1. tenant owner 创建用户，`role=admin` 且未传 `tenant_role`，结果必须是 `contributor`
2. tenant owner 创建用户，`role=editor` 且未传 `tenant_role`，结果必须是 `contributor`
3. tenant owner 创建用户，`role=viewer` 且未传 `tenant_role`，结果必须是 `viewer`
4. 显式传 `tenant_role=admin` 时，tenant admin 仍然可以创建 `admin`
5. 显式传 `tenant_role=owner` 时，只有 owner 或 privileged operator 可以创建 `owner`

其中需要注意：

- `TestResolveTenantRoleForProvision_DefaultsViewerForTenantAdmin`

如果修复是放在 `resolveTenantRoleForCreateUser(...)` 这一层完成，那么这个 helper 测试可以保留；

如果团队选择把缺省映射逻辑下沉到 `resolveTenantRoleForProvision(...)`，那再同步调整这个测试的预期即可。

换言之，当前最关键的是补上 `resolveTenantRoleForCreateUser(...)` 的回归覆盖，而不是机械地改掉所有“default viewer”相关测试名。

### 5.3 P1：前端组织管理创建对话框补齐空间级角色表达

相关文件：

- `frontend/src/views/admin/components/CreateUserDialog.vue`

这里建议两种方案二选一：

方案 A，最小改动：

- 提交时显式补一个自动推导的 `tenant_role`
- `admin/editor -> contributor`
- `viewer -> viewer`

方案 B，更完整：

- 复用 WorkspaceSetupWizard 的“空间级角色 + 组织角色”双层表达
- 在对话框里同时让操作人选择 `tenant_role` 和 `role`

本问题的最小修复并不依赖前端先改，因为后端默认策略修正后，即使前端继续不传，也能得到正确结果。

但前端仍建议补齐，原因是：

- 请求语义更清晰
- 便于未来需要显式创建 tenant admin / owner 的场景
- 能和 WorkspaceSetupWizard 的行为保持一致

### 5.4 P1：不要让 `UpdateUserInOrg()` 隐式联动修 tenant role

虽然当前 `UpdateUserInOrg()` 不会修正错误的 `tenant_members.role`，但不建议简单地在“修改组织角色”时自动同步 tenant role。

原因是这会引入另一个风险：

- 某些本来就是显式 tenant admin 的账号
- 如果后续只是在组织树里调整其 org role
- 可能被误降级成 `contributor`

因此更稳妥的做法是：

1. 修正创建时的默认策略
2. 对已错写的历史数据做一次性修复
3. tenant role 的后续调整继续保持显式管理，不与 org role 自动强绑定

### 5.5 P1：旧数据修复单独执行，目标值应直接修成 `contributor`

当前已经创建错的账号，需要单独修复 `tenant_members`。

推荐修复原则：

1. 对“应为子组织管理员/协作者”的账号，直接把 `tenant_members.role` 修成 `contributor`
2. 不要修成 `admin`

原因有两点：

1. 业务语义上，子组织管理员本来就不是空间管理员
2. 当前 `/auth/me` 返回 membership 时直接把 `tenant_members.role` 回给前端，因此如果修成 `admin`，前端会把此人展示成空间管理员，造成新的认知偏差

### 5.6 P1：不要直接用当前 `repair_tenant_memberships.sh` 纠这个问题

相关脚本：

- `scripts/tenant_membership_repair/repair_tenant_memberships.sh`

当前脚本的映射规则是：

- org admin / owner -> tenant `admin`
- org editor / contributor -> tenant `contributor`
- org viewer -> tenant `viewer`

这与本问题的目标语义不一致，因为本问题里“子组织管理员”应该落成 `contributor`，而不是 `admin`。

所以对这批账号的纠偏，不应直接执行该脚本的默认映射；应改用单独审计、单独修复的方式处理。

## 6. 建议实施顺序

### 阶段 1：代码修复

1. 修改 `internal/handler/org_tree.go` 的默认 tenant role 推导逻辑
2. 更新 `internal/handler/org_tree_provision_test.go`
3. 跑后端相关单测，确认显式 `tenant_role` 场景不回归

### 阶段 2：历史数据修复

1. 审计当前租户内由组织管理创建的子组织管理员账号
2. 找出 `tenant_members.role=viewer` 但业务上应为协作者的账号
3. 人工确认名单后，将其修正为 `contributor`
4. 让这些账号重新登录并确认前端角色变为“协作者”

### 阶段 3：前端一致性补齐

1. 给 `CreateUserDialog.vue` 增加显式 `tenant_role` 提交
2. 如产品需要，再增加空间级角色选择 UI
3. 统一组织管理与 WorkspaceSetupWizard 的角色表达

## 7. 验收标准

修复完成后，至少应满足以下验收条件：

1. 空间 owner 在组织管理中创建 `role=admin` 的子组织管理员
2. 新账号首次登录后，当前空间角色显示为“协作者”
3. 新账号可以执行 contributor 级能力，例如创建自己的 KB / Agent
4. 新账号不能进入 tenant admin / owner 专属的空间管理能力
5. 组织管理能力仍保留在其被授权的组织子树内
6. WorkspaceSetupWizard 显式传 `tenant_role=admin/owner` 的场景不受影响

## 8. 回归测试建议

建议补三类回归：

### 8.1 后端单测

- `resolveTenantRoleForCreateUser(...)`
- `CreateUserInOrg()` 对 `tenant_members` 的落库结果

### 8.2 接口级测试

模拟 owner/admin 调用：

- 不传 `tenant_role` + `role=admin`
- 不传 `tenant_role` + `role=editor`
- 不传 `tenant_role` + `role=viewer`
- 显式传 `tenant_role=admin`

分别校验：

- 返回成功
- `tenant_members.role` 是否符合预期
- `/auth/me` 返回的 `memberships` 是否符合预期

### 8.3 前端冒烟测试

至少验证：

1. 组织管理创建“子组织管理员”后登录，角色徽章为“协作者”
2. 组织管理创建“只读成员”后登录，角色徽章仍为“只读”
3. WorkspaceSetupWizard 创建 `tenant_role=admin` 用户后登录，角色仍为“管理员”

## 9. 最终建议

本问题不建议理解成“前端显示错了”，也不建议只在 UI 上做兜底文案处理。

真正需要修的是：

- `CreateUserInOrg` 在 `tenant_role` 缺省时的默认策略

推荐最终落地方案是：

1. 后端先改缺省映射，作为根因修复
2. 历史错误账号单独修成 `contributor`
3. 前端再补齐 `tenant_role` 的显式提交或选择能力

这样可以同时解决：

- 当前组织管理创建子组织管理员后只读的问题
- 后续其他调用方再次漏传 `tenant_role` 时重复踩坑的问题
- 以及历史错误数据无法自愈的问题
