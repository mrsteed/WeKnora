# 切换空间后权限与智能体问题代码审查报告

## 1. 审查范围

本次审查仅分析代码与现象，不修改业务代码。审查目标对应以下 5 个问题：

1. 用超级管理员新建空间后的角色落点。
2. 组织管理页面与成员管理页面对同一账号显示的权限不一致。
3. 切换空间后，智能体页面显示英文而不是中文。
4. `intramind@hlsa.com` 账号下，内置智能体默认模型未配置；编辑后提示权限不足。
5. 当前 `intramind@hlsa.com` 账号可以在系统设置中添加模型。

审查的核心代码面包括：

- 租户创建与租户成员权限：
  - `internal/handler/tenant.go`
  - `internal/application/service/tenant.go`
  - `internal/application/service/tenant_member.go`
  - `frontend/src/views/settings/TenantMembers.vue`
- 共享空间 / 组织成员与组织树成员：
  - `internal/application/service/organization.go`
  - `internal/application/repository/organization.go`
  - `internal/handler/organization.go`
  - `internal/handler/org_tree.go`
  - `frontend/src/views/admin/components/MemberTable.vue`
  - `frontend/src/views/organization/OrganizationSettingsModal.vue`
- 智能体内置配置、本地化与权限：
  - `config/builtin_agents.yaml`
  - `internal/types/builtin_agent_config.go`
  - `internal/application/service/custom_agent.go`
  - `internal/application/service/agent_visibility.go`
  - `internal/handler/custom_agent.go`
  - `frontend/src/views/agent/AgentList.vue`
  - `frontend/src/views/agent/AgentEditorModal.vue`
  - `frontend/src/utils/agent-readiness.ts`
- 模型管理权限：
  - `internal/router/router.go`
  - `frontend/src/views/settings/Settings.vue`
  - `frontend/src/views/settings/ModelSettings.vue`

---

## 2. 总结结论

当前现象不是单点 bug，而是 **三套角色/成员模型并存且 UI 表达混用** 导致的结果：

1. **租户成员权限（tenant_members）**
   - 角色：`owner / admin / contributor / viewer`
   - 用于空间级设置、模型管理、API 配置、成员管理等。

2. **共享空间成员（organization_tenant_members）**
   - 角色：`admin / editor / viewer`
   - 这是按 **tenant 聚合** 的共享空间成员，不是逐个 user 的成员表。
   - `owner` 不是这个表里的角色字段，而是由 `organizations.owner_id / owner_tenant_id` 叠加出来的“所有者语义”。

3. **组织树成员（organization_members_pre_plan3）**
   - 角色：`admin / editor / viewer`
   - 这是旧的、按 **user** 维度组织树成员体系。
   - 也没有真正的 `owner` 角色，只有 `is_owner` 辅助判断。

因此：

- “组织管理页面”与“成员管理页面”现在并不是在展示同一个权限域。
- 智能体英文问题本质上不是前端整体语言切换失败，而是 **内置智能体的 DB 覆盖记录把英文 name/description 固化了**。
- “可以添加模型，但不能保存内置智能体模型配置”是明显的权限设计不一致：
  - **模型管理** 按租户 `Admin+` 放行；
  - **内置智能体配置更新** 却被 handler 单独限制成了 `SuperAdmin`。

建议的统一方向是：

- **租户级能力**：以 `tenant_members.role` 为唯一权威。
- **共享空间成员展示**：明确标注“这是空间账号/租户成员，不是单个用户”。
- **组织树账号管理**：明确标注“这是组织树角色，不是空间角色”。
- **内置智能体配置**：允许当前空间的 `Admin+` 做“配置覆盖”，但不允许修改名称/描述等内置元数据。
- **显示语言**：内置智能体名称/描述不应持久化本地化快照，应在读取时按当前 UI locale 重算。

## 3. 逐项问题分析与修正计划

## 3.1 问题 1：用超级管理员新建空间后的角色落点

### 现状代码结论

新空间（租户）创建后，创建者会被自动设为该租户的 `Owner`。

关键路径：

- `internal/handler/tenant.go: CreateTenant`
  - 调用 `TenantService.CreateTenant`
  - 创建成功后调用 `memberService.EnsureOwner(ctx, caller.ID, createdTenant.ID)`
- `internal/application/service/tenant_member.go: EnsureOwner`
  - 为该用户补一条 `tenant_members.role = owner`

这意味着：

- 如果是超级管理员发起 `POST /tenants`，那么超级管理员会自动成为该空间的 `Owner`。
- 这是系统的当前设计，不是偶发行为。

### 风险与影响

如果业务预期是“空间最终由 `intramind@hlsa.com` 作为主负责人”，那么 **由超级管理员先创建空间** 会天然带来一个后续动作：

- 需要再把 `intramind@hlsa.com` 提升为 `Owner`
- 视业务需要决定是否保留超级管理员的 `Owner`

当前系统允许一个租户同时存在多个 `Owner`；但没有专门的“转移所有权”流程，只有成员角色修改能力。

### 修正建议

这个点本身不一定要改代码，但需要明确产品规则：

#### 方案 A：保留现状，文档化

- 超级管理员创建空间时，自己先成为 `Owner`。
- 再由 `Owner` 页面把目标运营账号提升为 `Owner`。
- 如需“唯一 Owner”，再把超级管理员降为 `Admin` 或移出（前提是至少保留一个 `Owner`）。

#### 方案 B：增加“代建空间”语义

- 允许超级管理员在创建空间时指定“初始 Owner 用户”。
- 创建后直接给指定用户写入 `Owner`，避免出现“超管先占 Owner 再人工转移”的中间态。

### 建议优先级

- 优先级：中
- 原因：不影响功能正确性，但会影响后续权限预期与运维流程一致性。

## 3.2 问题 2：组织管理页显示“管理员”，成员管理页显示“所有者”

### 现象复述

同一个账号 `intramind@hlsa.com`：

- 在“组织管理页面”看到的是“管理员”
- 在“成员管理页面”看到的是“所有者”

### 根因分析

这不是同一字段被显示错了，而是 **两个页面拿的是两套不同的成员模型**。

### 2.1 页面 A：组织管理页（旧组织树成员）

对应代码链：

- 前端：`frontend/src/views/admin/components/MemberTable.vue`
- API：`frontend/src/api/org-tree/index.ts -> getOrgMembers`
- 后端：`internal/handler/org_tree.go: ListOrgMembers`
- Repository：`internal/application/repository/organization.go: ListOrgTreeMembers`

特点：

- 读的是旧表 `organization_members_pre_plan3`
- 成员维度是 **user**
- 角色字段只有：`admin / editor / viewer`
- 返回值里虽然有 `is_owner`，但展示逻辑是：
  - `is_super_admin` 优先
  - `is_owner` 时显示“所有者”
  - 否则 `is_admin` 显示“管理员”

而创建组织时，代码是：

- `internal/application/service/organization.go: CreateOrganization`
  - `org.OwnerID = userID`
  - `org.OwnerTenantID = tenantID`
  - 但创建成员行时写的是：`Role = types.OrgRoleAdmin`

也就是说：

- “组织创建者”在数据上是 `owner_id` 单独保存
- 但组织成员表里的 `role` 仍然是 `admin`

所以，**如果某页只看成员 role，它会把创建者显示成管理员**。

### 2.2 页面 B：成员管理页（共享空间成员 / tenant-keyed）

对应代码链：

- 前端：`frontend/src/views/organization/OrganizationSettingsModal.vue`
- API：`frontend/src/api/organization/index.ts -> listMembers`
- 后端：`internal/handler/organization.go: ListMembers`
- Repository：`internal/application/repository/organization.go: ListMembers`

特点：

- 读的是新表 `organization_tenant_members`
- 成员维度是 **tenant**，不是 user
- 前端 `isOwnerMember()` 判定逻辑：
  - 优先 `member.tenant_id === orgInfo.owner_tenant_id`
  - 否则回退 `member.user_id === orgInfo.owner_id`

这意味着：

- 这个页面展示的“所有者”实际上是 **owner tenant 对应的成员行**
- 该成员行同时又挂了一个 `representative_user_id` 作为展示用户
- 所以前端会把“owner tenant 的代表用户”视觉上显示成“所有者”

### 2.3 还有第三套判定：组织响应本身的 `is_owner`

`internal/handler/organization.go: toOrgResponse` 中：

- `IsOwner = org.OwnerID == currentUserID`

这里又是按 **user_id** 判的，不是按 `owner_tenant_id` 判的。

于是同一个“是否 owner”语义，在代码里至少有三种算法：

1. `org.OwnerID == currentUserID`
2. `member.user_id == org.owner_id`
3. `member.tenant_id == org.owner_tenant_id`

这会继续放大页面间的不一致。

### 结论

现在的“管理员 / 所有者”不一致，本质上不是一个页面错了，而是：

- 一个页面在展示 **组织树成员角色**
- 一个页面在展示 **共享空间 owner 叠加语义**
- 还有一个响应层在用 **第三套 owner 判定** 给前端喂数据

### 修正计划

#### 第一层：先统一概念命名

把页面含义明确区分，不再让用户误认为它们是同一权限。

建议：

- 现“组织管理页面”改名或加说明为：
  - `组织树账号管理`
  - 角色列显示：`组织管理员 / 编辑者 / 只读`
- 现“成员管理页面”改名或加说明为：
  - `空间成员管理`
  - 如果是 tenant-keyed 列表，页面必须明确说明“按空间账号聚合展示”

#### 第二层：统一 owner 语义来源

推荐规则：

- **空间 Owner 的权威来源**：`owner_tenant_id` + 租户级/空间级 owner 规则
- **组织树角色**：保持 `admin/editor/viewer`，不要复用“所有者”这个词作为 role 值
- **共享空间成员页**：如果保留 tenant-keyed 行，则 owner 显示为单独 badge，而不是把 role 本身替换成 owner

#### 第三层：收敛为单一 helper

新增统一的 owner 判定 helper，避免在 handler / frontend 中各自写一套：

- 组织 owner（user 维度）
- 组织 owner tenant（tenant 维度）
- 租户 owner（tenant_members.role = owner）

前后端都改为调用统一规则，不再分散比较 `owner_id` / `owner_tenant_id`。

#### 第四层：决定是否继续保留旧组织树成员体系

当前旧表：`organization_members_pre_plan3`
当前新表：`organization_tenant_members`

如果产品已经以“共享空间 + tenant 聚合成员”为主，应评估：

- 是否继续维护旧组织树成员体系
- 或者把旧页彻底标记为“组织树治理”，不再与空间成员权限做对照

### 建议优先级

- 优先级：高
- 原因：这是当前所有权限认知混乱的源头。

## 3.3 问题 3：切换空间后，智能体页面显示英文

### 现象复述

切换空间后，智能体卡片标题与描述显示为英文，例如：

- `Quick Answer`
- `Smart Reasoning`
- `Wiki Questioner`
- `Data Analyst`

但页面其余 UI 仍是中文。

### 根因分析

这说明 **不是前端整体 locale 切错了**，而是“智能体数据本身”被后端按英文返回了，或被 DB 中历史英文快照覆盖了。

### 3.1 配置文件本身是有中文的

`config/builtin_agents.yaml` 已提供多语言：

- `default` 英文
- `zh-CN` 中文
- 其他语言也有

因此，只要后端正确按 `zh-CN` 解析，理论上卡片应该显示中文。

### 3.2 请求层也在发送 `Accept-Language`

`frontend/src/utils/request.ts`：

- 每个请求都会带 `Accept-Language`
- 来源是 `i18n.global.locale` 或 `localStorage['locale']`

所以，前端已经把“当前 UI 是中文”的信息发给后端了。

### 3.3 真正的问题：内置智能体一旦在 DB 中有覆盖记录，就不再重新本地化

关键路径：

- `internal/application/service/custom_agent.go: ListAgents`
- `internal/application/service/custom_agent.go: GetAgentByID`

逻辑是：

- 如果某个内置智能体已经在 DB 中存在一条当前租户记录
  - 直接返回 DB 里的那条记录
- 只有 DB 中不存在该内置智能体记录时
  - 才会调用 `types.GetBuiltinAgentWithContext(ctx, builtinID, tenantID)`
  - 即按当前 locale 动态本地化

问题在于，内置智能体覆盖记录落库时，`name/description` 也被带着一起持久化了。

见：

- `internal/application/service/custom_agent.go: updateBuiltinAgent`

创建新的 builtin override 记录时：

- `newAgent.Name = defaultAgent.Name`
- `newAgent.Description = defaultAgent.Description`

而 `defaultAgent` 是根据 **当时** 的上下文 locale 取出来的。

结果就是：

- 如果这条 override 最初是在英文 locale 下创建的
- 后续不管当前页面语言是不是中文
- 只要读取 DB 行，就会稳定显示英文

这是“把本地化展示文案错误地持久化到了 DB”导致的典型问题。

### 3.4 另一个次级问题：某些路径甚至没走 context-aware 本地化

`internal/application/service/agent_visibility.go` 中：

- fallback 用的是 `types.GetBuiltinAgent(builtinID, tenantID)`
- 不是 `types.GetBuiltinAgentWithContext(...)`

`GetBuiltinAgent()` 走的是 registry 默认工厂，默认 locale 为空，最终会回落到 `default` 英文。

这意味着：

- 即便没有 DB override
- 某些列表路径也可能直接拿到英文默认文案

### 3.5 locale 来源本身还混用了“文档处理语言”和“UI 显示语言”

`internal/middleware/language.go` 的优先级是：

1. `WEKNORA_LANGUAGE`
2. `Accept-Language`
3. `zh-CN`

注释里已经说明，这个中间件本来是偏“文档处理语言”设计的。

但现在 builtin agent i18n 也复用了这条 context，带来一个副作用：

- 如果部署层设置了 `WEKNORA_LANGUAGE=en-US`
- 即使前端 UI 是中文
- 内置智能体名称/描述仍可能被强制按英文返回

### 修正计划

#### 第一层：把内置智能体 DB 记录改成“只存配置覆盖，不存本地化文案”

推荐原则：

- built-in agent 的 `name / description / avatar / builtin metadata`
  - 始终来自 `builtin_agents.yaml`
  - 每次读取时按当前 locale 重新计算
- DB 中只保留：
  - `tenant_id`
  - `id`
  - `is_builtin`
  - `config`
  - 时间戳

也就是说：

- built-in override 是“配置覆盖”
- 不是“把一个多语言模板拍平后存成租户私有快照”

#### 第二层：所有 built-in 读取路径都切到 context-aware 本地化

包括但不限于：

- `customAgentService.ListAgents`
- `customAgentService.GetAgentByID`
- `agent_visibility.go`

统一要求：

- 只要是 built-in agent 的展示对象
- 最终出参前都要走 `GetBuiltinAgentWithContext` 或等价的 locale-aware 组装逻辑

#### 第三层：把 UI 显示 locale 与文档处理语言解耦

建议不要继续用 `middleware.Language()` 这一条 context 同时承担：

- 文档处理语言
- 显示本地化语言

更合理的拆分是：

- `UI locale`：来自 `Accept-Language` / 前端 locale
- `document processing locale`：来自 `WEKNORA_LANGUAGE` 或业务参数

built-in agent 的本地化显示应读取 UI locale，而不是文档处理语言。

#### 第四层：一次性清理已有英文快照数据

历史上已经写入 `custom_agents` 的 built-in 行，需要一次性修复：

- 清空或忽略 built-in 行的 `name/description/avatar`
- 后续读取时统一从 YAML 重新渲染

### 建议优先级

- 优先级：高
- 原因：这是直接可见的 UI 错误，且根因在后端数据模型上。

## 3.4 问题 4：`intramind@hlsa.com` 账号下，内置智能体默认模型未配置，编辑后提示权限不足

### 现象复述

现象分成两段：

1. 新空间下内置智能体未就绪，缺少模型配置
2. 打开编辑器补模型后，保存时报错：
   - `Only super admins can update built-in agents`

### 根因分析

### 4.1 “默认模型未配置”不是偶发问题，而是当前设计就是显式配置

前端：`frontend/src/utils/agent-readiness.ts`

- 内置/自定义智能体的 chat model 必须显式有 `model_id`
- agent 模式下，如果能用 `knowledge_search`，则还必须显式有 `rerank_model_id`
- **不会因为租户里存在一个 default model 就自动视为已配置**

后端也保持同样逻辑：

- `internal/application/service/session_qa_helpers.go`
  - agent 有 `model_id` 才算配置完成
- `internal/application/service/session_agent_qa.go`
  - knowledge_search 可用时，`rerank_model_id` 为空直接报错
- `internal/application/service/model.go`
  - 注释已明确：`default model selection logic has been removed`

因此：

- 现在的系统不是“有默认模型即可自动继承到智能体”
- 而是“智能体配置必须显式写模型 ID”

### 4.2 前端允许 tenant Admin 进入编辑，但后端只允许 super admin 保存

前端：`frontend/src/views/agent/AgentList.vue`

- `canManageAgent()` 逻辑：
  - 创建者可管理
  - 否则 `authStore.hasRole('admin')` 也可管理
- 对 built-in agent 来说，`created_by` 为空
- 因此 tenant `Admin+` 会被前端允许进入编辑态

前端编辑器：`frontend/src/views/agent/AgentEditorModal.vue`

- 也明确写了：
  - 名称/描述对 built-in 只读
  - 但配置参数可以调整

后端：`internal/handler/custom_agent.go: UpdateAgent`

- 一旦 `types.IsBuiltinAgentID(id)` 为真
- 直接要求 `user.IsSuperAdmin`
- 否则返回：`Only super admins can update built-in agents`

但服务层：`internal/application/service/custom_agent.go: updateBuiltinAgent`

- 已经实现了 **per-tenant 的 built-in config override**
- 且逻辑就是“只改 config，不改基础信息”

也就是说，当前系统内部已经同时存在两种相互冲突的意图：

1. **前端 + service 层意图**：租户内可以覆盖 built-in agent 配置
2. **handler 层意图**：只有 super admin 才能更新 built-in agent

这就是现在“能编辑、能选模型、但保存时报权限不足”的直接原因。

### 4.3 为什么问题 5 会和问题 4 同时出现

`intramind@hlsa.com` 可以在模型设置里创建模型，但却不能把模型绑定到 built-in agent。

这说明：

- 模型管理权限是按 `tenant Admin+` 放开的
- 但 built-in agent 配置更新被额外收紧到了 `SuperAdmin`

这两者在当前产品语义下明显不一致。

### 修正计划

#### 第一层：明确产品决策

建议采用以下统一规则：

- **built-in agent 的基础元数据**（名称、描述、头像、ID、内置工具框架）
  - 平台统一控制
  - 租户不可改
- **built-in agent 的租户级配置覆盖**（模型、rerank、是否启用 web search、是否启用多轮等）
  - 当前租户 `Admin+` 可改
  - 保存到当前租户自己的 override 行

这是当前前端和 service 层已经接近实现的语义，也是最符合空间自治的方案。

#### 第二层：去掉 handler 层的 super admin 硬拦截

`UpdateAgent` 对 built-in agent 的鉴权需要改成：

- 不是 `user.IsSuperAdmin`
- 而是与租户角色守卫一致的 `Admin+`（或如果产品要更严格，则 `Owner+`，但必须前后端统一）

由于路由本身已挂了 `g.OwnedAgentOrAdmin()`，这里需要进一步明确：

- built-in agent 没有 creator，天然应按 `tenant Admin+` 走
- 不应再在 handler 中追加一个更窄的 `SuperAdmin` 限制

#### 第三层：保留显式模型配置，不回退到“静默继承默认模型”

当前显式配置设计是合理的，因为它避免了：

- 模型来源不透明
- agent 配置与租户设置耦合
- 排查就绪状态困难

因此不建议简单恢复“智能体自动继承默认模型”。

更合理的做法：

- 新租户首次进入智能体页时，如果存在唯一可用聊天模型 / 默认 rerank 模型
  - 提供“应用推荐默认配置”按钮
  - 或在创建空间后自动做一次显式初始化
- 但最终写回的仍应是 agent 自己的 `model_id / rerank_model_id`

#### 第四层：补齐审计与提示

- 内置智能体配置被 tenant admin 修改时，记录审计日志
- 保存失败时，不再出现“Only super admins...”这种与当前产品心智不一致的错误文案
- 改成“你没有当前空间的管理权限”或类似 tenant-scoped 文案

### 建议优先级

- 优先级：最高
- 原因：这是直接阻断空间内智能体可用性的主因。

---

## 3.5 问题 5：当前 `intramind@hlsa.com` 账号可以在系统设置中添加模型

### 现象复述

当前 `intramind@hlsa.com` 账号可以在设置页的模型管理中添加模型。

### 代码结论

这不是越权，而是 **当前设计本来就是 tenant Admin+ 可以管理租户模型**。

前端：

- `frontend/src/views/settings/ModelSettings.vue`
  - 添加模型按钮：`v-if="authStore.hasRole('admin')"`

后端：

- `internal/router/router.go: RegisterModelRoutes`
  - `POST /models` → `g.Admin()`
  - `PUT /models/:id` → `g.Admin()`
  - `DELETE /models/:id` → `g.Admin()`
  - `GET /models` 才是 `g.Viewer()`

而平台级系统设置：

- `frontend/src/views/system/SystemSettings.vue`
- `internal/router/router.go: RegisterSystemAdminRoutes`

这一组才是 `SystemAdmin` 专属。

### 关键结论

当前设置页里其实混了两类能力：

1. **租户级能力**
   - 模型管理
   - parser/storage/vector/websearch 等 tenant 级配置
2. **平台级能力**
   - system global settings
   - system admin 管理

所以“能在设置中添加模型”并不等于“拿到了平台级系统权限”。

### 是否应该修改？

#### 如果产品目标是“空间管理员能自主管理本空间模型”

则当前行为应保留。

而且从问题 4 看，这个能力应当保留，否则：

- `intramind` 既不能创建模型
- 又不能给内置智能体补模型
- 新空间将无法自助完成智能体初始化

#### 如果产品目标是“只有平台管理员可以配置模型”

则要整体收紧，而不能只动前端：

- 前端：
  - 隐藏添加/编辑/删除按钮
- 后端：
  - `/models` 写接口从 `g.Admin()` 收紧到 `g.Owner()` 或 `g.SystemAdmin()`
- 同时要回答一个新问题：
  - 那普通空间如何完成 built-in agent 的模型绑定？

所以，从现有产品结构看，不建议收紧到 SystemAdmin。

### 建议修正方向

- **保留模型管理为 tenant Admin+ 能力**
- 在权限文档和页面文案上明确：
  - 这是“当前空间的模型管理”
  - 不是“平台全局模型管理”
- 把问题 4 修好后，使模型管理与 built-in agent 配置权限形成闭环

### 建议优先级

- 优先级：中
- 原因：更像权限说明与产品边界澄清，不是立即功能阻断。

## 4. 统一修正方案（建议落地顺序）

## P0：先打通空间内智能体可用性

目标：解决“能配模型但不能把模型绑到 built-in agent”这一阻断。

建议动作：

1. 允许当前租户 `Admin+` 更新 built-in agent 的配置覆盖。
2. 保持 built-in agent 基础信息只读。
3. 审计日志记录 built-in 配置修改。
4. 前端 readOnly / 保存按钮 / 错误提示与后端权限完全一致。

---

## P1：修复 built-in agent 英文化问题

目标：切换空间后，智能体卡片和编辑器一律按当前 UI locale 显示中文。

建议动作：

1. built-in agent 的 DB 记录不再作为文案来源。
2. 所有读取路径按当前 locale 从 YAML 重新组装 `name/description`。
3. `agent_visibility.go` 改成 context-aware 本地化。
4. 清理历史英文快照数据。
5. 将 UI locale 与 `WEKNORA_LANGUAGE` 解耦。

---

## P2：统一“空间成员 / 组织树成员 / 共享空间成员”概念

目标：让用户知道自己看到的究竟是哪一种成员与权限。

建议动作：

1. 明确页面命名：
   - `空间成员管理`
   - `组织树账号管理`
   - `共享空间成员`
2. 角色列不再混用同一个“管理员/所有者”文案去表达不同域。
3. owner 统一改成 badge，而不是随处替换 role 字段。
4. 收敛 owner 判定 helper。
5. 评估是否逐步淘汰 `organization_members_pre_plan3`。

---

## P3：澄清模型管理的权限边界

目标：把“模型管理是租户级配置，不是平台级配置”的规则说清楚。

建议动作：

1. 保留 `/models` 写权限为 `tenant Admin+`。
2. 设置页把模型管理明确归类为“当前空间配置”。
3. 平台级 `SystemSettings` 继续保持 `SystemAdmin` 独占。

---

## 5. 推荐的最终统一规则

如果以“空间自治 + 平台托底”为目标，建议最终统一到下面这套规则：

### 5.1 租户 / 空间级权限（权威来源：`tenant_members.role`）

- `owner`
  - 删除空间
  - API Principal / 高敏设置
  - 成员提升 / 降级 / 移除
- `admin`
  - 模型管理
  - built-in agent 配置覆盖
  - parser/storage/vector/websearch 等租户配置
- `contributor`
  - 资源内容协作
- `viewer`
  - 只读访问

### 5.2 共享空间成员（权威来源：`organization_tenant_members`）

- `admin / editor / viewer`
- owner 不作为 role 枚举值存储
- owner 仅作为组织/空间创建者 badge 叠加显示

### 5.3 组织树成员（旧域）

- `admin / editor / viewer`
- 明确标注其为“组织树治理角色”
- 不与租户 Owner/Admin 文案混用

### 5.4 内置智能体

- 名称/描述/提示模板来源：YAML + locale
- 配置覆盖来源：当前租户 DB 行
- 修改权限：当前租户 `Admin+`
- 平台级默认模板维护：`SystemAdmin`

---

## 6. 建议验收用例

修正后建议至少验证以下场景：

1. 超级管理员创建新空间后：
   - 自己是 `Owner`
   - 可把 `intramind@hlsa.com` 提升为 `Owner`
2. 在组织树账号管理页：
   - 创建者显示为“组织管理员 + 创建者 badge”或等价统一表达
3. 在共享空间成员页：
   - owner badge 与 tenant-keyed 行语义一致
   - 不再把代表用户误读成 owner role 本身
4. 切换到中文空间后：
   - built-in agent 卡片、编辑器标题、描述均为中文
5. `intramind@hlsa.com` 作为当前空间 `Admin+`：
   - 可创建模型
   - 可为 built-in agent 配置 `model_id / rerank_model_id`
   - 保存不再提示 “Only super admins can update built-in agents”
6. 非 `Admin+` 用户：
   - 仍可看模型列表
   - 不可新增/编辑/删除模型
   - built-in agent 配置为只读或入口不可见

## 7. 最终建议

本组问题不建议用“改一个页面文案”或“把某个 if 条件放宽”来局部修补。

更稳妥的修法是：

1. **先统一权限域**：明确哪个页面展示 tenant role，哪个页面展示 org-tree role，哪个页面展示 shared-space role。
2. **再统一 built-in agent 配置语义**：平台控制元数据，租户控制配置覆盖。
3. **最后做语言与页面表达清理**：把本地化从 DB 快照里拿出来，彻底回归按 locale 渲染。

如果只修问题 4 而不修问题 2 和问题 3，后续还会继续出现：

- 用户以为自己是“管理员”，实际操作却按“所有者”或另一套角色在走
- 智能体文案随空间/历史配置漂移
- 设置页权限看起来像越权，实际上只是权限域没讲清

因此建议按 `P0 -> P1 -> P2 -> P3` 顺序落地。
