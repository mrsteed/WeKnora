# IM 渠道知识库范围误判审查与修正计划

## 1. 审查范围

本次审查聚焦以下问题：

1. mxd 账号创建并绑定 IM 渠道后，通过 IM 渠道提问“有多少个知识库”，为什么智能体回答的是“全部知识库”。
2. 当前代码里，IM 渠道运行时到底使用的是谁的权限范围。
3. 为什么前一轮“同租户当前账号 agent 越权收口”没有覆盖这条 IM 链路。

本次审查主要核对以下资料与代码：

1. 日志
   - my_docs/test/1

2. IM 身份与会话链路
   - internal/im/service.go
   - internal/im/types.go
   - internal/types/principal.go
   - internal/im/identity_test.go

3. Agent KB 范围解析链路
   - internal/application/service/session_qa_helpers.go
   - internal/application/service/session_knowledge_qa.go
   - internal/application/service/session_agent_qa.go
   - internal/application/service/agent_kb_scope.go

4. Agent runtime_context 注入链路
   - internal/application/service/agent_service.go
   - internal/agent/observe.go
   - internal/agent/prompts.go

## 2. 结论摘要

结论先行：

1. 当前 IM 渠道问答并不是以 mxd 这个 WeKnora 用户身份在执行，而是以租户合成账号 `system-10008` 在执行。
2. 因为运行时身份是合成账号，不是人类账号，所以第一阶段新增的“当前账号已授权知识库范围”收口逻辑不会命中 IM 路径。
3. IM 路径在 `KBSelectionMode=all` 时会继续走旧的 fallback 分支，直接枚举租户 10008 下全部可用知识库，再按能力过滤，最终得到 8 个知识库。
4. 这 8 个知识库随后被写进 Agent 的 `KnowledgeBases` 和 `SearchTargets`，并注入到用户消息里的 `<runtime_context><bound_knowledge_bases>` 中。
5. 这次回答“有多少个知识库”的依据，不是知识检索结果，而是 runtime_context 里已经暴露给模型的绑定知识库列表。
6. mxd “创建/绑定渠道”这件事，在当前代码里只影响渠道配置的管理归属，不影响 IM 运行时资源鉴权身份。

因此，当前现象的根因不是“第一阶段代码失效”，而是：

1. 第一阶段修的是“当前人类账号同租户 agent all 模式越权”。
2. IM 当前没有人类账号运行身份，只有租户级合成账号。
3. 所以 IM 仍然按租户范围回答“全部知识库”。

## 3. 日志证据

日志文件：my_docs/test/1

从日志可以直接确认以下事实。

### 3.1 IM 会话使用的是 `system-10008`

日志中明确出现：

1. `session.go:138[GetSession] | Retrieving session, ID: ..., tenant ID: 10008, user ID: system-10008`

这说明当前 IM 会话在 SessionService 看来，owner/user_id 不是 mxd，而是合成账号 `system-10008`。

### 3.2 当前提问绑定的是内置智能体 `builtin-smart-reasoning`

日志中明确出现：

1. `session_agent_qa.go:69[AgentQA] | ... agent tenant ID: 10008, query: 有多少个知识库 ...`
2. `last_request_state.agent_id":"builtin-smart-reasoning"`

因此，本次现象不是某个特殊自定义智能体独有，而是当前 IM 渠道绑定的“智能问答知智能体 / builtin-smart-reasoning”运行时行为。

### 3.3 KB 解析实际走的是旧 fallback 分支，不是第一阶段的新 current-user 分支

日志中出现的是：

1. `session_knowledge_qa.go:474[resolveKnowledgeBasesFromAgent] | KBSelectionMode=all: tool-capability filter removed 1 own + 0 shared KBs`
2. `session_knowledge_qa.go:478[resolveKnowledgeBasesFromAgent] | KBSelectionMode=all: loaded 8 knowledge bases (own + shared)`

而不是第一阶段新增的这组日志：

1. `KBSelectionMode=all: loaded ... accessible knowledge bases for current user`

这说明 IM 路径没有命中新加的“current user scope”收口逻辑，而是回退到了旧的“租户全量 KB”分支。

### 3.4 8 个知识库被正式写进了 AgentConfig

日志中随后出现：

1. `Agent configured with 8 knowledge base(s): [...]`
2. `Built 8 search targets: 8 full KB`
3. `Registered grep_chunks tool with searchTargets: 8 targets`

这说明“8 个知识库”不是 UI 显示误差，而是已经成为本次 Agent 运行的真实知识库范围。

### 3.5 最终答案直接引用了当前会话绑定知识库信息

日志里的最终 answer preview 是：

1. `根据当前会话绑定的知识库信息，共有 8 个知识库 ...`

同一轮工具调用里：

1. `web_search` 失败
2. `grep_chunks` 在 8 个 KB 范围内找到 0 个 chunk

所以模型最终答案不是基于检索事实，而是基于 prompt/runtime_context 中已经暴露的绑定知识库列表直接生成。

## 4. 当前代码链路

## 4.1 IM 运行时身份是租户合成账号，不是渠道创建者

`internal/im/service.go` 的 `withIMIdentity` 当前直接这样构造上下文：

1. `TenantIDContextKey = tenantID`
2. `UserIDContextKey = fmt.Sprintf("system-%d", tenantID)`
3. `Principal = PrincipalIMUser(...)`
4. `TenantRoleContextKey = viewer`

也就是说：

1. 当前 IM 消息只带了一个“外部 IM 用户 principal”。
2. 同时，真正进入大多数旧服务层授权判断的 `UserIDContextKey` 被强制设置成 `system-租户ID`。
3. 这里并没有把渠道创建者 mxd 或任何内部 WeKnora 用户注入成运行时资源授权用户。

## 4.2 Session owner 也不会从 `PrincipalIMUser` 推导出 mxd

`internal/types/principal.go` 的 `SessionOwnerIDFromContext` 当前只对两类 principal 做特殊处理：

1. `PrincipalAPIExternalUser`
2. `PrincipalEmbedSession`

而 `PrincipalIMUser` 不在这个分支里。

因此 IM 场景下：

1. `SessionOwnerIDFromContext` 会回退到 `UserIDFromContext`
2. 也就是回退到 `system-10008`

这和日志里 `GetSession ... user ID: system-10008` 完全一致。

## 4.3 第一阶段的新 same-tenant current-user resolver 明确跳过 synthetic user

`internal/application/service/agent_kb_scope.go` 中的 `ResolveAgentKnowledgeBasesForCurrentUser` 当前只服务于“当前人类账号”场景，并明确写了：

1. 如果 `UserIDFromContext` 为空，跳过
2. 如果 `types.IsSyntheticUserID(userID)`，跳过

所以当 IM 上下文是 `system-10008` 时：

1. 这个 resolver 会直接返回 `ok=false`
2. 表示“当前路径不适用 current-user 收口逻辑”

这不是 bug，而是第一阶段的明确设计边界。

## 4.4 IM 因此回退到旧的 `KBSelectionMode=all` 全租户分支

`internal/application/service/session_knowledge_qa.go` 的 `resolveKnowledgeBasesFromAgent` 现在是两段逻辑：

1. 先尝试 `ResolveAgentKnowledgeBasesForCurrentUser`
2. 命不中时，再进入旧的 `switch customAgent.Config.KBSelectionMode`

当前 IM 因为使用 synthetic user：

1. 第一段直接跳过
2. 第二段 `case "all"` 继续执行
3. 调用 `s.knowledgeBaseService.ListKnowledgeBases(ctx)`
4. 取到租户 10008 的全量知识库，再做 capability filter

所以最终得到 8 个知识库。

## 4.5 这 8 个知识库会进入 runtime_context

`internal/application/service/session_agent_qa.go` 的 `buildAgentConfig` 会把解析后的 KB IDs 写入：

1. `agentConfig.KnowledgeBases`
2. `agentConfig.SearchTargets`

随后 `internal/application/service/agent_service.go` 的 `resolveKBAndDocInfos` 会根据这些 KB IDs 取知识库元数据。

最后 `internal/agent/observe.go` 的 `buildRuntimeContextBlock` 会把这些 KB 信息包装成：

1. `<bound_knowledge_bases>`
2. 内部再嵌 `<knowledge_bases> ... </knowledge_bases>`

所以即使没有任何检索命中，模型也已经在用户消息 runtime_context 里看到了完整的“当前绑定知识库列表”。

## 4.6 mxd 的“创建 / 绑定渠道”只影响管理归属，不影响运行鉴权

`internal/im/types.go` 里 `IMChannel` 确实有：

1. `AgentID`
2. `CreatedBy`

但当前 `CreatedBy` 的用途主要在渠道管理：

1. `GetChannelByIDAndTenantAndCreator`
2. `ListChannelsByAgent`
3. `ListChannelsByTenant`
4. `DeleteChannel`
5. `ToggleChannel`

也就是说：

1. mxd 创建渠道后，只能说明这个渠道配置的 owner / creator 是 mxd。
2. 并不能说明运行时消息就自动继承 mxd 的知识库权限。
3. 当前 IM 运行时根本没有用到 `channel.CreatedBy` 去做 KB 鉴权。

## 5. 根因归纳

当前现象的根因可以归纳为三层。

### 5.1 运行时身份和配置归属身份是两套概念

当前系统里：

1. `IMChannel.CreatedBy` 表示谁创建了渠道配置。
2. IM 消息运行时却使用 `system-tenant` 作为资源访问用户。

这两者没有打通。

### 5.2 第一阶段修复范围只覆盖“当前人类账号”，不覆盖 synthetic IM user

第一阶段收口的前提是：

1. 当前请求上下文里存在可用于 KBVisibility 的真实内部用户 ID。

IM 当前不满足这个前提。

### 5.3 Agent runtime_context 本身会把绑定 KB 列表暴露给模型

一旦 fallback 分支把租户全量 KB 装进 `agentConfig.KnowledgeBases`：

1. 模型不需要检索到文档内容
2. 也可以直接根据 `<bound_knowledge_bases>` 回答“我能看到多少知识库”

所以这个问题不仅是“检索范围过大”，也是“prompt 元数据暴露范围过大”。

## 6. 为什么当前表现为“回答全部知识库”

把本次日志和代码串起来，当前行为是：

1. IM 收到微信消息
2. `withIMIdentity` 把用户身份设成 `system-10008`
3. Agent 绑定的是 `builtin-smart-reasoning`，且 `KBSelectionMode=all`
4. `ResolveAgentKnowledgeBasesForCurrentUser` 因 synthetic user 直接跳过
5. `resolveKnowledgeBasesFromAgent` fallback 到旧的租户全量枚举分支
6. 8 个知识库进入 `AgentConfig.KnowledgeBases` 与 `SearchTargets`
7. `buildRuntimeContextBlock` 把这 8 个知识库注入 `<bound_knowledge_bases>`
8. 模型先尝试 web_search 和 grep_chunks
9. 两个工具都没有提供支持“知识库数量”的事实内容
10. 模型最后直接依据 runtime_context 里的绑定 KB 清单，回答“共有 8 个知识库”

因此，“回答全部知识库”不是模型凭空幻觉，而是当前后端确实把“全部绑定 KB 列表”喂给了它。

## 7. 修正目标

本轮不进入第二阶段，只针对当前问题做最小收口，目标应限定为：

1. IM 渠道在同租户内运行时，智能体看到的知识库范围不再使用 `system-tenant` 的全租户范围。
2. 当渠道是由 mxd 这样的内部用户创建并绑定时，至少应使用该内部用户的可见知识库范围来解析 `KBSelectionMode=all`。
3. runtime_context 中暴露给模型的 `<bound_knowledge_bases>` 也必须同步缩小到该内部用户有权看到的范围。

## 8. 修正计划

建议按下面顺序修，而不是直接把 IM 全链路改成真实用户登录体系。

### 8.1 第一阶段-A：为 IM 增加“资源授权用户”概念

当前 IM 上下文同时承担了两件事：

1. 会话归属 / 外部平台身份
2. 资源鉴权身份

建议拆开。

新增一个明确的概念：

1. IM Runtime Resource User
   - 表示“本条 IM 消息在同租户资源鉴权时，应当按哪个内部用户的权限来看”。

最小方案建议直接使用：

1. `IMChannel.CreatedBy`

原因：

1. 当前系统里，这是唯一稳定可用的内部用户映射。
2. 用户也明确表达了预期：mxd 绑定的 IM，应该按 mxd 权限看知识库。

### 8.2 第一阶段-B：不要直接把 `UserIDContextKey` 改成 mxd

不建议直接在 `withIMIdentity` 里把：

1. `UserIDContextKey = channel.CreatedBy`

原因：

1. 这会改动 `SessionOwnerIDFromContext`
2. 进而影响 IM Session 归属、历史记录 owner、memory 归属、可能还有 stop / stream 关联行为
3. 风险超出当前问题范围

更稳妥的做法是：

1. 保留 IM 当前的 synthetic session owner 语义
2. 额外引入单独的“资源授权用户”上下文键或 helper
3. 让 KB scope resolver 优先读取这个“资源授权用户”

## 8.3 第一阶段-C：修改 Agent KB Scope Resolver 的取用户逻辑

当前 `ResolveAgentKnowledgeBasesForCurrentUser` 只读：

1. `UserIDFromContext`
2. `UserContextKey`

建议改成：

1. 优先读取 IM 资源授权用户
2. 若不存在，再回退到现有 `UserIDFromContext`

这样：

1. Web / API 现有逻辑不变
2. IM 可以单独带入 `channel.CreatedBy` 对应的人类账号权限

## 8.4 第一阶段-D：在 IM HandleMessage 链路注入创建者用户信息

建议在 `HandleMessage` 里，在拿到 `channel` 后补一段：

1. 根据 `channel.CreatedBy` 加载内部用户实体
2. 将该用户作为“IM 资源授权用户”注入 context
3. 同时把该用户实体注入一份给 visibility bypass 判断使用

注意这里的 tenant role / bypass 只用于资源可见性，不用于 Session owner。

## 8.5 第一阶段-E：让 runtime_context 也跟着缩小

只修检索还不够。

因为当前问题里，模型最后是根据 runtime_context 的 `<bound_knowledge_bases>` 直接作答。

所以只要把：

1. `buildAgentConfig` 里的 `agentConfig.KnowledgeBases`

改成使用 mxd 可见范围后，后面的：

1. `resolveKBAndDocInfos`
2. `buildRuntimeContextBlock`

自然会一起收口。

也就是说，本轮不需要单独改 prompt 模板；只要前面的 KB scope 解析改对，runtime_context 就会自动缩小。

## 8.6 建议补充的测试

至少补以下测试：

1. IM 身份测试
   - 验证 IM 仍保留 synthetic session owner
   - 同时存在单独的 resource auth user = channel.CreatedBy

2. IM Agent QA 范围测试
   - 渠道创建者 mxd 只能看 2 个 KB
   - `KBSelectionMode=all` 下，IM AgentConfig 只带这 2 个 KB

3. runtime_context 测试
   - `<bound_knowledge_bases>` 中不应再出现 mxd 无权看的 KB

4. 回归测试
   - Web 路径同租户 current-user resolver 行为不变
   - 跨租户共享智能体路径不受本轮影响

## 9. 不建议本轮一起做的项

当前先不要做以下工作：

1. 不要把 IM 外部平台用户直接映射成真实 WeKnora 用户登录体系
2. 不要把 Session owner 语义从 `system-tenant` 改成 `channel.CreatedBy`
3. 不要进入“共享智能体是否继续作为独立 KB 读权限来源”的第二阶段

这些都属于更大范围的身份模型调整，不适合和本次问题混修。

## 10. 最终判断

当前 IM 渠道之所以会回答“全部知识库”，根因已经明确：

1. IM 运行时身份是 `system-10008`
2. 不是 mxd
3. 第一阶段 current-user 收口逻辑显式跳过 synthetic user
4. 所以 IM 继续走 `KBSelectionMode=all` 的租户全量枚举分支
5. 这些 KB 又被注入 runtime_context，最终被模型直接拿来回答数量问题

因此，本问题的准确修正方向不是“继续补 agent all 过滤”，而是：

1. 给 IM 增加单独的资源授权用户
2. 最小实现先取 `IMChannel.CreatedBy`
3. 用这个内部用户权限来解析同租户 IM 的 agent 知识库范围
4. 让 runtime_context 与 searchTargets 一起同步缩小

这条路线能解决你当前的 mxd 场景，又不会提前进入第二阶段的大范围身份模型重构。
