# IM集成权限调整审查报告与实施说明

## 1. 背景与本次目标

本次需求已经明确收口为两点：

1. 仅放开 IM 集成权限。
2. 集成渠道逻辑和现有代码保持一致。

对应的权限要求是：

- 协作者及以上权限可以自由访问、编辑、绑定 IM 集成渠道。
- 只读权限没有访问权限。
- 网页嵌入与 API 集成权限不在本次放开范围内，继续保持原有更高权限门槛。

这意味着本次不引入新的“成员个人绑定实例”模型，也不改变当前渠道级绑定的数据结构。

## 2. 最终结论

### 2.1 权限策略

本次实施后的目标权限模型是：

- IM 集成：contributor / admin / owner 可访问并可编辑。
- IM 集成：viewer 不可访问。
- Embed / API 集成：继续保持 owner 才能管理。

这里的“可编辑”包括：

- 创建 IM 渠道
- 编辑 IM 渠道
- 删除 IM 渠道
- 启停 IM 渠道
- 微信扫码绑定 / 重新绑定

### 2.2 保持不变的渠道逻辑

本次不改变以下既有逻辑：

- IM 渠道仍然是渠道级配置，不是成员级配置。
- 微信绑定信息仍然保存在渠道自身的 credentials 中。
- 一个渠道同一时刻仍然只绑定一套微信凭证。
- 同一个微信 bot 仍然不能同时绑定到多个渠道。

因此本次权限放开后的业务语义是：

- 协作者及以上，不是“绑定自己的独立微信实例”。
- 而是“直接编辑这个共享 IM 渠道当前使用的微信绑定”。

这是本次需求明确接受的行为边界。

### 2.3 与此前审查结论的关系

此前审查曾给出一个更严格的架构判断：

- 如果目标是“每个成员各自绑定自己的微信，而互不影响”，则必须新增成员级绑定模型。

这个判断仍然成立。

但本次最新需求已经明确：

- 不改现有渠道逻辑。
- 只调整权限。

所以本次实现不会进入“成员级独立绑定实例”方案，而是采用更直接的权限放开方案。

## 3. 现有代码逻辑保留项

## 3.1 渠道仍是核心配置单元

后端 IM 渠道模型仍是：

- 一条 IMChannel 记录对应一个渠道。
- 渠道保存平台类型、Agent 绑定、知识库绑定、渠道凭证等信息。

这意味着：

- 当前没有“成员自己的渠道绑定记录”这一层表结构。
- 所有绑定行为仍然直接落在渠道本身。

## 3.2 微信仍然是渠道级单实例绑定

微信相关逻辑继续保持：

- 渠道凭证写入 IMChannel.credentials。
- bot_identity 由渠道平台凭证计算得出。
- bot_identity 继续保持唯一约束。

因此：

- 一个渠道只能绑定一个微信 bot。
- 一个微信 bot 也只能被一个渠道占用。

## 3.3 微信二维码返回的仍是渠道凭证

微信扫码接口的行为不变：

- 申请二维码
- 轮询二维码状态
- confirmed 后返回 bot_token、ilink_bot_id、ilink_user_id
- 前端将这些值写入当前渠道表单
- 保存时整体提交到渠道更新接口

所以本次只是把“谁可以执行这套流程”从 owner 放开到 contributor 及以上，并没有把绑定结果从“渠道级”改成“成员级”。

## 4. 权限调整实施方案

## 4.1 前端调整

前端需要实现以下权限收口：

### A. 侧边栏入口

发布集成入口从：

- owner 可见

调整为：

- contributor 及以上可见
- viewer 不可见

原因：

- 只要 IM tab 至少对 contributor 开放，侧边栏入口就应跟随“最宽可见 tab”开放。
- 具体到 embed/api 的更高权限，继续在集成页内部按 tab 控制。

### B. 集成页 tab 权限

需要改成：

- IM tab：contributor 及以上可见
- embed tab：owner 可见
- api tab：owner 可见

这样可以保证：

- 协作者进入发布集成页时，只能看到 IM 集成。
- 不会误看到仍未放开的 embed/api。

### C. IMChannelPanel 内部交互权限

IM 面板里以下交互需要从 admin 提升为 contributor 即可使用：

- 新增渠道按钮
- 卡片更多操作
- 删除渠道
- 打开抽屉编辑
- 保存按钮
- 渠道启用开关
- 微信扫码绑定与重新绑定

换句话说：

- 只读用户不能进入页面。
- contributor / admin / owner 进入后，拥有同等 IM 渠道编辑能力。

### D. Agent 编辑器内联入口

Agent 编辑器中的“发布渠道”入口需要同步对齐：

- IM 入口：contributor 及以上可见
- Embed 入口：仍然仅 owner 可见
- API 相关 owner-only 控件继续保持不变

这样能避免出现：

- 协作者从主菜单能进 IM 集成
- 但从 Agent 编辑器里又被挡住

的权限不一致问题。

## 4.2 后端调整

后端保持现有 IM 路由与处理逻辑不变，仅调整守卫角色：

### A. 调整为 contributor 及以上

以下接口应调整为 contributor 及以上可访问：

- 创建某个 Agent 的 IM 渠道
- 查询某个 Agent 的 IM 渠道详情列表
- 查询当前租户下全部 IM 渠道总览
- 更新渠道
- 删除渠道
- 启停渠道
- 获取微信二维码
- 轮询微信二维码状态

### B. viewer 不可访问

viewer 不应再访问：

- IM 渠道总览
- IM 渠道详情
- 微信扫码绑定接口

因为本次需求已经明确：

- 只读权限没有访问权限

### C. embed/api 不变

本次不调整：

- 网页嵌入渠道相关接口
- API 集成相关接口

这些接口继续按原有 owner 规则执行。

## 5. 已知影响与风险说明

## 5.1 协作者将直接修改共享渠道

这是本次方案最重要的副作用，也是需求接受的结果：

- 协作者重新绑定微信时，修改的是共享渠道当前绑定的微信凭证。
- 不是给自己新增一条独立绑定。

因此：

- 最后一次保存的人，会决定该渠道当前实际使用哪一个微信 bot。
- 这会影响同租户下其他同样使用这个渠道的人。

这不是 bug，而是“保持现有渠道逻辑不变”下的直接结果。

## 5.2 该方案不适用于“成员各自绑定互不影响”场景

如果未来需求升级为：

- 每个成员都能基于同一模板渠道绑定自己的微信
- 且彼此互不覆盖

则仍然必须新增：

- 成员绑定实例表
- 成员级二维码与保存接口
- 按绑定实例启动适配器的运行时逻辑

本次不做这部分改造。

## 5.3 重新绑定按钮问题已单独修复

此前审查确认：

- “重新绑定按钮无响应”是前端状态分支问题。
- 后端二维码接口本身是正常工作的。

本轮实现中，已同步修复该前端状态 bug：

- 已绑定状态下点击“重新绑定”后，界面会切换到二维码流程。
- 二维码生成失败时，已绑定渠道会回退到原绑定成功态。
- 重新绑定成功后，界面会恢复到“已绑定成功”状态。

因此当前 contributor 及以上用户获得 IM 编辑权限后，不会再遇到“重新绑定按钮看起来无响应”的旧交互问题。

## 6. 本次代码调整点

本次代码调整应覆盖以下文件与职责：

### 前端

- 发布集成 tab 的最小角色要求
- 侧边栏 integrations 入口可见性
- IMChannelPanel 内部编辑能力门槛
- Agent 编辑器内联 IM 入口权限

### 后端

- IM 路由组守卫从 owner 调整为 contributor
- 微信二维码接口守卫从 owner 调整为 contributor

### 不调整

- IM 渠道模型
- bot_identity 唯一约束
- 微信凭证保存结构
- embed/api 权限边界

## 7. 验证建议

建议至少验证以下场景：

### 7.1 contributor 用户

1. 可以看到发布集成菜单入口。
2. 进入后只能看到 IM 集成 tab。
3. 可以新增 IM 渠道。
4. 可以编辑已有 IM 渠道。
5. 可以触发微信扫码绑定与重新绑定。
6. 可以删除和启停渠道。

### 7.2 viewer 用户

1. 看不到发布集成菜单入口。
2. 即使手工访问 integrations 路由，也不应看到 IM 可操作界面。
3. 直接请求 IM 渠道接口应被拒绝。

### 7.3 owner 用户

1. IM 能力保持可用。
2. embed/api 入口与能力保持不变。
3. 不出现原有 owner 能做、现在反而不能做的回归。

### 7.4 既有渠道逻辑

1. 渠道绑定后的微信凭证仍然正常保存。
2. 同一个微信 bot 重复绑定到其他渠道时，仍然会被唯一约束拒绝。
3. 重新绑定后渠道仍然只保留一套最新微信凭证。

## 9. 最终结论

本次需求下的正确实现方式不是改模型，而是改权限。

最终方案如下：

- IM 集成权限放开到 contributor / admin / owner。
- viewer 无访问权限。
- 集成渠道逻辑保持现状不变。
- 因此 contributor 及以上编辑的是同一条共享渠道，而不是各自独立的微信绑定实例。
- embed / api 继续维持 owner-only。

如果后续产品需要“每个成员绑定自己的微信且互不影响”，那将是下一阶段的模型升级课题，而不是本次权限调整的范围。
