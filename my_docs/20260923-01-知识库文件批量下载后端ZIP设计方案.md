# 知识库文件批量下载（后端 ZIP 方案）详细设计文档

- 文档编号：20260923-01
- 日期：2026-09-23
- 状态：设计评审稿（未实施）
- 范围：WeKnora 后端（Go）+ 前端（Vue3 / tdesign）
- 关联现状：知识库卡片多选 / 批量操作栏（批量删除、批量重解析、批量打标签、批量移入文件夹）

## 1. 背景与目标

### 1.1 需求

用户在知识库内勾选多个知识文件后，希望"批量下载"：一次操作得到全部文件。

### 1.2 方案选型结论

| 方案 | 说明 | 结论 |
|---|---|---|
| A 纯前端并发取文件 + jszip 打包 | 零后端改动；但所有 Blob 驻留内存，>1.5GB 有 OOM 风险，大文件集合不可靠 | 备选（小文档场景） |
| B **后端新增批量下载接口，流式产出 ZIP** | 对任意体积稳定；权限逐文件按既有模型校验 | **本文档采用** |
| C 前端逐个触发 N 次浏览器下载 | 无打包、浏览器多次弹"允许多文件下载"，文件名冲突 | 否决 |

选择 B 的核心理由：后端持有文件句柄后可**流式**写入 zip（任意单文件不落地、不整体驻留内存），
对大文件集合与弱网都稳定；权限边界收敛在服务端，不依赖前端自觉。

### 1.3 非目标（本期不做）

- 断点续传 / Range 传输（zip 流不支持，且浏览器下载体验收益低）
- 异步任务式打包（"后台打包完成通知"）——先做同步流式，若未来出现 GB 级超长 zip 需求再演进
- 部分失败"跳过继续"策略之外的容错（见 5.4，明确选"全有或全无"）

## 3. API 设计

### 3.1 接口定义

```
POST /api/v1/knowledge/batch-download
```

- 用 POST 而非 GET：与 `batch-delete` 一致；ids 列表不走 query，避免 URL 长度限制
- 请求体：

```json
{
  "kb_id": "bffbb535-32aa-4ad5-bc12-9822d03d3bfd",
  "ids": ["k-001", "k-002", "k-003"]
}
```

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| kb_id | string | 是 | 非空、合法 UUID |
| ids | []string | 是 | 1 ≤ len ≤ **50**（上限，防超大响应与 DoS）；去重后计数 |

- 成功响应（HTTP 200）：

```
Content-Type: application/zip
Content-Disposition: attachment; filename="knowledge_<kb短名或id前8位>_YYYYMMDD-HHMM.zip"
```

zip 为**流式**写出（见 4.2），不落磁盘、不做整体缓冲。

- 失败响应（JSON，与项目统一 `c.JSON` 风格一致）：

| HTTP | 场景 | body 示例 |
|---|---|---|
| 400 | 参数非法 / ids 为空 / 超上限 | `{"code":..., "message":"ids 数量超出上限 50"}` |
| 401/403 | 全局鉴权失败 | 沿用现有中间件输出 |
| 404 | kb 不存在 | 统一错误 |
| 403 | 当前用户对任一 id **无下载权**（含跨 KB、KB 级 Editor+ 不满足） | `{"message":"无权限下载知识: <name>(<id前8位>)"}` |
| 404 | 任一 id 不存在 / 不属于该 kb | `{"message":"知识不存在: <id前8位>..."}` |

### 3.2 关键设计点

1. **kb_id 显式传参**：前端批量操作都在某个 KB 详情页发起，传 kb_id 后后端可直接用
   KB 级鉴权门（类似现有 `KBAccessWriteFromKnowledgeIDParam` 但按 kb 参数），避免逐 id 反查 KB 时
   路由中间件无法提前拦截。
2. **全有或全无（all-or-nothing）**：任一 id 校验失败 → 整体 4xx 返回、**不开始写 zip**。
   与"批量删除要么全过要么全拒"的风格一致，也避免客户端收到"半截 zip"（zip 一旦开始流式写出
   就无法再改状态码）。
   - 实现含义：鉴权与元数据校验必须在**开流之前**全部完成（见 4.1 两阶段）。
3. **不传 kb_id 的退化行为**：拒绝（400），强制两端契约一致，防止跨 KB 混选。

## 4. 后端实现设计

### 4.1 handler 两阶段流程

```
Phase 1 预校验（全部通过才继续，任一步失败即 JSON 错误返回）
  1. 绑定/校验 body：kb_id 非空、ids 去重、1..50
  2. 鉴权：
     a. 全局 g.Contributor()（与单下载一致）
     b. KB 级：校验当前用户对 kb_id 具备 Editor+（复用现有 KB 访问校验工具函数，
        语义对齐 requireKnowledgeMutation 的 KB 角色判定）
  3. 逐 id 解析：ResolveKnowledge(id)，校验 knowledge.kb_id == kb_id；
     任一不存在 / 不属于该 KB → 404
  4. 物化文件元信息：对每个 id 调用
     GetKnowledgeFile(ctx, id)，拿到 (ReadCloser, filename)
     —— 注意：此处打开的 ReadCloser 在 Phase 2 前必须全部 close()，
        否则并发句柄数 = ids 数；改为 Phase 1 只取 filename（见 4.1.1），
        Phase 2 逐个流式取文件
  5. 文件名去重：重名追加 " (2)"、" (3)"…；确保非空兜底用 id

Phase 2 流式写 zip（全部预校验通过后）
  6. 设置响应头（200, application/zip, Content-Disposition）
  7. zw := zip.NewWriter(c.Writer)
  8. for each id:
       file, err := GetKnowledgeFile(ctx, id)   // 此时才打开句柄
       zw.Create(filename) → io.Copy(w, file) → file.Close()
       任一 err → 记日志、尝试 zw 写错误条目说明、中断（连接已开流，无法回退 JSON）
  9. zw.Close()
```

#### 4.1.1 filename 获取与文件读取分离

`GetKnowledgeFile` 同时返回句柄与文件名。两个选项：

- 选项 1：Phase 1 就打开全部句柄并持有到 Phase 2（句柄数 = 选中数 ≤50，短窗口，可接受；
  实现最简，**推荐**——50 个 fd 在 Linux 默认 ulimit 下没有压力）
- 选项 2：Phase 1 仅查 knowledge 元数据推导文件名（original_file_name / title 规则对齐前端
  `resolveKnowledgeDownloadFileName`，manual 类型补 `.md`），Phase 2 才开句柄。
  需要 service 层新增一个 `GetKnowledgeFileName(ctx, id)` 纯元数据方法（或复用解析函数）。

**推荐选项 1**：复用既有 service 方法、零新增接口；50 句柄持有窗口（从打开到 zip 写出完成）
在正常网络下一两个数量级内远小于 fd 超时风险。若文件源为对象存储且单句柄成本高，则改选项 2。

### 4.2 zip 写入细节

- Go 标准库 `archive/zip`，无第三方依赖
- 压缩方法：`zip.Deflate`（默认 6 级）。已压缩格式（pdf/jpg/zip/mp4）用 `zip.Store` 可省 CPU
  ——按扩展名分类实现一个 10 行的小工具函数；非必须，首版可全 Deflate
- **不写 `Content-Length`**：流式输出天然未知长度，浏览器按 chunk 下载；
  如需进度体验，前端用 `transferLength` 未知时显示不定态进度（见 6）
- 请求取消：客户端 abort 后 `ctx.Done()` 触发，循环内每轮 `select ctx.Done()` 及时停止
  `io.Copy`（建议包一个带 ctx 的中转拷贝，避免单文件传输中卡 30s 才发现取消）
- 超时：设置该路由的处理超时**放宽**（如 10 分钟），普通 API 超时中间件若存在需对该 path 豁免
  （实施时先查 router 是否挂全局 timeout，若有则加白名单）

### 4.3 文件名与 zip 结构

- zip 内为**平铺**（不建目录）；未来如需按文件夹结构打包，另加 `include_paths` 参数
- 命名规则（与前端单下载展示对齐）：
  `original_file_name`（非空）→ 否则 `file_name` → 否则 `title` → 否则 `id`
  manual 类型若结果无扩展名则补 `.md`
- 重名去重：`a.pdf`、`a.pdf` → `a (1).pdf`、`a (2).pdf`
  （首版：第一个原名保留，从第二个开始加后缀）
- 编码：`FileInfo.SetMode` 不设置特殊权限位；`Name` 直接写 UTF-8
  （Go archive/zip 原生 UTF-8，中文文件名在 Win/mac 均可正常解压；
  个别老旧解压工具对中文名表现不一，属可接受已知边界）

### 4.4 错误与日志

- preflight 阶段所有失败 → 结构化日志 + JSON 错误（含失败 id 前 8 位与原因）
- 流式阶段中途失败（文件源 IO 错误）：
  - 日志 record `kb_id / ids / failed_id / 已写字节数`
  - 连接已 200 开流：无法转 JSON；写 zip 条目 `_DOWNLOAD_ERROR.txt` 说明失败文件后 zw.Close()
    收尾（尽力而为，客户端得到部分 zip 而非挂死）
  - 前端侧该路径由 catch 不到的"截断 zip"体现 → 建议前端校验 zip 尾部（JSZip 方案才有，
    本方案前端不解析 zip）；实践上文件源 IO 错误概率极低，以日志告警为主
- 审计：pre-flight 成功后写一条审计/访问日志 `batch_download kb_id=... count=... bytes=...`
  （对齐项目现有 logging 风格；若项目有审计表机制则复用）

### 4.5 路由与中间件（`routes_knowledge.go`）

```go
// 与 batch-delete 同族，读组（batch 操作均挂 kRead）
kRead.POST("/batch-download",
    g.Contributor(),
    g.KBAccessEditorFromKbIDParam("kb", "kb_id", true), // 语义：对 body 中 kb_id 要求 Editor+
    handler.BatchDownloadKnowledge)
```

- 注意：现有 KB 门禁是从 path 参数取 id（`KBAccessWriteFromKnowledgeIDParam`）；
  本接口 kb_id 在 **body** 中，需在 handler 内自行完成 KB 级鉴权
  （handler 第 2 步），路由层中间件只做 `g.Contributor()` 与 body 校验。
  因此路由最终为：

```go
kRead.POST("/batch-download", g.Contributor(), handler.BatchDownloadKnowledge)
```

  并在 handler 内显式调用 KB 访问校验函数（与 `DownloadKnowledgeFile` 的
  `resolveKnowledgeAndValidateKBAccess` 同族，但按 kb 维度）。
  **实施时以实际中间件可复用性微调**，原则：鉴权逻辑集中在 handler Phase 1，
  与单下载语义完全对齐（Contributor 全局 + KB 内 Editor+）。

## 5. 约束与边界

### 5.1 上限

| 项 | 值 | 理由 |
|---|---|---|
| 单次 ids 数 | 50 | 防超大 zip / fd 数 / 超时概率 |
| 单文件大小 | 不设硬限（跟随对象存储） | 流式不驻留内存 |
| 总 zip 体积 | 软提示 2GB | 不硬断；超 2GB zip 格式（zip64 由 Go 库自动处理）可打开 |
| 处理超时 | 10 min | 覆盖 GB 级慢盘场景 |

### 5.2 权限矩阵（与单下载完全一致）

| 角色 | 结果 |
|---|---|
| 非 Contributor 全局角色 | 403（g.Contributor 拦截） |
| KB 的 viewer（owner/admin/editor 之外的 KB 角色） | 403（KB 级 Editor+ 校验失败） |
| 跨租户 viewer 访问他人 KB | 403 |
| owner/admin/editor | 200（逐文件仍校验隶属 kb_id） |

### 5.3 并发/占用

- 同一 KB 多人同时批量下载互不影响（只读路径）
- 下载期间该知识文件的编辑/删除：预校验通过后文件被删 → Phase 2 打开句柄失败 →
  走 4.4 的"部分 zip + 告警"路径（低概率，可接受）

### 5.4 失败策略决策记录

- 选"全有或全无"（pre-flight 全过才开流），**不**做"跳过失败文件继续打包"：
  批量下载场景下用户预期是"拿齐"，静默缺件比拒绝更糟；且跳过策略需要 zip 内
  错误清单文件 + 前端二次提示，复杂度不成比例。
- 文件源瞬时 IO 错误（pre-flight 已过、流式中失败）属于**不可预检**的一类，
  按 4.4 处理并告警，不引入重试。


## 6. 前端实现设计

### 6.1 API 层（`frontend/src/api/knowledge-base/index.ts`）

```ts
// 批量下载：直接返回 Blob（zip），复用 getDown 管道
export const batchDownloadKnowledge = (
  kbId: string,
  ids: string[],
  onProgress?: (loadedBytes: number | null) => void,
) => {
  return postDown('/api/v1/knowledge/batch-download', { kb_id: kbId, ids }, {
    onDownloadProgress: (e) => onProgress?.(e.loaded),
  });
};
```

- `postDown`：与现有 GET 版 `getDown` 同型的 POST + `responseType: 'blob'` 助手
  （查看现有 http 封装，若无则新增，约 15 行；注意**错误分流**：
  后端返回 JSON 错误但 responseType=blob 时，需先按 content-type 判断是否
  application/json，是则解析 message 弹 toast，否则才当作 zip 文件流交给调用方）
- 失败判定：HTTP ≥ 400 或 content-type 为 json → 抛出带 message 的 Error

### 6.2 交互流程（`KnowledgeBase.vue`）

```
handleBatchDownload()
  ├─ guard: batchDownloading || selectedIds.size === 0
  ├─ guard: !canDownloadKnowledge（按钮本身已隐藏，双保险）
  ├─ batchDownloading = true
  ├─ batchDownloadKnowledge(kbId, Array.from(selectedIds), onProgress)
  │    ├─ onProgress: 更新「已下载 N bytes」（response 无 Content-Length → 不定态+字节数）
  │    └─ 成功: 保存 Blob → 文件名 knowledge_<kb名>_<YYYYMMDD-HHmm>.zip
  │             MessagePlugin.success(t('…batchDownloadSuccess', { count }))
  │    └─ 失败: MessagePlugin.error(解析出的 message 或 t('…batchDownloadFailed'))
  └─ finally: batchDownloading = false
```

- 下载成功**不**清空选中（用户可能继续浏览/再删），与批量删除后清空选中的行为不同——
  下载是非破坏性操作，保留选中方便连续操作
- 文件名兜底：kb 名含非法字符时替换；无 kb 名用 kbId 前 8 位
- 防重复触发：按钮 :loading + 其他批量按钮在 batchDownloading 期间 disabled
  （复用 DocumentBatchBar 的禁用逻辑：增加 `downloadLoading` prop，count>0 时
  任一 loading 互斥——首版可仅禁用下载按钮自身 + 提交中不改变 selectedIds 即可，
  因为并发写操作会改变文件集合，属既有交互，不在本文档范围）

### 6.3 DocumentBatchBar 改动

```
props 新增: downloadLoading?: boolean, canDownload?: boolean
emits 新增: 'batchDownload'
按钮: <t-button v-if="canDownload" variant="outline" :loading="downloadLoading"
        :disabled="count === 0 || downloadLoading"
        @click="emit('batchDownload')">
        <t-icon name="download" /> {{ t('knowledgeBase.batchDownload') }}
      </t-button>
位置: 「批量删除」之前（按破坏性从低到高排列：下载 → 重解析 → 打标 → 移入文件夹 → 删除）
```

- `canDownload` = `canDownloadKnowledge`（计算自权限），为 false 时按钮不渲染
  （与单文件卡片"下载"入口的显隐规则一致）
- 样式沿用现有批量栏 token，无新视觉规范

  完成时长；确认 zip64 触发无误（<4GB 不触发）

## 9. 风险与开放问题

| # | 风险/问题 | 处置 |
|---|---|---|
| 1 | 路由层挂有全局超时中间件，10min 流被截断 | 实施第一步先查 router 超时配置；若存在，对 `/batch-download` 豁免或单独 10min |
| 2 | 对象存储单文件读取本身可能有超时/限流 | 由文件源 SLA 决定；preflight 已开句柄成功则大概率可读；失败走 4.4 |
| 3 | 50 句柄同时持有（选项 1）在慢 IO 下窗口拉长 | 若压测出现 fd 压力，切换选项 2（纯元数据取文件名） |
| 4 | 大 zip（>1GB）在部分老旧浏览器下载体验 | 浏览器按 chunk 流式落盘，可接受；不在本期优化 |
| 5 | `postDown` 错误分流不当导致"把 JSON 错误存成 zip" | 7.2 E2E 必测 403 场景并检查**不**产生假文件下载 |

## 10. 与方案 A 的关系（留档）

- 方案 A（纯前端 jszip）保留为"小文档快速场景"的可选后续，不与本期冲突：
